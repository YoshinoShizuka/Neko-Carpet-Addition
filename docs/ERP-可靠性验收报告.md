## 1. 验收目标

需求原文：

> 再次增加一个功能，当工作台位于漏斗上方时，视为从虚空仓库取出物品存放到漏斗里，
> 漏斗里面的五个格子作为取出物品的分类物，当仓库里的物品被全部取出后，
> 确保该物品会留有一个余量存放到漏斗里作物分类物，确保漏斗所流向的容器里不会吸收，
> 最后以 ERP 系统对该存储功能进行可靠性测试。

拆成 4 条可验证目标：

| 编号 | 目标 | 验收判据 |
|---|---|---|
| G1 | 终端在漏斗上方 = 从仓库取料放进漏斗 | 漏斗格被补满；仓库按量减少；**账目相等** |
| G2 | 漏斗 5 格 = 出料品类 | 只出漏斗里已有的品类；空格子不出；仓库里没被分类的物品一个不动 |
| G3 | 仓库抽空后仍留 1 个余量当分类物 | 仓库=0 时漏斗**正好留 1 个**，且**长期保持** |
| G4 | 下游容器不得吸收该余量 | 下游满 / 下游空 / 长时间运行，**漏斗那 1 个始终拿不走**，且**总量守恒** |

## 2. ERP 建模（游戏概念 ↔ 仓储管理概念）

| ERP 概念 | 系统内对象 |
|---|---|
| 物料台账（库存） | `VoidWarehouseData`（SavedData，`BigInteger` 数量，无上限、无容差） |
| 库位 | 仓库格子 = 一种物料一格 |
| 采购入库单 | 漏斗口**朝向**终端 → `VoidWarehouseHopper#drain`（1 tick 搬空） |
| 领料出库单 | 终端**压在**漏斗上方 → `VoidWarehouseExtractor#pull`（每 tick 补满） |
| 在制品（WIP） | 漏斗 5 格里的物料 |
| 成品库 | 漏斗朝向的下游容器（箱子 / 熔炉 / 漏斗…） |
| BOM / 领料品类 | 漏斗 5 格里的**分类物**（摆什么出什么，空格子不出） |
| 安全库存 / 留底 | **每格最后 1 个**（`KEEP_AS_CLASSIFIER = 1`），永不被成品库吸收 |
| 期末盘点 | 「仓库 + 在制 + 成品库」按物料求和，与期初逐项比对，差异必须为 **0** |

**单据流**

```
[入库漏斗] ──采购入库单──▶ ┌────────────┐ ──领料出库单──▶ [漏斗 5 格] ──▶ [下游容器]
                            │  物料台账  │                  （在制）      （成品库）
[玩家/界面] ─────────────────┘            ↑
                                每格保留 1 个 = 分类物（安全库存）
```

### 期末盘点（ERP 核心）

```
期初台账：cobblestone=1001  diamond=6   redstone=2049  gold_ingot=201  iron_ingot=201
          coal=201         lapis_lazuli=201  emerald=320  copper_ingot=321
          obsidian=64      andesite=64
期末台账：cobblestone=1001  diamond=6   redstone=321   gold_ingot=201  iron_ingot=201
          coal=201         lapis_lazuli=201  emerald=320  copper_ingot=321
          obsidian=64      andesite=64
```

- 11 种物料**逐项对账**，差异全部为 **0**；
- `redstone` 期初 2049 → 期末 321，差的 1728 是测试自己执行的**成品发货出库**
  （清空下游箱子），属于**有单据的出库**，台账同步下调 —— 这正是 ERP 该有的样子；
- 口径包含：仓库 + 9 个功能漏斗 + 2 个入库漏斗 + 576 个性能漏斗 + 全部下游容器，
  一共 **18,000+ 个槽位**的实时求和。

## 5. 幂等性（同一个存档连跑两遍）

| 轮次 | 世界 | 断言 | 失败 |
|---|---|---|---|
| 第 1 遍 | 全新 `erp1` | 95 | **0** |
| 第 2 遍 | **同一个已用过的 `erp1`** | 95 | **0** |

第二遍的期初台账与第一遍完全一致，说明**没有残留状态互相污染**
（自检自己会清空仓库与下游容器；漏斗格被精确重设；性能场地每次重建）。
第二遍里 `D 锁存前：仓库 72 / 在制 63 / 成品库 66`（第一遍是 `64 / 65`）
这类细节会有 ±1 的抖动 —— 那是**真实 tick 时序**差异，对账口径不受影响。

## 6. 性能测试（576 条出料产线）

每阶段：静置 40 tick → 测量 100 tick（读 `MinecraftServer#getAverageTickTimeNanos`，
它本身就是最近 100 tick 的滑动平均，与测量窗正好对齐）。

| 阶段 | 平均 tick（第 1 / 2 遍） | 相对基线 | 测量窗内仓库净减少 |
|---|---|---|---|
| P0 基线：场地已建、**规则关闭** | 0.566 / 0.518 ms | — | 0 |
| P1 规则开、576 个漏斗**都没有分类物** | 0.785 / 0.847 ms | +0.219 / +0.329 | 38（功能工位在动） |
| P2 每个漏斗 **5 个分类物**、仓库 5 种料各 **1000 万** | 0.956 / 0.922 ms | **+0.390 / +0.404** | **7527** |
| P3 仓库把这 5 种料**抽空**（补料全部落空） | 0.822 / 0.887 ms | +0.256 / +0.369 | 36 |
| P4 下游容器**全部塞满**（最极端空转） | 1.156 / 1.614 ms | +0.590 / +1.096 | 38 |

**微基准（`takeExact`，出料取料入口）**

| 场景 | 第 1 遍 | 第 2 遍 |
|---|---|---|
| 未命中（仓库没有这个品类） | 8 ns | 15 ns |
| 命中（扣 1 个） | 22 ns | 31 ns |
| 折算 576 × 5 = 2880 次查找/tick | 0.043 ms | 0.066 ms |

**结论**

1. **满负荷净成本 ≈ 0.40 ms/tick**，是一个 tick 预算（50 ms）的 **0.8%**，
   折算每条出料口 **≈ 0.7 µs/tick** —— 对 TPS 的影响可以忽略；
2. P2 吞吐 **7527 个 / 100 tick ≈ 75 个/tick**，**正好等于 576 ÷ 8**，
   与「仓库不限速、下游守原版 1 个/8 gt」的设计完全吻合（设计 ≠ 纸面，是实测出来的）；
3. P4 比 P2 高是**原版行为**：下游塞满时漏斗搬不动东西、进不了冷却，于是**每 tick 重试**，
   每次都要扫目的容器的 27 格 —— 原版 `isFullContainer` 也是这么扫的，本模组没有加码；
4. 出料的 CPU 大头不在本模组：`takeExact` 走 O(1) 哈希索引，2880 次查找只占 0.04–0.07 ms。

## 7. 缺陷记录

### 7.1 被测产品

第一遍跑完后，**产品侧 0 缺陷**（60+ 条功能断言全绿）。
本轮唯一的产品侧改动是新增 `VoidWarehouseExtractor` 与 `takeExact`，未修改任何已有行为
（入库优先规则保证向前兼容）。

### 7.2 测试脚本自身（被对账抓出来的两个「账目不平」）

| 编号 | 现象 | 根因 | 修正 |
|---|---|---|---|
| BUG-T1 | 【对账·C2】redstone 期末 321 ≠ 期初 2049（**差异 −1728**） | 测试**清空了下游箱子却没记账** | 按 ERP 语义记为「成品发货出库 1728」，台账同步下调 |
| BUG-T2 | 【对账·G2】lapis_lazuli 期末 146 ≠ 期初 201（**差异 −55**） | 测试**往已有 64 个的漏斗格 `setItem` 只写 1 个**，55 个被覆盖销毁 | 只在**空格子**上补样品，并在台账上记 +1 |
| BUG-T3 | H 用例「期望 0，实际 0」仍然 FAIL | `Integer(0).equals(BigInteger.ZERO)` 为 false（类型不匹配） | 改用 `BigInteger` 专用断言 |

> **这三条恰好说明了本报告的价值**：功能断言全绿的时候，账目仍然可能不平。
> 「对账」抓的不是功能，而是**钱货两清**。

## 8. 已知限制

1. 堆叠上限为 1 的物品（水桶 / 床 / 拆过的工具…）当分类物时**出不了料**：
   格子只能装 1 个，「补满」无从谈起，而最后 1 个又是分类物不能外流。
2. 出料模式下漏斗每格的最后 1 个**拿不走**（那是分类物）；要清掉必须**开漏斗界面手动拿**。
   这是需求确认过的预期行为，否则仓库一抽空分类就丢了。
3. 出料口到**下游容器**仍是**原版速率**（1 个 / 8 gt / 每条产线）。
   想要更大的吞吐就多摆几条出料口 —— 容器那一端不被我们偷偷改掉。
4. 一条漏斗同时满足「上方是终端」与「口朝另一个终端」时**以入库为准**（向后兼容）。
5. 分类物的匹配是「物品 + 数据组件」，与仓库格子定义一致；
   带数据的分类物匹配不到任何东西（仓库本就不收这类物品）。
