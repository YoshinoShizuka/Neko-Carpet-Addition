# 中键取物被当成打印余料返还

> 修复：**客户端 mod** `litematica-printer`（`VoidWarehouseRestockAdapter`）。
> 服务端 carpet 侧无改动 —— 这个 bug 完全在客户端，本仓库的 1.0.16 jar 不变。
> 相关：`docs/仓库终端不能存进仓库.md`（同批修复的另一个问题，根因在服务端）。

## 现象

1. 中键（pick block）指向一个方块 —— 打印机把这一下当成一次补货请求，从虚空仓库取来对应物品；
2. 玩家顺手打开虚空仓库界面（或任何一个容器界面），看一眼、关掉；
3. 东西**不见了**，回到仓库里。

玩家视角就是「中键拿到手的东西，开一次仓库就没了」。而且它不会立刻消失 ——
**必须开一次界面再关掉**才发生，所以第一眼很难联想到「余料返还」。

## 为什么「开界面」是触发点，不是原因

返还控制器每 tick 都要判断「这批材料还退不退」，但它有一道界面闸门：

```java
if (!player.containerMenu.equals(player.inventoryMenu)) {
    // 开着别的容器时不碰背包：东西在玩家眼皮底下突然消失比卡住更吓人
    return;
}
```

（`VoidWarehouseReturnController#tick`，`containerMenu.equals(inventoryMenu)` 那一处，约 575 行）

这条设计的本意是好的：玩家正在翻箱子时，背包里的东西自己飞走会显得像作弊。
副作用是 —— **界面期间账本照样被记脏，只是不发货**；一关界面，下一 tick 立刻补发。
于是「开界面 → 关界面」成了这个 bug 唯一可见的时刻。

## 根因：三条补货路线，两条分了来源、一条没分

打印机缺料时会按顺序问三个地方要货，每个来源各有一个适配器：

| 适配器 | 有没有按 `Source` 分流 | 中键取物的语义 |
| --- | --- | --- |
| `TakeItOutAdapter`（世界容器） | 有（约 173 行） | 玩家的东西，不退 |
| `ChestTrackerAdapter`（记忆箱子） | 有（约 554 行） | 玩家的东西，不退 |
| `VoidWarehouseRestockAdapter`（虚空仓库） | **没有** | 被记成打印耗材 ⇒ 会退 |

`status()` 里一到货就记账，判据只有「服务端回了 OK」：

```java
Item availableItem = findAvailableItem(request);
if (availableItem != null) {
    if (this.returnController != null && status == PrinterTakeResultPayload.NONE) {
        return pending(request);        // 回执没到，先不认领
    }
    if (status == PrinterTakeResultPayload.OK) {
        recordDelivery(request, availableItem);   // 但没问 source 是什么
    }
    ...
}
```

「回执 OK 才记账」是上一个提交（`c4605a3f`，修复返还记账与物品归属）加的，
它解决的是「背包先到、回执后到」的认领时序，**并没有解决归属** ——
中键取物同样会拿到 `OK` 回执，所以照样被记进余料账本。

`recordDelivery` 再按「背包里多了几个」记进返还账本（`recordTaken` + `markDelivered`）。
于是同一个中键操作，在三条补货路线上有三种语义 —— 这本身就是个不该存在的分歧。

## 修法：把「算不算打印耗材」抽成一个判定

```java
static boolean booksAsLeftover(MaterialRequest.Source source) {
    return source != MaterialRequest.Source.PICK_BLOCK;
}
```

`recordDelivery` 的顺序变成：**读快照 → 推进基线 → 判来源 → 记账**。

```java
int before = this.heldBefore.getOrDefault(item, 0);
int now = countHeld(item);
this.heldBefore.put(item, now);        // 基线无条件推进
if (!booksAsLeftover(request.source())) {
    return;                            // pick block 到这儿就结束
}
int delivered = now - before;
if (delivered > 0) { ... }
```

**基线为什么必须继续推进**：它记的是「这一批到货了多少」的参照。
如果因为 pick block 就直接 `return` 而跳过 `put`，那么下一批**真打印**算增量时，
会把这一批 pick block 的量一起算成自己的到货量 —— 变成另一笔错账（多退）。
所以这里刻意不是「提前返回」，而是「只不记账」。

## 边界

| 情形 | 修前 | 修后 |
| --- | --- | --- |
| 中键取物 → 立刻开、关仓库界面，空槽紧张 | 物品被退回仓库 | 留在背包 |
| 中键取物后接着打印，空槽紧张 | pick block 的量被当成打印余料退回 | 只退真正打印剩下的 |
| 打印耗材（`PRINT` / `FILL` / `FLUID` / `MINE` / `COVER` / `BEDROCK`） | 照常记账、照常退 | **一字不变** |
| 客户端开关 `voidWarehouseReturn` 关掉 | 完全不动 | 不变 |
| 对端没装通道（`isSupported=false`） | 完全不动 | 不变 |

## 验证

真机要同时凑齐「中键 + 开关界面 + 背包空槽紧张到触发返还档位」，成本很高；
所以把判定抽成静态方法 `booksAsLeftover`，在单测里逐个边界咬死
（`VoidWarehouseReturnLedgerTest`，3 条）：

| 断言 | 咬的是什么 |
| --- | --- |
| `pickBlockIsNeverBooked` | `PICK_BLOCK` 不记账（这条一红就是这个 bug 回来了） |
| `everyPrintingSourceIsBooked` | 其余来源仍记账（防「只留 `PRINT`」的过度修复） |
| `newSourcesMustBeClassifiedExplicitly` | 记账集合写成字面量：将来新增 `Source` 会立刻翻红，逼着回答「算不算打印耗材」 |

**反证**：把 `booksAsLeftover` 临时改成无条件 `return true`（= 修复前的行为），
`3 tests completed, 2 failed` —— `pickBlockIsNeverBooked` 与
`newSourcesMustBeClassifiedExplicitly` 翻红，而 `everyPrintingSourceIsBooked` **仍是绿的**。
两组断言各自咬住一个方向，改错任何一边都会被抓到。

真机上仍需人工过一遍的操作序列（三件事必须同时成立，机器不好造）：

1. 装好 carp 服务端 + 打印机客户端，开 `voidWarehouse` / `voidWarehouseRestock`；
2. 仓库里放一批圆石，背包**塞到只剩 1~2 个空格**（返还档位就在这一段）；
3. 中键指向圆石方块 → 打开虚空仓库界面 → 关掉 → 圆石应留在背包，仓库数量不变。
