# 仓库终端不能存进仓库

> 修复：1.0.16（同版本号原地更新，未新增规则）。
> 相关：`docs/中键取物被当成打印余料返还.md`（同批修复的另一个问题，根因在客户端 mod）。

## 现象

玩家把工作台用铁砧改名为 **虚空仓库**（或 `void warehouse`），那就是仓库终端的「钥匙」。
以前这把钥匙本身也能被存进仓库：

- 打开仓库界面，Shift 点击 / 数字键把手里那台终端塞进去 → 存进去了；
- 漏斗把一台终端吸进来 → 存进去了；
- 挖掉一个摆在世界里的终端，`voidWarehouseBlockDrops` 把掉落物直接送进仓库 → 存进去了。

存进去之后的表现很别扭：**它能取出来，却再也存不回去**（如果只做了一半的修复），
或者「仓库里多了一格永远用不掉的东西」。更糟的是它取出来又是终端 ——
仓库里存着一台终端，等于存了一份「取之不尽的终端货源」，而它本身只是改过名的工作台。

## 为什么它是钥匙、不是货

终端的本质是**打开仓库的入口**（`VoidWarehouseTrigger#isVoidWarehouse`：工作台 + 自定义名）。
把它当货物收进仓库，语义上等于「把这个房间的门锁收进这个房间」——
门还能再拿出来用，但房间里从此多了一件永远用不上的东西。

而且它**没有成本**：玩家随手用铁砧给工作台改个名就有了一台。所以「收进仓库」既不保值、
也不稀缺，纯粹是给玩家添一条「为什么这个存不进去」的疑惑（或者反过来，「为什么能取出来」）。

## 三道闸门，各管一条路

入库有**四条**独立路径，它们唯一的共同出口是 `VoidWarehouseData#insert`：

| 路径 | 入口 | 经过的闸门 |
| --- | --- | --- |
| 菜单存入（Shift 点击 / 数字键 / 右键） | `VoidWarehouseMenu#insert` | ① `insert` |
| 漏斗进货 | `VoidWarehouseHopper#drain` | ② `isInsertable`（快筛）→ ① `insert` |
| 方块掉落物 | `VoidWarehouseBlockDrops` | ① `insert` |
| 打印机余料返还 | `PrinterReturnService` | ① `insert` |

所以闸门只有两处：

**① `insert` 开头（主闸门，拦所有路径）**

```java
if (VoidWarehouseTrigger.isVoidWarehouse(incoming)) {
    return false;
}
```

拒收时 `incoming` **原样不动**（这是 `insert` 一贯的契约：收下才清零、拒收不碰），
所以漏斗里那台终端会留在漏斗里、掉落物会照常掉在地上、打印机返还那一格会留在背包里 ——
**没有任何一条路会把它吞掉**。

**② `isInsertable`（给漏斗的快筛）**

与 `insert` 同一口径。放这里是为了让 `drain` 少白跑一趟 `insert`，
也让「上方容器整格搬」的循环不把终端吸进来又原样吐回去（那会变成每 tick 取放一次的空转）。

> `isInsertable` **不是**唯一的守门人 —— 只有漏斗用它做快筛。指望它拦菜单和掉落物是拦不住的，
> 所以主闸门必须在 `insert`。这也是自检里专门跑一遍漏斗路径的原因：
> 两道闸门各管一边，缺一条就有一条路漏。

**③ 拆盒的旁路：`unpackShulkerBox` 先查内容物**

`insert` 遇到潜影盒会**先判盒子、后判内容物**（拆开是既定行为）。于是「把终端装进潜影盒」
能绕过 ①：`insert` 看到的是「一个盒子」，放行 → `unpackShulkerBox` 里的 `put(inside)`
**直接写账、不经过 `insert`** → 终端进仓库。

所以拆盒之前必须先把内容物过一遍：

```java
for (ItemStack inside : contents) {
    if (VoidWarehouseTrigger.isVoidWarehouse(inside)) {
        return false;   // 整笔拒收，一格都不拆
    }
}
```

判在**循环之前**是刻意的：拆盒承诺「全成或全不成」，判在循环里就只能把已经拆出来的几样留下，
比整笔拒收更难解释（玩家会看到「盒子没了、壳和箱进来了、终端还在盒子里」这种半截状态）。

## 「打开界面期间」这个限定，为什么没有单独实现

需求里说「在玩家打开虚空仓库期间……不应该能被放进去」。实现上没有按「界面是否打开」来判断，
而是**从所有入库路径一起挡掉**，理由有三条：

1. **拦在 `insert` 天然覆盖「打开界面期间」**：菜单存入走的就是 `insert`，
   所以界面里那一次操作一定被拦住；
2. **只拦界面等于留了三个洞**：漏斗、掉落物、打印机返还都不需要玩家打开界面，
   它们照样能把终端送进去 —— 而「仓库里有一格终端」这件事，进去之后是一样的；
3. **「界面关着时能存进去」是不可能解释的行为**：同一个物品，开着界面存不进去、
   关掉界面就能存，玩家只会当成 bug。

## 边界

| 情形 | 行为 | 说明 |
| --- | --- | --- |
| `虚空仓库`（中文，精确） | 拒收 | 与触发判定同一套 |
| `Void Warehouse` / `void warehouse` | 拒收 | 英文忽略大小写 + 容忍首尾空白 |
| `虚空仓库 `（带尾空格） | **照收** | 中文维持精确匹配（与触发一致：带空格的工作台本来也打不开仓库） |
| 无名字的普通工作台 | 照收 | 对照组，白名单没有误伤 |
| 改名为「我的工作台」 | **照收** | 只要不叫那两个字，它就是普通建筑材料 |
| 装着终端的潜影盒 | 拒收，**一格都不拆** | 见上面第 ③ 道闸门 |
| 装着圆石等普通物品的潜影盒 | 照常拆开入库 | 对照组 |
| 老存档里**已经存进去**的终端 | 不主动清理 | 它能正常取出；只是此后存不回来 |

最后一条是刻意的：清理存档里的物品属于「替玩家删东西」，而它并不造成刷物品或崩服。
真要清，应该由玩家手动取出 —— 而取出这条路一直是通的。

## 验证

真服务端 **18 条断言全绿**：

```
TNS [A] 三种写法拒收、三种对照照收，仓库工作台=1
TNS [B] 装终端的盒子拒收、装圆石的盒子照拆
TNS [C] 漏斗路径：终端不搬、普通工作台照搬
SMOKE RESULT vw-terminal-not-storable/26.3 checks=18 failures=0
```

反证（把三处判定临时改成 `false && …`）**红 10 条**，且对照组 8 条**全部仍是绿的**：

```
FAIL: [A1] 改名「虚空仓库」的工作台被拒收
FAIL: [A2] 改名「Void Warehouse」的工作台被拒收
FAIL: [A3] 改名「void warehouse」（全小写）的工作台被拒收
FAIL: [A4] 三笔都拒收之后，三种写法在仓库里都是 0
FAIL: [B1] 装着终端的潜影盒被整笔拒收
FAIL: [B2] 没有拆出任何潜影壳（实际 2）
FAIL: [B3] 没有拆出箱子（实际 1）
FAIL: [B4] 也没有把终端收进去
FAIL: [C1] 漏斗里的终端搬不进仓库
FAIL: [C2] 终端原样留在漏斗格 0（不是被丢掉）
SMOKE RESULT vw-terminal-not-storable/26.3 checks=18 failures=10
```

### 断言口径的坑（这一轮踩到两次）

**① `amountOf(Item)` 只认「无组件」那一格。**

它内部是 `find(new ItemStack(item))`，而三台终端带着**不同的自定义名**、各占一格 ——
`amountOf(Items.CRAFTING_TABLE)` 一台都数不到。第一版断言因此变成空的：
「终端全进了仓库」和「一台都没进」在数字上完全一样。反证时 A4/B4/C1 该红没红，
就是被这一点骗过去的。改用 `amountExact(sample)`（物品 + 数据组件）才咬得住。

**② 追加型补丁的幂等判定必须先判 `new`、再判 `old`。**

同步脚本第一次跑完若干版本后重跑，`old` 片段**仍然在文本里**（因为 `new = old + 新增一段`），
于是「old 在就改」又追加了一遍 —— 26.3 里出现了两个 `msgTerminal()`，编译直接报
「已在类中定义」。修法是把判定顺序反过来：`new` 在就跳过，否则再看 `old`。
