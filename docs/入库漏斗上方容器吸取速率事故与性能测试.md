# 入库漏斗「上方容器」吸取速率事故 + 性能测试

> 日期：2026-09-30
> 影响版本：26.3 / 26.2 / 26.1.1 / 26.1.2 / 1.21.11（五版本同步修复）
> 症状（用户报告）：**入库漏斗上方的容器，里面的东西是「一个一个」被吸走的**，
> 而掉落物却是每 tick 全收 —— 两者速率不一致。

---

## 一、现象

同样是 **320 个圆石**，从三条不同的进料路径送进入库漏斗，实测进库数量：

| 进料路径 | 修复前（tick0 / 1 / 2…） | 修复后 |
|---|---|---|
| 上方摆一个漏斗（5 格 × 64） | 0 → 2 → 3 → 4 → 5 → 6（**每 tick 1 个**） | **tick0 就 320** |
| 上方摆一个箱子（5 格 × 64） | 0 → 1 → 2 → 3 → 4 → 5（**每 tick 1 个**） | **tick0 就 320** |
| 掉落物（5 个实体 × 64） | tick0 就 320 | tick0 就 320 |

**差 320 倍。**

这不是「速率慢一点」，而是那条路径**根本没在工作** —— 用户的观察完全准确。

---

## 二、根因：`addItem` 的 source / destination 写反了

### 2.1 原版签名（javap 逐条核对）

```java
public static ItemStack addItem(Container source, Container destination, ItemStack stack, Direction direction);
private static ItemStack tryMoveInItem(Container source, Container destination, ItemStack stack, int slot, Direction direction);
```

**第 1 个参数是来源、第 2 个才是目的地。** 两处独立佐证：

- `addItem(Container, ItemEntity)` 的字节码里，调用 4 参版本时先 `aconst_null`（source = null），
  再 `aload_0`（destination = 第一个参数，也就是要吸进的那个漏斗）；
- `addItem` 4 参版本开头 `aload_1 instanceof WorldlyContainer` —— 判的是第 2 个参数，
  接着 `tryMoveInItem(aload_0, aload_1, aload_2, slot, aload_3)`。

### 2.2 出错的那一行

```java
// 修复前（VoidWarehouseHopper#suckUnlimited）
ItemStack leftover = HopperBlockEntity.addItem(hopper, source, taken, null);
//                                            ^^^^^^  ^^^^^^
//                                            实际=来源 实际=目的地 ← 完全反了
```

于是每 tick 发生的事是：**从上方容器 `removeItem` 取出一整格 → 塞回同一个容器**。
漏斗一个都没收到，`drain` 自然也无事可做。

那为什么还能看到「一个一个」在动？因为**原版 `suckInItems` 还在跑**（我们只是没取消原版逻辑），
而 TAIL 注入把 `cooldownTime` 清零了，所以原版那条路从「8 gt 吸 1 个」被松开成了「每 tick 吸 1 个」——
**恰好就是用户看到的现象**，也是上一轮审计里那个「100 tick 只搬了 114 个」的真实来源。

### 2.3 连带损害：分类物白名单整条失效

`canPlaceItemInContainer(destination, stack, slot, direction)` 是白名单的关卡。
参数写反之后，**关卡收到的「目标容器」是上方箱子而不是入库漏斗**，于是：

```java
if (!(container instanceof HopperBlockEntity hopper)) return;   // 箱子不是漏斗 → 直接放行
```

白名单在「上方容器 → 入库漏斗」这条路上**一次都没拦过**。
而当时的功能自检没覆盖这条路径，所以没人发现 —— 这次补上了（见第五节 I 组）。

---

## 三、修复

```java
// 修复后
ItemStack leftover = absorbStack(source, hopper, taken);
```

同时把两处「喂料」逻辑合并成一个私有方法 `absorbStack(source, destination, payload)`，
掉落物路径（`absorbEntity`）与上方容器路径**共用同一份**：
既保证超过堆叠上限的部分按堆切片（绕开 `HopperBlockEntity#setItem` 里 `limitSize` 的静默吞料），
也保证两条路径今后不会再各自演化出不一致的行为。

其余改动：

- `suckUnlimited` 用 `accepted > 0` 判定是否真的有进展（不再「取出来又塞回去」也算成功）；
- 塞不下的部分走 `mergeBack` 原样并回上方容器的原格；
- `source.setChanged()` 从「每格调一次」挪到「只在真搬动时调一次」。

## 四、性能测试

### 4.1 怎么测的

沿用 `docs/入库漏斗性能基准.md` 的那套口径，并补了一条此前**完全没测过的路径**：

- 微基准每轮先 `refillAbove` 复位状态再计时（否则第一轮搬空后，剩下 199 轮量到的都是空跑）；
- 真实 tick 读 `MinecraftServer#getTickTimesNanos()`（纯 tick 计算时间，不含 sleep）；
- 设 `vanilla_container` 对照（拆掉终端，同一批箱子 + 漏斗变成原版组合）。

**微基准（1024 个入库漏斗，per_hopper，同一进程内对比才可信）**

| 项目 | 256 档 | 1024 档 | 说明 |
|---|---|---|---|
| `intake` 空转全流程 | 114 ns | **114 ns** | 与上一轮（122 ns）一致，**空转一分钱没变贵** |
| `intake_push`（入库漏斗，上方是空气） | 465 ns | 384 ns | |
| `suckUnlimited`（上方有货，搬 320 个） | 1555 ns | **1677 ns** | |
| `intake`（上方容器全流程） | 1963 ns | **2089 ns** | |
| 对照 `vanilla_push`（普通漏斗） | 500 ns | 341 ns | |
| `intake` 满载一轮（吸 1 个掉落物实体） | 61396 ns | 29283 ns | 掉落物路径本身才是贵的那条 |

**真实 tick（1024 个入库漏斗，50 ms/tick 预算）**

| 场景 | median | 说明 |
|---|---|---|
| `baseline`（没有漏斗） | 0.592 ms | |
| `idle`（1024 个空转） | 0.740 ms | 净开销约 0.15 ms（0.3% 预算） |
| `load_container`（每 tick 全抽 **32.7 万个**物品） | **3.616 ms** | 净 2.88 ms（5.8% 预算） |
| `load`（掉落物，每 tick 1024 个实体） | 6.406 ms | |
| `spawn_only` 对照（同样造 1024 个实体但没人吸） | 5.479 ms | 净 0.93 ms |

### 4.2 结论

**① 线性扩展、无超线性项。** 256 → 1024（4 倍数量），per_hopper 只从 1963 ns 涨到 2089 ns（+6%）。

**② 空转成本一点没变。** 绝大多数入库漏斗绝大多数时间都是空的，而 `intake` 空转仍是 114 ns/漏斗，
与修复前同档完全一致 —— 这次改动只影响「上方真的有货」的那一小撮。

**③ 「上方容器」其实是三条进料路径里最便宜的。** 搬 320 个物品约 2089 ns（≈ 6.5 ns/物品）；
而掉落物路径吸 1 个实体就要约 29 µs（实体查询 + `discard` + 事件）。
换句话说：**把上游从掉落物改成容器对接，性能上是赚的。**

**④ 满载是极端场景。** `load_container` 那个 3.6 ms 的前提是「上游每 tick 给每个漏斗供满 320 个物品」
= 每个漏斗每秒 6400 个。真实产线远达不到这个量级。

### 4.3 测试过程中修掉的两个测量陷阱（值得记住）

1. **跨轮污染**：上一轮跑完在漏斗上方留了 256 个箱子没拆，这一轮再 `build()` 时
   漏斗上方已经有容器 → 原本要测掉落物的场景全部走去容器分支。
   代价：实体一个都吸不走、300 tick 堆出 30 万个，**tick 被污染到 321 ms**（正常 3~11 ms）。
   → 加了 `resetField()`（开局 + 收尾各清一次场）。

2. **对照拆掉的东西忘了装回去**：`case 19` 为了做 `vanilla_push` 对照把终端拆了，
   而后面新增的容器场景**没有把终端装回来** → 那一整段 `isIntake=false`，
   量到的是「普通漏斗」的开销，数据全部作废。
   → 加了 `restoreTables()`。

这两条都是「数据看起来正常、其实是假的」—— 靠着「同一个 `intake_push` 在两种场景下
数字差 10 倍」这个自相矛盾点才揪出来。

## 五、功能回归

- **`UnlimitedIntakeSelfCheck` 29 项全绿**：
  - H 组（新增）：上方容器 320 个 **1 tick 全入库**、上方被抽空、总量守恒 `320 + 0 + 0 = 320`；
  - I 组（新增）：分类物白名单在这条路上**真的生效** —— 圆石 0 个进库、10 个原样留在上方箱子，
    橡木原木正常入库（10 + 超出 KEEP 余量的部分）；
  - E 组顺手修了一个**早就存在的不稳定断言**：数「实体个数」会被原版 `ItemEntity` 的
    合并机制打乱（6 个 count=1 的钻石会并成 1 个 count=6），改数「物品总个数」。
- **`VanillaParitySelfCheck` 16 项全绿、连跑两轮数字一致**：
  - A 普通漏斗→箱子 13 次 / E 带分类物标记 13 次（原版 12~13）；
  - C 组守恒：上游 320 个**一分没丢**（修复前是「100 tick 才搬 114 个」）；
  - C 组的「上游漏斗自己仍在 8 gt」这条断言**语义已失效**并改为观察项：
    上游现在是被下游主动抽空的，它自己没活可干，冷却自然递减到 0；
    「上游漏斗有没有被改节拍」由 A / E 两组负责证明（那里没有入库漏斗参与）。

## 七、一句话教训

**原版工具方法的参数顺序，javap 一下只要 10 秒；不核对，就会写出一个「看起来在干活、
其实在原地绕圈」的实现，而且它会伪装成「速率慢」这种无害症状。**
更麻烦的是：这种错误会**连带让另一条防线静默失效**（这次是分类物白名单），
而功能自检只要没覆盖到那条路径，就永远发现不了。
