# 入库漏斗：分类物被摊开成 `1 1 1 1 1`（事故与修复）

> 日期：2026-09-30
> 影响版本：26.3 / 26.2 / 26.1.1 / 26.1.2 / 1.21.11（五版本同一份代码，已全部同步）
> 结论：**已修复**。分类物只进自己那一格；顺带把「一 tick 吞吐被漏斗 5 格容量卡死在 320」也解决了。

---

## 1. 现象

玩家反馈：

> 入库漏斗上方的容器填满橡木原木，分类漏斗中手动填充一个橡木原木。手动填充之后是 `1 0 0 0 0`，
> 但上方容器内的物品流向虚空仓库之后，入库漏斗的表现是 `1 1 1 1 1`。

也就是说：**玩家摆的分类只剩第一格，后面四格被流过来的货物占住了**。
后果不只是「不好看」——想加第二种分类物时那几格已经没位置了。

---

## 2. 根因：白名单关卡只问了「是不是分类物」，没问「该进哪一格」

### 2.1 关卡本身没错，错在它管得不够细

分类物白名单挂在 `HopperBlockEntity#canPlaceItemInContainer` 上——
那是**机器往容器里塞东西的唯一关卡**（javap 核对过：`canPlaceItemInContainer` 全类只有
`tryMoveInItem` 一个调用点，`addItem → tryMoveInItem → canPlaceItemInContainer`）。

修复前这一关只判了一件事：

```java
if (!VoidWarehouseClassifier.matchesAny(hopper, stack)) {   // 这物品在不在白名单里？
    cir.setReturnValue(false);
}
```

`matchesAny` 只回答「漏斗里<b>有没有</b>同种分类物」，**不回答「这一格是不是它的格子」**。

### 2.2 而原版 `addItem` 是「按 slot 0→N 逐个试」

`javap -c` 导出的 `addItem(Container, Container, ItemStack, Direction)`（节选）：

```
67: aload_1;  invokeinterface Container.getContainerSize()   // ← aload_1 是 destination
75: iconst_0; istore 6
78: iload 6;  iload 5;  if_icmpge 108                        // for (i = 0; i < size; i++)
85: aload_2;  invokevirtual ItemStack.isEmpty()              //  && !stack.isEmpty()
92: aload_0; aload_1; aload_2; iload 6; aload_3;
    invokestatic tryMoveInItem(source, destination, stack, i, direction)
```

（我们传的 `direction` 是 `null`，所以走的是「遍历所有格子」这条分支，
不是 `WorldlyContainer#getSlotsForFace` 那条。）

`tryMoveInItem` 拿到一个**空格子**时干的事是：

```
39: aload_1; iload_3; aload_2; invokeinterface Container.setItem(slot, stack)
47: getstatic ItemStack.EMPTY; astore_2          // 整摞塞进去，然后声称「搬完了」
```

### 2.3 于是两个条件合起来，5 格被逐个开垦

漏斗 slot0 摆着 1 个橡木原木，上方灌进来 64 个橡木原木：

| 步骤 | 动作 | 结果 |
|---|---|---|
| slot0 | `matchesAny` 通过 → `canMergeItems` → 补到堆叠上限 | slot0 = 64，还剩 1 个 |
| slot1 | 空格子 → `matchesAny` 照样通过 → `setItem` 整摞写入 | **slot1 = 1（被开垦）** |
| … | 上方容器每格都来一次 | slot2 / 3 / 4 依次被开垦 |

一 tick 遍历完上方容器的 27 格，5 格就全变成 `1 1 1 1 1`。

**为什么手动填充看不出来**：玩家手动放东西走的是 `Slot#setByPlayer`，
**根本不经过 `canPlaceItemInContainer`** —— 手动只写一次、只碰一格，所以永远是 `1 0 0 0 0`。
这个 bug 只在「机器持续灌货」时才显形。

---

## 3. 修复一：给白名单加「格子归属」判定

新增 `VoidWarehouseClassifier#isOwnSlot(hopper, stack, slot)`：

```java
public static boolean isOwnSlot(HopperBlockEntity hopper, ItemStack stack, int slot) {
    if (stack.isEmpty() || slot < 0 || slot >= hopper.getContainerSize()) {
        return false;
    }
    ItemStack resident = hopper.getItem(slot);
    return !resident.isEmpty() && ItemStack.isSameItemSameComponents(resident, stack);
}
```

关卡改成<b>两道</b>：

```java
if (!VoidWarehouseClassifier.matchesAny(hopper, stack)) { cir.setReturnValue(false); return; }
if (!VoidWarehouseClassifier.isOwnSlot(hopper, stack, slot)) { cir.setReturnValue(false); }
```

规则一句话：**分类物只许合并进已经放着同种分类物的格子，不许开垦新格子。**
于是「哪格是哪种」永远等于玩家摆出来的样子。

两道检查在语义上是包含关系（格子里的东西与 `stack` 同种 → 漏斗里当然有这个分类物），
都保留是为了让「是不是白名单物品」和「该进哪一格」这两件事在代码里各自说清楚。

---

## 4. 修复二（顺带发现）：一 tick 的吞吐被「漏斗 5 格容量」卡死在 320

加了上面那道限制之后，**分类物模式下每格每次最多只能吃 `64 - KEEP` = 63 个**
（那一格永久占着 `KEEP=1` 个当种子）。顺着查下去发现一个更早就存在的问题：

`intake` 原来的结构是「吸 → 最后统一 `drain` 一次」。漏斗只有 5 格（320 个容量），
塞满之后原版 `addItem` 一分都吃不下，**剩下的要等下一 tick**。
实测：上方桶整整 27 格 × 64 = 1728 个，一 tick 只搬得走 320 个。

改法是在 `suckUnlimited` / `suckEntitiesUnlimited` 里**边吸边入库**：

```java
if (leftover.isEmpty()) {
    break;
}
mergeBack(source, slot, leftover);
// 当场入库腾位，然后<b>回头再啃同一格</b>
if (drain(level, hopper, keepClassifiers) <= 0 || retries >= MAX_RETRY_PER_SLOT) {
    break;
}
retries++;
```

两条硬保险，保证不会转不出来：

1. **`drain` 搬不动任何东西就立刻退出**（仓库拒收时不会空转）；
2. **`MAX_RETRY_PER_SLOT = 4`** 的次数上限（漏斗 320 容量 / 单格最多 64，
   正常腾一次位就够，4 次是给潜影盒拆出来的内容物之类超常规堆叠兜底）。

只在「真吃不下」时才 `drain`：上方容器前几格通常一口气填满 5 格、一次都不用腾，
**空转与常规场景的开销和改之前完全一样**。

## 5. 实测验证（真实 `runServer`，不是单测）

### 5.1 `UnlimitedIntakeSelfCheck` —— 46 项全绿

| 组 | 场景 | 实测 |
|---|---|---|
| H | 上方桶 320 个圆石，无分类物 | 仓库 320，上方剩 0 |
| I | 分类物=橡木，上方桶「10 圆石 + 10 橡木」 | 仓库 `oak=10 cobble=0`；上方剩 `cobble=10`；漏斗 `1 0 0 0 0` |
| **J** | **分类物=橡木，上方桶 27 格 × 64 = 1728 橡木** | **仓库 1728，上方剩 0，漏斗 `1 0 0 0 0`** |
| K | 分类物=橡木(slot0) + 圆石(slot1)，上方三种货各 10 | 仓库 `oak=10 cobble=10 dirt=0`；上方剩 `dirt=10`；漏斗 `1 1 0 0 0` |
| L | 上方桶 1728 圆石，无分类物 | **一 tick 全进库 1728**，上方剩 0 |

J 组就是玩家报的那个现象：**修复前是 `1 1 1 1 1`，修复后是 `1 0 0 0 0`，且货一个没少。**

### 5.2 `VanillaParitySelfCheck` —— 17 项全绿

普通漏斗 100 tick 仍只搬 13 次（原版 8 gt 节流），红石锁存、带分类物标记的普通漏斗、
规则关闭后的入库漏斗全部照旧。

> 顺手修掉一个**语义失效的探针**：C 组原本用「上游漏斗的 `cooldown > 0`」判断
> 「上游有没有被加速」。这个判据不成立 —— 上游漏斗正好压在入库漏斗头上，
> 而入库漏斗每 tick 会把**上方容器（漏斗也算容器）**抽干，
> 那 320 个是<b>被吸走</b>的，不是上游自己推的；上游被抽空后没活可干，`cooldown` 自然就是 0。
> 现在 C 组只断言「物品一分不丢」，上游节拍由 A / E 两组证明（同样是普通漏斗，100 tick 只搬 13 次）。

## 6. 性能（1024 个入库漏斗，与上一轮同档对比）

| 指标 | 上一轮 | 本轮 | 说明 |
|---|---|---|---|
| `intake` 空转全流程 | 114 ns/漏斗 | **94 ns/漏斗** | 同档噪声内，空转没变贵 |
| `suckUnlimited(上方有货)` | — | 2222 ns/漏斗 | |
| `intake(上方容器全流程)` | 2089 ns/漏斗 | **1847 ns/漏斗** | 略降 |
| 真实 tick `baseline` | 0.592 ms | 0.537 ms | |
| 真实 tick `idle`（漏斗空转） | 0.740 ms | 0.764 ms | 净开销 ~0.23ms / 1024 个漏斗 |
| 真实 tick `load_container` | 3.616 ms | **4.041 ms** | +12% |
| 上方容器吞吐 | 320 个/漏斗/tick | **1341 个/漏斗/tick** | **4.2 倍** |
| 净开销占 50ms 预算 | 5.8% | **7.0%** | |

**重点：tick 只贵了 12%，吞吐涨了 4.2 倍 —— 单位物品成本从 ~11.3 ns 降到 ~1.4 ns。**
`load_container` 的 4.041ms 是「每个漏斗每 tick 被塞满一整桶、每秒供 8 万个物品」的极端条件，
现实产线到不了。

> 另一个测量陷阱（与上一轮同款，值得记下来）：本轮的 `load` / `spawn_only`
> 比上一轮高了 5 倍，一开始看着像严重回归 —— 其实是**供给速率不同**：
> `LOAD_PER_HOPPER` 在模板里是 4（N=1024 时每 tick 撒 4096 个实体），
> 上一轮跑的是 1（1024 个）。`spawn_only` 是对照组（终端已拆、我们的代码根本不跑），
> 它也一起涨了 5 倍，正说明这是撒实体的成本，与本次改动无关。
