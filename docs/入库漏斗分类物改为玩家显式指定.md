# 入库漏斗分类物改为「玩家显式指定」（含存档 air bug 修复）

> 日期：2026-09-30 ｜ 版本：26.3 / 26.2 / 26.1.1 / 26.1.2 / 1.21.11 同步
> 关联：[入库漏斗分类物摊开事故与修复.md](入库漏斗分类物摊开事故与修复.md)（上一轮 `isOwnSlot` 修复，本轮被更彻底的重构取代）

## 1. 现象

用户实机反馈（上一轮 `isOwnSlot` 修复之后仍存在问题）：

> 入库漏斗上方放一个箱子，箱内石头跟橡木原木各占 50%。漏斗预先只填了 1 个橡木原木
> （分类物应该是 `橡木 空 空 空 空`）。等箱子里的物品流过后，漏斗变成
> `橡木 石头 空 空 空`。**漏斗里的填充物只能由玩家指定，不能以上方容器的物品来分类。**

## 2. 根因（两层，本轮补齐第二层）

第一层（上一轮已修）：分类物清单本身的来源是错的 —— `hasAny` / `matchesAny` 反推漏斗当前
格子里有什么，于是残留杂物（石头）被一并认成分类物 → 漏斗变成 `橡木 石头 空 空 空`。
这一层用「玩家种子清单」修复：机器再也不碰清单，清单只由 `SlotMixin#setByPlayer` 写。

第二层（**本轮修复，也是「修完仍复现」的真凶**）：旧存档污染。种子清单上线之前写的存档
只有开关 `classifierFilter`、没有逐格种子，分类物靠 `adoptLegacy` **就地把当时漏斗内容认作
分类物**。玩家迭代测试的存档正是这种：漏斗被污染成 `橡木 石头` 并保存了 filter 标记，
新版加载时 `adoptLegacy` 把这份残留写成**永久的逐格种子** → 石头变成合法分类物 →
**以后每次加载都复现**，且玩家重开世界也清不掉（污染已写进种子）。

诊断印证：同一份源码在**全新世界**里 M/N 组全绿（石头一个都进不来），但加载**旧存档**就
复现 `橡木 石头 空 空 空` —— 根因不在关卡、不在构建陈旧，而在旧存档的反推认领。

## 3. 修复：分类物 = 玩家亲手指定的种子清单

不再反推漏斗内容，改为每个入库漏斗存一份**按格子对齐的玩家种子清单**：

- `VoidWarehouseHopperFilter` 新增 `ItemStack[] classifierSeeds`（5 格，每格一个数量归一的 `ItemStack`，
  `null`/空 = 这一格没被指定）。
- `SlotMixin`（玩家 `setByPlayer` 路径）每次玩家往漏斗放/取时，**重写整份种子清单**——
  放进去的才算，掏空哪一格就清掉哪一格。这是「只能由玩家指定」的唯一写入点，
  机器搬运（`suckUnlimited` / 邻居推料 / 掉落物吸入）**绝不**碰这份清单。
- 关卡（`canPlaceItemInContainer`）改为两问：`matchesSeed`（这物品在不在玩家清单里）
  + `isOwnSeedSlot`（该不该进这一格）。判定依据全是玩家清单，与漏斗当前装着什么无关。
- `drain` 只给玩家清单里标了的那几格留 `KEEP` 个余量，其余格子里的货物照常入库。
- **旧存档治愈（`healLegacy` + schema 标记）**：种子清单上线前的旧存档只有开关、没有逐格种子，
  当年的分类物靠「反推漏斗当前内容」得到 —— 漏斗里若混着杂物（事故现场 `橡木 石头 空 空 空`），
  那份杂物会被写成永久的逐格种子，**每次加载都复现**。所以旧存档**一律不信任**：
  `loadAdditional` 读到 `CarpetNekoAdditionClassifierSchema` 标记缺失时，直接调
  `VoidWarehouseClassifier.healLegacy` 清掉所有种子、关掉过滤，让玩家重新手动指定
  （分类物只能由玩家的手声明）。带新格式 schema 标记的存档（本轮之后写的）才信任其逐格种子。
- 注：上一轮用的 `adoptLegacy`（旧存档就地认领当前内容为分类物）正是「依然复现」的元凶，
  本次已删除，改由 `healLegacy` 一律清空重来。

> 注：`isOwnSlot` 那套「反推漏斗内容」的逻辑已不再使用，判定全部走玩家清单。

## 4. 顺带修掉的存档 bug

重构时发现 `saveAdditional` 把 5 格**全部**写进 NBT 列表，空槽的 `ItemStack.EMPTY`
（air / count=0）被 `ItemStack.CODEC` 拒绝：

```
Failed to append value '0 minecraft:air' to list 'CarpetNekoAdditionClassifierSeeds':
  Value must be within range [1;99]: 0; Item must not be minecraft:air
```

改成**按格子独立 key、跳过空槽**：`CarpetNekoAdditionClassifierSeed0` … `4`，
只写非空的种子；`loadAdditional` 用 `ValueInput.read(tag+i, CODEC)` 按格读回。
日志 air 警告从每次存档刷屏降为 **0**。

## 5. 实测（真实 runServer，26.3）

- `UnlimitedIntakeSelfCheck` **62 项全绿**（本轮新增 **P 组**：旧存档污染治愈）。本轮关键几组：
  - **M**（混合货物只认玩家指定的那件）：上方桶 13×64 圆石 + 14×64 橡木，玩家只指定橡木 →
    仓库 `oak=896 cobble=0`，圆石 832 个全留在上方，漏斗 `1 0 0 0 0`。
  - **N**（残留杂物不许占位）：玩家动手前就躺在漏斗里的 1 个杂圆石 → 被搬空入库
    （仓库 `cobble=1`），漏斗仍 `1 0 0 0 0`，不再被当成分类物留种。
  - **P**（旧存档污染治愈，本轮根因修复）：模拟「种子清单上线前写的污染旧存档」—— 漏斗
    `橡木 石头`、filter 开着、无逐格种子。加载时 `healLegacy` 清掉种子并关过滤；玩家重指定
    只放橡木后，上方桶 13×64 圆石 + 14×64 橡木 → 仓库 `oak=896 cobble=1`（残留 1 石被清掉）、
    圆石 832 全留上方、漏斗 `1 0 0 0 0`。
  - J 1728 橡木 → 仓库 1728、漏斗 `1 0 0 0 0`；K 两分类物各守各格 `1 1 0 0 0`（泥土被拦）。
  - **Q**（顺序复现用户实机步骤 1-5：工作台 + 漏斗 + 箱子上，漏斗只填 1 橡木当分类物，

    专门确认顺序不会让圆石钻进来占位成 `橡木 圆石 空 空 空`。
- `VanillaParitySelfCheck` **17 项全绿**（普通漏斗 100 tick 仍只搬 13 次，原版节拍没被动）。
- 存档 air 警告：**0**。

# 附录：第三轮 —— 「实机仍复现」的真凶是 Lithium 绕过关卡（2026-09-30 晚）

> 本节记录第三次排查。前两轮（`isOwnSlot` 重构、种子清单 + `healLegacy`）在
> **服务端自检里全绿**，但用户实机（模组环境）依旧复现 `橡木 圆石 空 空 空`。
> 这次直接从实机 `latest.log` + 存档 NBT 取证，定位到**关卡注入点错位**。

## A1. 取证过程

用户实机日志：`E:\Game\Minecraft\.minecraft\versions\RO26.3\logs\latest.log`
（17:25:07 启动，`carpet_neko_addition 1.0.3`，共加载 163 个模组）。

1. **日志里关卡判定本身是对的。** 上一轮为排查临时加的 `[VW-DIAG]` 打印共 17660 行：
   - `oak_log` 60 行，**全部 `matches=true`**（20× slot0 `ownSlot=true`，其余各 10× `ownSlot=false`）
   - `cobblestone` 17600 行，**全部 `matches=false ownSlot=false`**
   - 漏斗坐标唯一：`BlockPos{x=65, y=64, z=197}`
   → 白名单逻辑本身**工作正常**：圆石被判为「非分类物」。可它还是进了漏斗。

2. **存档 NBT 直读，确认圆石确实被搬走了。**
   - 仓库数据 `void_warehouse.dat`（gzip+NBT，路径
     `saves/<world>/dimensions/minecraft/overworld/data/carpet_neko_addition/`，根键
     `data.items[]`，每项 `{item:{id,count}, count:long}`）：`cobblestone` 测试前后均
     `220821`，**净变化 0**（入库 576 又被取出 576）。
   - 区块方块实体 NBT（`region/r.0.0.mca`，区域头 3 字节大端偏移，chunk 压缩类型 2=zlib）：
     - `(65,64,197) minecraft:hopper`：`Items=[{Slot:0, id:'minecraft:oak_log', count:1}]`
       （**只剩 1 个橡木，没有圆石**）、`CarpetNekoAdditionClassifierFilter=1`、
       `CarpetNekoAdditionClassifierSeed0={oak_log,1}`、`Schema=1`、`TransferCooldown=0`
     - `(65,65,197)` / `(65,65,196) minecraft:chest`：`Items=[]`（**箱子被抽空**）

3. **反编译 Lithium，找到了绕过点。** 日志模组列表里有
   `lithium 0.26.1+mc26.3`（还有 `bbe`/`c2me`）。反编译
   `net/caffeinemc/mods/lithium/common/hopper/HopperHelper.tryMoveSingleItem(Container,ItemStack,Direction)`：
   **零次调用 `canPlaceItemInContainer`**（grep 计数 = 0），只调
   `Container.canPlaceItem(slot, stack)` + `WorldlyContainer.canPlaceItemThroughFace(...)`。
   `HopperBlockEntityMixin.lithiumInsert` / `lithiumExtract` 都走这个 helper ——
   **Lithium 把整个漏斗搬运整体替换掉了，压根不经过原版 `canPlaceItemInContainer`。**

## A2. 根因

| 路径 | 经过 `HopperBlockEntity#canPlaceItemInContainer` 吗 |
| --- | --- |
| 原版漏斗搬运 | 经过（所以自检全绿） |
| Lithium 漏斗搬运 | **不经过**（所以实机复现） |
| 玩家手动放物品 | 不经过（走的 `Slot#mayPlace`，直接 `return true`） |

上一轮把闸门挂在 `canPlaceItemInContainer`（**`private static` 的私有实现**）上。
服务端自检环境**没装 Lithium**，走的是原版路径 → 一直绿；实机装了 Lithium →
闸门整条失效 → 圆石以 1 个/gt 被吸进漏斗并占位。

**关键认知：`canPlaceItemInContainer` 不是公共契约，只是原版实现细节。
要拦住所有优化模组，必须挂到它们绕不过的公共契约上。**

## A3. 修复：主闸门挪到 `Container#canPlaceItem`

`Container#canPlaceItem(int, ItemStack)` 的默认实现就是 `return true`，
`HopperBlockEntity` **并未覆写**它；而原版 `canPlaceItemInContainer` 的实现 =
`canPlaceItem && canPlaceItemThroughFace`，Lithium 调的也正是这两个 ——
**所以 `Container#canPlaceItem` 是 vanilla 和 Lithium 两条路都绕不过的公共契约。**

- 新建 `mixin/ContainerClassifierMixin.java`：`@Mixin(Container.class)`，
  在 `canPlaceItem` 的 HEAD 注入，判定为真则 `setReturnValue(false)`。这是**主闸门**。
- `mixin/HopperBlockEntityMixin.java`：原 `canPlaceItemInContainer` 注入**保留为兜底**
  （`require = 0`），注入体改为委托共享方法。双保险。
- 判定逻辑收敛到 `VoidWarehouseClassifier.blockMachineInsert(Container, int, ItemStack)`，
  两个注入点共用：先确认 `container instanceof HopperBlockEntity` 且带分类过滤、
  是虚空仓库入库口、有任意种子；然后 `!matchesAny` → 拦；
  `matchesAny` 但不属于该格（`!isOwnSlot`）→ 拦。
- **不影响玩家**：漏斗界面的槽位是普通 `Slot`，`Slot#mayPlace(ItemStack)` 直接 `return true`
  （已核 26.3 字节码），玩家手动放分类物走 `Slot#setByPlayer`，**不经过任何 `canPlaceItem`**。
- 已扫描 CrystalCarpetAddition / ams / fga / igny / org / tis / servux / tweakeroo 的所有
  Hopper mixin，`canPlaceItem` 引用数均为 **0** —— 没有别的模组抢这个契约。
