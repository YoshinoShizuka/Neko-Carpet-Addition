# 入库漏斗「吸取速率有限」事故与修复

> 日期：2026-09-30　适用：全部五个版本（26.3 / 26.2 / 26.1.1 / 26.1.2 / 1.21.11）

## 一、现象

物品从入库漏斗**上方经过**时，只有一小部分进了虚空仓库，其余的被冲走、最终消失（despawn / 流入销毁端）。
漏斗 → 仓库 那一段早就「1 tick 搬空」了，所以问题不在仓库，在**进货**那一端。

## 二、根因（两条，都已用字节码 / 实测钉死）

### ① 掉落物分支根本没被接管 —— 原版一次只收 1 个实体

`HopperBlockEntity#suckInItems` 的掉落物分支（26.3 字节码逐行核对）：

```java
for (ItemEntity item : getItemsAtAndAbove(level, hopper)) {
    if (addItem(hopper, item)) return true;   // ← 收到第一个就收工
}
return false;
```

每次调用只收 **1 个实体**，再叠上 `tryMoveItems` 结尾无条件的 `setCooldown(8)`
（见 ②），实际速率是「**每 8 gt 收 1 个**」= 2.5 个/秒。水流传物的速度是每秒好几格，
绝大多数根本来不及进漏斗。

### ② 已有的「无上限」是假的 —— `resetCooldown()` 白做

原版骨架（字节码核对）：

```java
public static void pushItemsTick(Level level, BlockPos pos, BlockState state, HopperBlockEntity hopper) {
    hopper.cooldownTime--;
    hopper.tickedGameTime = level.getGameTime();
    if (!hopper.isOnCooldown()) {            // ← 冷却 >0 就直接出队
        hopper.setCooldown(0);
        tryMoveItems(level, pos, state, hopper, () -> suckInItems(level, hopper));
    }
}

private static boolean tryMoveItems(...) {
    if (level.isClientSide) return false;
    if (hopper.isOnCooldown()) return false;
    if (!state.getValue(HopperBlock.ENABLED)) return false;
    boolean flag = false;
    if (!hopper.isEmpty()) flag = ejectItems(level, pos, hopper);
    if (!hopper.inventoryFull()) flag |= supplier.getAsBoolean();   // == suckInItems
    if (flag) { hopper.setCooldown(8); ... }   // ← 无条件写回 8
    return flag;
}
```

旧代码把 `resetCooldown()` 挂在 `suckInItems` 的 HEAD —— 那是 `tryMoveItems`
**内部**，紧接着就被结尾的 `setCooldown(8)` 盖掉，等于没做。所以连
「上方容器 → 漏斗」那一路也一直是 8 gt 一次。

### 顺带查出的第二个真实丢物点：`setItem` 的 `limitSize`

一个实体带着 **超过一堆**（200 个圆石）时，`tryMoveInItem` 往空格子里放东西写的是：

```java
destination.setItem(slot, stack);   // 整摞塞进去
stack = ItemStack.EMPTY;            // 然后声称「全搬完了」
```

而 `HopperBlockEntity#setItem` 里有 `limitSize`，会把数量截到 64 —— 多出来的
**被静默吞掉**，实体那边却已经 `discard()`。孤立诊断实测：

```
DIAG-B2 taken=1 removed=true count=0      ← 实体被整个收走、已 discard
DIAG-B2 slots after suck: 0=64 1=0 2=0 3=0 4=0   ← 漏斗里只有 64
```

原版遇不到（地面上的堆叠合并本来就止于一堆），但我们现在收得积极了，必须一起补上。

## 三、修复

| 处 | 做法 |
|---|---|
| `VoidWarehouseHopper#intake` | 每 tick 一次<b>全量清扫</b>：先搬空 → 进货 → 收完当场再搬空 |
| `VoidWarehouseHopper#suckEntitiesUnlimited` | 遍历 `getItemsAtAndAbove` 的<b>全部</b>实体（用原版自己的吸力盒，不擅自放大 / 缩小） |
| `VoidWarehouseHopper#absorbEntity` | 超过一堆的部分<b>按堆切片</b>喂给漏斗，绕开 `setItem` 的 `limitSize` |
| `HopperBlockEntityMixin` HEAD | 改调 `intake(...)`；`pushItemsTick` 的 HEAD <b>每 tick 必然执行</b>，不看冷却脸色 |
| `HopperBlockEntityMixin` TAIL | 整条 tick 走完之后把 `cooldownTime` 清零，原版那两条路径也不再被 8 gt 卡着 |
| 删掉 `suckInItems` 的接管 | 冗余了；它的 `resetCooldown()` 本来也是无效的 |

### 参考实现

Carpet-TIS 的 `hopperCountersUnlimitedSpeed`（已反编译核对）：在 `tryMoveItems` 里
**循环到无事可做**，收尾 `setCooldown(0)`，上限 32767 次防死循环。
我们抄的是它「收尾清零」那一手；区别是搬运主循环挂在 `pushItemsTick` 的 HEAD，
所以压根不依赖 `tryMoveItems` 有没有被走到 —— 冷却对它没有约束力。

### 刻意没做的事

- **两条进货路径仍二选一**（上方是容器 → 容器路径；否则 → 掉落物路径），与原版一致。
  不是「两样都做」：否则一个头顶放着箱子的入库漏斗会顺带把旁边地面上同一高度的掉落物
  也吸走（吸力盒横向比漏斗宽一格），那是玩家没预期的行为。
- **没有新加 Carpet 规则**：入库漏斗本来就已经不是原版行为了（1 tick 搬空），
  这里只是把「进货」也对齐到同一档。若需要开关可以事后加。

## 四、验证（真实 `runServer`，连跑两轮全绿）

`SMOKE RESULT unlimited_intake/26.3 checks=23 failures=0`

| 组 | 断言 |
|---|---|
| A | 9 个实体在一个服务端 tick 内收得一个不剩；漏斗清空；**ERP 对账 65=65**；四种物品各自数量精确 |
| B | 一个实体带 200 个（超 1 堆）：全进库 200，不拆零、不吞料 |
| C | 分类物白名单：圆石照收、泥土**原地不动**且一个都没进库，分类物留在漏斗里 |
| D | 不对着终端的普通漏斗：一 tick 后至少还剩 5/6（原版最多收 1 个）→ 没被接管 |
| E | 红石锁存（`ENABLED=false`）：6 个一个不收 |
| F | `cooldownTime` 强设 8：入库漏斗被清成 0，普通漏斗按原版留 7 |
| G | **闸门回归**：载入 2 条合法数据 → 清空 → 闸门不许误报，仓库照样能用 |

第二轮是**带着第一轮故意留下的 2 条真实数据**（cobble 1234 / dirt 5678）启动的，
用来验证「空壳闸门」不会对着一份正常存档报警。

## 五、顺手修掉的严重隐患：空壳闸门会误伤正常存档

上一轮加的闸门有一条判据是「此刻 `entries` 是不是空的」，而**仓库随时会被玩家取空**：

```
GATE loadedCount=2 entryCount=2 cobble=1234 dirt=5678 suspicious=false   ← 数据读得好好的
……玩家（或自检）把仓库清空之后……
虚空仓库读到了空壳：文件里实际有 2 条记录，载入后却是 0 格                  ← 误报
```

于是每次 `VoidWarehouse#data` 都抛异常，**仓库永久不可用**（只要玩家把东西全取空就会触发）。

修法两条：

1. `VoidWarehouseData` 新增 `loadedSuspicious`，**在构造函数里一次性定死**
   （「读成没读成」是载入那一刻的事实，`entries` 之后会随玩家存取变化，不能回头再判）；
2. `VoidWarehouse#data` 新增 `guardChecked`，闸门**只判一次**。
   真正的坠落路径（`readSavedData` 返回 null → 全新空实例）在第一次访问时
   `loadedCount()` 就是 0，照样拦得住 —— **保护力度一点没减**。

## 六、自检环境的两个坑（离线自检通用）

1. **刚 `addFreshEntity` 的实体当帧查不到**：`getItemsAtAndAbove` 间歇性返回 0，
   会让「吸力范围内查得到几个」这类断言假失败。所以场景必须**跨 tick**：
   这一 tick 布场景 → 空转一 tick → 下一 tick 断言。
2. **`setChunkForced` 不是立刻生效**（是排队的）：必须 `level.isLoaded(pos)`
   为真才开始撒实体 / 让漏斗 tick，否则漏斗压根不会被 tick。
   另外每个场景前要**大范围清场**，上一轮残留的实体会污染这一轮的总量对账
   （实测多出来的 1 个 / 3 个就是这么来的）。
