# 入库漏斗性能基准（256 / 1024 个漏斗实测）

> **一句话结论**：数量不是问题。**1024 个入库漏斗空转约 0.1~0.3 ms/tick**（预算 50 ms 的
> 0.3%~0.5%），线性扩展、没有超线性项；**与普通漏斗基本同价**。
> 唯一需要留神的是**附近掉落物的密度** —— 见最后一节。

---

## 1. 为什么值得专门测一次

上一轮把「上方经过的掉落物 → 漏斗」从原版的 **8 gt 收 1 个** 改成了 **每 tick 全收**。
代价是：原版漏斗 8 gt 才做一次实体查询，我们改成每 tick 都做 —— **频率 ×8**。
所以必须回答两件事：

1. 漏斗**铺很多**的时候，空转的白烧能不能接受？
2. **物品真的哗哗来**的时候，会不会把 tick 撑爆？

---

## 2. 两种测法，互相印证

### 微基准（`PERF` 行）

直接调 API 跑 **热身 100 轮 → 计时 200 轮** 取平均，能把成本拆到
「一次 `isIntake` / 一次实体查询 / 一次 `drain`」的粒度。

> 热身轮数很关键：一开始用 20 轮，前几项虚高 **4 倍**（JIT 还没编译），
> 出现过「空场查询 499ns」这种假数据，热完之后同一个操作只有 42ns。

### 真实 tick（`PERF-TICK` 行）

读 `MinecraftServer#getTickTimesNanos()`。已核对字节码：这个数组在 `tickServer()`
里写入，**计时起点在方法头、终点在方法尾，不含 tick 之间的 sleep** ——
所以空闲服务端也能测出真实的 tick 计算负担。采样 300 tick 刷满那个长度 100 的 ring buffer。

四组对照：

| 组 | 场景 |
|---|---|
| `baseline` | 没有漏斗（纯空区块） |
| `idle` | N 个入库漏斗空转 |
| `load` | N 个入库漏斗 + 每 tick 往每个漏斗上方撒物品（合计 1024 个/tick） |
| `spawn_only` | **拆掉终端**（漏斗变普通、没人吸），每 tick 同样创建+销毁 1024 个实体 |

`spawn_only` 是关键的对照组：`load` 里有一大块是「创建 + 销毁 1024 个物品实体」的
**原版开销**（物品掉在地上本来就要这笔钱），只有 `load − spawn_only` 才是
**本模组净加进去的入库开销**。少了这一组，很容易把原版的账算到我们头上。

## 3. 数据

### 3.1 微基准（每漏斗每 tick，1024 档，优化后）

| 项 | ns / 漏斗 |
|---|---:|
| `isIntake`（口是不是对着终端） | 44 |
| `data()`（取仓库句柄） | 11 |
| `getItemsAtAndAbove`（实体查询，空场） | 42 |
| `getContainerAt`（上方是不是容器） | 52 |
| `drain`（空漏斗，5 格扫一遍） | 21 |
| **`intake`（空转全流程）** | **122** |
| **`intake_push`（入库漏斗跑一次 pushItemsTick）** | **341** |
| `vanilla_push`（**同样这批漏斗**，拆掉终端后跑 pushItemsTick） | 357 |

### 3.2 真实 tick（median，300 tick 采样）

| 档 | baseline | idle | load | spawn_only | idle−baseline | load−spawn_only |
|---|---:|---:|---:|---:|---:|---:|
| 256（优化前） | 0.257 | 0.267 | 6.120 | 5.540 | 0.010 | 0.58 |
| 1024（优化前） | 0.605 | 0.767 | 6.118 | 5.196 | 0.162 | 0.92 |
| 1024（优化后） | 0.746 | 0.880 | 6.365 | 4.673 | 0.134 | 1.69 |
| 256（优化后） | 3.151 | 3.415 | 15.348 | 12.451 | 0.264 | 2.90 |

> ⚠️ **绝对值受机器负载影响很大**：最后那一行跑的时候机器上有别的负载，
> 光 `baseline` 就从 0.26 ms 涨到 3.15 ms（12 倍）。所以**别拿跨进程的绝对值下结论**，
> 只有**同一进程内**的 `idle − baseline`、`load − spawn_only` 是可比的。
> 反过来说：**空转开销小到会被机器噪声盖住**，这本身就是结论。

### 3.3 实体密度扫描（唯一的非线性项）

`getItemsAtAndAbove` 的成本随**附近掉落物数量**线性增长（这是原版漏斗也在做的查询）：

| 附近实体数 | 1024 档（优化后） | 1024 档（优化前） |
|---:|---:|---:|
| 0 | 81 ns | 42 ns |
| 500 | 216 ns | 305 ns |
| 2000 | 668 ns | 1050 ns |

粗算 **≈ 0.33 ns × 附近实体数**。

## 4. 结论

### ① 数量不是问题，且线性扩展

1024 个入库漏斗空转 **0.13~0.26 ms/tick**，占 50 ms 预算的 **0.3%~0.5%**。
按微基准口径（122 ns/漏斗）线性外推：**1 万个入库漏斗也才 1.2 ms/tick**。
没有超线性项 —— 每个漏斗只关心自己头顶那一格，彼此不干扰。

### ② 和普通漏斗基本同价（最硬的对照）

| | ns / 漏斗 / tick |
|---|---:|
| 入库漏斗（`intake_push`） | 341 |
| **同一批**漏斗拆掉终端后（`vanilla_push`） | 357 |

**我们没有让漏斗变贵。** 原因是：原版漏斗干活那一 tick 本来也要做
「上方容器查询 + 实体 AABB 查询」，我们只是把「8 gt 干一次、一次干完」
摊平成「每 tick 干一点、每 tick 都能干」—— **总量没变，延迟降了 8 倍**。

### ③ 满载很便宜

每 tick 吞 **1024 个物品**（≈ 20480 物品/秒），净开销 **0.6~2.9 ms/tick**
（2%~6% 预算）。其中 4.7~12.5 ms 是「创建+销毁 1024 个实体」的原版开销，
不是本模组的 —— 物品掉在地上本来就要这笔钱。

### ④ 唯一要留神的：附近掉落物密度

`load` 场景之所以可控，是因为撒下来的物品**当 tick 就被吸走了**，稳态下附近最多 1024 个。
**如果有一批掉落物卡在入库漏斗旁边、既吸不进来也不消失**，那每个漏斗的那次查询都会扫到它们：

- 附近 2000 个 → 查询 668 ns/漏斗 → 1024 个漏斗 = **0.68 ms/tick**
- 若堆到 1 万个 → 查询 ≈ 3.3 μs/漏斗 → 1024 个漏斗 = **3.4 ms/tick**

这是原版漏斗也有的行为（`getItemsAtAndAbove` 就是原版方法），
我们只是把频率从「8 gt 一次」提到「每 tick 一次」= **×8**。
所以给玩家的实用建议只有一句：**别在入库漏斗旁边堆几千个吸不走的掉落物**
（比如水流死角、被方块卡住的角落）。

---

## 5. 顺手做掉的两处无用功

测之前 `intake()` 每 tick 白做了两件事，实测空转成本 **170 ns**，优化后 **122 ns（−28%）**：

1. **「上方是不是容器」查了两遍** —— `intake` 判断走哪条进货分支时查一次，
   `suckUnlimited` 进门又查一次。改成查一次、结果直接传下去
   （`suckUnlimited(Container source, HopperBlockEntity hopper)`）。
2. **一条都没收上来时，第二次 `drain` 无事可做** —— 绝大多数入库漏斗绝大多数时间是空的，
   这一步 100% 是白跑。改成 `got == true` 才做。

两处都在 `VoidWarehouseHopper` 内部，不动 mixin。改完重跑
`UnlimitedIntakeSelfCheck` **23 项全绿、连跑两轮**，行为没有任何变化。

## 6. 怎么复现

```bash
# 1. 把基准挂上（测完连同 hook 一起删）
cp .workbuddy/tools/IntakePerfBenchmark.java.template \
   modern/26.3/src/main/java/neko/voidwarehouse/IntakePerfBenchmark.java
#    在 VoidWarehouseExtension#onTick 开头加一行： IntakePerfBenchmark.run(server);

# 2. 选规模（改 IntakePerfBenchmark 的常量）
#      GRID = 16 → 256 个漏斗     GRID = 32 → 1024 个漏斗
#      LOAD_PER_HOPPER × N = 每 tick 撒多少个物品（两档都调到 1024 便于横向对比）

export JAVA_HOME="C:/Users/12286/.jdks/ms-25.0.4.1"
./gradlew :modern:26.3:runServer --console=plain 2>&1 | grep PERF
```

跑完大约 90 秒，日志里会依次出现 `PERF`（微基准）与 `PERF-TICK`（真实 tick）两类行。

> 提醒：这台开发机负载不稳，同一档两次跑出来的绝对值能差 10 倍以上。
> **要看趋势就多跑几次，别一次定论。**
