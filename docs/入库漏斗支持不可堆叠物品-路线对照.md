# 入库漏斗支持不可堆叠物品 —— 三条路线对照

> 状态：**评估文档，尚未实现**。出料端已在 1.0.16 完成（`docs/出料漏斗支持不可堆叠物品.md`），
> 入库端按用户决定「暂时不做」，本册把三条路的改动点、风险与验收摊开，供拍板。
>
> 文中所有「现状」都是**真服务端实测**（`runServer` + 临时探针，14 条断言全绿），不是推理。

---

## 0. 结论先行

| | 路线 | 净改动 | 玩家看得见标本 | 碰客户端 | 风险 |
| --- | --- | --- | --- | --- | --- |
| **A** | 直取旁路：新货不经格子，直接 `insert` | ≈70 行（1 个文件） | ✅ | ❌ 不用 | 中 |
| **B** | 客户端叠加：服务端下发 seed，客户端画虚拟图标 | ≈320 行（服务端 4 文件 + 客户端 3 文件） | ✅ | ✅ 要 | 低（但两端要成对发版） |
| **C** | 余量归零：`drain` 对不可堆叠物不保留 | ≈2 行（1 个文件） | ❌ 格子空 | ❌ 不用 | 最低 |
| **C+** | C 再叠一个「标题栏写收纳清单」的补丁 | ≈30 行 | ⚠️ 只在标题栏 | ❌ 不用 | 低 |

**推荐顺序：C+ → A → B。**

理由：C+ 用 30 行就能让功能可用、且玩家知道这一格绑了什么；只有当你要求「图标必须出现在格子里」时，
才值得为 A 的 70 行（或 B 的 320 行 + 双端发版）付代价。

## 1. 实测：现状到底卡在哪

探针摆四组，全部真跑 tick（`VoidWarehouseExtension#onTick` 驱动），20 tick 后读数：

| 组 | 摆法 | 结果 | 说明 |
| --- | --- | --- | --- |
| **A** | 格 0 有 1 个矿车（玩家手放 = 分类物），上游箱子 20 个矿车 | 仓库 20 → **20**、上游 20 → **20**、格 0 仍 1 个 | **一个都没入库** |
| **B** | 格子全空、**没有**分类物，上游 20 个矿车 | 上游 20 → **0**、仓库 **20**、漏斗 **0** | **不可堆叠物本身能入库**，同一 tick 内进完 |
| **C** | 格 0 有 1 个圆石（分类物），上游 64 个圆石（对照） | 上游 0、仓库 **64**、格 0 仍 1 个 | 白名单机制正常，余量 1 留着 |
| **D** | 格 0 有矿车（分类物），上游 8 个**水桶** | 仓库水桶 **0**、上游 **8**、格 0 仍 1 个 | 白名单对不可堆叠物也有效 |

```
SMOKE RESULT vw-intake-unstackable-probe/26.3 checks=14 failures=0
```

**这三条实测把问题范围收得很死：**

1. **入库通路本来就是通的**（B 组 20 个一 tick 进完）—— 不存在「不可堆叠物进不了仓库」这回事；
2. **卡住的只有「不可堆叠物当分类物」这一种组合**（A 组 0 个）；
3. 对照组 C 证明白名单整体没坏，D 证明白名单对不可堆叠物也没坏 ——
   所以 A 组红的原因**不是过滤失灵**，而是「格子物理上腾不出位置」。

## 2. 根因（代码级）

两处，缺一不可：

**① `drain` 把它当余量留着** —— `VoidWarehouseHopper#drain`：

```java
int keep = keepClassifiers && VoidWarehouseClassifier.isOwnSlot(filter, stack, i)
        ? VoidWarehouseClassifier.KEEP      // KEEP == 1
        : 0;
int count = stack.getCount();
if (count <= keep) {
    continue;                               // 1 <= 1 ⇒ 永不搬
}
```

**② `suckUnlimited` 取出来又放不回去** —— 格子已被标本占满（1/1），
`HopperBlockEntity#addItem` 一格都放不下，于是每一格货物都走一遍
`removeItem → addItem 失败 → mergeBack`，**一个都没进去，但每 tick 白跑一轮**：

```java
ItemStack taken = source.removeItem(slot, available);   // 取出来
ItemStack leftover = absorbStack(source, hopper, taken); // 放不进（格子 1/1）
mergeBack(source, slot, leftover);                       // 原样还回去
if (drain(...) <= 0 || retries >= MAX_RETRY_PER_SLOT) break;   // drain 也搬不动 ⇒ 退出
```

A 组上游 20 格 × 20 tick = **400 次无用的取放**，这是现状的隐性成本。

**注意：这不是 `KEEP` 的数值问题。** 格子对这类物品的物理上限就是 1，
所以「让第二个进来」这件事**永远不可能通过格子发生**。这一条是后面所有推导的地基。

## 3. 一个绕不过去的推导

```
要让玩家在格子里「看见」分类物
  ⇒ 标本必须真的留在那 1 个格子里
  ⇒ 这一格永远是 1/1（maxStackSize == 1，装不下第二个）
  ⇒ 新货不可能经由格子中转
  ⇒ 必须给这类物品开一条「绕开格子」的旁路（仓库直连上游）
  ⇒ 只有 A（服务端旁路）或 B（客户端虚拟渲染）两条路
```

反过来：

```
允许格子空着（看不见）
  ⇒ drain 可以把标本一起搬走，格子腾空给下一件
  ⇒ 新货照常走格子中转，搬运链一个字都不用改
  ⇒ C 路线（2 行）
```

**没有中间态。** 想要「标本留着 + 新货仍走格子」在物理上不成立 —— 除非把 `maxStackSize` 改大
（那是改原版物品属性，会把整组矿车塞进一格，绝对不能碰）。

## 4. 路线 A：直取旁路（标本留着 → 看得见）

### 4.1 改动点

**只改一个文件：`modern/<ver>/src/main/java/neko/voidwarehouse/VoidWarehouseHopper.java`**

| 位置 | 改什么 | 行数 |
| --- | --- | --- |
| 新增 `bypassesHopper(filter, stack)` | 判定「这件货要不要绕开格子」：`maxStackSize <= 1` ∧ 不是潜影盒 ∧ 有白名单 ∧ 命中白名单 ∧ 属于某一格 | ≈25 |
| `suckUnlimited`（容器来源） | 在 `canTakeFrom` 之后插一段：整格取出 → `data.insert` → 成功即完、失败 `mergeBack` | ≈18 |
| `suckEntitiesUnlimited` / `absorbEntity`（掉落物来源） | 同上，`insert` 成功则 `entity.setItem(EMPTY) + discard()` | ≈20 |

`drain`、`intake`、`VoidWarehouseClassifier`、`SlotMixin`、`HopperBlockEntityMixin`、
`VoidWarehouseHopperFilter` **全部不用改** —— seed 清单与「只认玩家的手」的机制已经就位。

### 4.2 关键难点

**① 旁路要自己重判白名单，不能依赖闸门。**
`blockMachineInsert` 挂在 `Container#canPlaceItem` 上，而旁路根本不调 `addItem` / `setItem`，
所以那道闸门**不会被问到**。旁路内部必须自己走一遍
`matchesAny(stack)` + `isOwnSlot(filter, stack, i)`。漏了这一步 = 白名单在有标本的漏斗上失效。

**② `insert` 会就地清空参数，`mergeBack` 要按「取出时的数量」还。**
`VoidWarehouseData#insert` 的契约是「收下即清零、拒收原样不动」，所以：

```java
ItemStack taken = source.removeItem(slot, available);   // taken.getCount() == available
if (!data.insert(taken)) {
    mergeBack(source, slot, taken);      // 拒收时 taken 未被动过，原样还回去
}
// 收下时 taken 已被清零，不需要 mergeBack
```

这比出料端的 `returnUnplaced` 简单（出料要处理「部分送出」），但**「部分」依然存在**：
`insert` 对潜影盒是「拆开入库」，拆完原堆叠被 `setCount(0)` —— 也算「全部收下」。

**③ 掉落物路径的 `discard()` 时机。**
`absorbEntity` 现在是「吃进去一部分 → 写回实体；全吃进去 → `discard()`」。
旁路版是「`insert` 成功 → `discard()`；失败 → 实体原样留着」。
**先 `discard` 再 `insert` 就是丢货**，顺序不能反。

**④ 一条格子里可能同时有「可堆叠物分类物」和「不可堆叠物分类物」。**
旁路只对 `maxStackSize <= 1` 生效，可堆叠物照旧走格子，两条路在同一 tick 内并存 ——
这没问题，但自检里要覆盖（否则「混装漏斗」这个最常见场景没测）。

### 4.3 风险清单

| 风险 | 后果 | 缓解 |
| --- | --- | --- |
| 旁路没重判白名单 | 有标本的漏斗变成「什么都收」 | 单测 + 自检 D 组（水桶必须被拦） |
| `removeItem` 后 `insert` 前抛异常 | 那一堆货凭空消失 | `insert` 不抛受托异常；仍旧建议 `try/finally` 里 `mergeBack` 兜底 |
| `mergeBack` 写错（比如原格已被别的 tick 填满） | 丢货 / 溢出 | `mergeBack` 是既有方法，原样复用；上游容器在同一 tick 内只有本漏斗一个读者 |
| 掉落物路径 `discard` 顺序写反 | 丢货 | 代码评审 + 自检「上游掉落物数量守恒」断言 |
| 旁路绕过了 `canPlaceItemInContainer` | 某些优化模组（Lithium）的白名单路径与旁路不一致 | 旁路内部判定与 `blockMachineInsert` 共用同一组 `VoidWarehouseClassifier` 方法，不各写一份 |

### 4.4 验收用例（A）

1. 矿车标本 + 上游 20 个 → 20 tick 内全部入库；**标本全程在格 0**
2. 空潜影盒标本 + 上游 15 个 → 同上
3. 非空潜影盒标本 → **拆盒入库**（壳 + 箱 + 内容物），不下发整盒（见第 7 节）
4. 水桶标本 + 上游 8 个矿车 → 一个都不进（白名单隔离）
5. 圆石标本（可堆叠对照）+ 上游 64 个 → 行为与现在**完全一致**（走格子，余量 1）
6. 混装：格 0 矿车、格 1 圆石 → 两条路各自生效，互不串格
7. 玩家把标本拿走 → `SlotMixin` 抹掉 seed → 回到原规则（不可堆叠物仍能整批入库，见 B 组实测）
8. 服务器重启 / 区块重载 → 白名单还在（seed 已落盘，`CarpetNekoAdditionClassifierSeeds*`）
9. 连做 3 轮 → 每轮数字完全一致（不累积、不漂移）
10. 上游容器塞满 27 格各 1 个不可堆叠物 → 一 tick 的吞吐量、以及「不丢不复制」的账

## 5. 路线 B：客户端叠加（服务端零改动 → 看得见）

标本不留在格子里（走 C 的搬运逻辑），但**客户端在空格子上画一个半透明图标**。

### 5.1 改动点

**服务端（4 个文件，≈150 行）**

| 文件 | 内容 | 行数 |
| --- | --- | --- |
| `hopper/HopperSeedsPayload.java`（新） | S2C：`containerId:int` + `ItemStack.OPTIONAL_LIST_STREAM_CODEC`（5 个，已 javap 确认 26.3 有这一个） | ≈40 |
| `hopper/HopperSeedsNetwork.java`（新） | 注册（撞名 try/catch 幂等） | ≈35 |
| `hopper/HopperSeedsService.java`（新） | 从 `HopperBlockEntity` 读 seed、判 `isIntake`、下发 | ≈40 |
| `mixin/ServerPlayerOpenMenuMixin.java`（新） | `ServerPlayer#openMenu` TAIL → 若是 `HopperMenu` 则下发 | ≈35 |

**⚠️ 这里有个真难点**：`openMenu(MenuProvider, …)` 的 `MenuProvider` 是原版匿名的，**拿不到方块坐标**。
只能从 `HopperMenu` 的私有字段 `container` 反查（`instanceof HopperBlockEntity` → `getBlockPos()`），
需要再写一个 `@Accessor` 接口。这条比表面看起来脆 —— 原版改一次 `HopperMenu` 的字段就断了。

**客户端（3 个文件，≈170 行）**

| 文件 | 内容 | 行数 |
| --- | --- | --- |
| `HopperSeedsPayload`（镜像） | 与 carpet 侧**逐字节一致**（现有 `voidwarehouse-search` 的红线） | ≈40 |
| `HopperSeedsClient` | `Map<containerId, ItemStack[]>` 缓存 + `disconnect` 清理 | ≈50 |
| `MixinAbstractContainerScreen` | `extractRenderState` TAIL：格子为空时 `guiGraphics.renderItem(seed, x, y)` + 30% 透明度 | ≈80 |

### 5.2 风险清单（B）

| 风险 | 后果 | 缓解 |
| --- | --- | --- |
| payload 与 carpet 侧不逐字节镜像 | 解码失败 / 静默不收 | 沿用 `check_return_protocol_parity.py` 那套判据 |
| `HopperMenu#container` 字段名变了 | 拿不到 pos → 永不下发（静默失效） | `require = 0` + 自检里反射数 handler |
| 客户端没装 mod | 格子空、功能正常但看不见 | 这是 B 的设计前提，写进 README |
| 两端版本错配 | 单边更新 = `NoSuchMethodError` 当场崩（已在 2026-10-31 踩过） | 两个 jar 必须成对发版 |
| 消息里带物品组件 | 带宽（每格一个完整 `ItemStack`） | `ItemStack.OPTIONAL_LIST_STREAM_CODEC` 一次发 5 格，量级可忽略 |

### 5.3 B 的额外收益

`voidwarehouse-search` 已经有「客户端渲染 + 服务端目录下发」的全套管线，B 可以并进同一个客户端 mod
（不用再开第三个 jar）。代价是那个 mod 的职责从「搜索框」扩成「虚空仓库客户端增强」。

## 6. 路线 C：余量归零（2 行 → 看不见）

### 6.1 改动点

**`VoidWarehouseHopper#drain` 一行条件：**

```java
int keep = keepClassifiers
        && VoidWarehouseClassifier.isOwnSlot(filter, stack, i)
        && stack.getMaxStackSize() > 1          // ← 新增：不可堆叠物的标本也要搬空
        ? VoidWarehouseClassifier.KEEP
        : 0;
```

于是不可堆叠物标本会被 `insert` 搬进仓库（入库 1 个）、格子腾空；
下一 tick `suckUnlimited` 吸 1 个进来、`intake` ③ 步再 `drain` 搬空 ——
配合 `MAX_RETRY_PER_SLOT = 4`，一 tick 能走 5 轮。

**为什么分类物清单不会跟着丢**：seed 存在 `carpetAutomending$classifierSeeds` 里，
由 `Slot#setByPlayer`（玩家的手）写、由「掏空漏斗」清。
`drain` 走的是 `hopper.setItem`，**碰不到 seed** —— 所以格子空了白名单仍在，`canPlaceItem` 闸门照旧生效。

**⚠️ 但玩家会看到「这个漏斗什么都不收」** —— 因为界面上一片空白，
而实际上它只收某一件东西。这是 C 唯一的、也是最刺眼的代价。

### 6.2 C+：给「看不见」补一个廉价出口

既然格子空着，就把分类清单**写到漏斗的显示名上**：

- 打开界面时标题显示 `漏斗 · 收纳：矿车 / 水桶`（`AbstractContainerMenu` 的标题来自 `MenuProvider`，
  原版 `HopperMenu` 的标题是 `block.minecraft.hopper`，需要 mixin `HopperBlockEntity#getDisplayName`
  或 `ServerPlayer#openMenu` 时改 `CustomName`）
- 或者更轻：**物品栏上方不发任何 UI，只在聊天栏提示一次**（玩家放入标本的那一刻）
  `[虚空仓库] 这个漏斗只收 矿车（标本已入库，白名单仍生效）`
- 代价：改 `CustomName` 会与玩家自己命名的漏斗冲突，必须记录原值并在白名单清空时还原；
  聊天提示只有一次性、事后看不见

**C+ 的价值**：30 行换「玩家知道这格绑了什么」，不需要客户端 mod、不需要 payload。
**它的局限**：图标不在格子里，视觉上与原版漏斗一样是空的。

## 7. 潜影盒：三条路都要面对的语义问题

这不是路线选择能绕开的，是**既有模型的不对称**：

| 方向 | 行为 | 代码 |
| --- | --- | --- |
| 入库 | **非空盒被拆开** → 盒内物品 + 2 潜影壳 + 1 箱子（染色盒再 + 1 染料）；**空盒整盒入库** | `VoidWarehouseData#insert` → `unpackShulkerBox` |
| 出料 | 按样本**精确取整盒**（`withdraw` 走 `takeStack`，不拆） | `VoidWarehouseData#withdraw` |

所以「拿非空潜影盒当分类物」在语义上**从一开始就不成立**：

```
标本 = 装着 5 个钻石的潜影盒
上游来 1 个同样的盒子 → 入库时被拆成 5 钻石 + 2 壳 + 1 箱
仓库里「非空盒」这一格数量永远是 0
⇒ 出料端 withdraw(非空盒样本) 永远取不到 ⇒ 进得去、出不来
```

而「空潜影盒」是成立的（整盒入库、整盒出库，1.0.16 的出料端 B 组自检就是这个）。

**建议（三条路都一样）**：

- 旁路 / 余量归零只对「非潜影盒」的不可堆叠物生效，潜影盒**继续走原路径拆盒** ——
  这是玩家已经接受的行为，不改；
- README / CHANGELOG 明确写「非空潜影盒不支持作为分类物，它会按既有规则拆开入库」；
- 如果将来要支持「整盒进、整盒出」，那是**另一件事**：要给 `insert` 加一个
  「整盒入库」模式（不进 `unpackShulkerBox`），会牵动盒模式的材料账，
  必须单独评估（与 `docs/盒模式潜影盒嵌套刷盒子事故与修复.md` 相邻）。

## 8. 对比与推荐

### 8.1 工作量与代价

| | A 直取旁路 | B 客户端叠加 | C 余量归零 | C+ 标题栏补丁 |
| --- | --- | --- | --- | --- |
| 净改动 | ≈70 行 / 1 文件 | ≈320 行 / 7 文件 | **≈2 行 / 1 文件** | ≈30 行 |
| 碰客户端 | 否 | **是**（两端成对发版） | 否 | 否 |
| 五版本同步 | 5 份副本 | 5 份服务端 + 5 份客户端 | 5 份副本 | 5 份副本 |
| 自检规模 | ≈25 断言（含掉落物路径） | ≈15 断言（服务端逻辑简单）+ 真机看图标 | **≈12 断言** | ≈15 断言 |
| 实机风险 | 中（动两条进货路径） | 低（不碰搬运） | **最低** | 低 |
| 玩家看得见 | ✅ 格子里 | ✅ 格子里（虚拟） | ❌ | ⚠️ 标题栏 |

### 8.2 推荐

1. **先做 C+**。2 行 + 30 行的组合，把「能不能用」和「玩家知不知道这格绑了什么」一起解决，
   不动搬运链、不碰客户端、五版本同步成本最低。
2. **只有当你明确要求「图标必须画在格子里」时，才做 A**。
   A 的 70 行里有一半是「重判白名单 + 保账」，与出料端的 `ejectSpecimen` 是同一个模式的镜像 ——
   那个模式已经用 22 条断言 + 反证验过，所以 A 的风险是可估的，不是未知。
3. **B 只在 A 实机出问题时才值得**。它的技术风险最低，但代价是「所有玩家都必须装客户端 mod，
   否则看不见」—— 一个纯服务端的 carpet 规则，为了一个图标引入客户端依赖，性价比最差。

### 8.3 如果都不做

现状（实测）：不可堆叠物**能入库**（B 组），只是**不能当分类物**（A 组）。
把这个边界原样写进 README 也是完全站得住的 ——
「分类物白名单对不可堆叠物不生效，请用可堆叠物当分类物，或用 9 合 1 / 配方扣料间接收纳」。

## 9. 附：探针怎么复跑
