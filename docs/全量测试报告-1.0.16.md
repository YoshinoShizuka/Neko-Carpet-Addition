# 全量测试报告（carpet-Neko-Addition 1.0.16 / MC 26.3）

## 一句话

在**真实服务端**里跑了一轮覆盖性能、语言、边界、回归四大类的全量测试：**209 条断言全绿、0 失败、0 跳过**，
五个发布版本**全部从源码重编成功且产物 md5 与已发布件逐字节一致**；

本轮**未发现新缺陷**，遗留的都是「覆盖范围」类风险而非代码缺陷（见第六、七章）。

| 项 | 内容 |

### 1.2 环境

- `TARGET_MC_VERSIONS=26.3 ./gradlew :modern:26.3:runServer`（真服务端，非单元测试；同时加载 carpet / lithium / c2me / servux 等既有 mod，验的是「和真实环境共存」）
- 20 个**真实 `ServerPlayer` 对象**（26.3 已无 Fabric `FakePlayer`）：`new ServerPlayer(server, level, profile, ClientInformation)` + 一个 `SERVERBOUND` 的空 `Connection` + `ServerGamePacketListenerImpl`。**有连接**，「同步给客户端 / 发消息」的代码路径才会真的被执行。
- 双语组另建一个 `enBot`（`ClientInformation` 的 language = `en_us`）与 `bots`（`zh_cn`）对照。

### 1.3 执行方式（为什么这么设计）

- **阶段机**：`VoidWarehouseExtension#onTick` 每个 tick 推进一个 stage，共 26 个（stage 0 等 5 tick 让世界稳定后建玩家，1–15 功能组，16–22 性能组，23 多人压力，24 双语，25 收尾）。性能必须量「真 tick 里发生的事」，不能在一个不被打扰的 CPU 循环里一口气跑完。
- **微基准自动定批**：Windows 上 `nanoTime` 分辨率约 100 ns，单次几十纳秒的操作会读成 `0.00 us`。所以先把一批凑到 200 µs 以上再除回单次；报告里所有 µs 数都来自定批后的值（日志里的「批 N」就是该轮自适应出来的批大小）。
- **反证是硬要求**：每条规则、每个子功能都配一条「关掉开关必须失效」的断言，否则「绿」可能只是别的原因凑巧成立。
- **判据只有一条**：日志末行 `SYSTEM TEST RESULT v26.3 checks=209 failures=0 skips=0`。`runServer` 崩了也可能返回 `EXIT=0`，所以不看退出码。
- **跑完还原**：`install_systest_263.py remove` 删源码 + 还原钩子，`git status` 为空（已核对）。

### 1.4 判定标准（四大类各自的口径）

| 类别 | 判定标准 |
| --- | --- |
| 性能 | ① 单次动作 < 200 µs；② 20 人同 tick 各做一次动作合计 < 10 ms（50 ms tick 的 20%）；③ 最坏 tick（20 人同 tick 各自入库 + 刷新可兑表）< 5 ms；④ 400 格仓库堆增长 ≤ 1 MB 且清空后回落；⑤ 可兑表重算不随人数线性叠加（同 tick 只算一次） |
| 语言 | ① 语言判定只由 `player.clientInformation().language()` 决定，`en` 开头为英文；② 每条文案断言必须**成对**：中文环境命中中文关键字、英文环境命中英文关键字，且互不串味；③ 触发别名忽略大小写与首尾空格，中文名维持精确匹配；④ GUI 标题跟随触发物的显示名 |
| 边界 | ① 异常输入（空栈 / 空气 / 负数 / 0 / 越界 / null / 未知 id / 坏配方 / 缺上下文）必须「不抛异常」且「仓库状态不变或返回安全值」；② 容量与材料极限给出正确降级（只给现有的 / 只给做得到的 / 明确失败）；③ 每个子功能必须有「规则关闭态」反证 |
| 回归 | ① 既有 192 条功能断言 100% 通过、0 跳过；② 五版本从源码构建成功；③ 产物 md5 与已发布件/CHANGELOG 表一致（证 dist 与源码同源） |

7 个阶段：兑换规划（9 合 1）、配方扣料规划、可兑表重算、入库/取出吞吐、漏斗入库吞吐（真世界）、界面打开成本、内存占用；

### 2.3 多人压力

| 人数 | 打开界面 | 取货 | 翻页 | 整页刷新 | 合计 | 占 50 ms tick |
| --- | --- | --- | --- | --- | --- | --- |
| 1 人 | 0.039 ms | 0.018 ms | 0.003 ms | 0.033 ms | **0.092 ms** | 0.2% |
| 5 人 | 0.088 ms | 0.003 ms | 0.004 ms | 0.042 ms | **0.138 ms** | 0.3% |
| 10 人 | 0.026 ms | 0.002 ms | 0.003 ms | 0.031 ms | **0.063 ms** | 0.1% |
| 20 人 | 0.062 ms | 0.004 ms | 0.006 ms | 0.069 ms | **0.140 ms** | 0.3% |

- 极限连点：20 人 × 20 次 = 400 次「取货 + 回填」合计 **0.032 ms**，单次 **0.08 µs**（阈值 200 µs，余量 2500 倍）。
- **最坏 tick**（20 人同 tick 各自「入库一格 + 界面刷新」）：整 tick 含 1 次可兑表重算 = **1.664 ms（3.3% tick）**，同 tick 后续 20 人合计 **0.0049 ms**。
  → 证明 `markChanged()` 只置脏、重算**按 tick 合并**的修复仍然有效：20 人的代价 ≈ 1 人的代价。
  → 修复前同场景 **30.573 ms（61.1%）**，现为 3.3%，且**与人数无关**（上限锁死「每 tick 一次重算」）。

### 2.4 性能结论

- **通过**。所有指标量级都在微秒到毫秒之间，最贵的路径（可兑表重算）1.7 ms 且只在「脏了之后的第一次读」付一次，20 人同 tick 也仍是 1.7 ms。
- 内存线性可控且可回落，没有「入库越多越胖」的迹象。
- **注**：`menu` 构造 2.9 µs → 1.550 µs、可兑表 1.99 ms → 1.716 ms 这两项是**同代码路径下的漂移**（JIT 状态 / 机器负载不同），不代表发布版有性能改动；判定必须以「量级 + 阈值」为准，不能拿两次运行做逐位比较。
- **注**：`displaySlotAt` 从 0.22 µs 升到 0.375 µs 是双向缓存分键（`displayZh/displayEn`）后每格多一次分支与字段选择，绝对值 8.3 ns/格、45 格 0.375 µs = tick 的 0.0008%，可忽略；详见风险 7.6。

### 3.3 语言结论

- **17 / 17 通过**。中英两套文案在**同一进程内**由两个玩家对象同时验证，因此「串语言」与「缓存被跨玩家污染」两类问题都被真实覆盖（`displayZh/displayEn` 双份缓存 + `invalidateDisplays()` 一次作废四份的设计成立）。
- **已知行为（非缺陷）**：界面的语言在**打开那一刻**定格（`VoidWarehouseMenu` 构造时求一次 `isEnglish`）。玩家在使用中切换客户端语言，已打开的界面不会实时切换，需关掉重开。这是刻意取舍（避免每 tick 重算文案），已记入风险 7.3。
- **测试自身的坑（已修）**：`ClientInformation.createDefault()` 的 language 是 `en_us`（`javap -c` 确认字节码里是 `ldc "en_us"`），第一版假玩家用它导致 17 条中文断言全红。现所有中文用例显式构造 `zh_cn`。

## 八、改进建议（按优先级）

1. **给 1.21.11 补一套同源断言（对应 7.1）**：它是唯一走 `loom-remap + Mojang mappings` 且有 `playC2S/playS2C`、`render(...)` 差异的版本，风险最高。做法：把模板按版本条件编译（`//#if MC >= 12111`）后跑一次 `runServer`，至少覆盖语言组 17 条 + 兑换/配方核心 20 条。
2. **README 明确「仅中/英」并写清判定口径（对应 7.2）**：一行说明省掉大量「为什么日语玩家看到中文」的 issue。
3. **加一个两阶段脚本验持久化（对应 7.7）**：第一次 `runServer` 灌数据后 `halt`，第二次启动只断言「条数与数量与上次一致」。这是目前唯一完全没有自动化覆盖的红线区（丢存档级）。
4. **给性能阶段加「结果区间断言」而不是只打印（对应 7.5）**：例如 `planExchange < 50 µs`、`可兑表重算 < 5 ms`，让性能回归也能自动红/绿，而不是靠人读日志。
5. **补一条「界面开着时切换语言」的断言（对应 7.3）**：把当前行为钉成契约（重开才生效），避免以后有人「顺手修」成每 tick 重算。
6. **边界组再加 3 条**（当前空白）：BigInteger 超大数量（> Long.MAX）的入库/取货；同一 tick 两人取同一格到空；`takeExact` 在数量刚好等于库存时的边界。
