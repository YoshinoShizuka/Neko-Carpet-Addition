# 出料漏斗性能基准（1024 个出料漏斗实测）

> **一句话结论**：**数量不是问题，速率上去了也不贵。**
> 1024 个出料漏斗空转的净开销小到被机器噪声盖住；满载时每 tick 出料约 **39 万个**物品
> （382 个/漏斗），净开销仍然只是 **个位数 ms/tick** —— 而且**与普通漏斗基本同价**
> （`extractor_push` 357 ns vs `vanilla_push` 350 ns）。
> 唯一真正变贵的是「**下游塞满时的空转快筛**」（`eject(下游满)` 1612 ns/漏斗），
> 真实场景下游不满时不会走这条 —— 见第 4 节。

---

## 1. 为什么要专门测一次

本轮把出料端的速率从原版「**每 8 gt 搬 1 个**」（2.5 个/秒）改成了「**每 tick 整格搬 + 清冷却**」。
和入库端的改造是同一类动作，但方向相反，代价模型也不同：

- 入库端改的是「**把漏斗 5 格搬进仓库**」—— 每 tick 扫 5 格 + `BigInteger` 记账；
- 出料端改的是「**把仓库的料塞进下游容器**」—— 每 tick 走一遍 `getContainerAt(下游)` +
  `isFullContainer` 快筛 + `addItem`，而且**搬得比原版多得多**（原版一次 1 个，现在一次整格）。

所以要回答两件事：

1. **空转成本**：N 个出料漏斗什么都不干（仓库空 / 下游满）时，每 tick 白烧多少？
2. **满载成本**：仓库哗哗出货时，会不会把 tick 撑爆？

---

## 2. 两种测法，互相印证

### 微基准（`PERF` 行）

直接调 API，**热身 100 轮 → 计时 200 轮**取平均，把成本拆到
「一次 `isExtractor` / 一次 `getContainerAt` / 一次 `eject` / 整条 `pushItemsTick`」的粒度。

> 热身轮数很关键：JIT 没编译时前几项能虚高数倍。参考入库那份基准的教训
> （20 轮热身时「空场查询」虚高 4 倍）。

### 真实 tick（`PERF-TICK` 行）

读 `MinecraftServer#getTickTimesNanos()` —— 已核对字节码：这个数组在 `tickServer()`
里写入，**计时起点在方法头、终点在方法尾，不含 tick 之间的 sleep**，
所以空闲服务端也能测出真实的 tick 计算负担。采样 300 tick 刷满 ring buffer。

四组对照：

| 组 | 场景 |
|---|---|
| `baseline` | 没有漏斗（纯空区块） |
| `idle` | N 个出料漏斗空转（下游塞满、仓库空，谁都不动） |
| `load` | N 个出料漏斗 + 每 tick 补满仓库、下游腾空 → **满负荷搬出** |
| `vanilla` | **撤掉终端**，同样这批漏斗变普通漏斗（量原版 8 gt 节流的基准） |

> ⚠️ `load` 与 `vanilla` 是**同一批漏斗**（只是前者上方压着终端、后者没有），
> 所以 `load − vanilla` 才是本模组**净加进去**的出料开销；
> `idle − vanilla` 是空转的净开销。

---

## 3. 数据

### 3.1 微基准（每漏斗每次，N=1024）

| 项 | ns / 漏斗 |
|---|---:|
| `isExtractor`（口是不是该出料） | 73 |
| `data()`（取仓库句柄） | 15 |
| `getContainerAt(下游)`（下游是不是容器） | 180 |
| `pull(仓库空)` | 24 |
| **`extractor_push`（出料漏斗跑一次 pushItemsTick）** | **357** |
| `vanilla_push`（**同样这批漏斗**，撤掉终端后跑 pushItemsTick） | 350 |
| `eject(下游满)`（下游塞满时的整条出料尝试） | **1612** |
| `eject(满载一轮)`（每漏斗真推 320 个，单次调用） | 31,692 |

> `eject(满载一轮)` 那一行是**一次性**的（每漏斗推 320 个），不是每 tick ——
> 折算下来 **≈ 99 ns / 个物品**，就是「把一个物品穿过整条 `addItem` 链条」的价。

### 3.2 真实 tick（median，300 tick 采样）

| 组 | median | p95 | max | mean | 相对 baseline |
|---|---:|---:|---:|---:|---:|
| `baseline` | 27.301 | 41.300 | 55.792 | 28.648 | — |
| `idle` | 28.250 | 46.330 | 62.795 | 30.429 | **+0.95 ms** |
| `load` | 38.821 | 57.043 | 67.059 | 41.250 | +11.5 ms |
| `vanilla` | 20.846 | 34.401 | 43.095 | 22.769 | — |

> ⚠️ **这一轮的机器负载很重**：光 `baseline` 就是 **27.3 ms/tick**，
> 也就是说**服务端什么都没干就烧掉了一半预算**。这恰恰说明：
> **绝对值绝不能跨进程比较**，只有**同一进程内**的 `idle − vanilla`、`load − vanilla`
> 才是有效信号。第一轮（机器较空）跑出来 `baseline` 只有 **1.786 ms**，
> 同一份代码 `idle` 4.088 ms、`load` 18.056 ms、`vanilla` 1.590 ms。

**换算成「本模组净加的开销」（同进程相减）：**

| 口径 | 本轮（重载机） | 第一轮（空载机） |
|---|---:|---:|
| 空转净开销 `idle − baseline` | **0.95 ms/tick** | 2.30 ms/tick |
| 满载净开销 `load − vanilla` | **17.98 ms/tick** | 16.47 ms/tick |
| 普通漏斗基准 `vanilla − baseline` | （负值，噪声） | （负值，噪声） |

- **空转 0.95 ms** —— 占 50 ms 预算的 **1.9%**。而且注意 `idle` 只比 `baseline` 高不到 1 ms，
  说明「1024 个出料漏斗什么都不干」这件事**几乎不要钱**。
- **满载 17.98 ms** 看着吓人，但要知道这一档**每 tick 从仓库取料 117,309,440 ÷ 300 ≈ 391,032 个**
  （382 个/漏斗/ tick）—— 换算下来 **≈ 46 ns / 物品**，
  和 3.1 里「一个物品穿过 addItem 链条 99 ns」是同一个数量级，
  剩下的是「把物品从仓库搬出来再记账」的那部分。**这是真在干活，不是白烧。**

### 3.3 与入库端横向对比

| | ns / 漏斗 / tick |
|---|---:|
| 入库漏斗（`intake_push`） | 341 |
| 出料漏斗（`extractor_push`） | **357** |
| 普通漏斗（`vanilla_push`，两批都是） | 350 ~ 357 |

**三者基本同价。** 也就是说：本模组把漏斗两个方向都改成了「无速率上限」，
但**单个漏斗每 tick 的计算成本与原版几乎一模一样** —— 因为我们没取消原版逻辑，
只是把原版那一步「8 gt 干一次」摊成了「每 tick 都能干」，总量没变、延迟降了 8 倍。

## 4. 结论

### ① 数量不是问题，线性扩展

1024 个出料漏斗空转净开销 **0.95 ms/tick**（重载机上测的；空载机 2.30 ms），
按 357 ns/漏斗 线性外推：**1 万个也才 3.6 ms/tick**。没有超线性项 ——
每个出料漏斗只关心「正上方那格 + 正下方那格」，彼此不干扰。

### ② 与普通漏斗基本同价（最硬的对照）

| | ns / 漏斗 / tick |
|---|---:|
| 出料漏斗（`extractor_push`） | 357 |
| **同一批**漏斗撤掉终端后（`vanilla_push`） | 350 |

**我们没有让漏斗变贵。**

### ③ 满载很便宜

每 tick 出料约 **39 万个**物品（≈ 7,820 个/秒/漏斗），
净开销 **17.98 ms/tick**（36% 预算）—— 但这一档是**故意把下游腾空、每 tick 灌满仓库**造出来的极端，
真实世界不会有人让 1024 条出料线永远满载。折算到**单个漏斗**则是 **≈ 17.6 μs/tick**，
远低于一个 tick。

### ④ 唯一要留神的：下游塞满时的空转快筛

`eject(下游满)` = **1612 ns/漏斗**，是 `extractor_push` 的 4.5 倍。这一项为什么贵？

- `eject` 进门先做 `isFullContainer(target, side)` 快筛；
- 然后**逐格**扫漏斗的 5 格，对每格尝试 `addItem`；
- 下游塞满时**每一个 `addItem` 都会走完整条「找槽位 → 试放 → 退回剩菜」的链条**，
  最后一个个都失败 —— 这一整轮是**白跑**。

> 但这是**我们主动选的**：原版 `ejectItems` 里就有 `isFullContainer` 快筛，
> 我们照抄了它、没有自己加「已知满就跳过」的缓存。理由是**下游箱子的内容可能被外部
> 每 tick 改变**（其它漏斗、玩家、红石），缓存会导致「下游空了但漏斗还不知道」——
> 宁可每 tick 白跑一次快筛，也不引入可能卡死的状态。
>
> 实用建议：**出料漏斗下面别长期摆一个塞满的箱子**。真那样摆，等于让这 1024 个漏斗
> 每 tick 白跑 1612 ns（合计 1.6 ms/tick）—— 仍然不致命，但纯属白烧。

## 5. 怎么复现

```bash
# 1. 把基准挂上（测完连同 hook 一起删）
cp <验收脚本>/ExtractorPerfBenchmark.java.template \
   modern/26.3/src/main/java/neko/voidwarehouse/ExtractorPerfBenchmark.java
#    在 VoidWarehouseExtension#onTick 开头加一行： ExtractorPerfBenchmark.run(server);

# 2. 选规模（改 ExtractorPerfBenchmark 的常量）
#      GRID = 16 → 256 个漏斗     GRID = 32 → 1024 个漏斗

export JAVA_HOME="C:/Users/12286/.jdks/ms-25.0.4.1"
./gradlew :modern:26.3:runServer --console=plain 2>&1 | grep PERF
```

跑完大约 **100 秒**（比入库那份长，因为多了 `load` 满载档），
日志里会依次出现 `PERF`（微基准）与 `PERF-TICK`（真实 tick）两类行。

> 提醒：这台开发机负载不稳，同一档两次跑出来的绝对值能差 **10 倍以上**
> （本轮 `baseline` 27.3 ms vs 第一轮 1.786 ms）。**要看趋势就多跑几次，别一次定论**；
> 跨进程的绝对值一律不可比，只有同进程内的差值是有效信号。
