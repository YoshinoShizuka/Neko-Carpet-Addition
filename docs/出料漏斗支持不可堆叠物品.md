# 出料漏斗支持不可堆叠物品（标本 + 旁路）

> **一句话结论**：堆叠上限为 1 的物品（矿车、水桶、潜影盒、床、破损工具…）
> 以前当出料分类物时**一个都出不来** —— 格子里那 1 个既是「货」又是「分类物」，
> 搬走就没分类、不搬就没货。本轮换成「**标本 + 旁路**」：
> 格子里那 1 个**永不搬走**（同时解决了「分类物看不见」），出货改由仓库**直连下游**，
> 每 tick 1 个（20 个/秒）。实测 20 tick 出 20 个矿车、仓库账 200 → 180 分毫不差。

---

## 1. 问题：`KEEP = 1` 撞上 `maxStackSize = 1`

出料端的模型是「漏斗 5 格里摆着什么，仓库就出什么」。为了让分类不丢，
`eject` 的规矩是「每格搬走 `数量 - KEEP` 个，留 1 个当分类物」：

```java
// 改前的 VoidWarehouseExtractor#eject
if (stack.isEmpty() || stack.getCount() <= KEEP_AS_CLASSIFIER) {
    continue;                     // ← 只剩分类物，不许搬
}
int payload = stack.getCount() - KEEP_AS_CLASSIFIER;
```

对圆石（64）没问题：格子 64 → 推 63 → 留 1。
对矿车（1）：格子**最多就 1 个**，`1 - 1 = 0` ⇒ **永远搬不动**。

`pull` 那端同样死：`room = limit - count = 1 - 1 = 0`，补料也补不进去。

所以旧版类注释里那条「已知限制」写的是实话：

> 堆叠上限为 1 的物品（水桶、床、被拆过的工具…）当分类物时，格子本来就只能装 1 个，
> 「补满」无从谈起，而最后 1 个又是分类物不能外流 —— 所以这类物品出不了料。

**潜影盒也在这条限制里**（它同样是 `maxStackSize = 1`），只是平时没人拿它当出料分类物。

## 2. 两条想当然的路，都不通

### ① 把 `KEEP` 改成 0

搬空就没分类了。`pull` 靠「格子里的那件物品」判断该补什么品类
（空格子什么都不出，仓库不替玩家挑品类），所以出 1 个之后格子空掉，
**下一 tick 就不知道该补什么** —— 出 1 个断供，分类也丢了。

### ② 搬走 → 从存档里的分类物清单补回来

`VoidWarehouseHopperFilter` 里确实有一份按格独立的 `classifierSeed[5]`
（入库端的白名单，`Slot#setByPlayer` 写入）。看起来可以「搬空 → 再从 seed 填回 1 个」，
但那是**凭空造物品**：仓库 +1、格子 -1、再 +1 ⇒ 净多一个。

想不刷就得从仓库 `withdraw` 那 1 个补回来 —— 白跑一趟，而且**仓库没货时标本照样消失**，
又回到「看不见」。

## 3. 修法：标本 + 旁路

这一格那 1 个**干脆不动**，从此只当「标本」；出货走仓库 → 下游的**直连**：

```java
// VoidWarehouseExtractor#eject 循环里
if (stack.getMaxStackSize() <= 1) {
    // 这 1 个是标本：既是分类声明，也是玩家看到的图标，永不搬走
    if (ejectSpecimen(level, hopper, target, side, stack)) {
        moved = true;
    }
    continue;
}

private static boolean ejectSpecimen(ServerLevel level, HopperBlockEntity hopper, Container target,
                                     Direction side, ItemStack sample) {
    VoidWarehouseData.Withdrawal withdrawal =
            VoidWarehouse.data(level.getServer()).withdraw(sample, BigInteger.ONE);
    if (withdrawal.isEmpty()) {
        return false;                                        // 仓库没货 → 静默，标本留着
    }
    ItemStack cargo = withdrawal.stack();
    int want = cargo.getCount();
    // 给副本：addItem 会就地 shrink 参数，而撤销要按「原本要送几个」算
    ItemStack leftover = HopperBlockEntity.addItem(hopper, target, cargo.copy(), side);
    int accepted = want - leftover.getCount();
    if (accepted <= 0) {
        withdrawal.returnUnplaced(0);                         // 下游不收 → 整笔撤回
        return false;
    }
    if (!leftover.isEmpty()) {
        withdrawal.returnUnplaced(accepted);                  // 部分收下 → 退回剩下的
    }
    return true;
}
```

**`pull` 一个字都没改** —— 格子恒为 1/1，`room` 天然是 0，本来就是对的。

### 为什么给 `addItem` 的是副本（这一条能丢东西）

`HopperBlockEntity.addItem` 会**就地 shrink** 传进去的那个堆叠。
而 `Withdrawal#returnUnplaced(kept)` 是拿**它自己保存的那个堆叠的当前数量**去算「该退多少」的：

- 直接喂原件 → `addItem` 收下后数量变 0 → `返销量 = 0 - 0 = 0` → **下游一拒收就把这 1 个蒸发了**
- 喂副本 → 原件的数量仍是 `want` → 撤销算得对

## 4. 「显示」是白送的

标本永远在格子里 ⇒ **原版漏斗界面直接就能画出这个物品**。

不需要额外渲染、不需要网络通道、不需要客户端模组 —— 这一点和入库端正好相反
（入库的物品必须真的进仓库，格子必然空，想显示就只能开 S2C 通道 + 客户端叠加渲染）。
入库端本轮**没有改动**，仍然是「不可堆叠物当不了入库分类物」。

### 反证

把 `eject` 里那句 `stack.getMaxStackSize() <= 1` 临时改成 `<= 0`（永远不成立，
不可堆叠物退回老路），重跑：

```

FAIL: [A2] 仓库正好少了 20 个（200 → 180，实际 200）
FAIL: [B1] 潜影盒（maxStack=1）能出料，15 tick 出 15 个（实际 0）
FAIL: [B2] 潜影盒仓库账对得上（100 → 85，实际 100）
FAIL: [E1-1] [E1-2] [E2-1] [E2-2] [E3-1] [E3-2]
SMOKE RESULT vw-unstackable-out/26.3 checks=22 failures=10
```

红的 10 条**全在 A / B / E 主组**，而 **C 组（圆石对照组）依然全绿**
（1260 个、每格 1 个）—— 证明断言咬的确实是「标本旁路」这一条路径，
而不是顺手把可堆叠物也改了。

## 6. 边界与已知取舍

- **速率 = 1 个/tick（20 个/秒）**。这是「一次只能搬一件」的物品在物理上的上限；
  原版漏斗是 2.5 个/秒，所以仍然是它的 8 倍。想更快就得让 `addItem` 一次填下游多个空格，
  那是另一个量级的改动。
- **比较器读数恒定**。格子永远是 1 个，所以拿比较器监控「漏斗有没有在出货」这件事
  对不可堆叠物不成立 —— 但旧版它们本来就一个都出不来，谈不上退化。
- **下游拒收时每 tick 白跑一次 `withdraw` + `returnUnplaced`**。`isFullContainer` 快筛能挡掉
  「下游真的满了」的情况，挡不掉「下游只收特定品类」的情况。开销量级与可堆叠物那条路相同。
- **9 合 1 兑换照旧生效**：`withdraw` 内部「成品有货就绝不兑换」的结构性保证没变，
  兑换产生的账由 `returnUnplaced` 反向执行，不会漏。
- **入库端仍不支持**。入库的物品必须真的进仓库，格子必然被搬空；
  要「标本 + 入库」同时成立，只有两条路：让新货绕过格子直接入库（动核心路径），
  或者服务端下发分类物清单 + 客户端叠加渲染（要客户端模组）。两条都还没做。
