# 出料漏斗「满盒分类物」刷物品事故与修复

> **一句话结论**：漏斗里放一个**装满东西的潜影盒**当分类物时，漏斗交出去的是**那只满盒本身**
> （盒内 1728 个圆石），而仓库只按「1 个空盒」或「2 壳 + 1 箱」收钱 ——
> 净效果等于 `2 潜影壳 + 1 箱子 → 1728 个圆石`，20 次/秒。
> 根因在 `VoidWarehouseData#withdraw` 第 ② 段：它把**调用方手里的样板**整份复制出去当成品。
>
> **最终口径**：盒子**怎么进就怎么出**（原样交出那一件），代价是**盒里那些实物也要从仓库里扣**；
> 盒里的东西付不出就**整笔拒绝**，绝不交一个空盒充数。

---

## 1. 玩家报的现象

> 往出库漏斗放置一个塞满盒的物品，再与出库漏斗下方放置一个箱子，会有刷物品的行为。

搭法就是文档里的标准出料口：

```
[工作台]        ← 终端压在漏斗正上方
[漏斗]          ← 口朝下，slot0 放一个装满圆石的潜影盒
[箱子]          ← 每 tick 冒出一个同样的满盒
```

潜影盒堆叠上限是 1，所以它走的是**标本 + 旁路**那条路（见
[出料漏斗支持不可堆叠物品](出料漏斗支持不可堆叠物品.md)）：格子里那 1 个永远不动，
出货由 `VoidWarehouseExtractor#ejectSpecimen` 每 tick 从仓库取 1 个、直接塞给下游。

---

## 2. 复现（真服务端，不是手工调 API）

自检 `SpecimenDupeSelfCheck`（临时工具，验证完已从仓库摘掉）搭「工作台压漏斗、下方接箱子」，
让服务端自己跑 tick，然后只数两件事：**下游每个盒子里到底装了没有**、
**仓库少了什么**。这一节把三版口径的读数都留着 —— 因为这个 bug 修错过两次，方向相反。

### 2.1 修复前：盒里的东西白送

| 组 | 跑法 | 结果 |
|---|---|---|
| Z1 | 不走漏斗，直接 `withdraw(满盒, 1)`，仓库 100 个**空盒** | 空盒 100→**99**（成本对），交出的却是**满盒（盒内 1728 件）** |
| Z3 | 同上，仓库 0 空盒、100 壳 + 50 箱 | 壳 100→**98**、箱 50→**49**（成本对），交出**满盒（1728 件）** |
| Z5 | 同上，仓库里**真的**存着 3 个满盒 | 满盒 3→2，交出满盒（1728 件）✅ 这条本来就是对的 |
| A | 漏斗 10 tick，仓库 100 空盒 | 下游 10 个盒子，**盒内共 17,280 件圆石**；空盒 100→90；仓库圆石 0 |
| B | 漏斗 5 tick，仓库 0 空盒、100 壳 + 50 箱 | 下游 5 个盒子，**盒内共 8,640 件圆石**；壳 100→90、箱 50→45 |
| C | **反证**：仓库真存 5 个满盒 | 下游 5 个满盒、盒内 8,640 件、守恒 ✅ |
| D | 仓库彻底清空 | 一件都不出 ✅ |

`checks=23 failures=6`，红的全是「盒内不该有东西」。

**注意 A / B 两组的成本一分不差**：1 个空盒换 1 个盒子、2 壳 + 1 箱换 1 个盒子。
错的不是账，是**交出去的货**。

### 2.2 第一版修法：改成交纯净空盒 —— 账平了，东西没了

| 组 | 结果 |
|---|---|
| Z1 | 空盒 100→99，交出**空盒（盒内 0 件）** |
| Z3 | 壳 100→98、箱 50→49，交出**空盒（盒内 0 件）** |
| A | 10 tick → 10 个**空盒**，空盒 100→90，仓库圆石 0，全场圆石 0 |
| B | 5 tick → 5 个**空盒**，壳 100→90、箱 50→45 |

`checks=25 failures=0` —— 自检全绿，但这是**把玩家的盒子倒进了虚空**：
满盒进漏斗、空盒出来，盒里 1728 件没了。**「没有凭空多出东西」不等于「没有丢东西」**，
第一版自检只咬了「不许白送」这一头，于是这个方向的全绿毫无意义。

### 2.3 最终口径：原样交出 + 盒里的实物照扣

同一套自检扩到 `checks=35`，每一组都同时咬**形态 / 扣了什么 / 总数守恒**三件事：

| 组 | 结果 |
|---|---|
| Z1 | 空盒 100→**99**、圆石 10000→**8272**，交出**满盒（盒内 1728 件）** |
| Z4 | 壳 100→**98**、箱 50→**49**、圆石 10000→**8272**，交出**满盒（1728 件）** |
| Z7 | 仓库真存 3 个满盒 → 满盒 3→2、**圆石一格不动**（精确匹配那条不额外收钱） |
| Z9 | `goodsTemplate`：合成 → 盒内 0 件；库存 → 盒内 1728 件 |
| Z11 | 盒里的东西**付不出** → `isEmpty=true`，空盒 100→100、圆石 1000→1000 |
| Z13 | 盒里装的是**改过名**的圆石 → 拒绝，**不许拿纯净圆石充数**（纯净 10000 不动） |
| A | 5 tick → **5 个满盒（盒内 8,640 件）**；空盒 100→**95**；圆石 10000→**1360** |
| B | 5 tick → 5 个满盒（8,640 件）；壳 100→90、箱 50→45；圆石 10000→**1360** |
| C | **反证**：仓库真存 5 个满盒、**0 圆石** → 照样出 5 个满盒、盒内 8,640 件 |
| D | 仓库清空 → 一件都不出 |
| E | 100 空盒 + **1000** 圆石（不足一盒 1728）→ **一件都不出**，空盒与圆石都不动 |

`checks=35 failures=0`。三处关键读数：

- **A / B 的圆石都从 10000 掉到 1360** = 5 × 1728，盒内成本一分不少地扣了；
- **C 组的圆石始终是 0** —— 仓库里真有满盒时走的是 ① 精确匹配，不额外收盒内的钱；
- **E 组一件都没出** —— 这是「宁可拒绝，也不交个空盒出去」的唯一判据。

### 2.4 变异实测（证明断言真的咬得住）

把第 ② 段退回「一律交纯净产物」（`if (true)`，一个 token 的改动），
`checks=35 failures=14`：

```
[Z1]  交出的必须是满盒（盒内 0 件，期望 1728）
[Z3]  盒内成本扣 1728 个圆石（实际 10000→10000）
[Z4]  合成分支：交出的必须是满盒（盒内 0 件）
[Z6]  合成分支：盒内成本也扣得一样（实际 0 个圆石）
[Z11] 盒内实物不够时必须整笔拒绝（实际 isEmpty=false）
[Z12] 且外盒材料也要退回来（实际 99 / 1000）
[Z13] 盒内是改名物品时不许拿纯净圆石充数（实际 isEmpty=false）
[Z14] 纯净圆石与空盒都不许被动（实际 10000 / 99）
[A2]  原样交出满盒（共 8640，实际 0）
[A4]  盒内成本扣圆石（10000 → 1360，实际 10000）
[B2]  原样交出满盒（盒内共 8640，实际 0）
[B5]  盒内成本扣圆石（实际 10000）
[E1]  盒里的东西付不出 → 一件都不出（实际盒数 5）
```

## 3. 根因

`VoidWarehouseData#withdraw` 分两段：

```java
// ① 成品有货：走老路，绝不兑换
Entry entry = this.find(sample);
if (entry != null && entry.amount().signum() > 0) {
    ItemStack taken = this.takeStack(sample, ask);      // ← 仓库里那一格的真实形态
    return new Withdrawal(this, sample, taken, null);
}
// ② 成品一件都没有：9 合 1 兑换 / 按已学配方扣料
VoidWarehouseExchange.Plan plan = this.planExchangeMax(sample, limit);
...
return new Withdrawal(this, sample, sample.copyWithCount(plan.amount().intValue()), plan);
//                                     ^^^^^^^^^^^^^^^^^^^^^^^^^^ 就是这里
```

第 ② 段的**前提是仓库里压根没有这种形态**——`sample` 只是调用方手里拿着的一件东西
（漏斗格子里的标本、界面上的一格图标、打印机图纸里的一格）。而合成层
（`VoidWarehouseRecipes.Recipe`）只存 `(输出物品 id, 数量, 原料)`，**数据组件一个都复现不出来**。
所以照抄 `sample` 有**两种错法，方向相反**：

| `sample` 身上挂着什么 | 整份复制的后果 |
|---|---|
| 潜影盒的 `CONTAINER`（27 格 × 64） | **1728 个物品白送**，每 tick 一次 |
| `CUSTOM_NAME`（改过名） | 名字被无限复制（没有任何材料账可以对） |
| `BEES` / `CHARGED_PROJECTILES` | 蜜蜂 / 弩里的箭 |

### 为什么只有「满盒」中招

仓库按「一格一种形态」存东西，而 `insert` 对潜影盒的处理是**拆**：

- **空盒** → 当普通物品整盒入库（占一格，记 1 个 `minecraft:shulker_box`）；
- **满盒** → 拆成「内容物 + 2 潜影壳 + 1 箱子 + 染料」，**盒子本身不存在了**。

所以 `find(满盒)` 永远不命中（`isSameItemSameComponents` 会比对 `CONTAINER`），
出料路径必然落进第 ② 段。空盒反倒没事 —— 它走 ①，`takeStack` 交还的是仓库那一格的真实形态。

### 第二个入口：`VoidWarehouseWithdraw`

「按数量取货」（右键输入数字）在走过兑换之后，仍然用 `sample` 铺散货：

```java
appendLoose(outputs, sample, loose);   // ← 兑换来的那部分也是 sample 的副本
```

危害同源但小得多：GUI 的 `sample` 来自仓库真实格子，满盒进不了仓库，
只剩「改名物品被复制」这一档。这次一并收口成 `goodsTemplate(sample, synthesized)`。

## 4. 改法

判据只有一句话：**「身上有没有挂着实物」**。

- 有 → **原样交出那一件**，代价是把盒里那些实物也从仓库里扣掉；
- 没有 → 交**纯净产物**（与 `produce()` 的「找零本来就是合成产物，不可能带附魔或改名」同一口径）。

### 4.1 `payloadOf(stack)`：哪些东西算「实物」

```java
static List<ItemStack> payloadOf(ItemStack stack) {
    List<ItemStack> merged = new ArrayList<>();
    ItemContainerContents container = stack.get(DataComponents.CONTAINER);          // 潜影盒
    if (container != null) container.nonEmptyItemCopyStream().forEach(p -> mergePayload(p, merged));
    ChargedProjectiles charged = stack.get(DataComponents.CHARGED_PROJECTILES);    // 弩里装的
    if (charged != null) charged.itemCopies().forEach(p -> mergePayload(p, merged));
    BundleContents bundle = stack.get(DataComponents.BUNDLE_CONTENTS);             // 收纳袋
    if (bundle != null) bundle.itemCopies().forEach(p -> mergePayload(p, merged));
    return merged;
}
```

- 只认 `ContainerComponent` 这一族组件 —— 只有它们装着**别的东西**；
  改名、附魔、lore 没有材料账可对，不在此列（照抄就成了「凭空复制」）。
- **同一件物品在盒里占多格时先合并成一份**：后面要按「每份需要多少」逐项验，
  分成两份各 64 个去验，仓库只有 64 个时两条都能过、实际却要 128 个 —— 那会扣出一个半截状态。
- 返回的每一份都是**拷贝**，扣账不会改到标本本身。

⚠️ 三个组件的方法名**不是五个版本都一样**，这是本轮唯一需要分叉的地方：

| 版本 | 盒子 | 弩 | 收纳袋 |
|---|---|---|---|
| 26.3 | `nonEmptyItemCopyStream()` | `itemCopies()` | `itemCopies()` |
| 26.2 / 26.1.2 / 26.1.1 | `nonEmptyItemCopyStream()` | `itemCopies()` | **`itemCopyStream()`** |
| 1.21.11 | **`nonEmptyStream()`** | **`getItems()`** | **`itemCopyStream()`** |

（26.x 有一个 `ContainerComponent` 接口，1.21.11 **没有** —— 第一版就是照接口写的，1.21.11 直接编译不过。）

### 4.2 第 ② 段：原样交出，实物照扣

```java
int amount = plan.amount().intValue();
List<ItemStack> payload = payloadOf(sample);
this.applyExchange(plan);                       // 外盒的钱（空盒 / 2 壳 + 1 箱）先扣
if (payload.isEmpty()) {
    return new Withdrawal(this, sample, new ItemStack(product, amount), plan);
}
if (!this.takePayload(payload, amount)) {       // 盒里那些实物的钱
    this.applyExchange(plan.negate());          // 付不出 → 整笔退回
    return new Withdrawal(this, sample, ItemStack.EMPTY, null);
}
return new Withdrawal(this, sample, sample.copyWithCount(amount), plan, payload);
```

`takePayload` 是「**先全验、再全扣**」：扣了圆石才发现附魔书不够，这种半截状态
与「扣了料交不出货」一样不可接受。数量按「物品 + 数据组件」精确匹配
（与 `amountExact` / `takeExact` 同一口径）—— 盒里装的是改过名的圆石时，
仓库里的纯净圆石**不算数**，宁可整笔拒绝。

**① 那条路一个字节都没动**：仓库里真有某种形态时，取出来还是那一件。

### 4.3 回滚也要把实物退回去

`Withdrawal` 多带一份 `payload`（单份，同一件物品已合并），
`returnUnplaced` 在反向执行兑换计划之后按 `back` 份退回：

```java
for (ItemStack part : this.payload) {
    long n = (long) part.getCount() * back;
    if (n > 0) this.data.restore(part.copyWithCount((int) Math.min(Integer.MAX_VALUE, n)));
}
```

少这一步，下游一拒收就**凭空少掉一整盒东西**（而外盒的材料却退了回来）。

### 4.4 `goodsTemplate(sample, synthesized)`

`VoidWarehouseWithdraw` 的包内纯函数保持不变：

```java
static ItemStack goodsTemplate(ItemStack sample, boolean synthesized) {
    return synthesized ? new ItemStack(sample.getItem()) : sample;
}
```

那条路拿不到满盒样板（网格里永远只有仓库真实条目与纯净的虚拟条目），
所以「原样交出」只需在 `withdraw` 这一处实现，两处口径不会分叉。

## 5. 行为变化（要说清楚，别让玩家以为是新 bug）

漏斗里放**满盒**当分类物，现在**原样出真盒**，但仓库要同时付两笔：

| 仓库有什么 | 每 tick |
|---|---|
| 100 个空盒 + 足够圆石 | 扣 1 个空盒 + 1728 个圆石，交 1 个满盒（1728 件） |
| 0 空盒，100 壳 + 50 箱 + 足够圆石 | 扣 2 壳 + 1 箱 + 1728 个圆石，交 1 个满盒 |
| 圆石不足一盒（< 1728） | **一件都不出**，一个字节都不扣 |
| 什么都没有 | 一件都不出 |

这与「分类物是铁块、仓库只剩铁粒 → 出铁块」是同一条既有规则（`withdraw` 内部允许 9 合 1 / 配方扣料），
区别只是：**盒里装着的那部分也要照价付**。

⚠️ **代价要提前说**：拿满盒当分类物等于持续把圆石装进盒子搬走，1728 个/tick。
玩家的圆石库存会很快见底 —— 这不是 bug，是账算对了。

## 6. 测具自己差点冤枉被测代码

第一版自检摆了**两个**场地（A 组、B 组各一套「工作台 + 漏斗 + 箱子」），
结果 A 组「每 tick 少 2 个空盒、只出 1 个盒子」—— 像是代码在重复扣费。

真相：**仓库是全存档唯一的一份**，B 组漏斗里也放着满盒标本，于是它每 tick 也在从同一个仓库取货、
往 B 组的箱子里塞。A 组的空盒少 2 = A 取 1 + B 取 1。

在主代码里插一行临时打印就看见了：

```
[DUP-DBG] eject enter pos=460, 119, 460     ← A 的漏斗
[DUP-DBG] eject enter pos=466, 119, 460     ← B 的漏斗（同一 tick 也在动）
```

**教训**：涉及全局唯一状态（这里是 `VoidWarehouse.data(server)`）的测试台，
多个场地必须**彼此隔离或者串行**。最终版改成**单场地、组间串行**：
每组开始前把漏斗与箱子都清干净，测量窗口里只有一个漏斗在动。

同一轮还有三处「读数骗了自己」的地方：

- `amountOf(Item)` 只认**纯净**条目（`find(new ItemStack(item))`），
  带 `CONTAINER` 的满盒在它眼里永远是 0。数满盒必须用 `amountExact(filledBox())`。
- **计数窗口差 1**：`VoidWarehouseExtension#onTick` 跑在漏斗 tick **之前**，
  `if (++i < N)` 只能跑到第 N−1 次出料（实测 9 个盒子、空盒 100→91）。要用 `<=`。
- **只咬「不许白送」这一头**会让 2.2 那版错误修法全绿。所以最终每一组都同时咬
  形态 / 扣了什么 / 总数守恒；反证组（C）和拒绝组（E）就是用来堵这两个方向的。

## 8. 遗留

- **`withdraw` 第 ② 段的「形态」问题仍然是从外面堵住的，没有从模型上解决**：
  合成层依旧只认 `(物品, 数量)`。真正的解法是让配方本记下产物的**完整堆叠**
  （含数据组件），但那要动 `RecipeLinesCodec` 与五份存档格式，不在这次的范围里。
- **`returnUnplaced` 的实物退还按「等份」算**：`back` 份就退 `back` 份的实物。
  这对潜影盒（堆叠上限 1 ⇒ `back` 只能是 0）是精确的；将来若有堆叠上限 > 1 的容器，
  这里需要重新想（部分退还时「哪几份的盒子里装了什么」并不唯一）。
- **漏斗每 tick 都会白跑一次 `withdraw`**（下游拒收的情况下）。这是 1.0.16 就有的量级，
  没有变化。
- **容器套容器**（非潜影盒的容器物品，如原版箱子里装着箱子）仍按「物品 + 组件」整体匹配，
  不做递归拆解 —— 那类物品在仓库里只能整件存取，不经过第 ② 段。
