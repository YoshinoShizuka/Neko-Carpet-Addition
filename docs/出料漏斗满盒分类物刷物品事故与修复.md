# 出料漏斗「满盒分类物」刷物品事故与修复

> **一句话结论**：出料漏斗里放一个**装满东西的潜影盒**当分类物，漏斗交出去的是
> **那只满盒本身**（盒内 1728 个圆石），而仓库只按「1 个空盒」或「2 壳 + 1 箱」收钱 ——
> 净效果等于 `2 潜影壳 + 1 箱子 → 1728 个圆石`，20 次/秒。
> 根因在 `VoidWarehouseData#withdraw` 第 ② 段：它把**调用方手里的样板**整份复制出去当成品。

---

## 1. 玩家报的现象

> 往出库漏斗放置一个塞满盒的物品，再与出库漏斗下方放置一个箱子，会有刷物品的行为。

搭法就是文档里的标准出料口：

```
[工作台]        ← 终端压在漏斗正上方
[漏斗]          ← 口朝下，slot0 放一个装满圆石的潜影盒
[箱子]          ← 每 tick 冒出一个同样的满盒
```

潜影盒堆叠上限是 1，所以它走的是**标本 + 旁路**那条路（见
[出料漏斗支持不可堆叠物品](出料漏斗支持不可堆叠物品.md)）：格子里那 1 个永远不动，
出货由 `VoidWarehouseExtractor#ejectSpecimen` 每 tick 从仓库取 1 个、直接塞给下游。

## 2. 复现（真服务端，不是手工调 API）

自检 `SpecimenDupeSelfCheck`（临时工具，验证完已从仓库摘掉）搭「工作台压漏斗、下方接箱子」，
让服务端自己跑 tick，然后只数一件事：**下游每个盒子里到底装了没有**。

### 修复前

| 组 | 跑法 | 结果 |
|---|---|---|
| Z1 | 不走漏斗，直接 `withdraw(满盒, 1)`，仓库 100 个**空盒** | 空盒 100→**99**（成本对），交出的却是**满盒（盒内 1728 件）** |
| Z3 | 同上，仓库 0 空盒、100 壳 + 50 箱 | 壳 100→**98**、箱 50→**49**（成本对），交出**满盒（1728 件）** |
| Z5 | 同上，仓库里**真的**存着 3 个满盒 | 满盒 3→2，交出满盒（1728 件）✅ 这条本来就是对的 |
| A | 漏斗 10 tick，仓库 100 空盒 | 下游 10 个盒子，**盒内共 17,280 件圆石**；空盒 100→90；仓库圆石 0 |
| B | 漏斗 5 tick，仓库 0 空盒、100 壳 + 50 箱 | 下游 5 个盒子，**盒内共 8,640 件圆石**；壳 100→90、箱 50→45 |

**注意 A / B 两组的成本一分不差**：1 个空盒换 1 个盒子、2 壳 + 1 箱换 1 个盒子。
错的不是账，是**交出去的货**。

## 3. 根因

`VoidWarehouseData#withdraw` 分两段：

```java
// ① 成品有货：走老路，绝不兑换
Entry entry = this.find(sample);
if (entry != null && entry.amount().signum() > 0) {
    ItemStack taken = this.takeStack(sample, ask);      // ← 仓库里那一格的真实形态
    return new Withdrawal(this, sample, taken, null);
}
// ② 成品一件都没有：9 合 1 兑换 / 按已学配方扣料
VoidWarehouseExchange.Plan plan = this.planExchangeMax(sample, limit);
...
return new Withdrawal(this, sample, sample.copyWithCount(plan.amount().intValue()), plan);
//                                     ^^^^^^^^^^^^^^^^^^^^^^^^^^ 就是这里
```

第 ② 段的注释本来写着「取不满时按有多少给多少」—— 它的**前提是仓库里压根没有这种形态**，
`sample` 只是调用方手里拿着的一件东西（漏斗格子里的标本、界面上的一格图标、打印机图纸里的一格）。
而合成层（`VoidWarehouseRecipes.Recipe`）只存 `(输出物品 id, 数量, 原料)`，
**数据组件一个都复现不出来**。拿 `sample` 去 `copyWithCount`，等于把它身上挂着的**任何**东西白送一遍：

| `sample` 身上挂着什么 | 白送的东西 |
|---|---|
| 潜影盒的 `CONTAINER`（27 格 × 64） | **1728 个物品**，每 tick 一次 |
| `CUSTOM_NAME`（改过名） | 名字被无限复制 |
| `BEES` / `CHARGED_PROJECTILES` | 蜜蜂 / 弩里的箭 |

### 为什么只有「满盒」中招

仓库按「一格一种形态」存东西，而 `insert` 对潜影盒的处理是**拆**：

- **空盒** → 当普通物品整盒入库（占一格，记 1 个 `minecraft:shulker_box`）；
- **满盒** → 拆成「内容物 + 2 潜影壳 + 1 箱子 + 染料」，**盒子本身不存在了**。

所以 `find(满盒)` 永远不命中（`isSameItemSameComponents` 会比对 `CONTAINER`），
出料路径必然落进第 ② 段。空盒反倒没事 —— 它走 ①，`takeStack` 交还的是仓库那一格的真实形态。

### 第二个入口：`VoidWarehouseWithdraw`

「按数量取货」（右键输入数字）在走过兑换之后，仍然用 `sample` 铺散货：

```java
appendLoose(outputs, sample, loose);   // ← 兑换来的那部分也是 sample 的副本
```

危害同源但小得多（GUI 的 `sample` 来自仓库真实格子，满盒进不了仓库，只剩「改名物品被复制」这一档）。
这次一并收口。

## 4. 改法

### 4.1 第 ② 段一律交纯净产物

```java
Item product = resolveItem(plan.itemId());
if (product == null) {
    // 解析不出产物就别执行计划：扣了料却交不出货，比整次拒绝更坏
    return new Withdrawal(this, sample, ItemStack.EMPTY, null);
}
this.applyExchange(plan);
return new Withdrawal(this, sample, new ItemStack(product, plan.amount().intValue()), plan);
```

`resolveItem` 本来就是「两套 id 口径的分岔收口处」，直接复用。
这与 `produce()` 的既有口径完全一致 —— 那里写着「找零本来就是合成产物，不可能带附魔或改名」。

**① 那条路一个字节都没动**：仓库里真有某种形态时，取出来还是那一件（改名、附魔、盒内物品都在）。

### 4.2 `goodsTemplate(sample, synthesized)`

`VoidWarehouseWithdraw` 新增一个包内可见的纯函数，`executeCore` 用它决定「货」的样板：

```java
static ItemStack goodsTemplate(ItemStack sample, boolean synthesized) {
    return synthesized ? new ItemStack(sample.getItem()) : sample;
}
```

- 没动过合成 → 原样保留（仓库真实的那一格）；
- 动过合成 → 纯净产物。

抽成纯函数是为了**能单测**：真正的执行路径要一个 `ServerPlayer`，而这条判断与玩家无关。

**对普通物品零影响**：纯净样板的 `new ItemStack(item)` 与 `sample` 组件完全相同，
所以 99% 的正常取货一个字节都不变 —— 只有「带数据组件 + 走了兑换」这一组合才被改。

## 5. 行为变化（要说清楚，别让玩家以为是新 bug）

漏斗里放**满盒**当分类物，现在出的是**空盒**：

| 仓库有什么 | 每 tick |
|---|---|
| 100 个空盒 | 扣 1 个空盒，交 1 个空盒 |
| 0 空盒，100 壳 + 50 箱 | 扣 2 壳 + 1 箱，交 1 个空盒 |
| 什么都没有 | 一件都不出 |

这与「分类物是铁块、仓库只剩铁粒 → 出铁块」是同一条既有规则（`withdraw` 内部允许 9 合 1 / 配方扣料）。
**想把盒内东西一起拿出来，请用「按数量取货」或盒模式** —— 那两条是**装盒**，
材料账由 `planBoxMaterials` / `consumeBoxMaterials` 单独算，本来就有完整的守恒校验。

## 6. 测具自己差点冤枉被测代码

第一版自检摆了**两个**场地（A 组、B 组各一套「工作台 + 漏斗 + 箱子」），
结果 A 组「每 tick 少 2 个空盒、只出 1 个盒子」—— 像是代码在重复扣费。

真相：**仓库是全存档唯一的一份**，B 组漏斗里也放着满盒标本，于是它每 tick 也在从同一个仓库取货、
往 B 组的箱子里塞。A 组的空盒少 2 = A 取 1 + B 取 1。

在主代码里插一行临时打印就看见了：

```
[DUP-DBG] eject enter pos=460, 119, 460     ← A 的漏斗
[DUP-DBG] eject enter pos=466, 119, 460     ← B 的漏斗（同一 tick 也在动）
```

**教训**：涉及全局唯一状态（这里是 `VoidWarehouse.data(server)`）的测试台，
多个场地必须**彼此隔离或者串行**。最终版改成**单场地、组间串行**：
每组开始前把漏斗与箱子都清干净，测量窗口里只有一个漏斗在动。

同一轮还有第二个「读数骗了自己」的地方：`amountOf(Item)` 只认**纯净**条目
（`find(new ItemStack(item))`），带 `CONTAINER` 的满盒在它眼里永远是 0。
拿它数满盒，会得出「5 个满盒全是 0」这种荒谬结论。满盒必须用 `amountExact(filledBox())` 查。

## 8. 遗留

- **`withdraw` 第 ② 段的「形态」问题只是被堵住，没有从模型上解决**：
  合成层依旧只认 `(物品, 数量)`。只要将来有人再往 `Withdrawal` 里塞「带组件的成品」，
  同一个坑就会再出现一次。真正的解法是让配方本记下产物的**完整堆叠**（含数据组件），
  但那要动 `RecipeLinesCodec` 与五份存档格式，不在这次的范围里。
- **漏斗每 tick 都会白跑一次 `withdraw`**（下游拒收的情况下）。这是 1.0.16 就有的量级，
  没有变化。
