# 出料漏斗速率对齐入库漏斗（无 8 gt 节流）

> **一句话结论**：出料漏斗（终端压漏斗正上方）原来受原版「每 8 gt 搬 1 个」的节流，
> 下游只能拿到 **2.5 个/秒**，而入库漏斗是「一 tick 搬空」。本轮把出料端改成
> **整格搬 + 收尾清冷却**，两端速率彻底对齐：**下游每个 tick 都能拿到漏斗那一刻的全部存货**
> （实测 40 tick 内下游进 **1,728** 个 vs 普通漏斗 **5** 个，差 345 倍）。

---

## 1. 问题：一端无上限、一端 2.5 个/秒

虚空仓库的漏斗有两个方向：

| 方向 | 摆法 | 谁负责 | 改前速率 |
|---|---|---|---|
| 入库 | 漏斗口**朝向**终端 | `VoidWarehouseHopper` | **一 tick 搬空**（无上限） |
| 出料 | 终端压在漏斗**正上方** | `VoidWarehouseExtractor` | 仓库→漏斗无上限，**漏斗→下游 2.5 个/秒** |

出料端的瓶颈全在最后一段。追下来是这样一条链：

```java
// HopperBlockEntity#tryMoveItems（26.3 字节码实证）
if (hopper.isOnCooldown()) return false;      // ← 冷却未清直接出队
...
flag = ejectItems(...);                        // ← 出料
flag |= supplier.getAsBoolean();               // ← 26.3 里 == suckInItems
if (flag) { hopper.setCooldown(8); ... }       // ← 搬成功就写回 8
```

而改前的 `VoidWarehouseExtractor.eject` 是照抄原版写的：**每次只搬 1 个**，搬成功
`return true` ⇒ `tryMoveItems` 收尾 `setCooldown(8)` ⇒ **下游每 8 gt 才拿到 1 个**。
仓库这端每 tick 把漏斗补满，下游却 8 gt 才被喂一次 —— 「漏斗永远满、下游永远饿着」。

## 2. 修法：两处改动，一个口径

### ① `eject` 改成整格搬（`VoidWarehouseExtractor`）

```java
// 改前：每次只搬 1 个
ItemStack leftover = HopperBlockEntity.addItem(hopper, target, stack.copyWithCount(1), side);
if (leftover.isEmpty()) { ...; return true; }

// 改后：整格搬（留下 KEEP_AS_CLASSIFIER 个当分类物，其余全部推下去）
int payload = stack.getCount() - KEEP_AS_CLASSIFIER;
ItemStack leftover = HopperBlockEntity.addItem(hopper, target, stack.copyWithCount(payload), side);
int accepted = payload - leftover.getCount();
if (accepted <= 0) continue;                    // 下游吃不下 → 换下一格
hopper.setItem(i, stack.copyWithCount(stack.getCount() - accepted));   // 只减真被收下的
```

与入库端 `VoidWarehouseHopper.drain` 的「整格搬」是同一个口径。

**关键：只减真被收下的那部分。** `addItem` 会把装不下的剩菜原样退回来，
所以必须用 `accepted = payload - leftover.getCount()` 记账，
不能用 `payload`（否则下游只收下 60 个时漏斗会少 63 个 —— 凭空丢 3 个）。

### ② 收尾清冷却时，出料漏斗也算上（`HopperBlockEntityMixin`）

```java
// 改前：只清入库
if (!VoidWarehouseHopper.isIntake(serverLevel, pos, state)) { return; }
((VoidWarehouseHopperFilter) hopper).resetCooldown();

// 改后：入库或出料都清
if (!VoidWarehouseHopper.isIntake(serverLevel, pos, state)
        && !VoidWarehouseExtractor.isExtractor(serverLevel, pos, state)) { return; }
((VoidWarehouseHopperFilter) hopper).resetCooldown();
```

只改 ① 不改 ② 的话，`eject` 搬成功依旧会触发 `setCooldown(8)`，只是「每次搬得多一点」而已
—— 速率仍是 8 gt 一次。**两处必须一起改。**

> 清冷却的位置很关键：必须放在 `pushItemsTick` 的 **TAIL**。
> 早先在 `suckInItems` 中途清零是无效的 —— 紧接着 `tryMoveItems` 收尾就把 8 写回去了。

## 3. 实测证据（`runServer` 真跑 tick）

搭一组「终端 + 出料漏斗（口朝下）+ 空箱子」，仓库灌满圆石，漏斗 5 格各 64 个分类物，
让服务端自己跑 40 tick，逐 tick 记下游箱子的增量：

```
EXT 起点：A 下游=0，漏斗 A=[64, 64, 64, 64, 64]
EXT tick0 A下游+=315   (累计 315)     ← 5 格 × 63 = 315，整格搬
EXT tick1 A下游+=315   (累计 630)
EXT tick2 A下游+=315   (累计 945)
EXT tick3 A下游+=315   (累计 1260)
EXT tick4 A下游+=315   (累计 1575)
EXT tick5 A下游+=153   (累计 1728)     ← 下游箱快满，剩多少搬多少
EXT tick6..39 A下游+=0   (累计 1728)
EXT 40 tick 共出料 1728 个圆石
```

**每一个 tick 都在进一大笔**，这就是节流被拆掉的直接证据。

### 反证组（保证断言有区分力）

| 反证 | 观察 |
|---|---|
| **普通漏斗对照**：同摆法但撤掉终端 | 40 tick 只搬 **5 个**（8 gt 节流原样保留） |
| **分类物余量**：仓库抽空 + 下游腾空 | 漏斗每格停在 **[1, 1, 1, 1, 1]** —— 整格搬不能把分类物也搬走 |
| **下游容量边界**：下游只余 60 空位 | 箱 +60 / 漏斗 −60（`in == out`，不丢不复制） |
| **普通漏斗零影响** | 规则开着，普通漏斗的冷却照常被原版写回 8 |

改前出料漏斗 40 tick 应是 5 个；改后 1728 个。**差 345 倍**，反证组同时证明
「普通漏斗一个字节都没被动」。

## 5. 兼容性 / 不变量（一条都没破）

- **每格最后 `KEEP_AS_CLASSIFIER`(1) 个永不外流** —— 仓库抽空后分类物还在，玩家不用重摆；
- **下游容器的限制全部照旧** —— 搬运仍走原版 `HopperBlockEntity.addItem`
  （熔炉只收燃料、朝向过滤、堆叠上限、容器白名单）；
- **红石语义不变** —— 被红石锁存（`ENABLED = false`）时调用方根本不进这里；
- **只影响 `voidWarehouse` 规则开时的出料漏斗** —— 普通漏斗一个字节都不碰；
- **不丢东西 / 不复制** —— 只减 `accepted`（真被收下的量），`copyWithCount` 造新实例，
  绝不把同一个 `ItemStack` 挂在两处。

## 6. 五版本同步要点

这次改的三份文件在五版本里**内容完全一致**（只有 EOL 与一处与本次无关的既有 javadoc 差异），
所以用 `.workbuddy/tools/sync_extractor_rate.py` 打补丁即可：

```bash
python .workbuddy/tools/sync_extractor_rate.py     # 26.2 / 26.1.1 / 26.1.2 / 1.21.11
```

顺手修正了 26.2 / 26.1.1 / 26.1.2 里一处**过时的 javadoc**：`isExtractor` 的注释
写「已登记的仓库终端 / `isTerminal`」，而代码五个版本一直都是 `isWorkbench`
（工作台，不要求登记）。三个版本共 9 处，改完五版本 `VoidWarehouseExtractor` 逐字节一致。

> ⚠️ `VoidWarehouseTerminals` 里 `isTerminal`（要求登记）与 `isWorkbench`（不要求登记）
> 是两个不同的方法，javadoc 与代码必须对得上。
