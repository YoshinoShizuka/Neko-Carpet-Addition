# 功能审计 / 性能定位 / 纯服务端可行性评估

> 审计日期 2026-10-20，对象 `carpet-Neko-Addition` 1.0.12（26.3 规范分支）。
> **全部结论来自真实 `runServer` 实测或字节码级核对，没有推断项。**

## 0. 三句话结论

1. **它已经是一个纯服务端模组了** —— 全仓库 `net.minecraft.client.*` 引用数 = **0**，
   12 个 mixin 全部注入服务端类，界面用的是原版 `MenuType.GENERIC_9x6`。
   服务器玩家**今天就不需要**在客户端装 `carpet_neko_addition`。
2. **性能上已经没有明显瓶颈**：1.0.12 修完兑换重算后，10 万件库存从 71.56 ms 降到 0.22 ms；
   本轮新测的「普通漏斗被拖慢多少」是 **+90 ns/漏斗/tick**（4096 个 ≈ 0.37 ms/tick）。
3. **剩下的问题集中在三处**：多观众界面的全量重发（未实测，量级估算过）、
   「按数量取货」劫持聊天框这条设计（纯服务端的唯一输入通道，副作用最大）、
   以及 README 里 `voidWarehouse` 的默认值写错（已修）。

### 1.2 九合一兑换（`voidWarehouseExchange`）

47 条边（29 条 9:1 + 17 条 4:1 + 1 条 3:1）+ 1 条多原料配方（5 海晶碎片 + 4 海晶棱镜 → 1 海晶灯），
覆盖 88 个物品。兑现方式四条：目标本身 → 下级合成 → 拆上级找零 → 单向边上游。
守恒式 `Σ(数量 × 价值) == 需要数 × 目标价值` 逐笔校验，含 150 次随机 fuzz。
**26.3 上 310 条断言 / 0 failures**（A–K + P + Q + R + S + T 组）。

### 1.3 补货与材料统计（`voidWarehouseRestock`）

| 通道 | 方向 | 谁注册 |
|---|---|---|
| `carpet_neko_addition:printer_take` | C2S | 服务端注册类型 + 收包；客户端（打印机）注册类型 |
| `carpet_neko_addition:printer_take_result` | S2C | 服务端注册；客户端幂等补位 |
| `carpet_neko_addition:printer_query` | C2S | 同上 |
| `carpet_neko_addition:printer_query_result` | S2C | 同上 |

- 取货：限流 50 ms/次（≈20 组/秒上限），一次一组，背包放不下**整笔回滚**
- 材料统计：先建 `id → 数量` 索引再查表（加法不是乘法），只读，5 秒一次也不疼
- 两端**共用同一个 FQCN 的 payload 类**（`neko.voidwarehouse.restock.PrinterTakePayload`），
  codec 结构必须逐字节等价 —— 这是两个模组之间**唯一的**耦合点

## 2. 性能定位（实测）

### 2.1 总览

| 路径 | 成本 | 数据来源 |
|---|---|---|
| 兑换重算（10 万件库存） | **0.22 ms**（1.0.11 是 71.56 ms） | `VoidWarehouseExchangePerfCheck` |
| 兑换重算（11 种 / 2 万件混合） | **1.08 ms**（1.0.11 是 5.73 ms） | 同上 |
| 入库漏斗空转 | **122 ns/漏斗/tick** | `IntakePerfBenchmark` |
| 入库漏斗整体 `pushItemsTick` | **341 ns** vs 普通漏斗 357 ns | 同上 |
| 1024 个入库漏斗空转 | **0.1~0.3 ms/tick** | 同上（真实 tick 采样） |
| **普通漏斗被本模组拖慢** | **+90 ns/漏斗/tick** | **本报告 P 组（新增）** |

### 2.2 本轮新增：普通漏斗的净开销

此前所有基准都只测「入库漏斗自己花多少」，**没有一个不带模组的对照**，
所以「跟虚空仓库毫无关系的普通漏斗，每 tick 白付多少」一直是空白。

测法：同一批 1024 个「上下左右都没有工作台」的漏斗、同一份字节码（注入两轮都在），
**只切规则开关**；交叉跑两轮取最小值，排除 JIT 顺序偏差。

```
PERF pushItemsTick(规则开，普通漏斗)                  213 ns/漏斗/tick
PERF pushItemsTick(规则关，普通漏斗)                  123 ns/漏斗/tick
PERF 净增量（规则开 − 规则关）                         90 ns/漏斗/tick
PERF isIntake                                         23 ns/漏斗
PERF isExtractor                                      20 ns/漏斗
PERF 外推   1024 个普通漏斗 → 净增   0.092 ms/tick
PERF 外推   4096 个普通漏斗 → 净增   0.370 ms/tick
PERF 外推  16384 个普通漏斗 → 净增   1.479 ms/tick
SMOKE RESULT pure_server/26.3 checks=8 failures=0
```

`90 ns ≈ 2 × (23 + 20)` —— 和「HEAD、TAIL 各判一次 `isIntake` + `isExtractor`」的结构
**完全对得上**，说明测到的就是这四行判定，没有别的隐藏开销。

**结论：不是瓶颈。** 默认关规则时是 0 ns；开着也只在漏斗极多时才可见
（1.6 万个漏斗 = 50 ms 预算的 3%）。**因此不建议为它改代码** ——
把 HEAD/TAIL 合成一次判定只能省 43 ns/漏斗，收益 0.7 ms @1.6 万漏斗，
却要动「清零冷却必须在 `tryMoveItems` 之后」这个被事故验证过的时序。

### 2.3 剩下真正的风险点（按量级排序）

**(a) 多观众界面的全量重发 · 结构性，未实测**
`syncAllViewers` 对**每一个正在看同一个仓库的玩家**都调一次 `sendAllDataToRemote()`，
即每人 54 格 × 带 lore 的全量内容包。一次点击 = `观众数 × 54` 格序列化 + 发包。
1 个人时无所谓（几十 KB）；10 个人一起看着同一个仓库高频点击时，
是「1 次点击放大 10 倍」的乘性放大，而且**每一次都发全量**（这是当初修预测错位的必付代价）。

**(b) 「按数量取货」劫持聊天框 · 设计性**
`ChatInputMixin` 拦住 `ServerGamePacketListenerImpl#handleChat`，把玩家的**下一条聊天消息**
当数量解析。对纯服务端来说这是唯一可用的输入通道，但副作用明确：
- 会吞掉玩家那条消息（不广播），玩家可能只是想说话；
- 在 `ci.cancel()` 处取消，**签名聊天链不推进**，与聊天相关模组/插件叠加时可能出现告警；
- 30 秒 TTL 内玩家说了任何非数字内容都会「取消请求」并吃掉一次提示。

**(c) README 默认值写错 · 已修**
`voidWarehouse` 的默认值在 README 里写成 `true`，代码是 `false`
（`VoidWarehouseSettings` 的类注释也明确写着「全部规则默认 false」）。已改。

**(d) 潜影盒模式的取货路径每次都要重规划**
`withdrawShulkerBox` 里对「可兑」条目会**再规划一次**（兼作新鲜度校验），
和 `exchangeOffers()` 里的规划重复。单次 ~0.2 ms 量级，点击频率下不构成问题，记录备查。

## 3. 优化方案

### P0 —— 建议做（风险低、收益明确）

**① 多观众重发：只对动作发起者发全量，其余观众改走差异包**

现在：`syncAllViewers` 对所有观众 `sendAllDataToRemote()`。
改成：
- 发起者 → `sendAllDataToRemote()`（必须，他的客户端做了错误预测）；
- 其他观众 → 只把他们的 `RemoteSlot` 标成「未知」（`force` 到哨兵值），
  让原版 `broadcastChanges` 在下一 tick 自动发**正确的差异包**。

正确性不变（他们页面上没有任何预测残留，因为他们根本没点），网络量从
`观众数 × 54 格全量` 降到 `1 × 54 全量 + (观众数−1) × 实际变化格数`。
**需要 2 个真实客户端实测**（假玩家测不出网络层），所以先落代码再验。

**② 把「按数量取货」从聊天框搬到第二个箱子界面**

用同样的原版 `GENERIC_9x6` 开一个「取货数量选择」页：9 个格子分别是
1 / 8 / 16 / 32 / 64 / 128 / 1 盒 / 自定义（点开后再进聊天） / 取消。
好处：
- 彻底去掉 `ChatInputMixin` —— 全模组**唯一**一个会碰玩家输入流的注入点；
- 不再有 30 秒 TTL、不再吞聊天、不碰签名聊天链；
- 仍然是 100% 原版界面，纯服务端可达成。

代价：多一个界面、玩家多点两下。**建议保留聊天输入作为「自定义」的兜底**，而不是唯一入口。

### P1 —— 可以不做（收益小、改动风险反而大）

**③ 漏斗 HEAD/TAIL 判定合并**：省 43 ns/漏斗/tick（见 §2.2），**不建议动**。
**④ 依赖收窄为 `fabric-networking-api-v1`**：全仓库只用到 `networking.v1` 这 30 处引用
（没有 `ClientModInitializer`、没有 `fabric-api-base` 之外的模块）。服务器上 Fabric API
本来就是标配，收益接近 0；**只有在你想出一个「无 Fabric API 也能跑」的极简版时才值得动**。

### 不做（已论证）

- **不做 `planMax` 二分**：可行性在本规则里「跳档」，不单调（9 个铜块时 1~9 可行、10~17 不可行、18 可行）。
- **不放松上界换性能**：上界偏大在功能上安全、在性能上是炸弹（1.0.12 的 TPS 事故就是这么来的）。
- **不把「可兑数量」写成常数**：被玩家连否两次。

## 4. 纯服务端改造评估

### 4.1 可行性：**已经达成，不需要改造**

这是本轮最硬的结论，证据分三层。

**第一层：静态 · 全仓库零客户端引用**

```
grep -rn "net.minecraft.client|com.mojang.blaze3d|net.fabricmc.api.client|LocalPlayer|Minecraft.getInstance"
      --include=*.java common/src modern/*/src versions/1.21.11/src
   →  0 命中（245 个源文件：common 5 + 五个版本各 48）
```

12 个 mixin 的目标类全部是服务端也存在的类，`mixins.json` 里**没有 `client` 数组**：

| mixin | 目标类 | 服务端存在 |
|---|---|---|
| `ItemUseMixin` / `BlockItemUseOnMixin` | `Item` / `BlockItem` | ✓ |
| `PlayerInteractOnMixin` | `Player` | ✓ |
| `ServerPlayerGameModeMixin` / `…UseItemMixin` | `ServerPlayerGameMode` | ✓（仅服务端） |
| `ServerGamePacketListenerImplMixin` / `ChatInputMixin` | `ServerGamePacketListenerImpl` | ✓（仅服务端） |
| `BlockPlacedByMixin` / `BlockRemovalMixin` | `Block` / `BlockBehaviour` | ✓ |
| `ContainerClassifierMixin` / `SlotMixin` | `Container` / `Slot` | ✓ |
| `HopperBlockEntityMixin` | `HopperBlockEntity` | ✓ |

`fabric.mod.json` 里 `entrypoints` 只有 `main`，**没有 `client`**。

**第二层：运行时 · 在一个「加载不到客户端类」的进程里跑通**

本轮新增的 S 组断言（真实 `runServer`，无任何客户端）：

```
  OK  S1 当前进程加载不到 net.minecraft.client.Minecraft（真·专用服务端）
       → RuntimeException: Cannot load class net.minecraft.client.Minecraft in environment type SERVER
  OK  S2 界面类型是原版 minecraft:generic_9x6
  OK  S3 界面类直接继承原版 ChestMenu
  OK  S4 标题是字面量「虚空仓库」而不是翻译键
  OK  S5 8 份展示堆叠的数据组件全是原版已注册组件（自定义 0 个）
  OK  S6 4 种库存物品全部来自原版物品注册表（未知 0 个）
SMOKE RESULT pure_server/26.3 checks=8 failures=0
```

S1 那句话本身就是证据：**Fabric 主动拒绝在 SERVER 环境里加载 `net.minecraft.client.Minecraft`**，
而本模组的全部功能（含界面创建、点击处理、漏斗、兑换）都在这个进程里跑通了。

**第三层：界面为什么纯原版能开**

| 环节 | 做法 | 纯原版客户端能否处理 |
|---|---|---|
| 开界面 | `player.openMenu(MenuProvider)` → `MenuType.GENERIC_9x6` | ✓ 原版就有的类型 |
| 渲染 | 继承 `ChestMenu`，6 行 54 格 | ✓ 原版大箱子那套代码 |
| 标题 | `Component.literal("虚空仓库")` | ✓ 不需要语言文件 |
| 格子图标 | 屏障占位 / 玻璃板 / 罗盘 / 潜影盒，全是原版物品 | ✓ |
| 数量显示 | 格子里 `count=1`，真实数量写在 `DataComponents.LORE` | ✓ 组件全是原版类型 |
| 配色 | `Style.withColor(int)` 走 RGB | ✓ |
| 输入 | 聊天栏打数字（`ServerboundChatPacket`） | ✓ |
| `/carpet` 里的规则名 | Carpet 的 `Translations.tr(...)` **服务端**解析成字符串 | ✓ 已验证：`SettingsManager` 里是 `Translations.tr` 而不是 `translatable` |

### 4.2 两个功能各自需要什么

| 功能 | 服务端 | 客户端 |
|---|---|---|
| 虚空仓库（开界面 / 存取 / 兑换 / 漏斗 / 潜影盒 / 排序） | `carpet_neko_addition` + Carpet | **什么都不需要**（原版即可） |
| 虚空仓库补货 + 投影材料统计 | 同上 | **`litematica-printer`**（打印机本体，本来就要装）。**不需要** `carpet_neko_addition` |

补货这条链路能成立，靠的是两边**各注册自己那一半**：
服务端注册 `printer_take` 的 codec + 收包端、`printer_take_result` 的 codec；
客户端（`litematica-printer` 的 `VoidWarehouseRestockNetwork#init`）注册
`printer_take` 的 codec + `printer_take_result` 的收包端，并发包前先问
`ClientPlayNetworking.canSend` —— 对面不认这条通道就干脆不发（纯原版客户端因此不会收到
解不开的包）。PR #22 合并后这套已经在打印机侧齐全了。

### 4.3 对功能的影响：**没有影响**

不需要任何改造，所以不存在功能损失。要特别说明的是：
**「客户端不需要装」和「客户端不能装」是两件事**。当前 `"environment": "*"` 属于前者。

### 4.4 实现约束（如果坚持要动 `environment`）

唯一的「纯化」动作是把五版本 `fabric.mod.json` 的 `"environment": "*"` 改成 `"server"`。
**不建议做**，理由是收益与代价严重不对称：

| | 保持 `"*"`（现状） | 改成 `"server"` |
|---|---|---|
| 服务器玩家客户端 | 不需要装 | 不需要装（**一样**） |
| 单人存档 / 局域网主机 | 可以用 | **完全不能用**（整合服务端不会加载它） |
| 玩家误装到客户端 | 无害，只是多 12 个空转注入 | 加载器直接不加载 |
| 改动量 | 0 | 5 个文件 + 五版本重构建 + 重跑自检 |

真要「既纯服务端、又保留单人可用」，正确做法是**打两个 jar**（同一份源码，
`"*"` 的给整合端、`"server"` 的给专用服务器），而不是把唯一的那个改成 `"server"`。

其它约束（无论改不改都要守住）：

1. **payload 类必须两端逐字节等价**：`neko.voidwarehouse.restock.PrinterTakePayload` /
   `PrinterTakeResultPayload` / `PrinterQueryPayload` / `PrinterQueryResultPayload`
   的 FQCN、字段顺序、`MAX_CANDIDATES`、codec 结构，改一边必须同步改另一边。
   不一致的表现是 `ClassCastException` + 掉线，不是编译错误。
2. **不能用任何自定义 `MenuType` / 自定义 `DataComponentType` / 自定义物品**。
   一旦用上，纯原版客户端就开不了界面 —— 这条是「纯服务端」的**红线**，
   任何新功能都得先在原版类型里找到表达方式。
3. **不能依赖客户端的语言文件**：所有面向玩家的文本必须是服务端算好的 `Component.literal`。
4. **`ChatInputMixin` 是全模组唯一的输入流注入**，任何「让玩家输入」的新需求
   都会想往这里加，这是最容易破坏「纯服务端 + 与其他聊天模组共存」的地方（见 §3 P0②）。
5. **Carpet 规则名不能与别的附加包重名** —— 重名会让 `SettingsManager#addCarpetRule` 直接抛异常，
   同装时服务端起不来。
