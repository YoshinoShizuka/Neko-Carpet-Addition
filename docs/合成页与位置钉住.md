# 合成页与位置钉住：两个交互问题的一次性修法

> 2026-11-17。玩家两句话：
> ①「处理合成入口受仓库已有物品限制的问题，在底部栏新增固定按钮跳转到独立合成页面」；
> ②「修复按数量排序时快速连续拾取多组物品后列表刷新过快、条目位置变化导致拿错物品的问题，
> 参考类创造排序在连续点击时更稳定的表现」。
>
> 两件事看着一个是「内容」一个是「手感」，根因其实是同一个：
> **把「我能做什么」和「我有什么」混在同一条序列里，并且让这条序列跟着库存实时重排。**

---

## 一、合成入口被库存绑住

### 现象

仓库里存着 2 块铁锭、想做 60 块。打开界面翻遍七页也找不到「铁锭」这一格 ——
那一格原本写着「可合成 65 个，用 9 个铁粒」，可它**消失了**。

### 根因

可兑条目的入选条件是两条，其中第一条是「这件物品**仓库里一件都没有**」：

```java
// 老代码（VoidWarehouseData#collectNineInOneOffers）
if (this.amountOf(item).signum() > 0) {
    continue;   // 有货就不列
}
```

它当初是为了避免**同一件东西占两格**：一格是真库存（2 个铁锭），一格是「可兑 65 个」，
玩家会以为能拿两份。这个顾虑是真的，但代价被写歪了 ——
「已经有一点」恰恰是「还想做更多」的前提。库存 2 个 → 合成入口消失 →
玩家永远无法从 2 做到 60，只能先把 2 个全部取出来、等它变回 0 再回来。

### 修法：不是删条件，是分页

删掉那条早退只解决一半：删了之后同一页里会同时出现「铁锭 2 个」和「铁锭（可兑）65 个」，
玩家照样会算错。**两件事必须在两张纸上。**

于是新增第二个界面（详见 `VoidWarehousePageContainer`）：

| 界面 | 内容源 | 一格代表 |
| --- | --- | --- |
| **仓库页** | `entries`（真实库存） | 我存了什么、有多少 |
| **合成页** | `exchangeOffers()`（9 合 1 + 配方本） | 我还能做多少 |

- 切入口固定在**底栏第 45 格**：仓库页显示「合成台」，合成页显示「箱子 · 返回仓库」。
  同一个格子两个方向，玩家只需要记一个位置。
- 仓库页从此**恒等于库存种类数**，不再有「虚拟格」，页数也不再被可兑条目撑大。
- 合成页列的是**全部做得出**的条目，与「仓库里有没有」无关；
  但**「现在库存真的能拿出至少 1 个」这条筛选保留** —— 那是噪音过滤器，不是库存限制：
  满本 746 条配方若全列出来，绝大多数当前做不动。
- 合成页的 tooltip 多一行 `仓库已有 N`：列的是「还能做多少」，不写清「现在已经有多少」，
  玩家会以为手里那些凭空没了。
- 合成页的左键是**取一组**（`offer.bulk()`，盒模式下是一盒），不是取 1 个 ——
  合成本来就是批量动作，一次一个要点几十下。右键仍是「按数量取货」。

### 顺带砍掉的东西

`unifiedOrder()` 里那段「把可兑条目按创造栏位次归并进库存序」的 O(n) 归并**整段删除**。
留一个恒等序列（`0..n-1`）不是因为需要排序，而是因为界面需要一个
**不可变、可做引用比较**的快照：仓库一变它就整体重建，`PageContainer` 拿引用一比
就知道该不该重算过滤视图，不需要自己的失效时钟。

## 二、数量排序连点拿错物品

### 现象

开「数量排序」（第 51 格罗盘），从第 1 格连点取圆石。第一下拿到圆石，
第二下还是圆石，第三下**拿到的是铁锭** —— 而格子里画的还是圆石。

### 根因：排序键是数量

```java
// displayAmountOrder()：按「这一格现在能给我多少个」从大到小
int byAmount = this.amountAtDisplay(b).compareTo(this.amountAtDisplay(a));
```

**排序键就是玩家正在改变的那个量。** 取走一组，名次立刻变；
`markChanged()` 又把 `amountOrder` 作废，下一次渲染重新排 45 格 ——
于是「第 12 格」在两帧之间换了人。点击链路是「先解析这一格是谁 → 再扣账」，
两次解析落在不同的帧上，就拿到了另一件东西。

创造序（`VoidWarehouseSort.rankOf`）之所以稳，是因为它的键**只有物品身份**，
与数量、与存取历史都无关。玩家说的「参考类创造排序更稳定」正是这个意思。

### 修法：钉住（pin）

一页的 45 个位置记的是「**这一格是谁**」，不是一个会变的下标：

- 仓库页记 `VoidWarehouseData.Entry` **对象本身**（不是下标 —— `entries` 会增删会前移）；
- 合成页记 `itemId` 字符串，数量/账单每次实时去清单里查。

顺序只在**四个时机**重建：打开界面、翻页、切排序/搜索、**停手满 `IDLE_TICKS`（40 tick = 2 秒）**。

```java
private void ensurePin() {
    boolean rebuild = !this.pinValid || this.pinPage != page || this.pinSort != sort
            || this.pinCraft != craft || this.pinFilter != this.searchFilter;
    if (!rebuild && base != this.pinBase) {
        // 底层动过，但只在手停下来之后才跟
        rebuild = VoidWarehouseData.nowTick() - this.touchTick >= IDLE_TICKS;
    }
    ...
}
```

`touchTick` 由 `VoidWarehouseMenu#clicked` 每次点击、每次翻页、每次取满调用
`noteInteraction()` 归零。连点的手速在 3~6 次/秒，2 秒的空隙足够把
「连点」和「停下来看看」分开。

**为什么是 2 秒**：太短会重新引入抖动（1 秒内点 6 下就够触发一次重排），
太长则取空之后界面上挂着一片空洞看着像坏了。40 tick 是这两个约束的中点。

### 三个必须一起做的细节

1. **取空留空洞，绝不左移**。钉住的那一格被取到 0 之后，`slotAt` 返回
   `DisplaySlot.empty()`（渲染成屏障占位符），后面那件东西不许顶上来。
   否则「点第 1 格」会变成「点第 1 格现在装的东西」—— 还是拿错。
2. **空洞上点击是空操作**，不是「取最近一件」。这条是玩家最直接的诉求：
   「确保点击目标与实际获取物品一致」。
3. **数量本身照常实时刷新**。冻的是**名次**，不是数字。
   格子里写的 `数量：580` 每次取出后立刻变，`Entry#invalidateDisplays()` 负责。

### 扣账按对象，不按下标

`data.take(下标, n)` 改成 `data.takeEntry(entry, n)`（`take` 反过来委托它）。
钉住的一页记的是 `Entry` 对象，仓库的 `entries` 是一个会增删会重排的 `List` ——
下标今天稳定不代表点击那一刻还稳定，而**对象身份只要没被扣到 0 就一直有效**。
`VoidWarehouseMenu#withdrawShulkerBox` 里那句「取出必须排在扣材料之前」的老注释
也跟着改了：现在不再有「扣材料把格子前移、下标指向别人」这回事。

## 三、页码与视图状态

- `VoidWarehouseViews.View` 新增两个字段：`screen`（0 仓库 / 1 合成）与 `craftPage`。
  两个界面页数根本不是一个量级（库存几十页 / 合成页七百多条），**共用一份页码必然越界**。
- 都是 `optionalFieldOf(..., 0)`：**旧存档读进来就是仓库页第 1 页**，不需要迁移。
- 视图仍然按玩家 UUID 持久化：关界面、重连、重启服务器回来还是离开时的样子，
  而 A 的界面永远不影响 B。

## 四、验收

新增 `VoidWarehouseInteractionCheck`（**56 条 × 5 版本 = 280 条**），
纯逻辑、不需要假玩家：界面容器是包内可见的，直接 new 一个，
然后分别问它「你画的是什么」与「点下去给我什么」。

| 组 | 判据 |
| --- | --- |
| **G1** 合成清单与库存无关 | 只有 9 铁粒时出现「铁锭」条目、不出「铁块」；**再存 64 铁锭之后「铁锭」条目仍在**（老实现会消失）、「铁块」随之出现；仓库页格数恒等于库存种类数 |
| **G2** 连点不点错 | 数量序 900/800/700/100，连点第 0 格 5 次，每次「看到的 / 点中的 / 拿到的」都是圆石；格子上的数字实时变成 580 |
| **G2 对照组** | 取 3 次之后**后台数量序的第一名已经是铁锭**，而界面第 0 格仍是圆石 —— 证明这条判据真的在拦一件会发生的事 |
| **G2b** 取空留空洞 | 一直点到见底全是圆石；取空后该格是屏障占位、`slotAt` 为空、再点什么都不给、**顶上来的铁锭一个都没被误取**；按钮格不可取出 |
| **G3** 停手才归位 | 停手 39 tick 仍是空洞；满 40 tick 铁锭才归位，此时点下去拿到的确实是铁锭 |
| **G4** 合成页 | 页数 = ⌈条目/45⌉；第 45 格是「返回仓库」；条目不能被 `removeItemNoUpdate` 这条老路取出；仓库已有 736 铁锭时合成页仍列「铁锭」；两个界面页码各记一份、互不顶掉 |
| **G5** 守恒 | 仓库合计 = 2500 − 已交出 964，一件不多一件不少 |
| **G6** 惰性算源 | `bulk()` 与点击路径 `planExchangeMax(template, 64)` 同源（63 vs 63）；不是 `min(64, 可兑 81)` 瞎猜的 64；问两次同一个数 |

### 自检本身踩的两个坑

1. **`exchangeOffers()` 是按 tick 合并的**：同一 tick 里改了库存再读，拿到的还是旧名单。
   自检里每次改库存都要 `noteServerTick(nowTick() + 1)` 才算「下一个 tick 的第一次读」。
   （这条以前也踩过，是产品行为而不是测试取巧：界面只在 tick 边界渲染。）
2. **`IDLE_TICKS` 的空闲计时基准会差 1 tick**：每个 stage 占一个 tick，
   上一阶段最后一次 `noteInteraction()` 落在**前**一个 tick，直接拿 `nowTick()` 当基准，
   「停手 39 tick」其实已经算 40 —— 第一版就红在这一条。
   判据红了先分「被测代码错」还是「判据错」，这次是后者。

## 五、这一改的代价，以及一处必要的优化

合成页把 44 条「仓库里已有的物品」放回了清单（84 条 vs 原来 40 条），
重算一次可兑表的成本立刻翻上去：

| 场景（20 人同 tick 各自入库 + 刷新） | 改前 | 只做功能改动 | 加上惰性算源 |
| --- | --- | --- | --- |
| `SystemTest` 的 MP 峰值 | 2.11 ms | **6.38 ms（断言红）** | **1.93 ms** |

6.38 ms 那条是**真的红了**（阈值 5 ms，占 50ms tick 的 12.8%）。拆开量：

```
PROBE 9 合 1 only      offers=84（其中仓库已有 44）  重算 6.760 ms
PROBE 9 合 1 + 配方本  offers=84                    重算 6.069 ms
```

配方本一条都没多（这些物品本来就在 9 合 1 表里）—— 也就是说代价全在
`collectNineInOneOffers`，而且**不是条目变多这一件事**：84 条 vs 40 条只有 2.1 倍，
时间却是 3.2 倍。把 `bulk` / `boxed` 那两次规划临时换成 `min(...)` 再量：

```
（实验版）9 合 1 only  重算 2.589 ms
```

**2.6 ms vs 6.8 ms**：原来**七成的重算成本是「建表时顺手算掉的两个一次取货量」**。
这两个数每个都要一次 `planMax`（还不能用 `min(堆叠上限, 可兑)` 代替 ——
9 个铁块兑一组铁锭，瞎猜给 64，真值 63），于是一张 84 条的表就是 168 次多余规划。

而绝大多数重算**根本不画合成页**：仓库页一格可兑条目都没有，补货提示与取货路径也不读它们。

所以改成**惰性**：`ExchangeOffer#bulk()` / `boxed()` 第一次被问到时才算，算完缓存。
算源捕获的是建表那一刻的 `table` / `stock` 快照，与建表时算的结果**逐位相同**，
只是把成本从「每次重算 × 全部条目」挪到「真正画出来的那 45 格 + 真正点的那一格」。

- `ExchangeOffer` 因此从 `record` 变成 `final class`（多两个可变缓存字段）；
  另留一个**七参构造**收下「已经算好的两个数」，配方扣料那条路与各套自检、`LedgerListSelfCheck`
  的调用点一个字都不用改。
- 自检加了一组 **G6** 专门盯这件事：`bulk()` 必须与点击路径的 `planExchangeMax(template, 64)`
  同源（实测 **63 vs 63**）、必须是 63 而不是 `min(64, 可兑 81)` 给的 64、问两次拿同一个数（缓存生效）。

> 教训写在这里：**「新增内容」和「新增成本」要分开量**。
> 如果只看到「条目 40 → 84」就去调阈值，永远发现不了那 168 次规划本来就不该在那个时候发生。

## 六、没做的事 / 已知边界

- **合成页仍只列「现在做得出」的条目**。玩家说的问题是「仓库已有 → 条目消失」，
  不是「冷门配方也要列出来」；把 746 条全列出来是噪音。
- **合成页不新增「合成确认」**。左键一组、右键按数量，与仓库页同一套手势，
  只是口径从 1 个变成 1 组。
- **筛选（搜索）对两个界面都生效**，且是「先排序再过滤」：
  过滤只决定「谁留下来」，不改变留下来的那些的相对次序。
- **空洞最长存在 2 秒**。取空之后立刻停手的话，界面上会有一个屏障占位格挂到
  空闲计时满 40 tick 为止 —— 这是刻意的取舍（宁可短暂空着，也不在玩家手还没抬起来时换人）。
