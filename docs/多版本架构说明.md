# 多版本适配架构说明

本仓库已从「单模块、只支持 26.3」重构为「**单仓库 + 版本化目录**」的多版本结构，
目标是方便适配 Minecraft 1.15.2 ~ 26.3 的热门版本。

## 目录结构

```
carpet-Neko-Addition/
├── settings.gradle          # 根聚合：include 各版本子工程
├── build.gradle             # 根聚合（defaultTasks 'build'）
├── gradle.properties        # 根级共享属性（jvmargs 等）
├── gradle/ + gradlew        # 共享的 Gradle wrapper（9.7.0，服务 26.x）
│
├── common/                  # ★ 跨版本共享的纯逻辑（不引用 MC 版本类型）
│   └── src/main/java/neko/
│       ├── NekoConstants.java          # mod id / 分类名等常量
│       ├── automending/
│       │   ├── AutoMendingSettings.java  # 规则声明（只依赖 carpet-api 的 @Rule）
│       │   └── TranslationLoader.java    # Gson 读 lang json
│       └── voidwarehouse/
│           └── VoidWarehouseSettings.java
│
├── modern/                  # ★ 26.x 及以后（Minecraft 不再混淆）
│   ├── 26.3/                # 完整实现 + mixin + 资源（基准版本）
│   ├── 26.2/                # 与 26.3 仅差 1 处 API（Prediction）
│   ├── 26.1.1/              # 与 26.3 差 2 处 API（Prediction + ColorCollection）
│   └── 26.1.2/              # 同 26.1.1
│
└── versions/                # ★ 1.21.x 及更早（仍是混淆版本）
    └── 1.21.11/             # ✅ 已落地（Mojang 映射，与 26.3 只差 8 处 API）
        ├── build.gradle     # net.fabricmc.fabric-loom-remap + Mojang 官方映射，Java 21
        ├── gradle.properties
        └── src/main/        # 版本专用实现 + mixin + 资源
```

## 两条互斥的工具链

| | `modern/`（26.x） | `versions/`（≤1.21.x） |
|---|---|---|
| 混淆 | 不混淆（Mojang 官方命名） | 混淆，需映射 |
| Loom 插件 | `net.fabricmc.fabric-loom` | `net.fabricmc.fabric-loom-remap` |
| 映射 | 无需 mappings | **Mojang 官方映射**（见下方说明） |
| Java | 25 | 21 |
| 依赖 | `implementation` | `modImplementation`（要 remap） |

> **1.21.11 为什么用 Mojang 映射而不是 Yarn**：26.x 的源码本来就是 Mojang 命名，
> 换成 Yarn 会凭空多出几百处机械改名（`ScreenHandler`、`ResourceLocation`…），
> 而用 `loom.officialMojangMappings()` 之后类名可以直接沿用，真正要改的只剩 8 处
> **确实变了**的 API。代价是映射可读性略差，收益是差异面从「整体重写」降到「8 处」。

> 这两条工具链**互斥**，无法塞进同一个 Gradle 项目，所以只能拆成两个子目录。
> 这也是「版本化源码集」在「混淆 vs 不混淆」这道分界线上的最终形态。

## 新增一个版本的步骤

1. 复制 `versions/<最接近的版本>/`（或 `modern/<最接近的版本>/`）为一个新目录；
2. 改它的 `gradle.properties`（minecraft / yarn / carpet / loader 版本）；
3. 在根 `settings.gradle` 里 `include` 一行；
4. 把 `src/main/java` 里引用 MC 类型的类，按目标版本的 API 改写（**用 javap 核对真实签名，绝不猜**）；
5. `./gradlew :<module>:build` 构建，跑一次 `runServer` 自检验证。

`common/` 层的代码无需任何改动——它只放不引用 MC 类型的纯逻辑。

## 已落地的 26.x 版本（不混淆，与 26.3 差异极小）

26.x 起 Minecraft 停止混淆，所以 26.1.1 ~ 26.3 之间只是「小版本 API 演化」，差异点很集中。
下表是逐个用 `javap` 核对后确认的实际差异（均已编译 + runServer 自检通过）：

| 版本 | Carpet 坐标（Modrinth id） | 与 26.3 的源码差异 |
|---|---|---|
| 26.2 | `maven.modrinth:carpet:bGrLxJ8v` | 仅 1 处：`placeItemBackInInventory` 无 `Prediction` 参数 |
| 26.1.1 | `maven.modrinth:carpet:ygtmLbO3`（26.1/26.1.1/26.1.2 共用一个包） | 2 处：① 无 `Prediction`；② 染色物品用独立字段 `Items.RED_STAINED_GLASS_PANE`（`ColorCollection` 是 26.2 才引入的） |
| 26.1.2 | 同上 | 同上（与 26.1.1 完全一致） |

### 26.x 内部 API 差异速查

| 能力 | 26.3 / 26.2 | 26.1.1 / 26.1.2 |
|---|---|---|
| 物品放回背包 | `placeItemBackInInventory(ItemStack, boolean, Prediction)` | `placeItemBackInInventory(ItemStack[, boolean])`，无 `Prediction` |
| 染色物品 | `Items.STAINED_GLASS_PANE.red()`（`ColorCollection`） | `Items.RED_STAINED_GLASS_PANE`（独立字段，16 色各一个） |
| 存档读写 | `ValueInput` / `ValueOutput` | 同左 |
| 聊天包 | `ServerboundChatPacket` / `handleChat` | 同左 |
| 漏斗 | `HopperBlockEntity#pushItemsTick` 等 | 同左（已核对，签名一致） |
| 混凝土粉末 / 染色玻璃 | `Items.CONCRETE_POWDER.pick(color)` / `Items.STAINED_GLASS.pick(color)` | `Items.WHITE_CONCRETE_POWDER` / `Items.WHITE_STAINED_GLASS`… 16 个独立字段 |
| 熔炼配方构造 | `SmeltingRecipe(Recipe$CommonInfo, CookingBookInfo, Ingredient, ItemStackTemplate, float, int)` | **同左**（已 javap 核对） |
| `Recipe#assemble` | `assemble(T)` | **同左** |
| `AbstractFurnaceMenu#canSmelt` | `canSmelt(ItemStack)` | **同左** |

> `ColorCollection` 把 16 种染色物品收进一个 `ColorCollection<Item>` 字段（`Items.STAINED_GLASS_PANE.red()`），
> 这是 26.2 引入的；26.1.x 仍是传统的 `Items.RED_STAINED_GLASS_PANE` 等 16 个独立字段。
> `Prediction` 枚举（`net.minecraft.util.Prediction`）是 26.3 新增的，26.2 及更早没有。
>
> 第三条规则（混凝土粉末 → 染色玻璃）只用到**一个** 26.2/26.1.x 的差异：取色方式。
> 三个 Mixin 的注入点（`RecipeManager#getRecipeFor(RecipeType, RecipeInput, Level)`、
> `RecipeManager#byKey`、`AbstractFurnaceMenu#canSmelt`）在 26.x 四个版本里**签名完全一致**，
> 字符串描述符可以直接复制。

## 已落地的 1.21.11（混淆，与 26.3 差 12 处 API）

用 Mojang 官方映射之后，26.3 的源码整包复制过来只有 **11 个编译错误**，归拢成 7 个 API
差异；另外 **1 处只在运行时才暴露**的 mixin 描述符差异。全部经 `javap` 核对后修正，
最终 `compileJava` 通过、`runServer` 自检 **checks=55 failures=0**。
（其中 8 处属于虚空仓库，另 4 处属于后加的第三条规则，见下。）

### 编译期就能发现的 7 处

| # | 26.3 | 1.21.11 | 涉及文件 |
|---|---|---|---|
| 1 | `net.minecraft.util.Prediction` | **没有这个类** | `VoidWarehouseMenu` |
| 2 | `placeItemBackInInventory(stack, Prediction.SERVER_ONLY)` | `placeItemBackInInventory(stack)`（另有 `(ItemStack, boolean)` 重载） | `VoidWarehouseMenu` |
| 3 | `net.minecraft.world.inventory.ContainerInput` | **没有这个类**，用 `ClickType` | `VoidWarehouseMenu` |
| 4 | `ContainerInput.QUICK_CRAFT` / `.PICKUP` | `ClickType.QUICK_CRAFT` / `.PICKUP`（枚举成员名完全一致） | `VoidWarehouseMenu` |
| 5 | `SavedDataType(Identifier, ...)` | `SavedDataType(String, Supplier, Codec, DataFixTypes)` —— **id 是 `String`** | `Data` / `Views` / `Terminals` |
| 6 | `Items.STAINED_GLASS_PANE.red()`（`ColorCollection`） | `Items.RED_STAINED_GLASS_PANE`（无 `ColorCollection`） | `VoidWarehouseNav` |
| 7 | `ItemContainerContents#nonEmptyItemCopyStream()` | `nonEmptyItemsCopy()` | `VoidWarehouseShulker` |

> `Clicked(int, int, ClickType, Player)`、`computeIfAbsent(SavedDataType<T>)`、
> `ValueInput#getBooleanOr` / `ValueOutput#putBoolean` 三项签名与 26.3 **完全一致**，无需改。

### 只有运行时才暴露的 1 处（mixin 描述符）

| # | 26.3 | 1.21.11 |
|---|---|---|
| 8 | `Player#interactOn(Entity, InteractionHand, Vec3)` | `Player#interactOn(Entity, InteractionHand)` —— **没有 `Vec3` 参数** |

> 这一处是 mixin 字符串描述符，**编译器不检查**，错了只会在服务端启动阶段混入失败。
> 因为 mixins.json 里 `defaultRequire = 1`，注入点失配会直接把服务器带崩 ——
> 所以每个版本落地都必须 `javap` 逐个核对注入点，且必须真的跑一次 `runServer`。

### 第三条规则（混凝土粉末 → 染色玻璃）的 4 处

| # | 26.3 | 1.21.11 |
|---|---|---|
| 9 | `Items.CONCRETE_POWDER.pick(color)`（`ColorCollection`） | `Items.WHITE_CONCRETE_POWDER` … 16 个独立字段（无 `ColorCollection`） |
| 10 | `new SmeltingRecipe(new Recipe.CommonInfo(true), new CookingBookInfo(BLOCKS, ""), Ingredient, new ItemStackTemplate(glass), f, i)` | `new SmeltingRecipe(String group, CookingBookCategory, Ingredient, ItemStack, float, int)` —— **`Recipe$CommonInfo` 与 `ItemStackTemplate` 这两个类都不存在** |
| 11 | `Recipe#assemble(T)` | `assemble(T, HolderLookup$Provider)` —— **两参** |
| 12 | `mixins.json` 的 `compatibilityLevel` | 26.x 是 `JAVA_25`，1.21.11 必须 **`JAVA_21`** |

> 第 9 / 10 处的取色与构造差异各自**只影响一个方法**，`powderOf` / `glassOf` 这两个 helper
> 把差异挡在了一个文件里；第 11 处只影响临时自检（1.21.11 的副本多带一个 `level` 参数）。
> 三个 Mixin 的注入点在这一版**签名与 26.3 完全一致**，字符串描述符直接沿用、不需要改。

### 其余 8 个注入点（已 javap 核对，与 26.3 完全一致）

`BlockItem#useOn`、`Block#setPlacedBy`、`BlockBehaviour#affectNeighborsAfterRemoval`、
`ServerGamePacketListenerImpl#handleChat`、`HopperBlockEntity#pushItemsTick` /
`saveAdditional` / `loadAdditional` / `suckInItems` / `canPlaceItemInContainer` / `ejectItems`、
`Item#use`、`ServerPlayerGameMode#useItemOn`、`Slot#setByPlayer`。

### 1.21.11 自检覆盖（55 项 + 25 项 + 14 项）

数据层（任意精度累加 / 取货 / 清空）、展示文本（盒组换算、**无「≈」**、每行都有颜色、
盒模式不出现普通模式话术、不可堆叠物品不出现「组」）、潜影盒（打包守恒 / 盒容量）、
终端登记（增 / 删 / 幂等 / 注销）、**漏斗搬空 + 不指向终端的漏斗保持原版**、
假玩家开菜单点击取货。

第三条规则另有一套 `ConcretePowderToGlassSelfCheck`（25 项，五版本各跑一次全绿）：
Mixin 是否真挂上、规则关时的**反证组**、16 色逐个 `assemble()` 校验颜色、
真熔炉逐 tick 烧 + 经验发放链路、Shift 点击走真实 `quickMoveStack`。

**出料速率对齐**另有一套 `ExtractorRateSelfCheck`（14 项，五版本各跑一次全绿）：
出料漏斗逐 tick 搬空（40 tick 出 1728 个）、普通漏斗 8 gt 节流的**反证组**、
分类物余量停在 1、下游只余 60 空位时 `in == out` 不丢不复制。

> ⚠️ 1.21.11 偶尔首跑会因「测量窗口打开时 `pull` 还没补满漏斗」出现 1~2 项波动，
> **连跑两次确认**即可（本轮的两次复跑都是 `checks=14 failures=0`）。

## 各版本间需要重点核对的 API（差异清单）

| 能力 | 26.3 | 更早的 1.21.x / 1.20.x |
|---|---|---|
| 资源位置 | `Identifier` | 1.21.11 用 Mojang 映射后仍是 `Identifier` |
| 容器菜单 | `AbstractContainerMenu` | 同上（Mojang 映射） |
| 存档数据 | `SavedDataType(Identifier, ...)` | 1.21.11：`SavedDataType(String, ...)` |
| 数据组件 | `DataComponents` / `ItemLore` | 1.21.x 有；**1.20.4 之前是 NBT** |
| 实体右键汇聚点 | `interactOn(Entity, Hand, Vec3)` | 1.21.11：`interactOn(Entity, Hand)` |
| 创造栏 | `CreativeModeTabs`（服务端可用） | 需核实服务端是否可用 |

> 1.15.2 ~ 1.20.4 是最大的鸿沟：尚无数据组件体系（纯 NBT）、无 `SavedData` 新 API，
> 且若改用 Yarn 映射则类名与 Mojang 命名差异极大，落地时需要单独评估。
> 建议仍然优先用 Mojang 官方映射，只在 Mojang 没有覆盖的老版本（1.16.5 及更早）改用 Yarn。
