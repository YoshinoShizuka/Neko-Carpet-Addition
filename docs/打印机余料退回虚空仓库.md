# 打印机余料退回虚空仓库

> 对应代码：`neko/voidwarehouse/restock/PrinterReturn*`（服务端）、
> `integration/voidwarehouse/VoidWarehouseReturnController`（客户端）。
> 通道名：`carpet_neko_addition:printer_return` / `...:printer_return_result`。

## 一、要解决的问题

补货（`printer_take`）每次给的是**一整组**。一个 30 种以上材料的投影打到后面，
背包里会堆满「只用掉三五个、剩下五六十」的整组材料：

- 36 格被零头占满之后再要新材料，服务端只能回 `INVENTORY_FULL`；
- 打印机把它当成普通缺料，于是**卡死在那一种方块上**，而不是继续打别的。

原版打印机的对策是「储存管理 → 有序存放」（`storeOrderly`）：把从背包潜影盒里
取出来的东西**原样退回那个潜影盒**。仓库来的材料没有潜影盒可退，
这条通道就是给那个思路补上「退到仓库」的另一半。

## 二、为什么不复用 `storeOrderly`

`OrderedStorageController` 的每一步都是「打开源潜影盒 → 点格子 → 关掉」，
全程要占容器租约与主手租约；本通道是「发一个包，服务端自己塞回仓库」，
不占任何租约、不开任何界面。两条路时序上完全不相容，硬塞进同一个类只会互相踩状态。

因此实现是**独立组件**。`storeOrderly` 的代码一行未改，原来开它的玩家行为不变，
两个开关可以同时开：潜影盒来的退潜影盒，仓库来的退仓库。

## 三、协议

| 通道 | 方向 | 内容 |
| --- | --- | --- |
| `printer_return` | C2S | `nonce` + **槽位号清单**（0–35，最多 36 个） |
| `printer_return_result` | S2C | `nonce` + 状态码 + 实收数量 |

状态码：`OK=0`、`RULE_OFF=1`、`NOTHING=2`、`THROTTLED=3`、`BAD_REQUEST=4`、`NONE=-1`（本地态）。

### 为什么发槽位号，不发物品

这是整个特性的安全红线：**服务端只认自己那份背包里的真实内容**。

客户端说「第 12 格不要了」，服务端自己去读第 12 格，读到什么就把什么入库 ——
客户端从头到尾没有机会描述物品内容，因此**不可能凭这条包凭空造出物品**。
反过来，如果改成「客户端把 ItemStack 发过来、服务端照单入库」，一个改过的客户端
就能无限刷物资，仓库直接变成刷物品机。

这条包的能力上界 = 「把玩家自己背包里的东西挪进玩家自己仓库」，
与漏斗、拆潜影盒完全同一量级，没有新增任何凭空产出。

### 为什么潜影盒一律跳过

`VoidWarehouseData#insert` 遇到非空潜影盒是**拆开**入库（变成壳 + 箱子 + 内容物）。
那是漏斗与手动存盒该有的行为，但放在自动返还路径上就是灾难：
只要发一个盒子所在槽位，玩家的盒子就被不可逆地拆了。
所以这里与取货的拒绝清单保持一致，整类挡掉 —— 何况仓库本来也不会把盒子发给打印机。

### 为什么整条路径不需要回滚

`insert` 只有「收下」和「拒收」两种结果，且**收下时把传入堆叠清零、拒收时原样不动**。
所以每一格只能按「先入库，拿到 `true` 才清空槽位」的顺序走，
不存在「仓库收到了、背包也还留着」的中间态，也就不需要像取货那样准备撤销路径。

## 四、客户端什么时候发

| 触发 | 行为 | 说明 |
| --- | --- | --- |
| 打印收工（工作总开关关掉） | 账上有多少退多少 | 玩家最需要的场景：干完活把余料还回去 |
| 打印中，空槽 ≤ 4 | 退到空槽回到 8 | 不这么做，下一次补货必然撞 `INVENTORY_FULL` |
| 打印中，空槽 ≤ 1 | 只退 1 格，不管是否还在用 | 紧急档：先腾出格子，缺了再去要，总比卡死强 |

**账怎么记**：只记「仓库给了什么、给了多少」（按物品累计**件数**），不记槽位 ——
打印机会把材料在快捷栏与背包之间搬来搬去（`InventorySwitchGuard`），记槽位第二天就对不上。
每 tick 用「背包里现在还有多少」给账做一次**上限收敛**：

- 打印机消耗掉的部分会自动掉出账外；
- 玩家自己攒的同种物品**绝不会**被算成「仓库给的」而多退；
- 到货时记的是**净增量**（不是请求里写的 64），背包只塞得下一部分时不会记多。

**为什么要跳过「正在要的物品」**：打印机对同一种材料是「用完 → 再要一组」的循环。
在它正等这一种时把剩下的半组退回去，就变成「退 → 要 → 退」死循环，每轮白烧两次包。
常规档跳过当前请求里的候选物品，只有紧急档不管。

## 五、开关与失败姿态

- 服务端：复用 `voidWarehouse` + `voidWarehouseRestock` 两条规则（这是同一套「打印机自动化」能力的两个方向），**没有新增 Carpet 规则**。
- 客户端：`voidWarehouseReturn`，默认开。
- 对面没装带这条通道的服务端模组 → `canSend` 为假，客户端清账并完全不发包；返还整个特性静默失效，补货照旧。
- 服务端回 `RULE_OFF` → 客户端退避 200 tick，不每 tick 撞门。
- 回执超时 60 tick → 放弃这一笔，账交给下一 tick 的收敛（服务端若真收下了，背包同步一到件数自然掉下去）。
- 服务端限流 50ms / 次（与取货**分开记账**：返还紧跟取货发生，共用一张表会互相拖后腿）。

## 六、验收要点

1. **不能凭空产出**：只发槽位号，服务端读自己那份背包；潜影盒拒绝。
2. **不动玩家的东西**：`reconcile` 只往下夹，账不会因为玩家囤货而变多。
3. **不改原功能**：`storeOrderly` 一行未改；关掉 `voidWarehouseReturn` 时行为与之前完全一致。
4. **多人环境能编码**：客户端也注册 C2S 类型（撞名异常吞掉）。
   取货那条（`printer_take`）历史上只在单人验过，多人环境里客户端进程的
   `SERVERBOUND_PLAY` 表是独立的一份，没登记的类型会被 `DiscardedPayload`
   静默丢掉、而 `canSend` 仍说「支持」—— 2026-10-31 已按同样写法补上（`VoidWarehouseRestockNetwork#registerC2S()`）。
   注册顺序是安全的：carpet 在 `onInitialize`（主入口）注册，打印机的
   `onInitializeClient` 一定晚于它，所以单人时客户端那份必然走「撞名吞掉」分支。
