# 投影材料列表显示虚空仓库库存（`printer_query` 只读通道）

> **一句话结论**：Litematica 材料列表里的「已有数量」从「玩家背包 + 末影箱」变成了
> **「玩家背包 + 末影箱 + 虚空仓库」**，并且「缺失数量」同步改成
> **「需求 − 已有」的净值**（仓库里已备齐就显示 0，只备了一部分就显示还差的那部分）——
> 于是「缺料清单」只剩下**仓库里也拿不到**的材料，玩家一眼就能看出还需要去外面收集什么。
> 实现方式是新增一条**只读**的 `carpet_neko_addition:printer_query` 通道，
> 客户端每 5 秒问一次「我这份清单上这些物品，仓库里各有多少」，
> 把答案分别合成进 `MaterialListEntry#getCountAvailable()` 与 `#getCountMissing()` 的返回值。

涉及两个仓库：

| 仓库 | 角色 | 本轮改动 |
|---|---|---|
| `carpet-Neko-Addition`（服务端） | 提供数据（仓库在它的 `SavedData` 里） | 新增 `neko.voidwarehouse.restock.PrinterQuery{Payload,ResultPayload,Service,Network}` + `AutoMendingMod` 注册 |
| `litematica-printer`（客户端） | 展示数据 | 镜像载荷 + 网络层 + 快照缓存 + `MixinMaterialListEntry`（已有 + 缺失两个注入）+ 三个「口径变更的消费者」修正 Mixin + 配置项 + 文案 |

---

## 1. 需求与三条已确认的口径

原始诉求（玩家原话）：

> 添加投影的材料列表的已有数量的来源替换为虚空仓库，让玩家能直观看到投影材料于虚空仓库的库存情况，
> 能更方便的收集虚空仓库里没有的物品。

三条口径是**问过玩家**才定下来的，不是我们自己拍的（第三条是第二轮玩家报出矛盾现象后补的）：

| 口径 | 选择 | 理由 |
|---|---|---|
| 数量怎么算 | **仓库 + 背包合计** | 只看仓库：玩家刚取出来拿在手里的材料会显示成 0；只看背包：完全反映不出仓库有多少。两个都要算才回答得了「我还差多少」 |
| 覆盖范围 | **GUI 与信息 HUD 都覆盖** | 两个入口读的是同一个字段（见 §3），本来就该一致；只改一个反而会导致「界面说不缺、HUD 说缺」 |
| 「缺失」怎么算 | **需求 − 已有，夹到 0**（第二轮补的口径） | 只看「已有」会出现「已有 500、还缺 300」这种自相矛盾的行（原版 `countMissing` 是个 `final` 字段，压根不随已有量走，见 §4）。完整推导在 §4 |

## 2. 协议：一条只读通道，与取货通道彻底分开

| 通道 | 方向 | 用途 | 有没有副作用 | 服务端限流 |
|---|---|---|---|---|
| `carpet_neko_addition:printer_take` | C2S/S2C | 缺料时领一组材料 | **有**（扣仓库、改背包） | 50 ms |
| `carpet_neko_addition:printer_query` | C2S | 「这些物品仓库里各有多少」 | 无（**纯只读**） | 200 ms |
| `carpet_neko_addition:printer_query_result` | S2C | 上一条的答案 | — | — |

**为什么必须分成两条**：两者节奏差一个数量级。材料列表每 5 秒刷新一次，取货只在真的缺料时发一次。
把它们塞进同一条通道，要么查询被取货的强限流卡住，要么取货的限流形同虚设。

### 请求 `PrinterQueryPayload`

```java
public record PrinterQueryPayload(int nonce, List<String> itemIds) implements CustomPacketPayload
// MAX_IDS = 1024；IDS_CODEC = ByteBufCodecs.list(1024).apply(STRING_UTF8)
```

**为什么由客户端列出物品，而不是服务端把整个仓库发过来**：仓库可能有上千种物品，
而一个投影的材料清单通常只有几十到几百种。只问自己要显示的那些，包小了、服务端也省了。
代价是「换投影就要重问一次」—— 那正好，因为它本来就要重新拉一次数。

### 应答 `PrinterQueryResultPayload`

```java
public record PrinterQueryResultPayload(int nonce, int status, List<String> itemIds, List<Long> amounts)
// status: OK=0 / RULE_OFF=1 / BAD_REQUEST=2 / THROTTLED=3
```

四个设计决定，都不是随手写的：

- **回显 id**（明明客户端刚发过）：让这个包自解释 —— `itemIds[i]` 对应的就是 `amounts[i]`，
  不依赖「客户端还记得第 i 个问的是谁」。更实际的理由：客户端只保留**最新一次**请求的上下文，
  回显让「拿旧响应去套新请求」这种错配根本无从发生。
- **只回有货的**：「查不到 = 0」与「回一条 0」对使用方完全等价，
  而「投影要的、仓库里没有」的那部分往往占大多数，省下来的都是净赚。
- **数量是 `long` 不是 `int`**：仓库的账是 `BigInteger`，可以到天文数字。
  `VAR_LONG` 编码对一位数只占 1 字节。**超过 `Long.MAX_VALUE` 时饱和**，不环绕
  —— 环绕会得到负数，界面上就是「仓库里有 -9223372036854775808 个」。
- **同一个 id 被问两次只回一次**：客户端与响应靠**下标**对应，多回一条会让两条数组错位。
  服务端用 `HashSet` 去重而不是 `List#contains` —— 清单上限 1024，线性查会退化成平方级。

### 服务端 `PrinterQueryService`：先建索引再回答

```java
Map<String, BigInteger> stock = index(server);   // 一遍上千次
for (String raw : itemIds) { ... stock.get(id) } // 再几百次
```

请求里可能有几百个 id、仓库里可能有上千格。逐个扫就是「几百 × 上千」的**乘积**；
先摊成一张 `id → 数量` 的表，总和就变成了**加法**。这点在小仓库上无所谓，
但它决定了这个功能能不能被「开着材料列表边建造边刷」—— 那是每 5 秒一次的常态。

> ⚠️ 索引里同一个 id 是 **`merge` 累加**而不是覆盖：仓库的格子是「物品 + 数据组件」，
> 同一个物品的两种形态（比如附魔不同的书）会各占一格，而材料列表是**按物品**统计的。
> 不累加就成了「仓库里明明有 200 本附魔书却显示 0」。

`canonicalId()` 用 `Identifier.tryParse` + `BuiltInRegistries.ITEM.getOptional`：
客户端传什么都可能，一个畸形字符串不该在服务端主线程上抛异常。

主开关与取货同一个口径：`voidWarehouse && voidWarehouseRestock` 任一为 false 就回
`RULE_OFF`。查询虽然只读，但「仓库界面都被强制关了却还能看到库存」同样会让人困惑。

## 3. Litematica 侧的数据流，以及注入点为什么选 `getCountAvailable`

26.3 源码（`litematica-fabric-26.3-0.29.0-sources.jar`）实证：

```java
// MaterialListUtils#updateAvailableCounts —— 每处刷新都先调它，把 countAvailable 整个覆盖重算
for (MaterialListEntry entry : list) {
    entry.setCountAvailable(playerInvItems.getInt(type) + enderItems.getInt(type));
}
```

调用它的只有两处，之后界面才读 `entry.getCountAvailable()`：

| 消费点 | 时机 | 用这个数做什么 |
|---|---|---|
| `GuiMaterialList` 构造器（第 58 行） | 打开界面时一次 | — |
| `MaterialListHudRenderer#render`（第 87 行） | **每 2000 ms** | — |
| `GuiMaterialList` 第 490 行 | 每帧 | 列表里显示「已有」 |
| `MaterialListBase#recreateFilteredList` 第 88 行 | 列表重建时 | `available < missing` 决定这条算不算「缺」 |
| `MaterialListHudRenderer` 第 129/195 行 | 每 2 秒 | `missing - available` = HUD 上那个红字 |
| `MaterialListSorter` | 排序时 | `SortCriteria.COUNT_AVAILABLE` |
| `MaterialListJsonExporter` | 导出时 | 导出的「Available」列 |

结论：**`countAvailable` 是一个可变的 int 字段，而每处刷新都会把它整个覆盖掉**，
所以「往背包计数里加」这种写法活不过 2 秒。有两条路可走：

| 方案 | 问题 |
|---|---|
| ① 注入 `setCountAvailable`，在赋值**之后**累加 | 要求「每次覆盖之后必须恰好补一次」。GUI 与 HUD 是两条独立路径，一旦哪条漏调或重调，账面就飘 |
| ② **注入 `getCountAvailable()` 的返回值** ✅ | 纯读、**幂等**（不改字段，读几百次也只补同样多的数）；且签名在四个版本里逐字节一致 |

选 ②。另一个现实理由：两个 Litematica 版本里
`MaterialListUtils.getInventoryItemCounts` 有重载差异（1.21.11 只收 `Container`，
26.x 多一个布尔），而 `MaterialListEntry#getCountAvailable()` 四版本一致
（`javap` 逐个核对过：1.21.11-0.26.16 / 26.1-0.27.14 / 26.2-0.28.8 / 26.3-0.29.0）。

### `MixinMaterialListEntry`

```java
@Mixin(value = MaterialListEntry.class, remap = false)          // 模组类 → remap = false
public abstract class MixinMaterialListEntry {
    @Inject(method = "getCountAvailable", at = @At("RETURN"), cancellable = true, remap = false)
    private void litematicaPrinter$addVoidWarehouseStock(CallbackInfoReturnable<Integer> cir) {
        String id = VoidWarehouseMaterialIds.idOf(((MaterialListEntry) (Object) this).getStack());
        if (id == null) return;
        long amount = VoidWarehouseMaterialCache.get().amountOf(id);
        if (amount <= 0L) return;                                // 绝大多数条目走这条，提前返回
        cir.setReturnValue(VoidWarehouseMaterialCounts.merge(cir.getReturnValueI(), amount));
    }

    @Inject(method = "getCountMissing", at = @At("RETURN"), cancellable = true, remap = false)
    private void litematicaPrinter$subtractAvailableStock(CallbackInfoReturnable<Integer> cir) {
        if (VoidWarehouseMaterialCache.get().isReady() == false) return;   // 功能没生效 → 原版行为
        MaterialListEntry self = (MaterialListEntry) (Object) this;
        cir.setReturnValue(VoidWarehouseMaterialCounts.netGap(cir.getReturnValueI(), self.getCountAvailable()));
    }
}
```

**这里刻意不判断配置开关**：开关、通道可用性、服务端规则状态全部由**发包那一侧**
（`VoidWarehouseMaterialNetwork`）统一裁决 —— 只要功能不可用（没进世界 / 配置关掉 /
对面不支持 / 服务端回 `RULE_OFF`）它就调 `VoidWarehouseMaterialCache#clear()`。
于是这里只需要认一个信号：`isReady()`「有没有拿到过快照」。

- 对 `getCountAvailable` 而言，空快照读出来是 0，`merge` 原样返回背包数量；
- 对 `getCountMissing` 而言，直接原样返回。

两者都**与没装这个功能完全相同**。反过来说，如果把开关判断抄一份到这里，
就等于把「什么时候该生效」写成了两份实现，而这两个方法每帧会被调几百次。

**注意第二个注入刻意复用 `getCountAvailable()`**（而不是自己再查一遍仓库）：
那个数已经是「背包 + 仓库」了，各查一次等于同一件事有两个实现，迟早会分叉
（比如一边忘了算末影箱）。

**⚠️ 只补「已有」是不够的** —— 原版那两个数各算各的，缺失量是个 `final` 字段。
这一点的完整推导与三个必须跟着改的消费者见下一节。

## 4. 「缺失数量」也要跟着改（净缺口口径）

### 症状

第一版只补了「已有数量」，玩家随即报了一个自相矛盾的现象：

> 当玩家打开原理图材料列表时，如果虚空仓库已有该原理图所组成的物品，
> 那么在已有数量大于缺失数量前提下，缺失数量的显示应已显示为 0；
> 如果虚空仓库内的物品小于该物品，那么应显示该物品需要的总数减去库存的部分。

### 原版事实（26.3 源码 + 字节码实证）

| 事实 | 位置 |
|---|---|
| `countMissing` 是 **`final` 字段，没有 setter** | `MaterialListEntry:11` |
| `updateAvailableCounts` **只覆盖 `countAvailable`，从不重算 `countMissing`** | `MaterialListUtils:248-255` |
| 开「原理图」列表时 `missing` 传的是 `countsTotal.clone()` ⇒ **恒等于总数** | `MaterialListUtils:127` |
| 行里的三列 = `Total ｜ Missing ｜ Available`，颜色判据是 `available >= missing` | `WidgetMaterialListEntry:242-257` |
| 信息 HUD 自己在做减法：`count = getCountMissing() - getCountAvailable()` | `MaterialListHudRenderer:129/195` |

结论：「已有 500、还缺 300」是**必然**的 —— 缺失量根本不由已有量决定。

### 口径

```
缺失 = max(0, 需求 − 已有)        已有 = 背包 + 末影箱 + 虚空仓库
```

于是：仓库备齐 → 缺失 0；只备了一部分 → 缺失正好是还差的那部分。
夹到 0 是必须的，否则已备齐时会出现负数。

### ⚠️ 改了「缺失」，就必须同步修所有拿这两个数比较的地方

原版所有判断都建立在一条不变式上：

```
missing = 需求、available = 持有   ⟹   available >= missing 就是「材料够不够」
```

把 `missing` 换成**净缺口**之后这条不变式当场失效 —— 比较变成
「持有 ≥ 需求 − 持有」，也就是「持有是否已达需求的一半」。
逐一看四个消费点：

| 消费点 | 原式 | 处理 |
|---|---|---|
| GUI 行的「缺失」列 / 列宽 / 悬浮提示 | 直接显示 `getCountMissing()` | **不用改** —— 显示净值正是本功能要的 |
| 顶部进度行（`MaterialListBase#updateCounts` 求和） | Σ `getCountMissing()` | **不用改** —— 求和自然变成「还没收齐的部分」 |
| 排序 `COUNT_MISSING` / CSV·JSON 导出 | 直接读 `getCountMissing()` | **不用改** —— 按净值排、按净值导出，正是玩家要的 |
| 「只显示缺料」过滤器 `MaterialListBase#recreateFilteredList` | `available < missing` | **要改** |
| 信息 HUD `MaterialListHudRenderer#render` | `missing - available` | **要改**（不改会显示成很大的负数） |
| 行的绿/金/红配色 `WidgetMaterialListEntry#render` | `countAvailable >= countMissing` | **要改**（不改会在收集到六成时显示成金色 = 撒谎） |

三个修正都是**同一个动作**：把参与比较的「持有」侧当成 `0`，
让判据退回它真正想表达的那句话 —— **「净缺口是不是 0」**。

| 新 Mixin | 目标 | 写法 |
|---|---|---|
| `MixinMaterialListBase` | `recreateFilteredList` | `@Redirect` 唯一的 `getCountAvailable()` 调用点 → 生效时返回 `0` |
| `MixinMaterialListHudRenderer` | `render` | 同上（一个处理者覆盖两处同表达式调用） |
| `MixinWidgetMaterialListEntry` | `render` | `@Redirect` `GuiBase.TXT_GREEN` / `TXT_GOLD` 两次 **GETSTATIC**，把「够不够」的判据改由净缺口决定 |

过滤器那一处的等价性值得单独说一句：原式「持有 < 需求」⟺ 净值「`max(0, 需求 − 持有) > 0`」，
所以功能没生效时返回真实持有量、生效时返回 0，**两种写法得出同一个「留还是不留」**，
`hideAvailable` 那个把已备齐条目移出预过滤列表的 `else` 分支也一致。

### 关于「不写 ordinal」

`MixinMaterialListHudRenderer` 与 `MixinWidgetMaterialListEntry` 的注入点在各版本里
分别出现 **2 次**（HUD 两处同表达式）与 **各 1 次**（两个颜色常量）。
这里刻意**不写 `ordinal`**：`@Redirect` 本来就会注入到所有匹配到的调用点上，
而靠序号定位等于把「上游在这段代码里恰好有几处这样的调用」变成一个隐含依赖，
将来上游多画一行就会指错地方。Mixin 的 `RedirectInjector` 里也没有
「多匹配即失败」的判定（只在两个处理者抢同一个注入点时才报 conflict），
所以单处理者 + 不加序号是这里最稳的形态。

### 两个可见的副作用（都是口径变更的必然结果，已确认）

1. **配色从三级塌成两级**：原版「绿 = 世界不缺了／金 = 世界还缺但我材料够／红 = 材料不够」，
   在新口径下「世界不缺了」和「世界还缺但材料齐了」都等价于「缺失 = 0」，
   而对外可见的数只有这一个 —— 没有依据再把它们分开染色。
   功能生效时：**绿 = 已备齐（缺失 0），红 = 还差一些**。
2. **顶部进度行的 `Missing%` 变成「还没收齐的比例」**，`Done%` 相应变大；
   对「原理图列表」（缺失原本恒等于总数）来说，这反而从「永远 100%」变成了一个有用的数。

> 功能没生效时（没进世界 / 配置关 / 对面不支持 / 规则没开），**上面每一条都保持原版行为** ——
> 三个修正处理者都会返回原值。这是刻意的：不装服务端模组的玩家不应该感到任何差别。

## 5. 客户端：三道闸 + 一份快照

```
客户端 tick ──► VoidWarehouseMaterialNetwork#tick()
                 ├─ 没进世界 / 配置关 / 对面不支持  → reset()（顺手清快照）
                 ├─ 还在等回执（超时 40 tick 放行）
                 ├─ 服务端说 RULE_OFF → 退避 1200 tick（60 s）
                 ├─ 距上次请求 < 100 tick（5 s）
                 ├─ 没人看（材料列表界面 / 材料信息 HUD 都没开）
                 └─ 拼清单（LinkedHashSet 去重，截到 MAX_IDS=1024）→ send()
                                          │
   服务端回执 ──► receive() ── nonce 比对 ──► VoidWarehouseMaterialCache#apply()（整体替换）
                                          │
   渲染路径（每帧几百次）──► cache.amountOf(id)   ← 只有一次哈希查找，不发包
```

**为什么必须把「发包」和「读值」拆开**：材料列表的「已有数量」是被**渲染路径**读的。
渲染路径里发网络包是禁忌 —— 帧率会被网络抖动绑架，而且同一次渲染里可能被调用几百次。

**为什么要判断「玩家真的在看」**：问一次要来回一趟包，而材料列表在玩家不建造时完全没人看。
只在界面开着或信息 HUD 开着时才发。这也顺带让「打开界面的那一刻」必然触发一次刷新 ——
看到的永远是刚问来的数。

**为什么缓存是整体替换而不是累加**：每次回执带的都是**当前那次询问的完整答案**。
换了投影之后，上一份快照里的键就不该再留着，否则「上一个投影要的方块」会继续显示过时数量。
整体替换还顺带解决了「怎么知道一个物品是 0」—— 不在表里就是 0。

**为什么所有方法都 `synchronized`**：回执从客户端网络线程写进来，读它的是渲染线程
（每帧几百次）。写是一次性的、读是高频的，所以用最朴素的一把锁：
写的时候没人读得到半张表，读的时候也绝不会看到一个「size 已经变了、桶数组还没换」的中间态
（那正是 `HashMap` 并发读最典型的翻车方式）。

### C2S 这次要自己注册

取货通道那边客户端没注册 C2S，靠的是「单人存档里服务端模组同进程、已经帮它注册过了」。
那在**专用服务器**上不成立（两个进程，客户端那张表是空的），而 Fabric 的 API 文档写得很清楚：
「`ClientPlayNetworking` 发出的包必须**两端**都注册」。所以这次两个方向都注册，
并且都写成**幂等形式**（单人环境下服务端已经注册过，`register` 的实现是
`containsKey → throw IllegalArgumentException`，**严格去重、不是 putIfAbsent**）。

`registerGlobalReceiver` 无论如何都要自己挂 —— 它按通道名挂 handler，与「谁注册了类型」是两件事。

## 6. 跨端 id 契约：最容易静默失效的一环

客户端拼清单时写成什么，服务端就用什么去查仓库。两边差一个字符（命名空间写法、
`toString()` 与 `getPath()` 混用、大小写），表现就是「材料列表上库存永远是 0」——
**不报错、不崩服，只是没效果**。

服务端的处理链是：

```
Identifier.tryParse(raw) → BuiltInRegistries.ITEM.getOptional(id)
                        → BuiltInRegistries.ITEM.getKey(item).toString()
```

也就是「再解析一次、再序列化一次」。所以客户端必须写 `Identifier.toString()`（`namespace:path`），
**不能写 `getPath()`**（会把 `minecraft:` 丢掉）。

为此单独抽了一个 `VoidWarehouseMaterialIds`，就为了它能被普通 JUnit 直接咬住：

- `idOfItem(Item)` 是真正干活的那个重载。**测试不能走 `new ItemStack(item)`** ——
  `Bootstrap.bootStrap()` 并不绑定数据组件注册表，单测里构造 `ItemStack` 会抛
  `NullPointerException: Components not bound yet`。
- `VoidWarehouseMaterialIdsTest#idSurvivesTheServerSideRoundTrip` 遍历**整个物品注册表**
  （约 1500 项），对每一项跑一遍服务端那条链，断言 `parsed.toString()` 原样回到同一个键。
- 配一条**反证**：原版物品全在 `minecraft` 命名空间下，光看它们区分不出
  `toString()` 与 `getPath()`（后者会被 `tryParse` 补回 `minecraft:`）。
  换一个命名空间两种写法立刻分道扬镳 —— 这才证明上面那条断言真的在检查命名空间，
  而不是「随便什么字符串都能过」。

Mixin 侧与发包侧**共用同一个转换**（`VoidWarehouseMaterialNetwork#collectItemIds` 调的是同一个
`idOf`）—— 「物品 → 仓库的键」只允许有一份实现，两边各写一份迟早会分叉。

## 7. 两个版本分叉，以及 mixins.json 的版本化

### ① 当前界面：`Minecraft.screen` ↔ `Gui.screen()`

26.2 起，`Minecraft` 上的 `screen` 公开字段被搬进了 `Gui`（变成一个 `screen()` 取值方法）；
26.1 与 1.21.11 还是原来的字段。`javap` 实证：

| 版本 | 取法 |
|---|---|
| 1.21.11 / 26.1 | `Minecraft.screen`（public 字段） |
| 26.2 / 26.3 | `Minecraft.gui.screen()`（`Minecraft` 上已经没有这个字段了） |

判据用仓库里已有的 `MC > 260100`（先例见 `MixinContainerScreenGuard`）：

```java
//#if MC > 260100
//$$ return client.gui.screen() instanceof GuiMaterialList;
//#else
return client.screen instanceof GuiMaterialList;
//#endif
```

> 📌 预处理器的 `//$$` 是**「本版本不生效」的标记**，不是一个固定的「低版本分支」。
> 主工程（26.1）里写 `//$$` 的行 = 在 26.1 里注释掉；生成 26.3 时预处理器会把 `//$$`
> **挪到另一条分支上**。留个心眼：生成物里的注释位置和源文件不一样是正常的。

### ② payload 注册 API

26.x（fabric-api 6.3.x）= `PayloadTypeRegistry.serverboundPlay()` / `clientboundPlay()`；
1.21.11 = `playC2S()` / `playS2C()`。这是两端目前唯一一处网络 API 差异。

### ③ mixins.json 的版本化靠 Gradle 占位符，**不能靠预处理器**

`src/main/resources/*.json` 不参与预处理（`grep -rn "//#if" src/main/resources/` 无命中）。
所以「只在某些版本挂这个 Mixin」这件事必须走 `ModProjectExtension.kt` 的 `placeholderProps`：

```kotlin
"void_warehouse_litematica_mixins" to if (mcVersionInt >= 12111) {
    "\"printer.litematica.MixinMaterialListEntry\",\n" +
            "    \"printer.litematica.MixinMaterialListBase\",\n" +
            "    \"printer.litematica.MixinMaterialListHudRenderer\",\n" +
            "    \"printer.litematica.MixinWidgetMaterialListEntry\","
} else { "" },
```

```json
  "mixins": [
    "printer.litematica.MixinInventoryUtils",
    "printer.litematica.MixinMaterialListEntry",
    "printer.litematica.MixinMaterialListBase",
    "printer.litematica.MixinMaterialListHudRenderer",
    "printer.litematica.MixinWidgetMaterialListEntry",
    "printer.litematica.MixinChunkRendererSchematicVbo",
```

**为什么必须成对**：老版本上这四个类整个被 `//#if MC >= 12111` 剔掉、
根本不产生 class 文件，而 mixins.json 里写死的类名会让 Mixin 在启动阶段直接报错。
占位符留空（而不是留个逗号）才能让 `mixins[]` 数组保持合法 JSON。

> 顺带一句：这四个类都是**客户端专用**的目标（GUI/HUD），放进 `mixins` 而不是 `client` 数组
> 是安全的 —— 本模组的 `fabric.mod.json` 是 `"environment": "client"`，
> Mixin 配置只会在客户端加载，与已有的 `MixinMaterialListEntry` / `MixinChunkRendererSchematicVbo` 一致。

## 9. 配置项

```java
// Configs.Special（//#if MC >= 12111 内，默认 true）
public static final ConfigBoolean VOID_WAREHOUSE_MATERIAL_LIST = bool("voidWarehouseMaterialList")
        .defaultValue(true)
        .build();
```

与 `voidWarehouseRestock` 的关系：**共享同一条服务端能力**（同两条 Carpet 规则、
同一套通道可用性判断），但**互不依赖** —— 关掉补货仍然可以只看库存，反之亦然。

文案（`zh_cn.json` / `en_us.json`）：`litematica-printer.config.voidWarehouseMaterialList` +
`.desc`，与 `voidWarehouseRestock` 的措辞保持一致（都写明「需要服务端装 carpet-Neko-Addition
并开启两条规则」）。
