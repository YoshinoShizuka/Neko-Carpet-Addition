# 搜索通道（search）五版本测试报告

> 结论先行：**五版本均如预期正常运行**。

## 一、测了什么、怎么测

搜索功能横跨两端，各测各的可测部分：

| 层 | 可无头验证的部分 | 手段 | 结果 |
|---|---|---|---|
| 客户端逻辑 | `SearchIndex` 匹配（中文/拼音/首字母/注册名） | JUnit（`common`，五版本共享） | **11/11 通过** |
| 客户端协议 | 三个 payload 与 carpet 侧逐字节镜像 | 字节码对拍（md5 比对） | **3 个全 SAME** |
| 服务端逻辑 | `SearchService.catalog` / `resolveFilter` / `applySearchFilter` | 自检（真服务端，五版本各跑） | **19/19 × 5 通过** |

客户端「搜索框出现 / 焦点 / 输入法」是 GUI 行为，无头服务端测不到，仍归入实机测试件（前一轮已交付）。

## 二、客户端：SearchIndex 单测（11 条）

`./gradlew :common:test --rerun-tasks` → `tests=11 failures=0 errors=0 skipped=0`。

覆盖：空查询=清除过滤、中文名（铁锭）、全拼连写/带空格（tieding / TieDing）、首字母（td / zs / gzt）、注册名（iron / oak_log）、错误首字母顺序不命中（dt）、拼音串词典事实（铁锭=td、铁块=tk、全拼=tieding）、未知 id 静默跳过、空显示名跳过、trim+大小写不敏感、namespace 剥离（`minecraft:iron_ingot`→`iron_ingot`）。

> 注：`SearchIndex` 是「纯 Java」（不 import 任何 Minecraft 类型），放在 `common/`，五版本编译时引用同一份源码 —— 跑一次即代表五版本。

## 四、服务端：搜索通道自检（19 断言 × 5 版本）

新增 `.workbuddy/tools/SearchChannelSelfCheck.java.template`（五版本通用，全程只用 `Items.*` 与字符串 id，不碰版本差异类型），逐版本 `runServer` 真机跑：

| 版本 | 断言数 | 失败 | 结论 |
|---|---|---|---|
| 26.3 | 19 | 0 | ✅ |
| 26.2 | 19 | 0 | ✅ |
| 26.1.2 | 19 | 0 | ✅ |
| 26.1.1 | 19 | 0 | ✅ |
| 1.21.11 | 19 | 0 | ✅ |

三段断言：

- **A 目录（catalog）**：插圆石/泥土/沙子三种后，目录含三者、`LinkedHashSet` 去重无重复、条目数恰为 3。
- **B 过滤解析（resolveFilter）**：有效 id → 对应 Item；无效 id → 空集合；混入 `null`/脏 id 不崩、其余照收；空列表/null → 空集合（= 清除过滤的协议语义）。
- **C 过滤生效（applySearchFilter）**：过滤成「只有圆石」后，第 0 格是圆石、第 1 格退成占位符（barrier）、数据层 `displayCount` 仍 3（过滤只改界面不改数据）、清空过滤后前 3 格恢复。

关键诊断行（26.3）：
```
[diag] 过滤后 slot0=minecraft:cobblestone slot1=minecraft:barrier slot2=minecraft:barrier displayCount=3
```
即过滤后只剩圆石 1 个真实格，其余退成 barrier 占位符 —— 与「创造模式物品栏搜索」同构的行为，正确。

## 五、过程中的一个插曲（非产品 bug）

首轮 26.3 自检报 `C3` 失败，diag 显示 `slot1=minecraft:barrier`。排查确认是**测试断言写错**：我把「空格子的 barrier 占位图标」当成了「有内容」来判 `isEmpty()`。修正为断言 `is(Items.BARRIER)` 后五版本全绿 —— 产品行为自始至终正确，错的是我的断言口径。
