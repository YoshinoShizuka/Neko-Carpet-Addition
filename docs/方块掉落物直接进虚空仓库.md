# 方块掉落物直接进虚空仓库（`voidWarehouseBlockDrops`）

## 一句话

玩家**挖掉**的方块，掉落物不进世界，直接进全服共享的虚空仓库。

## 从哪来、为什么改了名

规则思路来自 [Carpet-Org-Addition](https://github.com/fcsailboat/Carpet-Org-Addition) 的 `blockDropsDirectlyEnterInventory`（掉落物直接进物品栏）。这里把终点从「玩家背包」换成「虚空仓库」——掉落物不再占用背包格子、不再受背包满不满影响，全服一份、跨维度共享。

规则名**故意**不叫 `blockDropsDirectlyEnterInventory`：Carpet 的 `SettingsManager#addCarpetRule` 遇重名会直接 `throw`，沿用原名等于「两个附加包同装 = 服务端起不来」。这是本项目的既定规矩，`concretePowderToGlass` 当初也是这么避开的。

## 为什么不去改 `Block#popResource` / `playerDestroy`

每种方块掉落逻辑都不一样：`playerDestroy`、`getDrops`、`spawnAfterBreak`、方块实体里的东西、草方块掉种子、蜜块粘方块、精准采集换物品、时运加数量……想靠「按方块类型逐个挂」覆盖全部方块是不可能维护的。

而这些东西最终都收敛到**同一个出口**：

```java
Block.popResource(level, pos, stack)
  → level.addFreshEntity(new ItemEntity(level, x, y, z, stack))
```

所以只拦 `ServerLevel#addFreshEntity` 一处，就覆盖了**所有**方块掉落物，而且掉落表、附魔、时运、精准采集全部照原版算完再交给我们，一个数值都不用自己维护。

```java
@Mixin(ServerLevel.class)
public abstract class ServerLevelAddEntityMixin {
    @Inject(method = "addFreshEntity(Lnet/minecraft/world/entity/Entity;)Z",
            at = @At("HEAD"), cancellable = true)
    private void carpetAutomending$blockDropsIntoWarehouse(Entity entity, CallbackInfoReturnable<Boolean> cir) {
        if (!(entity instanceof ItemEntity item)) {
            return;
        }
        if (VoidWarehouseBlockDrops.collect((ServerLevel) (Object) this, item.getItem())) {
            cir.setReturnValue(false);   // 已经进仓库了，这一份不能再进世界
        }
    }
}
```

### 为什么是 `HEAD` 而不是「先进世界再删」

HEAD 时实体还没进世界，拦下来等于「它从来没存在过」—— 没有拾取判定要撤销、没有声音粒子要收拾、没有客户端先行预测要纠正。挂 `RETURN` 再 `discard()` 就会留下「玩家听见叮、看见实体、然后消失」的空窗。

## 怎么认定「这是玩家挖的」

`addFreshEntity` 不知道物品是谁弄出来的 —— 挖方块、爆炸、怪物死亡、玩家丢弃、发射器吐出，走的都是这一个方法。所以要在**挖掘调用**外面圈一个上下文：

```java
@Mixin(ServerPlayerGameMode.class)
public abstract class ServerPlayerGameModeDestroyMixin {
    @Shadow @Final protected ServerPlayer player;

    @Inject(method = "destroyBlock(Lnet/minecraft/core/BlockPos;)Z", at = @At("HEAD"))
    private void carpetAutomending$beginBlockDrops(...) { VoidWarehouseBlockDrops.begin(this.player); }

    @Inject(method = "destroyBlock(Lnet/minecraft/core/BlockPos;)Z", at = @At("RETURN"))
    private void carpetAutomending$endBlockDrops(...) { VoidWarehouseBlockDrops.end(); }
}
```

选 `destroyBlock` 而不是 `handleBlockBreakAction` / `Player#destroyBlock`，是因为它正好是「方块真的被破坏 → 掉落真的被 spawn」这一段，粒度最贴。HEAD 不带 `cancellable`：这条规则只改「掉落物去哪」，挖掘耗时、工具耐久、统计、成就一条都不动。

### 上下文为什么是一个 `static`

- 服务端的方块破坏全在主线程跑，不存在并发；
- `destroyBlock` 不会自我嵌套（破坏一个方块只跑一次，掉落物也不是方块破坏的入口）；
- 不用 `ThreadLocal` / `ScopedValue`：后者在 Java 21 上还是预览特性，而 1.21.11 那一轨正好锁在 Java 21。

### 🔴 泄漏兜底：tick 戳

HEAD / RETURN 这一对不是 `try/finally`。万一 `destroyBlock` 抛了异常（模组冲突、方块自己炸了），RETURN 那份不会执行，上下文就永久挂在了 static 上 —— 后果是**之后世界里每一个物品实体都被吸进仓库**，属于最不能接受的一类故障。

所以 `begin` 同时记下当次的服务端 tick，`collect` 只认**同一 tick**：

```java
if (server.getTickCount() != breakerTick) {
    breaker = null;   // 上一次挖方块漏下来的上下文，当它不存在
    return false;
}
```

「挖方块产生掉落」本来就全在这一次调用里同步完成，同 tick 这个条件不会漏收；而漏掉 `end` 的最坏影响被压到「本次 tick 的剩余部分」。等价于 WrapMethod 的 try/finally，代价是零依赖（MixinExtras 五个版本的类路径各不相同，不引）。

## 入库口径：和漏斗完全一致

直接调 `VoidWarehouseData#insert` —— 就是漏斗入库、潜影盒拆盒走的同一条路：

| 物品 | 结果 |
| --- | --- |
| 泥土 / 圆石 / 一般的方块 | `+1` 进对应那一格 |
| 空潜影盒 | **整盒**占一格（按方块本体存，不拆成潜影壳 + 箱子） |
| 带数据组件的（受损工具、附魔、改名、药水） | 按物品 + 数据组件归并，与漏斗同口径 |
| 时运掉多个 / 精准采集换物品 | 原版算出几个就收几个 |

## 🔴 绝不吞物品：任何一条不成立就照原样掉地上

`collect` 返回 `false` 的每一条路径，都意味着原版流程继续、物品该掉哪就掉哪：

- 主开关 `voidWarehouse` 没开（没有仓库，这条规则整体视为关闭）
- 上下文不在本次 tick（泄漏兜底）
- 空堆叠
- `VoidWarehouse.data(server)` 拿不到（存档闸门）
- `insert` 返回 `false`
- 任何 `RuntimeException`

开与不开的差别只有「掉落物去哪」，不存在「东西凭空没了」这一种结果。

## 收完说一声（但只说一句）

入库成功后会在聊天栏给挖方块的人发一条提示，样式与补货提示（`PrinterRestockNetwork#notifyTaken`）同一套：统一 `[虚空仓库] ` 前缀、浅灰正文、亮绿数字（`VoidWarehouseText#info`）。

```
[虚空仓库] 挖到 3 个 泥土，已直接入库
[虚空仓库] 挖到 1 个 泥土、12 个 圆石，已直接入库
[虚空仓库] 挖到 5 种共 15 个，已直接入库
[虚空仓库] 挖到 1 个 潜影盒（已拆开），已直接入库
```

### 为什么必须汇总

挖掘是高频动作：一棵树、一面墙、一条矿道，一秒能刨掉十来个方块。每入库一次发一条 = 聊天栏被自家消息淹没，玩家自己的聊天全被顶掉（补货提示当初也是为此只报「真的拿到东西」那一种）。所以：

| 机制 | 值 | 为什么 |
| --- | --- | --- |
| 先攒后发 | 每个玩家一份 `Pending` | 入库只记账，发送由 `tick` 统一做 |
| 合并同类 | 物品 + 数据组件相同就累加 | 「2 个 + 3 个泥土」= 一条里的「5 个」 |
| 发送窗口 | `MESSAGE_INTERVAL_MS = 1000`（每玩家每秒最多一条） | 连挖时把这一秒的都并进同一条；**不是延迟通知**，是合并报数 |
| 一条最多列 | `MAX_LISTED_KINDS = 4` 种 | 再多折成「N 种共 M 个」，免得一条比聊天框还长 |

窗口内的记录不会丢：`tick` 只把「到点」的那份取走发送，没到点的继续累加，下一条一并报数。

### 🔴 记账失败绝不影响「已入库」

`collect` 里 `record` 被 `try/catch` 单独包住：

```java
if (!data.insert(stack)) {
    return false;
}
try {
    record(player, dropped);          // 提示只是附带的
} catch (RuntimeException ignored) {
    // 记账出错绝不能反过来把「已经入库」判成没入库
}
return true;
```

反过来写（让异常冒到外层 `catch` 里）就是**复制 bug**：物品已经进了仓库，`collect` 却返回 `false`，mixin 于是放行那个物品实体 —— 世界里还多一份。

另外 `insert` 会把 `stack` 就地清零，所以提示要用的那份得在 `insert` **之前** `copy()` 出来。

### 两个细节

- **潜影盒标「已拆开」**：非空潜影盒入库时按漏斗口径拆成内容物 + 壳/箱，提示若仍写「1 个 潜影盒」就是在骗人，所以单独标注；空盒整盒入库，不加标注。
- **物品名保持可翻译组件**：走 `getHoverName()` + `VoidWarehouseText#body(Component)`，**绝不 `getString()`** —— 服务端解析会在专用服务器上固定成英文（理由与补货提示完全相同）。

## 不收的东西

| 情形 | 收不收 | 原因 |
| --- | --- | --- |
| 玩家挖掉方块 | **收** | `destroyBlock` 上下文内 |
| TNT / 苦力怕 / 活塞拆的方块 | 不收 | 不在 `destroyBlock` 里 |
| 怪物死亡掉落、玩家丢弃（Q 键） | 不收 | 同上 |
| 经验球 | 不收 | 不是 `ItemEntity` |
| 箭 / 滞留药水 / 掉落物发射物 | 不收 | 同上 |
| 创造模式挖方块 | 无掉落可收 | 原版本来就不掉 |
| 漏斗、发射器吐物品 | 不收 | 不是方块掉落物 |

## 默认值

`false`。理由和 `voidWarehouseRestock` 一样：它改变的是「全服共享库存能收进什么」，该由服主主动开。

`/carpet voidWarehouseBlockDrops true`（需要 `voidWarehouse` 也开着）。

## 是怎么验证的

自检 **39 条断言、7 组**（A mixin 挂载 / B 规则关 / C 规则开 / D 不误伤 / E 潜影盒 / F 依赖与兜底 / G 聊天提示汇总），在**真服务端**用真 `ServerPlayer` 真挖方块跑，五个版本全绿：

```
SMOKE RESULT vw-blockdrops/26.3     checks=39 failures=0
SMOKE RESULT vw-blockdrops/26.2     checks=39 failures=0
SMOKE RESULT vw-blockdrops/26.1.2   checks=39 failures=0
SMOKE RESULT vw-blockdrops/26.1.1   checks=39 failures=0
SMOKE RESULT vw-blockdrops/1.21.11  checks=39 failures=0
```

关键几条：挖掉一个泥土后，仓库 `+1`、世界里**没有**多出物品实体、玩家背包也没多 —— 少看任何一项都抓不到「既入库又掉地上」这种复制 bug。

G 组的验收口径是「该说的都说了、只准说一句」，所以不去抓「玩家真的收到几条」（那要拦 `sendSystemMessage`，属于另一层），而是直接咬三样纯逻辑：累计关系（同物品相加 / 不同物品并列 / 超 4 种折算）、限流判据 `due()`、以及拼出来的那一行文本。文本断言一律避开物品名 —— 专用服务器上 `getHoverName()` 按 `en_us` 解析，咬名字等于咬环境。

### 反证

把两条 mixin 从 `carpet_neko_addition.mixins.json` 里临时摘掉，同一套自检 `failures=7`：A1–A3（handler 找不到，诊断行直接打出 `ServerLevel[]` 为空）、C2 / C5（仓库一个都没收到）、E1，以及 C3 —— 诊断打出 **`dirt 实体 2 个，仓库 0`**，正是「东西全掉地上了」的形态。这说明这些断言咬住的是真代码。

### 两个测量坑（都真实踩过，以后别再踩）

1. **反射找 handler 必须按名字子串，不能 `getDeclaredMethod` 精确匹配**：Mixin 合并进目标类时会把 handler 改名成
   `handler$zhd000$carpet_neko_addition$carpetAutomending$blockDropsIntoWarehouse`。
   精确匹配必然 `NoSuchMethodException`，而功能其实好好的（C 组全绿）。按 `contains("blockDropsIntoWarehouse")` 数就对了。
2. **开局头几个 tick 不能数实体**：新区块要过一会儿才进入 entity-ticking，在那之前新 spawn 的物品实体在 `getAllEntities()` 里**看不到**。后果是两个方向的错：
   - 「掉落物照原样进世界」变成**假阴性**（实体明明在，数出来 0）；
   - 「世界里没有多出物品实体」变成**恒真的空转断言**（什么都看不到，当然等于 0）。

   自检的修法：第 0 阶段强制加载该区块并**等到 `isPositionEntityTicking(pos)` 为真**才开始测（冷世界要 8~26 tick），且 B / C 两组的实体断言都放到**下一 tick**验证，C3 还额外钉了一条「前提：该区块已 entity-ticking」。

## 已知边界

- 只覆盖**方块破坏**这一种来源。要覆盖「所有掉落的物品都进仓库」，那是另一条规则（终点不同、授权口径也不同）。
- 方块掉落物里若带**方块实体内容**（例如装了东西的箱子被精准采集），入库按物品 + 数据组件走，和漏斗吞潜影盒同口径，不做额外拆解。
- 玩家挖掉方块**本身不消耗仓库任何东西**，也不写白名单 —— 这条规则只做入库。
