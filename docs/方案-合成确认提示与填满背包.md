# 方案：合成后「记不记」由玩家点选 + 一键填满背包

> 状态：**已落地（2026-11-12）**，五版本同步、两套自检全绿。落地清单与实测见文末「落地情况」。
> 下面保留的是当时的方案与拍板过程 —— 单项决定为什么这么定，看「已拍板」那张表。

---

## 需求一：合成后在聊天栏给提示，玩家点击「确认 / 拒绝」

### 现状

`CraftResultMixin` 挂在 `ResultSlot#onTake`（HEAD），合成产物被取走时**直接**记住配方：

```
onTake → recipe = fromGrid(合成格, 产物)
       → data.learnCapturingOthers(recipe)      // 立即写进配方本
       → Notice.onCrafted(result, …)            // 「已记住配方：… 目前配方数量：X / 2,048。」
```

也就是说：**玩家没有选择权**，合成了就记。四种结局（`LEARNED` / `DUPLICATE` / `FULL` / `DISABLED`）
都已有文案与节流，`DUPLICATE` 是每玩家一次、`FULL` 是边沿 + 30 秒。

### 方案：加一个「待确认」态

把「记住」这一步从 `onTake` 里**挪到点击之后**，中间插一个 `PENDING` 状态：

```
onTake → 已经记过？ → 沿用 DUPLICATE（每玩家一次，不变）
       → 配方本满了？ → 沿用 FULL（边沿 + 30 秒，不变）
       → 否则：不记，挂一条待确认 + 发一条可点击提示
```

提示长这样（可点击的三个按钮，悬停有说明）：

```
[虚空仓库] 要记住这条配方吗？ 2 云杉木板 → 4 木棍    [记住] [不要] [总是记住]
```

点击后**追加一行**结果（聊天消息不能改，只能再说一句）：

```
[虚空仓库] 已记住配方：2 云杉木板 → 4 木棍，目前配方数量：1,845 / 2,048。
```

三个按钮的语义：

| 按钮 | 行为 |
| --- | --- |
| `[记住]` | 记住这一条，回上面那行「已记住」。**下一个新配方照样问** |
| `[不要]` | 不记，并且**本局**不再为这一条配方提问（不落盘） |
| `[总是记住]` | 记住这一条，并且**本局**后续所有配方都不再提问（等于回到现在的行为） |

> **`[记住]` 与 `[总是记住]` 的唯一差别是作用范围**：前者只管当前这一条，
> 后者顺手把「询问开关」关掉。两个都会写进配方本、都回同一行「已记住」。
>
> 🔴 **必须能切回来**：`[总是记住]` 一键切走，就得有切回的出口。
> **已定：不新增多余指令** —— 这个开关只活在**本局内存**里，**重登即恢复「一条条问」**，
> 并且切换成功时明写出来：「已切换为自动记住，本次登录内不再询问（重新登录后恢复）」。
> 不靠「玩家记得去输某条命令」来兜底，靠把状态说清楚。

### 点击是怎么实现的

原版聊天里唯一能「点一下就跑」的机制是 `ClickEvent.RunCommand`，所以**必须注册一个指令**
（三个子命令，一个不多加 —— `auto` 那条已经砍掉，理由见上）：

```
/vwr y <token>      记住这一条
/vwr n <token>      不要这一条
/vwr a <token>      总是记住（记住这一条 + 本局不再问）
```

- 注册点：`AutoMendingMod#onInitialize` 里的 `CommandRegistrationCallback.EVENT`（该处已在做
  payload 注册，是现成的入口）。权限 **0**，任何玩家可用。
- `token`：每位玩家每次提问随机生成（8 位 36 进制），**只能本人用、只能用一次**。
  过期 / 已用过 / 不是自己的 → 一句「这条提示已经处理过了」。
- 命令用 `sendSystemMessage` 回话、**不用 `sendSuccess`**，避免原版那行「[玩家] 已执行命令」。
- 已 javap 核对：`ClickEvent.RunCommand(String)` 与 `HoverEvent.ShowText(Component)` 在
  **26.3 与 1.21.11 完全一致**（都是 record），五个版本无差异。

### 必须处理好的五个细节

1. **shift 连合不能刷屏**：同一条配方在「待确认」里已有记录时**不再发第二条**。
   按键是 `recipeId`（内容文本），与 `learn` 的去重口径一致。
2. **待确认要有上限**：每人最多 3 条，超了丢最旧的（旧提示点了就是「已过期」）。
3. **超时**：60 秒（1200 tick）。点击时惰性判断，不需要每 tick 扫描。
4. **点击那一刻要重新验**：这 60 秒里可能别的玩家记了同一条（→ `DUPLICATE`），
   或者配方本被填满（→ `FULL`）。所以 accept 时重新走一次 `learn`，按真实结果出文案
   —— 直接复用 `Notice.onCrafted(...)`，不再抄一份文案。
5. **`[不要]` 的持久化范围**：建议**只在本局内存里**（`Map<UUID, Set<recipeId>>`，LRU 封顶）。
   落盘要新增一个 per-player 字段，代价远大于收益；代价是重登后可能再问一次。

### 风险

- **改成「问了才记」之后，「不点 = 没记住」**。玩家忽略聊天 → 配方本不涨 →
  之后「取木棍取不出来」会被当成新 bug 报上来（这和 1.0.17 那次
  「什么都没说 = 功能没生效」是同一类事故，只是方向反过来）。
  **已拍板：不点就是不记**（这是玩家要的选择权），靠三处兜底：
  ① `[总是记住]` 一键回到旧行为；② 提示里把「不点就不记」写清楚，不留想象空间；
  ③ 每次问都会说一句「这条还没记住」，让沉默本身有痕迹（吸取 1.0.17 的教训）。
- **聊天只有在按 T 之后才能点**。合成完还开着工作台界面时，点提示要先按 T
  （原版行为：开聊天会关掉容器界面，合成格里的东西会掉回背包）。这是原版限制，
  不是我们能绕的 —— 除非把提示同时画进仓库界面里（成本另算）。
- 指令会出现在 `/help` 与 tab 补全里。可接受，但要在 README 里写一句。

## 需求二：Ctrl+Alt+左键 一键填满背包

### 🔴 先说不行的那一半：原版协议里没有 Ctrl / Alt

容器点击只有 7 种输入，**没有修饰键通道**（26.3 叫 `ContainerInput`，1.21.11 还叫 `ClickType`，
两边枚举完全一样，已 javap）：

```
PICKUP  QUICK_MOVE  SWAP  CLONE  THROW  QUICK_CRAFT  PICKUP_ALL
```

修饰键到协议里的映射是**固定且唯一**的：

| 玩家动作 | 协议里看到的东西 |
| --- | --- |
| 左键 | `PICKUP` + button 0 |
| 右键 | `PICKUP` + button 1 |
| Shift + 左/右键 | `QUICK_MOVE`（**button 原样带着，但原版不看**） |
| 数字键 1–9 | `SWAP` + button 0–8 |
| F（副手交换） | `SWAP` + button 40 |
| 中键 | `CLONE` |
| Q | `THROW` |
| 拖拽 | `QUICK_CRAFT` |
| 双击 | `PICKUP_ALL` |

**Ctrl 和 Alt 根本没有地方放**。所以纯服务端模组 + 原版客户端，物理上收不到这个手势。
这不是「难做」，是「信号不存在」。

而且现有的 7 个值**已经全被占掉了**（`VoidWarehouseMenu#clicked`）：

| 输入 | 现在的行为 |
| --- | --- |
| `PICKUP` 0 | 取 1 个（盒模式：交出一盒） |
| `PICKUP` 1 | 普通模式「存/取切换」；盒模式「按数量取货」 |
| `QUICK_MOVE` | 取一组（盒模式：一盒）—— **button 被忽略** |
| `SWAP` | 数字键存入 |
| `PICKUP_ALL` | 取 1 个（注释写明：刻意压住，防连点误判） |
| `THROW` | 光标上的丢弃（有守卫） |
| `CLONE` | 明确拒绝（防创造造物） |
| `QUICK_CRAFT` | 交还原版 |

### 三条可选路线

**A. 换成 Shift+右键**

`QUICK_MOVE` + button 1。原版对 `QUICK_MOVE` 完全不看 button，而这个模组现在也忽略它
⇒ **Shift+右键目前是 Shift+左键的完全重复，改它不丢任何既有功能**，也不需要客户端。

> ⚠️ 实现第一步不是写功能，是**验这一条**：在 `clicked()` 里临时打一行
> `input + "/" + button` 的日志，五版本各点一次 Shift+左键、Shift+右键，
> 确认前者是 `QUICK_MOVE/0`、后者是 `QUICK_MOVE/1`。

**B. 严格照字面做 Ctrl+Alt+左键（✅ 已选）**

必须改客户端。见下一节。

**C. A + B 都做**：装了客户端用 B，没装用 A。成本最高。

## 需求二（B 路线）的落地设计

### 落点：客户端模组 `voidwarehouse-search`

这个手势只能活在**客户端**，所以它落在已经在维护的客户端伴生模组
`voidwarehouse-search`（mod id `neko_voidwarehouse_search`，五版本各一份）里。
**没装这个客户端模组的玩家，这个手势完全不存在** —— 没有残迹、没有报错、
服务端也不知道有这回事（和搜索框的降级策略一模一样）。

> 归属问题要写进 README：那个模组从此不再只是「搜索」，而是「虚空仓库的客户端增强」。
> 建议版本 0.1.0 → **0.2.0**（新增功能）。carpet 侧只加一条通道，不新增规则 ⇒
> 版本号**不升**，沿用 1.0.17。

### 客户端怎么认出「这是虚空仓库」

**不需要新机制**：搜索功能已经解决了这件事 —— 客户端只对 `ChestMenu` 发 `hello`，
服务端**只在 `player.containerMenu` 是 `VoidWarehouseMenu` 时才回 catalog**。
所以「收到过 catalog」就是「当前这个界面是虚空仓库」。

要补的只有一行状态：`SearchClientState` 加一个 `boolean warehouse`
（`onCatalog` 置 true，`removed` 清掉）—— 现在只有 `index`，而「仓库里一件可兑的都没有」
和「这不是仓库」用 `index.isEmpty()` 分不开。

### 手势判定（客户端）

注入 `AbstractContainerScreen#mouseClicked` 的 **HEAD**，条件全部成立才动手：

```java
menu instanceof ChestMenu        // 只碰大箱子家族，熔炉/酿造台一概不碰
&& SearchClientState.isWarehouse()   // 服务端认过这个界面
&& event.button() == 0               // 左键
&& (event.modifiers() & (MOD_CTRL | MOD_ALT)) == (MOD_CTRL | MOD_ALT)  // 两个都按住
&& hoveredSlot != null && hoveredSlot.index < 仓库格数
```

成立则：**发 `fill_request{slotId}` + `cancel` 掉原版点击**（否则会顺手取 1 个）。
不成立则一个字节都不碰。

- `MouseButtonEvent#modifiers()`：已 javap 核对，**26.3 与 1.21.11 签名完全一致**
  （`mouseClicked(MouseButtonEvent, boolean)` 也一样），所以这段源码五版本可以同文。
- 修饰键掩码用**字面量 2 / 4**（GLFW `MOD_CONTROL` / `MOD_ALT`）——
  本工程编译类路径上没有 GLFW，与 `KEY_ESCAPE = 256` 同一个处理方式。

### 服务端怎么执行（carpet 侧）

新增一对镜像 payload（照 `search_hello` 那套现成规矩，两 jar 逐字节相同）：

```
carpet_neko_addition:fill_request   （C2S，字段：int slotId）
```

服务端收到后**只信自己的数据**，客户端给的东西一律当不可信输入：

1. `player.containerMenu instanceof VoidWarehouseMenu`（不是就静默丢）
2. `0 ≤ slotId < VoidWarehouseData.TOTAL_SLOTS`
3. `menu.slotAt(slotId)` 解析出目标格（空格 → 丢）
4. **容量由服务端按玩家真实背包算**，绝不接受客户端报的数量
5. 取货 / 扣账

> 为什么 payload 只带 `slotId`：带物品 id 就等于让客户端指定「取什么」，
> 一旦校验漏一处就是凭空造物。带槽位则物品由服务端解析，客户端的权力仅限
> 「点的是哪一格」，而这一格本来就只能是他自己看得见的那一页。

### 能复用多少

| 已有 | 用途 |
| --- | --- |
| `VoidWarehouseWithdraw#execute(player, sample, requested)` | 按量取货的完整五步（校验 → 产物 → 背包 → 放 → 扣账），盒模式就是走它 |
| `VoidWarehouseMenu#withdrawShulkerBox` | 单盒路径，含「盒子材料够不够」「盒子先规划再放」两条守卫 |
| `VoidWarehouseData#planExchangeMax` | 「尽量给」的规划（9 合 1 + 配方扣料） |

两个缺口：

1. **`withdraw` 会夹到一组**（`want.min(getMaxStackSize())`）⇒ 填满背包**不能**用它，
   必须走 `execute`（吃 `long`）。
2. **`execute` 会顺手把散货装盒**（`packLoose`，散货 > 9 组时）⇒ 普通模式下这不符合预期，
   需要给它加一个「不许装盒」的开关（新增 `executeLoose` 或 `boolean allowBoxing` 参数）。
3. **盒模式批量**：现在一次只交一盒。要「交到背包满」得循环，但每一轮都会重发消息、
   重算材料。所以新增一个批量入口：一次规划 N 盒、一次校验材料、一次扣账、一条提示。

### 「填满背包」的口径

- **算哪些格**：主背包 36 格（快捷栏 0–8 + 主格 9–35）。**不含**盔甲 4 格与副手 1 格。
- **怎么算容量**：空格算满组，同类（`isSameItemSameComponents`）半组只算剩余空间。
  64 堆叠的物品 ⇒ 上限 **36 × 64 = 2,304**；`MAX_REQUEST = 2,000,000` 远大于它，不用夹。
- **普通模式**：按 2,304 取散装，`appendLoose` 拆成 36 组；仓库不够就给能给的；
  一件都凑不出时**必须说话**（不能像现在 `withdrawFrom` 那样静默返回）。
- **盒模式**：一盒 = 27 × 64 = **1,728** 个，36 格最多 **62,208** 个。
  但一盒要 1 个空盒（或 1 壳 + 1 箱）⇒ 通常会在**盒子材料**上先卡住，
  这时按材料够的数量交出，并在提示里说清「交了 N 盒 = M 个，用掉 N 空盒」。

### 性能门槛（上线前必须量）

「填满背包」= `planExchangeMax(sample, 2304)`。这条路在**大请求**上没被量过：

- `planMax` 是「从上界往下逐个试」，上界只要比真值高一点就是上百次递归 `drain`；
  硬预算 `MAX_PROBES = 1024` 兜底，但 1024 次递归在**满本（2048 条）**上可能就是几十毫秒。
- 门槛：单次 ≤ 5 ms（一次点击的 tick 预算）。超了就加缓存或换上界算法，**不能直接上**。
- 顺带要量盒模式批量：`planExchangeMax(sample, 1728)` × N 盒，N 最多 36。

### 风险

- **误触成本高**：一次点击取走 2,304 个（盒模式可到 62,208）。不过「取一盒」已经是 1,728，
  量级相当，属于既有可接受范围。
- **必须先装客户端模组**：没装 = 手势不存在。这是 B 路线的主要代价，要在 README 最显眼处写。
- 光标上拿着东西时点击：忽略（只按背包算），不做「先放光标再取」这种隐式动作。
- 背包完全没空间：一句话「背包放不下了」，不扣任何账。

## 工作量与验收（分工已定）

> **客户端那半由玩家自己实现**，本文档给它留下**接口契约**（见下一节）。
> 本仓库这轮只做 carpet 服务端侧。

| 项 | 规模 |
| --- | --- |
| 新增文件（carpet） | `VoidWarehouseRecipePrompt`（待确认状态机）、`VoidWarehouseCommands`（`/vwr`）、`FillRequestPayload` |
| 改动文件（carpet） | `CraftResultMixin`（改走 PENDING）、`VoidWarehouseRecipeNotice`（可点击文案）、`VoidWarehouseText`（`clickable(...)`）、`VoidWarehouseMenu`（填满入口）、`VoidWarehouseWithdraw`（`executeLoose` + 盒模式批量）、`AutoMendingMod`（注册指令 + 收包） |
| 五版本 | carpet 五份；mixin 描述符逐版本 javap 核对 |
| 自检 | 需求一：状态机 12~16 条（pending / 超时 / 重复 / 满本 / 非本人 / 二次点击 / `[不要]` 后不再问）；需求二：容量算法 6 条 + 真实背包 4 条 + 账平 3 条 + payload 往返 2 条 |
| 版本号 | carpet **不升**（不新增规则，沿用 1.0.17） |
| 产物 | carpet 五版本 jar 重出（第十次原地替换）+ md5 表刷新 |

### 交给客户端实现的接口契约

```
通道：carpet_neko_addition:fill_request     （C2S，客户端 → 服务端）
字段：int slotId                            （玩家点的那一格的菜单槽位下标）
```

- 客户端判定条件：`menu instanceof ChestMenu` + 已收到过 catalog（说明是虚空仓库）
  + 左键 + `modifiers` 同时含 Ctrl(2) 与 Alt(4) + `hoveredSlot != null`
  + `hoveredSlot.index < TOTAL_SLOTS`。
- 命中后**先发包、再 cancel 原版点击**（不 cancel 会顺手取 1 个）。
- 客户端**不要**自己算数量、也不要传物品 id：服务端只信自己那份数据，
  数量按玩家真实背包现算。传 id 等于给造物开口子。
- 服务端在任何条件不满足时**静默丢弃**（不回报错）—— 旧服务端没有这条通道，
  客户端 `canSend` 为 false 时也不该发。

## 落地情况（2026-11-12）

### 需求一：配方确认提示

| 文件 | 干什么 |
| --- | --- |
| `VoidWarehouseRecipePrompt`（新） | 待确认状态机：令牌、TTL、每人最多 3 条、`[不要]` / `[总是记住]` 的本局开关 |
| `mixin/CustomClickMixin`（新） | 截住 `ServerCommonPacketListenerImpl#handleCustomClickAction`，按 id 分派 |
| `VoidWarehouseRecipeNotice#askLine` | 那三个按钮（走 `ClickEvent.Custom`，**零指令**） |
| `VoidWarehouseText#button` | 按钮的统一外观（颜色 + `italic(false)` + 悬停说明） |
| `VoidWarehouseData#knows` | 「这条已经在配方本里吗」—— 必须先问再学，反了就问不出口 |
| `mixin/CraftResultMixin` | 合成那一刻只提问、不写本；四种情况直接走老路 |

**与方案的一处差别**：方案里「已挂着同一条就不再问」原本打算只判 `shouldAsk`，
落地时拆成了 `shouldAsk` + `isPending` 两个判断 —— 前者管「该不该问」，
后者管「已经挂着就别再挂」。合成动作本身不该因为我方状态而静默丢弃，
所以 `isPending` 命中时是**不发消息、直接 return**，不落进老路（否则会顺手把配方记进去）。

| 文件 | 干什么 |

| `fill/FillNetwork`（新） | 注册 + 四道校验 + 50ms 限流 + 下线清表 |

| `VoidWarehouseMenu#fillToBackpack` | `slotId` 边界校验 + 解析这一格 + 取完 `syncAllViewers` |

**与方案的一处差别**：方案的容量算法打算复用 `Inventory#getContainerSize()`，
实测那个值是 **43**（36 格 + 副手 + 身体盔甲 + 鞍），会把副手和盔甲槽算成能塞方块的地方
（第一版实测算出 2752 = 43 × 64，而正确答案是 2304）。现在统一按
`Inventory.INVENTORY_SIZE`（36）。这条错同时存在于既有的「按数量取货」里
（背包满时物品会落到副手），本轮一并修掉。

**盒模式的边界**（比方案写得更明确）：

- 材料够几盒就给几盒，剩下的格子**不会**退化成散货 —— 玩家要的是盒；
- 仓库不够一整盒 → 一个都不给，并报出「一盒 1728，现有 1000」；
- 目标本身就是潜影盒 → 走不装盒的分支（`isBoxable` 那道老红线）。

**落地后补的一条红线（材料预留）**：目标格本身是**潜影壳 / 箱子**时，盒子照给，但
**材料账必须先把「马上要离库的那批货」刨掉**。

- 原因：材料账是「先验、取货、再扣」，而这两样正是做盒子的材料 —— 取走整整一盒容量
  （1728 个壳）之后仓库里那 2 个壳恰好归零，`consumeBoxMaterials` 再也扣不到，只留一条 WARN。
- 算术（旧行为）：仓库 1728 壳 + 1 箱 → 取壳 → 拿到「装着 1728 壳的盒子」→ 送回仓库变回
  1728 壳 + **1 个空盒**。净效果 = **1 个箱子（8 木板）换 1 个潜影盒**，可无限循环；原版要 2 壳 + 1 箱。
- 改法：`VoidWarehouseData` 新增 `materialStock` / `hasBoxMaterials(plan, leaving, count)` /
  `maxBoxesUpTo(limit, sample)` + `canMakeBoxes`（二分，判据对盒数单调不增）。三处取货口
  （`fill` / `executeCore` / 菜单 `withdrawShulkerBox`）统一用这套口径；
  `isBoxPart` 只负责标出这两样，不再参与「要不要装盒」的判断。
- 两种结果：库存刚好够一盒容量时**一盒都不给**并报「盒子材料不够」；库存宽裕时照给满盒、
  材料随货一起扣（20000 壳 + 100 箱 → 11 满盒，壳扣 19030、箱扣 11）。菜单点一格会
  自动少装一点：1728 壳 + 1 箱 → 盒里 1726 个，另扣 2 壳 + 1 箱。
- **中途改过一次**：最初把这两样一律挡在装盒之外（点一下给散货），玩家要求保留「一盒壳」的能力，
  于是改成预留版，三处 `noPacking` 判据撤回。
- 这条**不是本轮引入的**：盒模式上线时就在，「按数量取货输 1728」同样能走通。`FillSelfCheck`
  的 E 组 18 条断言 + 变异实测（摘掉预留 10 条同时红）钉住。
