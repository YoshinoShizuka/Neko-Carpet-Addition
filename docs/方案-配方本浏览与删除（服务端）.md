# 方案：配方本浏览与删除（服务端侧）

> 状态：**已实现（1.0.17，未升版本号）**。本文最初是「待审阅、未实现」的设计稿，
> 实现完成后按实测结果回填了三处（见 5.1 / 5.2 / 8 的「实现后修正」），
> 声称过的风险里有 <b>一条是错的</b>，原样留在文里并标注，避免下次再推错。
> 客户端（`neko-client`）侧另议，第 6 节就是给它准备的字段约定。
> 版本：起草于 2026-11-17，针对 1.0.17 的现状；同日实现并铺满五版本。
> 自检：`VoidWarehouseRecipeBrowseCheck`（模板 `.workbuddy/tools/RecipeBrowseCheck.java.template`，
> 装/摘/跑 `.workbuddy/tools/install_recipe_check.py`），**100 条 × 5 版本 = 500**，全绿。

## 1. 需求理解

### 1.1 现状（已核对代码）

配方本是**全服唯一**的一份，存在 `VoidWarehouseData` 里：

| 项 | 现状 |
| --- | --- |
| 容器 | `LinkedHashSet<String> recipeTexts`（插入序 = 学习序） |
| 落盘键 | `learned_recipes_lines`，**一条一个元素**（旧的 `learned_recipes` 只读兼容） |
| 上限 | `VoidWarehouseRecipeBook.MAX_RECIPES = 2048` |
| 解码缓存 | `recipes`（`List<Recipe>`）、`recipesByOutput`（`Map<output, List<Recipe>>`）、`craftTree` + `craftScratch` |
| 写入者 | `CraftResultMixin` → `learnCapturingOthers`（唯一入口） |
| 读出者 | 合成页 `exchangeOffers()` / `maxCraftable` / `hasRecipeFor` / 聊天提示 |

它现在**只增不减**：

- 玩家唯一能感知的是聊天里那三条「记住了 / 重复 / 满了」，**看不到本子里到底有什么**；
- 学错了（摆错材料被记成一条永远用不上的配方）**没有任何办法删掉**；
- 满 2048 之后**静默停止记录**（只写一条服务端日志），玩家只能找管理员整档处理。

### 1.2 目标

1. 玩家能**浏览**配方本：看到「产物 → 原料 × 数量 → 一次产几个」。
2. 玩家能**删除**指定配方，删完立刻生效（合成页那一格随之消失）。
3. 界面由 `neko-client` 做；服务端只提供**查询**与**删除**两项能力 + 必要的失效通知。
4. **不改存档格式**、不改 `learn` 的语义、不影响纯原版客户端。

### 1.3 明确不做（本次）

- 不做导入 / 导出 / 手工编辑配方文本；
- 不做「每个玩家一本私有配方本」（那是另一个数据模型，见 §7 待确认 1）；
- 不做服务端 GUI（不占用底栏第 45 格那套「仓库页 / 合成页」语义）。

## 2. 服务端职责

### 2.1 只做四件事

| 职责 | 说明 |
| --- | --- |
| 建索引 | 给客户端一份「本子里有哪些**产物**」的去重 id 清单（不带原料明细） |
| 分页查询 | 按稳定序返回某一段**明细**（产物、产出数、原料候选与个数） |
| 执行删除 | 校验 + 批量移除 + 一次性重建 + 落盘 |
| 失效通知 | 增 / 删之后告诉正在浏览的客户端「变了，重取」 |

### 2.2 权威边界（三条硬线）

1. **`recipeId` 是唯一删除键**，服务端必须自己校验「这个 id 现在真的在本子里」，
   绝不按「第 N 条」「产物名」删 —— 插入序会随学习变化，产物名是一对多。
2. **服务端不做名字匹配**。中文 / 拼音匹配只能在客户端做（专用服务器没有 `zh_cn.json`），
   与 `search_*` 通道同一条理由。服务端只认 `recipeId` 与 `output`（物品 id）。
3. **删除是全局的**。一份配方本所有玩家共用 ⇒ 删一条对所有人生效，
   这一点必须在权限与提示上显式化（见 §4.3、§5.3）。

### 2.3 与 `learn` 的对称性（第一条硬约束）

`learnWithResult` 学会一条之后的收尾动作有五步，删除**必须逐条对齐**，漏一个就会出现
「删了还能合成」或「界面不刷新」或「存档没落盘」：

| 收尾动作 | 为什么删除也要做 |
| --- | --- |
| `rebuildRecipes()` | `recipes` / `recipesByOutput` / `craftTree` / `craftScratch` 四者必须同时换掉，否则树与分组表描述的不是同一本子 |
| `recipeGeneration++` | 配方相关的两处缓存（`craftOffers` / `craftDeps` 与展示序签名）都以它为键 |
| `offers = null` | 合成页的可兑表要重算（删掉某产物最后一条配方 ⇒ 那一格该消失） |
| `unifiedOrder = null` / `amountOrder = null` | 展示序缓存里可能还留着已失效的条目 |
| `setDirty()` | 不标脏就不落盘，重启后「删掉的又回来了」 |

## 3. 接口约定（与 neko-client 的契约）

### 3.1 通道命名

沿用 `carpet_neko_addition` 命名空间，路径加 `recipe_` 前缀，与 `search_*` 并列
（**不**挤进 restock 那 14 条 `printer_*`，那组是打印机联动的私有通道）。

| 通道 | 方向 | 载荷要点 | 限流 |
| --- | --- | --- | --- |
| `recipe_hello` | C2S | 空。能力探测 + 请求索引 | 100 ms |
| `recipe_index` | S2C | 产物 id 去重清单、总条数、`generation`、`canDelete` | — |
| `recipe_query` | C2S | 页码、页大小、排序、产物白名单 | 50 ms |
| `recipe_page` | S2C | 页码、总数、`generation`、条目明细 | — |
| `recipe_delete` | C2S | `recipeId` 列表（≤ 64） | 1000 ms |
| `recipe_delete_result` | S2C | 成功 id、失败 id + 原因、`generation`、剩余条数 | — |
| `recipe_changed` | S2C 广播 | `generation`、原因、操作者名、影响条数 | 500 ms 合并 |

> 全部走 `ServerPlayNetworking.canSend` 前置判断；**纯原版客户端永远不发这些包**，
> 旧版 neko-client 也没有这些通道（`canSend == false`），入口自然不出现。

### 3.2 字段定义

**`recipe_index`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `protocol` | int | 协议版本，首版 = 1；加字段不升、改语义才升 |
| `generation` | int | 配方本版本号，每次增 / 删自增 |
| `total` | int | 本子总条数（`recipeTexts.size()`） |
| `outputs` | string[] | **去重后的产物 id**（全命名空间）；排序由服务端给，客户端可自行重排 |
| `canDelete` | bool | 当前玩家能否删除（客户端据此灰掉删除按钮，**不要自己猜**） |
| `denyReason` | enum | `NONE` / `NO_PERMISSION` / `RULE_OFF` |

**`recipe_query`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `page` | int | 0 基；越界由服务端夹到合法范围并回夹后的值 |
| `pageSize` | int | 客户端建议值；服务端封顶（建议 32） |
| `sort` | enum | `OUTPUT_ASC`（默认）/ `RECENT_FIRST`（按学习序倒序） |
| `outputs` | string[] | 白名单；**空数组 = 不过滤**（与 `search_apply` 的「空 = 清除」同义）。服务端把不认识的 id 静默丢弃 |

**`recipe_page`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `protocol` | int | 同上 |
| `generation` | int | 与请求时的版本不同 ⇒ 客户端丢弃这一页重新请求 |
| `page` | int | 夹后的页码 |
| `total` | int | **过滤后**的总条数 |
| `entries` | 记录数组 | 见下 |

单条 entry：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `recipeId` | string | **opaque**：内容派生文本，客户端不得解析 / 拼接 / 猜测长度以外的东西 |
| `output` | string | 产物全名 id |
| `outputCount` | int | 一次合成产出几个（木板 4、活塞 1） |
| `parts` | 数组 | 每项 `{ candidates: string[], count: int }`；`candidates` 是**任意一种**的候选集合（目前恒为单元素，结构留着多候选用） |

**`recipe_delete`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `recipeIds` | string[] | ≤ 64 条；**超限整包拒**（回 `TOO_MANY`），不截断 |

**`recipe_delete_result`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `removed` | string[] | 真的删掉的 id |
| `failed` | 数组 | 每项 `{ id, reason }`；`reason ∈ NOT_FOUND / NO_PERMISSION / RULE_OFF / TOO_MANY / THROTTLED` |
| `generation` | int | 删除后的新版本号 |
| `remaining` | int | 剩余条数，便于客户端立刻更新「已用 N / 2048」 |
| `canDelete` | bool | 复述一次权限，防止客户端状态漂移 |

### 3.3 分页与顺序（稳定性）

- 服务端定义**唯一**顺序：`output` 字典序 → `recipeId` 字典序。
  两个键都是内容派生的稳定值，不受插入顺序影响 ⇒ 两次查询（同 `generation`、同过滤集）分页结果一致。
- 客户端**不得**假设跨 `generation` 的顺序稳定；收到比自己新的 `generation` 必须重取当前页。
- `sort = RECENT_FIRST` 用 `recipeTexts` 的插入序倒排（Redis 式 LRU 直觉：刚学的在最前）。

### 3.4 失效广播

- 何时发：`learn` 成功（新配方）与删除成功。
- 发给谁：**只发给 `canSend(recipe_changed)` 且当前正开着仓库界面的玩家**（不要全服广播，
  学配方是高频动作）。
- 合并：同一 tick 内多次增 / 删只发一条，`generation` 取最终值。
- 客户端收到后：丢弃本地页缓存、重发 `recipe_query`（**不要**复用旧页码之外的状态）。

## 4. 数据与权限处理

### 4.1 读侧

- 全部走**已有缓存**（`recipes` / `recipesByOutput`），不新建持久索引 ——
  2048 条的遍历与排序在微秒级。
- 排序结果按 `(generation, sort, filterHash)` 缓存一份（与 `craftCacheGeneration` 同款做法），
  避免恶意客户端靠高频 query 把排序变成 DoS 面。

### 4.2 写侧（删除）

- **一次性批处理**：先整体校验 → 一次移除 → 一次 `rebuildRecipes` → 一次 `setDirty`。
  绝不允许「循环里逐条删 + 逐条重建」（2048 条会变成 2048 次重建）。
- **可以删空**：删空等价于 `recipeTextsLines()` 返回 `Optional.empty()`，存档里那个键消失 ——
  与「从没学过」同形，**无损**，也不需要迁移。
- **删除不改 `recipeId` 的生成规则**：id 由内容算出，删掉再学一次会得到同一个 id（这正好是「撤销」的天然形态）。

### 4.3 权限：三道闸门

| 闸门 | 判据 | 理由 |
| --- | --- | --- |
| ① 规则 | `voidWarehouse` 且 `voidWarehouseCraft` 都开 | 与 `learnWithResult` 的 `DISABLED` 同源。规则关着时**读也不给**，保持「关着的规则不碰存档」这条不变式 |
| ② 会话 | `player.containerMenu instanceof VoidWarehouseMenu` | 照抄 `search_*` 的既有边界：能问的前提是**自己正开着仓库界面**。顺带保证了「看不到别人仓库的配方」 |
| ③ 权限 | 删除需 `player.permissions().hasPermission(Permissions.COMMANDS_GAMEMASTER)`；浏览不需要 | 已用 javap 核对：**五个版本**（26.3 / 26.2 / 26.1.2 / 26.1.1 / 1.21.11）都是 `permissions()` → `PermissionSet#hasPermission(Permission)`，`Permissions.COMMANDS_*` 常量齐备。**注意**：老写法 `ServerPlayer#hasPermissions(int)` 在 26.x 已不存在，别再照抄旧代码 |

- **单人 / 局域网**：无 cheats 时房主权限等级为 0 ⇒ 按 ③ 会被拒。建议对
  `server.isSingleplayerOwner(...)` 放行（**待确认**，见 §7-2）。
- **不新增 Carpet 设置项**：权限口径先硬编码成一个常量，避免规则面变化与版本号升级；
  真要可配置时再单独讨论。
- **拒绝必须回话**：无权限要回 `recipe_delete_result{failed:[{reason:NO_PERMISSION}], canDelete:false}`，
  不能静默 —— 客户端否则只能等超时（与 `search_hello` 的「静默 = 功能不存在」不是一回事，
  那里是探测，这里是明确的用户操作）。

### 4.4 异常与安全防护清单

| 风险 | 处置 |
| --- | --- |
| `recipeId` 超长 / 含非法字符 | 长度上限（建议 512）+ 逐条丢弃，不崩 |
| 一次删太多 | > 64 整包拒 `TOO_MANY`；**不截断**（截断会让客户端误以为全删成功） |
| 同一 id 重复提交 | 去重后处理；已不存在回 `NOT_FOUND`，不影响同包其它 id |
| 高频删除 | 1 次/秒/人；同一 tick 二次请求丢弃 |
| 高频查询 | 50 ms 限流 + 排序缓存 + `pageSize` 封顶 |
| 规则关闭时的请求 | **直接丢弃不回执**（与 `search_*` 一致：不向可疑客户端确认「这里有个仓库」） |
| 未开界面的请求 | 丢弃（同 ②） |
| 删除与取货并发 | 重建只换引用，安全；但**已在飞行中的取货计划**仍按旧表执行 —— 接受（与既有「陈旧 plan」同类风险，见 `REFERENCE-lessons.md`） |
| 事后追责 | 每次删除写一条服务端日志：操作者、删前剩余、被删 id 列表。日志本身可用来手工重建 |

## 5. 风险与兼容

### 5.1 老 `ExchangeOffer` 在删除后仍能出料（**原判断错了，实现后修正**）

> ⚠️ **原文（错误，保留以记档）**：
> `ExchangeOffer` 的 `bulk()` / `boxed()` 是**惰性算源**，闭包捕获的是**建表那一刻**的
> `table`（配方树）与 `stock` 快照。合成页的位置钉住有 `IDLE_TICKS = 40`（2 秒）的窗口：
> 在窗口内那一格仍指向删除前的 offer ⇒ 删掉一条配方，2 秒内点合成页对应格子，仍会按旧表
> 把东西做出来。
>
> **实测结论：这条不成立。** 合成页的钉住数组存的是 <b>`itemId` 字符串</b>
> （`VoidWarehousePageContainer#offerIdAt`），不是 `ExchangeOffer` 对象：
> `slotAt` 每次都用它去 `offerById(itemId)` 现查**当前**那一份清单。
> 惰性闭包捕获旧表是真的，但**没有任何地方会把删除前那个 offer 对象再交出去**。
>
> 真正兜住这件事的是另一处（原文没看见）：
> `VoidWarehouseData#virtualEntrySignature()` 把 `recipeGeneration << 2` 算进指纹，
> `exchangeOffers()` 每次取表前先 `revalidateExchangeCache()` —— 指纹一变就整体置空
> `offers`。所以「配方本变了 ⇒ 清单立刻作废」是**结构性**的，与「钉住多久」无关；
> `forgetRecipes` 里那句 `this.offers = null` 其实是**冗余**的（留着只为与
> `learnWithResult` 逐行对齐，读代码不用两处对照）。
>
> 变异验证（M3：同时删掉 `virtualEntrySignature` 里的 `recipeGeneration << 2` 与
> `forgetRecipes` 里的 `offers = null`）→ 自检 R8 **红了 4 条**
> （清单里还有剑 / 那一格没变空 / 图标还是剑 / 还能问到 obtainable=32）。
> 也就是说：这条判据咬的是真正的机制，不是摆设。

那 `refreshAfterRecipesChanged()` 还有用吗？有，但作用变了：它管的是**网络**，不是正确性。

- `sendAllDataToRemote()` 把 54 格**重新取一遍**再全量发下去，客户端手里那份「删之前的
  幽灵格」才会当场消失。不发的话，服务端已经取不出东西了，玩家却还看着那一格，
  直到他下一次点别的格子触发差异包（`AbstractContainerMenu#broadcastChanges` 只在
  服务端「以为的」和当前内容不一致时才发 —— 而客户端还会自己做预测，正是不发的理由）。
- `invalidatePin()` 只对**动作发起者**做：他刚点了删除，不在连续点击中间。
  别的浏览者**故意不 invalidate** —— 那会在别人连点的时候把页重排，正是 0.18 修掉的
  「点错物品」。他们的那一格会自然解析成空（拿不到东西），下一次交互即恢复整齐。

### 5.2 合成页 `pin` 本身不用改（结论对，理由错）

原文说「`ensurePin()` 已经含『底层对象换了 ⇒ 停手满 `IDLE_TICKS` 后重建』这条判定，
删除后 `exchangeOffers()` 会返回新对象，天然收敛」。**前半句对，后半句不成立**：
收敛不是靠 `IDLE_TICKS`，而是靠 5.1 那个指纹 —— 同一 tick 内就已经换了新对象，
根本不用等 2 秒。`IDLE_TICKS` 管的是「排序变化时别在玩家手指底下换人」，
与「工具表过期」是两件事，原文把两者混成一件了。

### 5.3 全局删除的社交风险

一份本子全服共用 ⇒ 管理员删掉一条，所有玩家的合成页都会少一格。缓解：

- 删除回执里带 `remaining` 与操作者名，广播里也带操作者名（谁干的看得见）；
- 建议客户端做二次确认（服务端**不**做「确认 token」：它挡不住恶意客户端，只增加状态）；
- 满本提示（`VoidWarehouseRecipeNotice`）里补一句「可以在配方本界面删掉不用的」，把唯一的解法告诉玩家。

### 5.4 与现有机制的兼容

| 机制 | 影响 |
| --- | --- |
| 存档格式 | **不变**（`learned_recipes_lines`）。删空 = 键消失 = 与从没学过同形 |
| `learn` / `learnCapturingOthers` | 不变（删除只加一个新入口，不改学习路径） |
| `recipesFor` / `hasRecipeFor` / `learnedRecipeCount` | 不变，读的都是重建后的缓存 |
| 合成页 `exchangeOffers()` | 删除后**同一 tick 内**就重算（`virtualEntrySignature` 含 `recipeGeneration`，见 5.1）；某产物最后一条配方被删 ⇒ 该条目消失 |
| 9 合 1 可兑表 | 与配方本独立；只是「可兑 + 可合成」的并集里少一条来源 |
| 位置钉住 | 见 5.1 / 5.2 |
| 搜索通道 | 互不影响（两个通道各自限流、各自 `containerMenu` 校验） |
| 纯原版客户端 | 零影响（不发包，界面还是那两张纸） |
| 旧版 neko-client | `canSend == false` ⇒ 入口不出现，功能自然降级 |

### 5.5 五版本

新通道**建议五份都铺**（模板逐字相同，只有行尾差异）。理由：

- 铺了：任何版本的服主都能用同一个 neko-client；
- 不铺（只 26.3）：`canSend` 天然表达能力差异，也不算破坏兼容，但会让「配方本浏览」变成
  「只有 26.3 服务器有」的半成品。

工作量差异只是复制 + 逐版本 `javap` 核对（`ServerPlayNetworking` 的方法名在 26.x / 1.21.x
已经差过一次：`playC2S/playS2C` vs `serverboundPlay/clientboundPlay`，照 `search` 的先例打补丁）。

### 5.6 性能

| 动作 | 成本（按现有实测口径估） | 处置 |
| --- | --- | --- |
| 删除 1~64 条 | 一次全本 decode + 树编译（2048 条 ≈ 毫秒级） | 主线程可接受，但必须限流 |
| 查询一页 | 排序 2048 条（微秒级）+ 截取 | 按 `(generation, sort, filter)` 缓存 |
| 增 / 删后的合成页重算 | 74 条目 ≈ 1.9 ms（20 人峰值口径） | 已在既有基线内，不新增热点 |

## 6. neko-client 接入所需的最小约定（给客户端那侧看）

1. **镜像 7 个 payload 类**，FQCN 与服务端完全一致（照 `neko.voidwarehouse.search.*` 的先例），
   放在 `neko.voidwarehouse.recipe.*`；两份必须逐字节等价，改一边必须同步改另一边。
2. **C2S 两端都要幂等注册**（撞名 try/catch 吞掉）——专用服务器是两个进程，只注册一边等于丢包。
3. **能力探测**：进服 / 打开界面时发 `recipe_hello`；`canSend(recipe_hello) == false` 或
   2 秒内没收到 `recipe_index` ⇒ 认为该服务端不支持，**整个入口不显示**（不要显示空界面）。
4. **只认 `recipeId` 的 opaque 语义**：不解析、不比较大小、不假设长度上限之外的东西。
5. **`generation` 是缓存键**：任何比本地新的 `generation` ⇒ 丢弃页面缓存并重取。
6. **删除结果逐条处理**：`failed` 里的 id 必须留在界面上（不能乐观删除后不回滚）。
7. **`canDelete == false` 时灰掉删除按钮**，并用 `denyReason` 给出原因文本（客户端自己翻译，服务端不发文案）。
8. **不用中文匹配服务端**：搜索/过滤全部在客户端完成（本地语言文件 + 拼音库），
   回传给服务端的是**产物 id 白名单**。

## 7. 拍板结果（2026-11-17，已按此实现）

| # | 问题 | 决定 | 落地情况 |
| --- | --- | --- | --- |
| 1 | 全局真删还是按玩家隐藏 | **全局真删** | `forgetRecipes` 直接从 `recipeTexts` 移除 + 重建 + 落盘 |
| 2 | 删除权限给谁 | **规则开着 = 所有玩家都有** | 不做 op 判断；`canDelete` 恒 `true`，字段留着供将来收紧（不改协议） |
| 3 | 入口形态 | **neko-client 实现** | 服务端只出通道，不加指令、不加按钮 |
| 4 | 要不要「撤销」 | **先不做** | 协议里没有 `undoToken`；真要做得改成「删 + 撤销」两段式 |
| 5 | 页大小 / 分组视图 | **neko-client 实现** | 服务端只保证排序与分页；`pageSize` 由客户端提（上限 32），分组在客户端做 |
| 6 | 五版本还是只 26.3 | **五份都铺** | 26.3 / 26.2 / 26.1.2 / 26.1.1 / 1.21.11 各一份，逐版本 `runServer` 验过 |
| 7 | 导出 / 导入配方本文本 | **不做** | —— |
| 8 | 删除后要不要全服提示 | **只在浏览者那里刷新** | `recipe_changed` 只发给「近 60 秒问过索引/页面 且 仍开着仓库界面」的人；动作发起者另走 `refreshAfterRecipesChanged()` |

### 8.3 自检覆盖（100 条 × 5 版本 = 500）

| 组 | 咬什么 | 条数 |
| --- | --- | --- |
| R1 | 索引：去重、字典序、`total`/`used` 两个口径、`canDelete`、代次一致 | 13 |
| R2 | `OUTPUT` 全序严格递增 + 三页拼回一页 + 不重不漏 + 跨页首尾相接 | 9 |
| R3 | 夹取：页码越界 / 负页码 / 页大小 0 / 页大小 9999 → 32 | 10 |
| R4 | `RECENT` = 学习序倒排；两种排序确实是两种序 | 3 |
| R5 | 白名单：命中 / 未知 id 静默忽略 / 全不命中 / 空与 null | 8 |
| R6 | 回执五态：`OK` / `NOTHING` / `PARTIAL` / `BAD_ID`×2 / 重复 id 去重 / null / 删空后旧页码 | 24 |
| R7 | 收尾对齐：代次 +1、用量 -1、解码条数 -1、两个派生缓存**已作废**、落盘数据里消失、删了能重新学 | 14 |
| R8 | **删完立刻不可得**（同 tick，不 bumpTick）+ 对照格仍在 + 重新学立刻回来 | 14 |
| R9 | 第一道闸门：规则关着时学习被拒、配方本不动 | 5 |

R8 的判据咬的是 `VoidWarehouseMenu#slotAt → pageContainer#slotAt`（点击路径的第一件事），
不是界面渲染 —— 所以「解析为空」等价于「点下去拿不到东西」。

**不能自检覆盖的两处，如实记下**：

- `capWarned`（满本警示复位）：要真填到 `MAX_RECIPES = 2048` 条，每次 learn 都整本重建，
  代价与本自检的目标不成比例；复位本身在 `forgetRecipes` 里是一行赋值。
- 第二 / 第三道闸门（`player.containerMenu`、权限）：需要真玩家，属网络层，
  `RecipeNetwork` 负责，本自检不造假玩家。

### 8.4 变异验证

| 变异 | 期望 | 实测 |
| --- | --- | --- |
| M1：`forgetRecipes` 只删 `offers = null` 这一行 | 应红 | **全绿** —— 说明那一行是冗余的（`virtualEntrySignature` 已覆盖），据此改了 5.1 的结论 |
| M3：同时删 `virtualEntrySignature` 的 `recipeGeneration << 2` 与 `forgetRecipes` 的 `offers = null` | R8 应红 | **红 4 条**（清单里还有剑 / 那一格没变空 / 图标还是剑 / 还能问到 `obtainable=32`） |

M1 的「全绿」比 M3 的「红」更有价值：它把一处**写完自己都没看清的设计依据**暴露了出来。
