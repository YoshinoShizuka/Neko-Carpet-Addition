# 混凝土粉末烧制染色玻璃：规则溯源与本模组移植

> 一次「我那个规则去哪了」的追问，最后变成给本模组加第三条规则。
> 本文记录：规则原本属于谁、为什么不能直接装回来、以及移植时踩到的每一处版本差异。

---

## 1. 事情是从一个存档开始的

玩家提问（原话）：

> 查看我 `E:\Game\Minecraft\.minecraft\versions\RO26.3\saves\20260906` 的这个存档中，
> 我之前开了一个染色粉末能被烧制成对应染色玻璃的规则，现在找不到这个规则来自于哪个模组了

### 1.1 先确认「规则确实开过」

存档里找到 `backup_1788669900932_carpet.conf`（Sep 16 23:54），内容含：

```
smeltConcretePowderToGlass true
```

而**当前**的 `carpet.conf` 里已经没有这一行了 —— Carpet 在加载时会把它不认识的规则行
从配置文件里删掉。所以现象成立：规则曾经开着，现在消失了。

对照实例 `26.1.1 20260824 Fabric/saves/20260906/carpet.conf:38` 里仍是 `true`，
说明它在另一个实例里还活着。

### 1.2 再查「这条规则来自哪个模组」

用 `.workbuddy/tools/find_rule_source.py` 按**原始字节**搜实例目录下的所有 jar
（class 常量池里的字符串是 modified UTF-8，直接搜字节才不会漏）：

```
python find_rule_source.py "E:\Game\Minecraft\.minecraft\versions\...\mods" smeltConcretePowderToGlass
```

命中：

| jar | 内容 |
| --- | --- |
| `carpet-dds-addition-v1.5.0-mc26.1.2.jar` | `carpetddsaddition/generated/CarpetDDSAdditionSettings.class` 里有规则名 |
| 同上 | `carpetddsaddition/generated/DDSRuleTranslations.class` 里有中文名与说明 |

**结论：`Carpet DDS Addition`（作者 DDS），规则 id `smeltConcretePowderToGlass`。**

> ⚠️ **踩坑提醒**：存档里的 `data/rulestackaddon_prefabs.json`（carpetgui 的「规则栈」）
> 写的是 `"carpet:smeltConcretePowderToGlass"`。这个 **`carpet:` 是所有 Carpet 附加包共用的
> 命名空间**，不能据此判断规则归属 —— 差一点就被它带偏。
>
> 另一个坑：中文文案**不在** `assets/carpet-dds-addition/lang/zh_cn.json` 里
> （那份文件只有 4 条无关的 gca 文案），而是在编译进 class 的 `DDSRuleTranslations` 里。

### 1.3 为什么不能把 DDS 装回来

| 事实 | 影响 |
| --- | --- |
| v1.5.0 的 `fabric.mod.json` 声明 `minecraft >=26.1 <26.2` | 26.3 上**装不了** |
| 上游当前只构建到 **26.2** | 没有 26.3 版本可下 |
| RO26.3 实例的 `mods/` 里没有 DDS，也没有 `.jar.disabled` | 确认是「规则随模组一起消失」，不是被禁用 |

于是有两条路：等上游出 26.3（不可控），或者**把这条规则移植进本模组**。
这条规则本质就是「往熔炉加 16 条 `粉末 → 对应染色玻璃` 的配方」，做成本模组的一条新规则完全可行
—— 这就是本文下半部分。

## 2. 规则名：故意不叫原名

DDS 叫 `smeltConcretePowderToGlass`，本模组叫 **`concretePowderToGlass`**。

不是随手改名，是**必须**改。Carpet 的 `SettingsManager#addCarpetRule`（javap 实证）是：

```java
if (rules.containsKey(rule.name())) {
    throw new UnsupportedOperationException(...);
}
```

**重名直接抛异常，没有商量余地。** 哪天玩家在同一个版本里同时装上 DDS 和本模组，
沿用原名就意味着**服务端起不来**。改个名字之后，两个模组即使共存也只是「两条开关做同一件事」，
最坏情况是冗余，不会崩。

改名有代价吗？没有：玩家存档里那条 `smeltConcretePowderToGlass true` **早就随着 DDS 被移除
而被 Carpet 从 `carpet.conf` 里删掉了**（见 §1.1），沿用原名也捞不回旧配置。

### 与本模组其它规则的一致性

- 默认值 **`false`** —— 与本模组其它规则一致。装上就悄悄多出 16 条熔炉配方属于「改变原版行为」，
  必须由服主显式开启。
- 分类 `neko` + `survival`，与 `voidWarehouse` / `voidWarehouseRestock` 相同。
- 规则名即字段名（`CookingSettings.concretePowderToGlass`），翻译键
  `carpet.rule.concretePowderToGlass.name` / `.desc`。

## 3. 实现：为什么不写成数据包

最直觉的做法是往 `data/<ns>/recipe/concrete_powder_to_glass/*.json` 塞 16 个配方文件。**不行**：

- 数据包配方是**开机时一次性加载**的，而 Carpet 规则要在**运行期**随意开关
  （`/carpet concretePowderToGlass true`）—— 写成数据包就意味着「改规则要重启服务器」；
- 规则关着的时候，配方照样存在于配方书里，与原版行为不一致；
- 规则关掉之后也会残留 `acceptedInputs`（见 §3.2）。

所以走**运行期方案**：这 16 条配方**不进 `RecipeManager` 的配方表**，
而是自己维护两张表（输入物品 → 配方、配方 id → 配方），由三个 Mixin 在「原版说没有」时补一句。

### 3.1 调用链（javap 实证，选注入点的唯一依据）

```
RecipeManager.getRecipeFor(type, input, level, ResourceKey)  → 委托 4 参（RecipeHolder）
RecipeManager.getRecipeFor(type, input, level, RecipeHolder) → 委托 3 参
RecipeManager.getRecipeFor(type, input, level)               ← 三参，全部汇入这里 ★注入点
    ├─ 原版查表（我们没注册 ⇒ 空）
    └─ 空 → ConcretePowderToGlass.findRecipe 兜底

RecipeManager.byKey(id)                                      ← ★注入点
    └─ 用来给玩家发经验（见 §3.3）

AbstractFurnaceMenu.canSmelt(stack)                          ← ★注入点
    └─ 影响「Shift 点击能不能把粉末送进输入槽」
```

熔炉方块实体走的是 `RecipeManager.createCheck(SMELTING)` 造出来的 `CachedCheck`，
它内部调的是 **4 参**那一版 —— 而 4 参又委托给 3 参，**所以挂 3 参就等于把 4 参那条路一起覆盖了**。
只挂一个点，少一处可能失配的地方。

注入用 `@At("RETURN")` 而不是 `@At("HEAD")`：让原版先查一遍，**原版配方永远优先**，
我们只在「原版说没有」时补一句。这样哪怕将来 Mojang 真给混凝土粉末加了熔炼配方，也不会被我们盖掉。

### 3.2 为什么光修配方还不够：`canSmelt`

26.3 的 `AbstractFurnaceMenu#canSmelt` 整个方法体只有一句（javap 实证）：

```java
return this.acceptedInputs.test(stack);
```

`acceptedInputs` 是**开机时按已注册配方算出来的** `RecipePropertySet` ——
我们的配方没注册，所以它里面永远没有混凝土粉末。

而 `canSmelt` 在整个原版里**唯一的调用点**在 `quickMoveStack` 里：

```java
else if (index == 0 || index == 1) moveItemStackTo(stack, 3, 39, false)   // 燃料/输入 → 背包
else if (canSmelt(stack))          moveItemStackTo(stack, 0, 1, false)   // → 输入槽
else if (isFuel(stack))            moveItemStackTo(stack, 1, 2, false)   // → 燃料槽
```

不补这一下，玩家 Shift 点击混凝土粉末时它会走 `isFuel` 分支
（混凝土粉末**确实**是可燃的），被当成燃料塞进下面那格 —— 看起来就像「模组没生效」。

补的时候**限定 `FurnaceMenu`**：只放行普通熔炉。高炉 / 烟熏炉的 `canSmelt` 走同一个方法，
但它们的 `RecipeType` 不是 `SMELTING`，配方那边本来就不会命中；这里再挡一道，
免得出现「高炉界面允许摆放、放进去却烧不动」的怪异状态。

> 实现细节：`@Mixin` 生成的混入类**不继承**目标类，所以 `this` 不能直接 `instanceof FurnaceMenu`，
> 必须先 `(((Object) this) instanceof FurnaceMenu)` 才判得了。

### 3.3 为什么 `byKey` 也要补：经验

原版烧完一个物品后，会拿「用过的配方 id」回来查一次配方，用于把经验发出去。
`AbstractFurnaceBlockEntity#getRecipesToAwardAndPopExperience` 的字节码是：

```
recipesUsed.reference2IntEntrySet() 遍历
  → level.recipeAccess().byKey(entry.getKey())
  → Optional.ifPresent(... createExperience(..., ((AbstractCookingRecipe) holder.value()).experience()))
```

我们的配方不在表里，不补这一下，烧出来的玻璃**不给经验**。

> 顺带纠正一个错觉：`AbstractFurnaceBlockEntity#getRecipeUsed()` 在 26.3 是
> **恒返回 `null` 的桩实现**（`aconst_null; areturn`）。真正的经验账记在私有字段
> `recipesUsed`（`Reference2IntOpenHashMap<ResourceKey<Recipe<?>>>`），由 `setRecipeUsed(holder)`
> 填充，与 `getRecipeUsed()` 无关。第一版自检就是栽在这个假设上（见 §6）。

### 3.4 数值：与「沙子 → 玻璃」完全一致

| 项 | 值 | 理由 |
| --- | --- | --- |
| 经验 | `0.1` | 抄原版 `sand → glass` |
| 时长 | `200` tick | 同上 |

同一条链上的产物，手感一致比另定一个数字重要。

### 3.5 延迟初始化：别让静态初始化把类变砖

16 条配方放在内部类 `Bag` 的静态块里构建，而不是直接写在 `ConcretePowderToGlass` 的静态字段上。

理由：主类只要被「碰」一下（哪怕只是被 Mixin 引用到），静态字段就会立刻去碰 `Items`。
放进内部类后，构建时机推迟到**第一次真的要用配方**的时候 —— 那时注册表早就 bootstrap 完了。
真正要防的是「在物品注册表就绪前构建 ⇒ 抛 `ExceptionInInitializerError` ⇒
这个类在整个 JVM 生命周期里永久变砖」。

`Bag` 里还有一条自检式的断言：每注册一条就检查
`BY_INPUT.size() == color.ordinal() + 1`，少一条立刻抛 —— 防止「两个颜色指到同一个物品」这类
取色错误在运行期静默发生。

## 4. 五个版本的差异（全部 javap 实证）

| 项 | 26.3 | 26.2 | 26.1.1 | 26.1.2 | 1.21.11 |
| --- | --- | --- | --- | --- | --- |
| `Items.CONCRETE_POWDER` | `ColorCollection` | `ColorCollection` | 16 独立字段 | 16 独立字段 | 16 独立字段 |
| `Items.STAINED_GLASS` | `ColorCollection` | `ColorCollection` | 16 独立字段 | 16 独立字段 | 16 独立字段 |
| `SmeltingRecipe` 构造 | `(CommonInfo, CookingBookInfo, Ingredient, ItemStackTemplate, float, int)` | 同左 | 同左 | 同左 | `(String, CookingBookCategory, Ingredient, ItemStack, float, int)` |
| `Recipe$CommonInfo` | 有 | 有 | 有 | 有 | **没有** |
| `ItemStackTemplate` | 有 | 有 | 有 | 有 | **没有** |
| `Recipe#assemble` | `assemble(T)` | 一参 | 一参 | 一参 | **两参**（多了 `HolderLookup.Provider`） |
| `Level#recipeAccess()` | 有 | 有 | 有 | 有 | 有 |
| `mixins.json` 的 `compatibilityLevel` | `JAVA_25` | `JAVA_25` | `JAVA_25` | `JAVA_25` | **`JAVA_21`** |

`RecipeManager.getRecipeFor(RecipeType, RecipeInput, Level)`、`byKey(ResourceKey)`、
`AbstractFurnaceMenu#canSmelt(ItemStack)` **五版本签名一致** —— 三个 Mixin 的字符串描述符因此
可以直接复制。

> **1.21.11 的 jar 是混淆的**，`javap` / `grep` 查不到可读名。要核对 API 得用手工 unmap 过的
> 那份：`~/.gradle/caches/fabric-loom/minecraftMaven/net/minecraft/minecraft-merged/`
> `1.21.11-loom.mappings.1_21_11.layered+hash.2198-v2/minecraft-merged-….jar`
> （Loom 为编译期生成的重映射 jar，名字都是可读的）。注意 **1.21.11 这一代已经用
> `Identifier` 而不是 `ResourceLocation`**，命名风格与 26.x 一致。

### 同步脚本

`.workbuddy/tools/sync_concrete_powder.py`

- 4 个 java 文件 + 1 个 mixin 配置 → 整文件复制（**保留目标原本的行尾**，否则制造整文件假 diff）；
- `ConcretePowderToGlass.java` 在三处打补丁：独立字段取色（26.1.1 / 26.1.2 / 1.21.11）、
  `SmeltingRecipe` 老构造（1.21.11）、摘掉两个 1.21.11 上没有的 import；
- `fabric.mod.json`、`AutoMendingMod.java`、两份 lang → 打补丁接线；
- 自检文件按版本复制，1.21.11 额外把 `assemble` 改成两参。

脚本里的 `patch_once()` 在「已经改过」时**跳过**而不是报错（方便反复跑），
但真正写下去的那一次一定要求：**锚点恰好 1 处 + 替换后确实变了**。
静默失效（改了但没生效）比崩掉更难查。

### 断言只能咬「真正被执行的代码」

本轮同步脚本连撞两次同一个坑：

- `assert 'Items.CONCRETE_POWDER.pick' not in cp` —— 咬到了 javadoc 里那句
  「26.2 起才统一收进 `ColorCollection`（`Items.CONCRETE_POWDER.pick(color)`）」的**说明文字**；
- `assert 'ItemStackTemplate' not in cp` —— 咬到了自己写的注释
  「26.x 才换成 `Recipe.CommonInfo` + `ItemStackTemplate`」。

两次都是**断言在咬注释，不是在咬代码**。改成
`'return Items.CONCRETE_POWDER.pick(color);'` / `'new ItemStackTemplate('` 之后才恢复区分力。

## 5. 自检：反证组才是牙

临时自检 `ConcretePowderToGlassSelfCheck`（跑完已删，模板存
`.workbuddy/tools/ConcretePowderToGlassSelfCheck.java.template`），在**真实 `runServer`** 里跑，
分五组：

| 组 | 断言内容 |
| --- | --- |
| **G** | 反射数 handler，证明两个 Mixin **真的挂上了**（`build` 成功 ≠ 挂上了） |
| **A** | **反证组**：规则关掉时，查配方必须为空、`byKey` 必须为空、`isEnabledInput` 必须为假、真熔炉烧 400 tick **一口都不许动** |
| **B** | 16 色逐个 `assemble()` 校验：产出**就是那个颜色**的染色玻璃、只产 1 个、16 个产出互不相同；`byKey` 反查一致；原版「沙子 → 玻璃」不被盖掉；高炉 / 烟熏炉拿不到；石头不误命中 |
| **C** | 真熔炉方块实体 + 逐 tick 驱动 `serverTick`：烧出对应颜色、输入槽被消耗、**经验发放链路认得这条配方** |
| **D** | 走真实 `quickMoveStack`：普通熔炉 Shift 点击能进输入槽；**反证**规则关时进不去；高炉不收 |

几个关键点：

- **G 组不可省**：「有 class 但没进 `mixins.json`」或「字符串描述符写错」都表现为**静默不生效**，
  `build` 照样成功、jar 里也有 class。所以先证明它挂上了，后面所有断言才有意义。
- **C3 是 `byKey` 那一钩的牙**：断言
  `getRecipesToAwardAndPopExperience(...)` 的返回列表里含我们的 recipe id
  —— 这条直接证明原版发经验时真的查到了我们的配方。
- **离线自检没有玩家 ⇒ 出生点区块不保证加载**：`setBlockAndUpdate` 在未加载的区块上
  **静默什么都不做**，`getBlockEntity` 返回 `null`，看着像「熔炉摆不下去」。
  必须先 `level.getChunkAt(pos)`。第一次跑就栽在这里。
- **泛型陷阱**：`getRecipeFor` 返回 `Optional<RecipeHolder<T>>`，而 `Optional` **不变**
  —— `Optional<RecipeHolder<SmeltingRecipe>>` 既不是 `Optional<RecipeHolder<?>>`，
  也推不出 `T`。所以既要显式写类型参数 `.<SingleRecipeInput, SmeltingRecipe>getRecipeFor(...)`，
  返回类型也要放宽成 `Optional<? extends RecipeHolder<?>>`。

## 6. 本轮踩到的坑（按代价排序）

1. 🔴 **断言建立在错误的假设上**：第一版 C3 断言 `be.getRecipeUsed()` 记下了我们的配方，
   结果 26.3 它是恒 `null` 的桩实现。**javap 查出真正的账在私有 `recipesUsed` 字段**之后，
   改成断言 `getRecipesToAwardAndPopExperience` 的返回值 —— 顺带得到一条**比原断言更有价值**
   的检查：它直接验证了 `byKey` 那一钩。
2. 🔴 **离线自检里区块没加载** ⇒ `setBlockAndUpdate` 静默失败。见 §5。
3. 🟡 **同步脚本的断言咬到了注释**（两次）⇒ 见 §4 末。
4. 🟡 **新增文件的行尾不能凭空造**：`copy_whole` 原先只从目标文件本身推断 EOL，
   而新增文件在目标处还不存在 ⇒ `FileNotFoundError`。改成从目标版本的**同族已有文件**
   （java 树取 `VoidWarehouseExtension.java`，resources 树取 `fabric.mod.json`）推断。

## 7. 与 Carpet DDS Addition 共存

| 场景 | 结果 |
| --- | --- |
| 只装本模组 | 规则 `concretePowderToGlass`，默认关 |
| 两个都装 | 两条独立规则，各自开关，**不冲突、不崩**（因为改了名，见 §2） |
| 两个都开 | 两条配方做同一件事；本模组的 `@At("RETURN")` 注入让**先查到的那条赢**，B 组断言保证原版配方不被盖 |
| 从 DDS 迁到本模组 | 旧配置行已不在 `carpet.conf` 里，需要手动 `/carpet concretePowderToGlass true` |
