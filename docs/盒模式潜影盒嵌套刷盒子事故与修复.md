# 盒模式取「潜影盒」会造出盒子套盒子，送回仓库后越刷越多

> 影响版本：1.0.6 起（盒模式引入 `planBoxMaterials` 空盒优先、并且空盒改为「整盒入库」之后）到 1.0.16 本次修复。
> 影响范围：**盒模式**（导航行槽位 47）点仓库里**潜影盒**那一格；点普通物品格不受影响。
> 修复版本：1.0.16 原地更新（`5a784f51…` 起的 26.3 产物）。未新增 Carpet 规则、未改存档格式与协议。

## 1. 现象

盒模式打开后点仓库里「潜影盒」那一格：

- 交出的是**一个装着 N 个潜影盒的潜影盒**（把外层放下、打开，能掏出 N 个盒子）；
- 仓库这一格的 N 个盒子**被扣光**（不是扣 N+1）；
- 把这堆盒子送回仓库，拆出来是 `N 个空盒 + 2 个潜影壳 + 1 个箱子`。

也就是说：**取 5 个盒子，实际拿到 6 个**。一来一回，仓库的盒子数量不变，但每循环一次就白得 `2 壳 + 1 箱`（正好是一整盒的配方），反复循环可无限增长。

## 2. 复现（真 26.3 服务端，`BoxNestingSelfCheck`）

修复前：

```
[A1] 交出盒子 1 个，里面套着潜影盒 5 个；仓库空盒 5→0，壳 0，箱 0
FAIL: A1 盒模式点潜影盒格：不交出「盒子套盒子」（里层潜影盒 = 0）
FAIL: A1 仓库恰好扣 1 个空盒（5→4）
[A2] 送回后 空盒=5，壳=2，箱=1
FAIL: A2 送回后没有凭空多出潜影壳
FAIL: A2 送回后没有凭空多出箱子
[A3] 来回 3 轮后 空盒=5，壳=8，箱=4
[B1] 盒内圆石 1728；仓库圆石 1728，空盒 0        ← 对照组，绿的
[B2] 送回后 圆石=2728，空盒=0，壳=2，箱=1        ← 对照组，绿的
SMOKE RESULT vw-boxnest/26.3 checks=25 failures=4
```

修复后：`checks=25 failures=0`，`[A3]` 来回 3 轮仍是 `空盒=5，壳=0，箱=0`。

## 3. 根因（两条，缺一不可）

### 根因一：`pack` 不认「不能装盒的东西」

`VoidWarehouseShulker#pack(template, count)` 拿模板 `copyWithCount(n)` 往格子里铺，然后直接
`box.set(DataComponents.CONTAINER, ItemContainerContents.fromItems(slots))`。

原版禁止「潜影盒装进潜影盒」并不靠容器本身，而是靠 `ShulkerBoxBlock#canFitInsideContainerItems`
在**物品放进容器那一刻**返回 `false`（依据 `minecraft:shulker_boxes` 物品标签）。而这里是**直接
写组件**，那道检查根本不参与 —— 于是服务端能造出原版永远造不出来的嵌套盒。

盒模式下点「潜影盒」那一格时，`withdrawShulkerBox` 拿 `entry.template()`（一个空潜影盒）当模板
去 `pack`，得到的就是「装着 N 个空盒的盒子」。

### 根因二：外盒的材料账与「取出」同源，取货先把这一格扣空

外盒本身也要 1 个空盒（`VoidWarehouseData#planBoxMaterials`，空盒优先）。可当**目标格就是那个
空盒格**时，扣账顺序是：

1. `take(realIndex, available)` —— 把 N 个盒子取走，格子数量归零、整格被移除；
2. `consumeBoxMaterials(plan)` —— `takeEmptyBoxes(1)` 这时已经找不到空盒了，返回 0。

而 `consumeBoxMaterials` 的返回值**没有任何调用方看**，注释还写着「少扣了说明并发操作把空盒抢走了，
调用方不必在意 —— 那部分材料本来就不该花出去」。这条理由只在「另一个玩家抢走了空盒」时成立；
「同一笔操作自己的取货把材料扣没了」显然不成立。于是外盒一分钱不付。

两条叠加 = 每点一次多出一个盒子。

## 4. 修法

### 4.1 盒子本来就是盒子，不再装一道盒（主修）

新增 `VoidWarehouseShulker#isBoxable(template)`（= 非空且不是潜影盒），两条取货口遇到目标格
本身是潜影盒时改走「散盒取出」：

- `VoidWarehouseMenu#withdrawShulkerBox`：开头早退到 `withdrawFrom(target, 0, player)`，
  与普通模式同一口径（每次 1 个盒子）；不 `pack`、不扣盒材料。
- `VoidWarehouseWithdraw#execute`（聊天按数量取货）：`boxTarget` 为真时
  `fullBoxes = 0 / loose = requested / packLoose = false`，产物走 `appendLoose`，`totalBoxes = 0`
  所以 `planBoxMaterials(0)` 是空账。

`pack` 的 javadoc 里补了「调用前必须先问 `isBoxable`」的警告 —— 方法本身不做类型检查，是为了
让「谁负责把关」这件事有唯一答案。

### 4.2 材料账不再「少扣就算」（兜底）

`consumeBoxMaterials` 改成：空盒实际扣到的数量少于计划时，把差额按原版配方折算成
`2 潜影壳 + 1 箱子` **补扣**；真补不上才留一条 WARN（并说清「反复出现说明取货路径与空盒材料
共用了同一格」）。

这样即使同类漏账将来从别的路径冒出来，最坏结果也只是「玩家多花了壳箱」，**不可能再凭空多出盒子**。

## 5. 验证

- **复现 + 回归自检 25 条**（`BoxNestingSelfCheck`，真 26.3 服务端 + 真仓库存档）：
  A 组（目标格是潜影盒，界面盒模式 + 连做 3 轮）、B 组（目标格是圆石，对照组）、
  C 组（目标格是潜影盒，聊天按数量取货 30 个 → 走 `pack` 分支）、每组后面都跟一步「把盒子全部
  送回仓库再对账」。
- **对照组常绿**：B 组修复前后都通过，证明红只出在「目标格本身是潜影盒」这一条路，
  不是断言写歪。
- **反证**：只把聊天取货口改回旧代码重跑，A/B 全绿、C 组 3 条红
  （`套着 27 个盒子`、背包只有 4 个盒堆、送回后多出 2 壳 1 箱）—— 证明两组断言各自咬的是
  各自那条路的代码。
- **五版本**：`26.3 / 26.2 / 26.1.2 / 26.1.1 / 1.21.11` 各 `build` 通过；26.3 真跑 `runServer`
  自检 `failures=0`。

## 6. 边界与已知遗留

- **已经刷出来的东西不会自动回收**：存档里若存在嵌套盒（`CONTAINER` 里又是潜影盒），
  送回仓库仍会按「拆盒」处理成「里层盒子 + 2 壳 + 1 箱」，这是既有语义，本次不改。
  真要清，手工把嵌套盒里的盒子拿出来即可（拿出后是普通空盒）。
- **染色空盒当材料时仍会丢颜色**：`pack` 造出来的永远是**无色**潜影盒，而消耗的可能是染色盒。
  这是既有的刻意取舍（见 README「染色潜影盒会被拆成无色的 2 壳 + 1 箱」），
  与本次刷物品无关，本次不动。
- **`takeEmptyBoxes` 仍按格子逆序取**：多个颜色的空盒格会从最后一个开始扣。无害，
  但「用哪个颜色」不确定 —— 想指定颜色就先把那一种单独存进去。
- **盒模式对潜影盒格不再有「1 盒 = 1,728 个」的意义**：一盒能装 27 个盒子这件事原版不允许，
  现在也不会发生。
