# 全功能系统测试报告（1.0.15 / MC 26.3）

## 一句话

在**真实服务端**里跑了一轮覆盖六条规则、192 条断言的系统测试：**192 项全绿、0 失败、0 跳过**；
性能上单次操作都在微秒级，测出的唯一中风险（可兑表重算在多人同 tick 下叠加到 30.6 ms）**已修复**，
修复后同一场景 **1.99 ms**（占 tick 4.0%）。

## 怎么测的

**测试代码不入库**，模板在 `.workbuddy/tools/SystemTest.java.template`；
临时把 `VoidWarehouseExtension#onTick` 的第一行接上 `SystemTest.run(server)`，跑完删掉源码、还原钩子。

- **环境**：`./gradlew :modern:26.3:runServer`，真服务端 + 全部既有 mod（carpet / lithium / c2me / servux …），
  日志判据 `SYSTEM TEST RESULT v26.3 checks=192 failures=0 skips=0`。
- **分 25 个阶段、每个 tick 只做一个阶段**：性能量的是「真 tick 里发生的事」，
  而不是「一个不被打扰的纯 CPU 循环」。功能组先跑，性能/多人组后面跑。
- **20 个真实 `ServerPlayer`**（无客户端）：`new ServerPlayer(server, level, profile, ClientInformation)` +
  一个 `SERVERBOUND` 的空 `Connection` + `ServerGamePacketListenerImpl`。
  Fabric 的 `FakePlayer` 在 26.3 里已经没有了。有连接，「同步给客户端 / 发消息」的代码路径才会真的被执行。
- **反证是硬要求**：每条规则都配一条「关掉开关必须失效」的断言。
  否则「绿」可能只是因为别的原因凑巧成立（例如库存本来就没有，取不出来也「对」）。
- **微基准自动定批**：Windows 上 `nanoTime` 实际分辨率约 100 ns，单次几十纳秒的操作会直接读成 `0.00 us`。
  所以先把「一批」凑到 200 µs 以上再除回单次。**报告里所有 µs 数都是这么来的**；
  第一版没定批，`insert` 量出来是 0.00 µs（假的）。

## 性能测试结果

单机环境（Windows / JDK 25 / 26.3 不混淆构建），warmup + 自动定批后取多轮最小值
（最小值比均值更能排除 GC / JIT 抖动）。

| 项目 | 数值 |
| --- | --- |
| `planExchange(铁锭, 64)` | **9.7 µs** |
| `planMax(铁锭, 64)` | **12.6 µs** |
| `planExchange(活塞, 1)`（递归扣料一层） | **5.2 µs** |
| `planExchange(活塞, 64)`（递归扣料一层） | **4.1 µs** |
| `insert(64 个圆石)` 单次 | **0.021 µs** |
| `take(下标 0, 1 个)` 单次 | **0.018 µs** |
| `new VoidWarehouseMenu`（200 格仓库） | **2.9 µs** |
| `displaySlotAt` 整页 45 次 | **0.22 µs**（≈ 5 ns/格） |
| 可兑表重算（空仓库） | **0.057 ms**（0 条可兑） |
| 可兑表重算（40 条可兑） | **1.6 ~ 1.7 ms** |
| 漏斗入库吞吐（连续调用） | **1 728 个 / 次**（27 格 × 64），折合 7.3 M 个/秒 |
| `insert` 合并吞吐（同一格） | **2 000 万次 / 秒** |
| 内存：400 格 + 2000 次入库后堆增长 | **0.1 MB**；清空后回落 **0.0 MB** |

**怎么读这几个数**：

- 兑换/扣料的规划是**只读**的（不改任何状态），所以这两行就是玩家每次点击的真实成本；
  10 µs 量级，对 50 ms 的 tick 完全无感。
- 入库/取出的 20 ns 是「同一格合并」的路径 —— 也就是漏斗每 tick 走的那条热路径。
- 可兑表重算是**界面开销的主项**，也是唯一上到毫秒级的操作：它要把整张 9 合 1 表的
  88 个物品挨个「从上界往下试探」。数值与库存**量级无关**（64 / 6 400 / 1 000 000 都是 1.6 ms），
  与「有多少条可兑」正相关 —— 说明 1.0.13 卡死事故的上界压紧确实生效了，
  成本只跟条目数走，不再跟库存数字走。

## 多玩家性能

「并发」在服务端是**同一 tick 内顺序执行**（主循环单线程），所以量的是
「N 个玩家在同一 tick 里各做一次动作」的总耗时 —— 那才是 TPS 真正感受到的东西。

| 人数 | 开界面 | 取货 | 翻页 | 整页刷新 | 合计 | 占 50 ms tick |
| --- | --- | --- | --- | --- | --- | --- |
| 1 人 | 0.066 | 0.030 | 0.002 | 0.036 | **0.134 ms** | 0.3% |
| 5 人 | 0.046 | 0.003 | 0.003 | 0.046 | **0.098 ms** | 0.2% |
| 10 人 | 0.032 | 0.002 | 0.003 | 0.054 | **0.091 ms** | 0.2% |
| 20 人 | 0.057 | 0.004 | 0.012 | 0.070 | **0.143 ms** | 0.3% |
| 20 人 × 20 次连点（400 次动作） | — | — | — | — | **0.032 ms** | 单次 0.08 µs |

**结论：稳态下人数几乎不影响开销**（0.098→0.143 ms，20 人翻两倍人数只多 0.05 ms）。
原因是每个玩家各自的动作都是 O(1) 表操作，共享的只有「同一个 `VoidWarehouseData` 实例上的缓存」。

### 峰值：入库 + 界面刷新（曾是最坏 tick）

| 场景 | 修复前 | 修复后 | 占 tick（修复后） |
| --- | --- | --- | --- |
| 20 人同一 tick 各自「入库一格 + 界面刷新」 | **30.573 ms** | **1.990 ms** | **4.0%** |
| 同 tick 内第 2~21 个人 | 各 1.6 ms（线性叠加） | **0.0046 ms**（全命中） | ≈0% |

修复前它**不是** 20 人 × 稳态值，而是 20 次**全表重算**堆在一起：每次入库都会让可兑表缓存失效，
界面刷新又必须立刻重算它。修复后上限锁死「每 tick 一次重算」，与人数无关。
详见「缺陷 P-1：已修复」。

## 缺陷清单

### P-1（中）可兑表重算在多人同 tick 下叠加到 30.6 ms —— **已修复**

#### 具体表现

20 名玩家在**同一个 tick** 内各自入库一次并刷新界面，主线程花掉 **30.573 ms**（61.1% 的 tick 预算），
那一个 tick 必然掉 TPS。不崩、不丢物品，就是卡一下。

#### 触发条件（三条缺一不可）

1. `voidWarehouse` + `voidWarehouseExchange` 开着（否则可兑表恒为空，重算只要 0.057 ms）；
2. 仓库是「只囤下级」形态 —— 可兑条目拉到 40 条（空仓库量不到这个成本）；
3. **≥ 2 名玩家在同一个 tick 里各自「改库存 → 读可兑表」**（改库存 = 入库/兑换/取货，
   读可兑表 = 界面刷新）。人越多线性叠加：1 人 1.6 ms、20 人 30.6 ms。

#### 根本原因

`exchangeOffers()` 是**带缓存的**（算一次要跑 40 次 `planMax`，每次几十次递归），
而缓存失效的口径是「库存一动就**整体置空**」：

```java
void markChanged() {
    ...
    this.offers = null;        // ← 直接置空
    this.unifiedOrder = null;
}
```

置空本身没错，错在**「置空」把「什么时候重算」的决定权交给了读的一方**：
谁先读谁就付那 1.6 ms。而界面刷新恰好是「每次渲染 45 格、每格都可能问一次」的路径，
于是同一 tick 里 N 个人各刷新一次 = N 次重算，**成本随人数线性叠加**，没有任何上界。

数据会证明这不是「缓存没生效」：单次重算 1.6 ms、且**与库存量级无关**
（64 / 6400 / 1,000,000 都是 1.6~1.8 ms）—— 说明 1.0.13 那次「上界压紧」的修复是有效的，
瓶颈纯粹是**重算次数**，不是重算本身的算法。

#### 修改方案

把「什么时候重算」从**读的一方**收回到**tick 边界**：同一 tick 内最多重算一次。

| 改动点 | 改法 |
| --- | --- |
| 缓存失效口径 | `markChanged()` 不再把 `offers` 置空，只置 `offersStale = true`（标脏） |
| 重算条件 | `offers == null \|\| (offersStale && offersTick != serverTick)` 才算 |
| tick 从哪来 | `VoidWarehouseData.noteServerTick(server.getTickCount())`，由 `onTick` 每 tick 写一次（**static**，不碰 `data()`，不会牵动「空壳闸门」的异常路径） |
| `unifiedOrder` | **仍然立刻作废**，不许偷懒 —— 它存的是 `entries` 下标，取空一格就会让后面整体前移，留旧数组轻则显示错格、重则越界。它重建只要一次 O(n) 归并（几十微秒），不是瓶颈 |
| 开关 / 配方本变化 | 走 `revalidateExchangeCache()` 的指纹路径，**真作废、不等 tick**（否则关掉规则后「可兑」幽灵格要多挂一个 tick） |

**为什么用服务端自己的 tick，而不是自己 `+= 1`**：万一哪天 `onTick` 不再被调用，
自己加一的计数器会停在原地，`offers` 就**永远**不再重算 —— 那比慢得多要糟。
用真 tick 则最坏退化成「每 tick 重算一次」，行为仍然正确。

**代价与取舍**：同一 tick 内第 2 个及以后的读者，最多拿到**旧 1 tick** 的名单。
这是有意的：界面只在 tick 边界渲染，同一 tick 内所有人看到的本来就是同一帧，
那 N−1 次多算纯属浪费。而且**拿旧名单去点击是安全的** ——
取出路径一律重新规划（`withdrawFrom → data.withdraw()`、`withdrawShulkerBox → planExchangeMax`），
凑不出来就是空操作，不会凭空造物；名单下标也有界检查（`displaySlotAt`）。

#### 修复前后（同一台机器、同一份 harness）

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 单次重算本身的成本 | 1.6 ~ 1.8 ms | 1.6 ~ 1.8 ms（**算法没动，也不该动**） |
| 20 人同 tick「入库 + 刷新」 | **30.573 ms（61.1%）** | **1.990 ms（4.0%）** |
| 同 tick 内第 2~21 个人 | 各 1.6 ms（线性叠加） | **0.0046 ms**（命中） |
| 20 人稳态（开界面/取货/翻页/整页刷新） | 0.143 ms | 0.110 ms |
| 与人数关系 | **线性**（N × 1.6 ms） | **常数**（上限 = 1 次重算） |

#### 验证步骤

1. **回归**：全量系统测试 192 条断言 —— 修复前 187 条全绿，修复后 **187 条仍全绿 + 新增 5 条**，
   证明「按 tick 合并」没有改坏任何既有行为。
2. **新增的 5 条是「合并契约」本身**（`O1`~`O5`），专治两种相反的坏法：
   - 只测「下一 tick 会更新」→ 发现不了「合并变成永不更新」；
   - 只测「同 tick 不重算」→ 发现不了「省电省成了永久陈旧」。

   | 断言 | 内容 |
   | --- | --- |
   | O1 | 9 粒铁粒 → 铁锭进可兑表（1 条） |
   | O2 | 同 tick 内取空库存**不重算**，仍返回上一份（这是设计取舍，被显式钉住） |
   | O3 | 进下一个 tick **立刻**反映库存变化（不会永久陈旧） |
   | O4 | 库存回来 → 下一个 tick 又出现在表里 |
   | O5 | 关规则**立刻**清空（走指纹作废，不等 tick） |
3. **峰值实测**：同一 tick 先推进 tick 戳（模拟「新 tick 的第一次读」），再让 20 个真实玩家
   交替「入库 + 刷新」，量到的就是「每 tick 一次重算」的真实成本 —— 1.99 ms。
   然后固定在同一 tick 里再让 20 人各做一轮，量「后续读者的命中价」—— 0.0046 ms。
4. **五版本**：改动同步到 26.3 / 26.2 / 26.1.2 / 26.1.1 / 1.21.11，逐个 `build + dist` 全绿
   （`getTickCount()` 两套工具链都核对过：26.3 与 1.21.11 都是 `public int getTickCount()`）。

### B-1（信息）可行性是「跳档」的，不是单调的

2 个铁锭（= 18 铁粒）时：要 **9** 个给得出（拆 1 整块）、要 **18** 个给得出（拆 2 整块），
而要 **10** 个**给不出**。这不是缺陷，是 `docs/虚空仓库 9 合 1 兑换.md` 里写明的口径
（「1~9 都给得出，10~17 一个都给不出，18 又给得出」），也是 `planMax` 不能二分的原因。
测试按「要么 null、要么正好 10，绝不给错数」断言 —— 通绿。

### B-2（信息）拆整块正好用完时，计划里只剩「铁锭 −1」

拆 1 块得 9 粒、当场全部拿走，所以 `deltas` 是 `{iron_ingot=-1}`，铁粒那笔 +9/−9 相消后不入账。
**这是对的**（净变化就是「少 1 块铁锭」），但看着像「铁粒凭空消失」。
测试第一版就误断言成 `{铁锭 −1, 铁粒 +9}`，红了两次才查清 —— 现已改成钉死「净变化」并打印实际账目。

## 没覆盖到的（诚实边界）

- **真实客户端 GUI**：20 个 bot 有连接但没有渲染线程，点击链路走的是数据层，不是真实的
  `clicked()` / 客户端预测。界面**逻辑**覆盖了，**观感/延迟**没覆盖。
- **跨维度 / 重启后重开界面**：存档往返测了 Codec，没测「重启服务端后玩家再进仓库」。
- **Servux / litematica-printer 真机联调**：补货通道只在服务端侧验了 `query` / `take` 的语义。
- **超过 20 人**：机器上能稳定造的对象数量到 20，没有再往上压。
- **真实 TPS 采样**：`runServer` 是空世界 + 20 个无客户端玩家，没有区块加载/实体 AI 的干扰，
  所以上表是「模组自身的净开销」，不是「满员服的实际 TPS」。
