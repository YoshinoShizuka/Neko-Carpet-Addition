# 虚空仓库存储改造 A1：自定义二进制容器（`Codec.BYTE_BUFFER`）

> 触发原因：`learned_recipes` 是单个 NBT 字符串，`writeUTF` 上限 65535 字节 ⇒
> **975 条配方顶格**（975 条 = 65,512 B 通过 / 976 条 = 65,596 B 超限）。
> 超限后的失败形态是 `NbtIo$StringFallbackDataOutput` 把字段内容**替换成空串**（键还在，值没了），
> 回读 0 条 —— 机理与实测见 §4.3 ③。
>
> 本文只覆盖 **A1**（自定义二进制塞进 `ByteArrayTag`）。A2（分片）与 B3（SQLite）另文。
>
> **状态：§4.1 的 `WarehouseBlob` 已编译并跑通三套测试共 90 条断言（见 §4.3），可直接落地。**
> 仍待做的只有「接进 `VoidWarehouseData` 后真服务端端到端」（§7 第 2~3 步）。

---

## 1. 目标与非目标

**目标**

1. 彻底去掉「单字段 65535 字节」这一约束，配方本上限只受堆内存限制。
2. 保持现有全部语义：跨维度唯一、`setDirty` + world save 时机、`.bak` 快照、
   空壳闸门、**坏条目原样保留**、逐行容错。
3. 老存档（`{items, learned_recipes}`）能直接读，**首次写盘自动升级**，不需要手动迁移命令。
4. 为以后加字段留一个版本号，不再动 NBT schema。

**非目标**

- **不追求「物品层也不碰 NBT」**（原因见 §2，那是伪命题）。
- 不改写盘时机、不改增量写、不改跨维度策略（那是 B 系列的事）。
- 不做压缩优化（外层 `SavedData` 已经 gzip，实测 10.8:1）。

---

## 2. 必须先说清的一件事：物品层离不开 NBT

`ItemStack` 的数据组件（`DataComponents`）没有独立的、稳定的二进制表示 —— 它整体就是
`ItemStack.CODEC`，只能编码到某个 `DynamicOps` 上。可选项只有：

| 通道 | 产物 | 评价 |
| --- | --- | --- |
| `NbtOps` | `CompoundTag` → 字节 | 紧凑、跨版本最稳（本模组现在就在用） |
| `JsonOps` | `JsonObject` → 文本 | 体积 2~3 倍、解析更慢，没有一项更好 |

所以 **A1 的定位是「换容器，不换物品编码」**：外层是自己定义的二进制，每条物品是
一段**独立的 NBT 片段**（`NbtIo.write(CompoundTag)` 出来的字节）。

这也带来一个额外好处：单条物品片段是**按长度前缀切出来的**，不依赖 NBT 解析器就能切分 ——
比现在「先把整个 `ListTag` 解析出来、再从里面逐条 `parse`」更抗损坏。

## 3. 容器格式

```
偏移  长度   内容
0     4     magic 'N','C','A','W'          0x4E 0x43 0x41 0x57
4     1     formatVersion = 1
5     1     flags（保留，恒 0）
6     4     payloadLength（int，大端）      仅用于校验 / 将来做分块
10    ...   payload

payload:
  varint  itemCount
  重复 itemCount 次:
    varint  fragLen
    byte[]  fragLen        // 单条物品的 NBT 片段（未压缩的 CompoundTag 字节）
  varint  recipeCount
  重复 recipeCount 次:
    varint  textLen
    byte[]  textLen        // 配方文本 UTF-8，不含 '\n'
```

**为什么长度全用 varint**

| 编码 | 1657 条物品 + 975 条配方的长度开销 |
| --- | --- |
| `int`（4 B） | 2632 × 4 ≈ 10.5 KB |
| `short`（2 B） | 5.3 KB，但重新引入 65535 上限 —— 直接否掉 |
| **varint** | 大多 1~2 B，约 **3.9 KB** |

实现只有 20 行，值得。

**没有做**：分块索引、每条的 CRC、压缩。理由 —— 单文件 100 KB 量级，
gzip 已在外面兜底；多一层索引只增加出错面。

## 4. 关键代码

### 4.1 `common/src/main/java/neko/voidwarehouse/WarehouseBlob.java`（纯逻辑，五版本共用）

只认 `byte[]` 与 `String`，**不碰任何 MC 类型**，所以能放进 `common/`。
「字节片段 ↔ 物品条目」的语义留给各版本 `VoidWarehouseData`。

```java
package neko.voidwarehouse;

import java.io.ByteArrayOutputStream;
import java.nio.charset.StandardCharsets;
import java.util.ArrayList;
import java.util.List;

/**
 * 虚空仓库的二进制容器：把「物品片段」与「配方文本」装进一段自描述字节。
 *
 * <h2>为什么不是 NBT</h2>
 * <p>物品那一条仍然是 NBT 片段（{@code ItemStack.CODEC} 的唯一稳定表示），
 * 但<b>容器</b>不能再是 NBT —— 因为 NBT 的字符串字段受 {@code writeUTF} 的 65535 字节限制，
 * 而配方本是「全部配方塞进一个字符串」，条数一多就写不出去（且是静默丢弃）。</p>
 *
 * <h2>容错原则</h2>
 * <p>本类<b>只负责切分</b>，不判断片段是否合法：长度前缀读完就交付，
 * 解析失败的片段由调用方原样保留、下次写回。所以一条坏数据永远不会牵连整份存档。</p>
 *
 * <h2>损坏输入的处置</h2>
 * <p>容器自身的边界一旦不可信（magic/版本不符、长度前缀越界、条数为负），
 * 一律抛 {@link CorruptException}，交给上层整份走兜底路径；
 * 绝不在这里「跳过坏片段」—— 按错误的长度往前读只会把后续数据全部错位成垃圾。
 * 所有长度比较都写成 {@code length > end - pos} 形式，避免 {@code pos + length} 的整数溢出。</p>
 */
public final class WarehouseBlob {

    private static final byte[] MAGIC = {'N', 'C', 'A', 'W'};
    private static final int FORMAT_VERSION = 1;
    private static final int HEADER = 4 + 1 + 1 + 4;   // magic + version + flags + payloadLength

    /** 预分配容量的上限：条数是外部输入，直接拿去 new ArrayList 会被损坏数据骗成 OOM */
    private static final int PRESIZE_CAP = 1024;

    private WarehouseBlob() {
    }

    /** 解码结果：两段原始数据，语义由调用方解释 */
    public record Raw(List<byte[]> itemFragments, List<String> recipes) {
        public Raw {
            itemFragments = List.copyOf(itemFragments);
            recipes = List.copyOf(recipes);
        }
    }

    public static byte[] encode(List<byte[]> itemFragments, List<String> recipes) {
        ByteArrayOutputStream payload = new ByteArrayOutputStream(1 << 16);
        writeVarInt(payload, itemFragments.size());
        for (byte[] frag : itemFragments) {
            writeVarInt(payload, frag.length);
            payload.write(frag, 0, frag.length);
        }
        writeVarInt(payload, recipes.size());
        for (String text : recipes) {
            byte[] utf8 = text.getBytes(StandardCharsets.UTF_8);
            writeVarInt(payload, utf8.length);
            payload.write(utf8, 0, utf8.length);
        }

        byte[] body = payload.toByteArray();
        ByteArrayOutputStream out = new ByteArrayOutputStream(HEADER + body.length);
        out.write(MAGIC, 0, MAGIC.length);
        out.write(FORMAT_VERSION);
        out.write(0);                      // flags（保留，恒 0）
        writeInt(out, body.length);
        out.write(body, 0, body.length);
        return out.toByteArray();
    }

    /**
     * 解出两段原始数据；magic / 版本不符或长度前缀越界时抛 {@link CorruptException}。
     */
    public static Raw decode(byte[] blob) {
        if (blob == null || blob.length < HEADER) {
            throw new CorruptException("blob 太短: " + (blob == null ? "null" : blob.length));
        }
        for (int i = 0; i < MAGIC.length; i++) {
            if (blob[i] != MAGIC[i]) {
                throw new CorruptException("magic 不符 @" + i);
            }
        }
        int version = blob[4] & 0xFF;
        if (version != FORMAT_VERSION) {
            throw new CorruptException("未知格式版本 " + version);
        }
        int payloadLength = readInt(blob, 6);
        // 减法的方向很关键：payloadLength 是 int，HEADER + payloadLength 会负溢出后放行
        if (payloadLength < 0 || payloadLength > blob.length - HEADER) {
            throw new CorruptException("payloadLength 越界: " + payloadLength
                    + " (可用 " + (blob.length - HEADER) + ")");
        }

        Cursor c = new Cursor(blob, HEADER, HEADER + payloadLength);

        int itemCount = c.readVarInt();
        if (itemCount < 0) {
            throw new CorruptException("物品条数为负: " + itemCount);
        }
        List<byte[]> items = new ArrayList<>(Math.min(itemCount, PRESIZE_CAP));
        for (int i = 0; i < itemCount; i++) {
            items.add(c.readBytes(c.readVarInt()));
        }

        int recipeCount = c.readVarInt();
        if (recipeCount < 0) {
            throw new CorruptException("配方条数为负: " + recipeCount);
        }
        List<String> recipes = new ArrayList<>(Math.min(recipeCount, PRESIZE_CAP));
        for (int i = 0; i < recipeCount; i++) {
            recipes.add(new String(c.readBytes(c.readVarInt()), StandardCharsets.UTF_8));
        }

        if (!c.atEnd()) {
            throw new CorruptException("payload 尾部多出 " + c.remaining() + " 字节");
        }
        return new Raw(items, recipes);
    }

    public static final class CorruptException extends RuntimeException {
        public CorruptException(String message) {
            super(message);
        }
    }

    // ------------------------------------------------------------------ varint / 游标

    private static void writeVarInt(ByteArrayOutputStream out, int value) {
        while ((value & ~0x7F) != 0) {
            out.write((value & 0x7F) | 0x80);
            value >>>= 7;
        }
        out.write(value);
    }

    private static void writeInt(ByteArrayOutputStream out, int value) {
        out.write((value >>> 24) & 0xFF);
        out.write((value >>> 16) & 0xFF);
        out.write((value >>> 8) & 0xFF);
        out.write(value & 0xFF);
    }

    private static int readInt(byte[] src, int offset) {
        return ((src[offset] & 0xFF) << 24)
                | ((src[offset + 1] & 0xFF) << 16)
                | ((src[offset + 2] & 0xFF) << 8)
                | (src[offset + 3] & 0xFF);
    }

    /** 只在 [pos, end) 里读，越界一律抛 —— 不做「宽容截断」 */
    private static final class Cursor {
        private final byte[] src;
        private final int end;
        private int pos;

        Cursor(byte[] src, int start, int end) {
            this.src = src;
            this.pos = start;
            this.end = end;
        }

        boolean atEnd() {
            return this.pos == this.end;
        }

        int remaining() {
            return this.end - this.pos;
        }

        int readVarInt() {
            int value = 0;
            int shift = 0;
            while (true) {
                if (this.pos >= this.end) {
                    throw new CorruptException("varint 读越界 @" + this.pos);
                }
                if (shift > 28) {
                    throw new CorruptException("varint 过长 @" + this.pos);
                }
                int b = this.src[this.pos++] & 0xFF;
                value |= (b & 0x7F) << shift;
                if ((b & 0x80) == 0) {
                    return value;
                }
                shift += 7;
            }
        }

        byte[] readBytes(int length) {
            // 写成减法：pos + length 在 length 接近 int 上限时会溢出成负数，从而放行
            if (length < 0 || length > this.end - this.pos) {
                throw new CorruptException("片段越界: len=" + length + " @" + this.pos
                        + " 可用 " + (this.end - this.pos));
            }
            byte[] out = new byte[length];
            System.arraycopy(this.src, this.pos, out, 0, length);
            this.pos += length;
            return out;
        }
    }
}
```

> 上面这份是**已编译并跑通**的版本（`C://tmp//blobtest`，JDK 25，53 条断言全绿）。
> 相对初稿改了三处，都是「损坏输入会把异常变成 OOM 或静默接受」这一级别的漏洞：
>
> | # | 原写法 | 问题 | 改法 |
> | --- | --- | --- | --- |
> | 1 | `HEADER + payloadLength > blob.length` | `payloadLength` 可达 `Integer.MAX_VALUE`，
> 相加负溢出后放行 | 改成 `payloadLength > blob.length - HEADER` |
> | 2 | `new ArrayList<>(itemCount)` | 损坏 varint 可解出 21 亿，直接 OOM 而**不是** `CorruptException`；
> 第 5 字节为 `0x0F` 时 `shift=28` 移位成负数，循环不执行而**静默当成 0 条** | 条数为负直接抛；
> 预分配容量封顶 `PRESIZE_CAP = 1024` |
> | 3 | `this.pos + length > this.end` | `length` 接近 int 上限时相加负溢出后放行 → OOM | 改成 `length > this.end - this.pos` |
>
> 另外补了「payload 尾部必须恰好读完」的校验（encode 从不产生尾巴字节，
> 长度声明之外的尾巴则有意忽略，给将来追加字段留余地）。
### 4.2 `VoidWarehouseData` 的改动（以 26.3 为样板）

**① `Decoded.Broken` 从 `Tag` 改成 `byte[]`**（这是 A1 的必要改动）

```java
private sealed interface Decoded {
    record Ok(RawEntry entry) implements Decoded { }

    /** 解析失败的**原始片段字节**，只为「原样写回」而留，不会进仓库 */
    record Broken(byte[] raw) implements Decoded { }
}
```

老格式那条路上，`ITEMS_CODEC` 拿到的是 `Tag`，需要在失败分支立刻转成字节：

```java
// ITEMS_CODEC 的列表解码循环里，parse 失败时：
ByteArrayOutputStream buf = new ByteArrayOutputStream();
NbtIo.write((CompoundTag) element, new DataOutputStream(buf));   // element 本来就该是 CompoundTag
builder.add(DataResult.success(new Decoded.Broken(buf.toByteArray())));
```

> ⚠️ `NbtIo.write` 对**超长字符串**会走 `writeUnnamedTagWithFallback` 静默降级 ——
> 但单个物品片段不可能有 64 KB 字段，这里安全。真正要防的是「元素根本不是 `CompoundTag`」，
> 那种情况直接产出 `Broken`（连字节都拿不到就丢一条，可接受）。

**② `CODEC` 改成「新格式优先、老格式兜底」**

```java
private static final String BLOB_KEY = "blob";

public static final Codec<VoidWarehouseData> CODEC = RecordCodecBuilder.create(instance -> instance.group(
        // 新格式：总是写；读的时候若存在就**独占**，老字段一概不看
        Codec.BYTE_BUFFER.optionalFieldOf(BLOB_KEY)
                .forGetter(VoidWarehouseData::encodeBlob),
        // 老格式：只读不写（getter 恒 empty ⇒ OptionalFieldCodec 不会写这个键）
        ITEMS_CODEC.optionalFieldOf(ITEMS_KEY)
                .forGetter(data -> Optional.<List<Decoded>>empty()),
        Codec.STRING.optionalFieldOf(RECIPES_KEY)
                .forGetter(data -> Optional.<String>empty())
).apply(instance, VoidWarehouseData::fromCodec));

private static VoidWarehouseData fromCodec(Optional<ByteBuffer> blob,
                                           Optional<List<Decoded>> legacyItems,
                                           Optional<String> legacyRecipes) {
    if (blob.isPresent()) {
        return fromBlob(blob.get());
    }
    // 老存档：两个字段都可能有、也可能都没有
    return new VoidWarehouseData(legacyItems.orElse(List.of()), legacyRecipes.orElse(""));
}
```

`CODEC` 的三字段结构保持不变的好处：**读的入口只有一个**（`computeIfAbsent` 走的还是同一个
`SavedDataType`），不需要在 `VoidWarehouse.data()` 里加"先试新格式再试老格式"的分支。

**③ 新增两个方法**

```java
private Optional<ByteBuffer> encodeBlob() {
    List<byte[]> frags = new ArrayList<>(this.entries.size() + this.brokenEntries.size());
    for (Entry entry : this.entries) {
        frags.add(writeFragment(entryToRawEntry(entry)));   // entry → RawEntry → NBT 字节
    }
    for (Decoded.Broken broken : this.brokenEntries) {
        frags.add(broken.raw());                            // 原样写回，不再解析
    }
    List<String> recipes = new ArrayList<>(this.recipeTexts);   // 保序：LinkedHashSet
    return Optional.of(ByteBuffer.wrap(WarehouseBlob.encode(frags, recipes)));
}

private static VoidWarehouseData fromBlob(ByteBuffer buffer) {
    byte[] bytes = new byte[buffer.remaining()];
    buffer.duplicate().get(bytes);
    WarehouseBlob.Raw raw;
    try {
        raw = WarehouseBlob.decode(bytes);
    } catch (WarehouseBlob.CorruptException ex) {
        // 容器本身坏了 —— 抛出去让 VoidWarehouse.data() 的空壳闸门接手（拒绝服务而不是清空）
        throw new IllegalStateException("虚空仓库二进制容器损坏: " + ex.getMessage(), ex);
    }
    List<Decoded> decoded = new ArrayList<>(raw.itemFragments().size());
    for (byte[] frag : raw.itemFragments()) {
        decoded.add(parseFragment(frag));       // 失败 ⇒ Broken(frag)，字节原样保留
    }
    return new VoidWarehouseData(decoded, String.join("\n", raw.recipes()));
}
```

**④ `brokenEntries` 的类型跟着改**：`List<Tag>` → `List<Decoded.Broken>`，写盘与计数逻辑同步。
`loadedBrokenCount()`、`isSuspiciouslyEmpty()` 的判据不变。

### 4.3 实测（2026-11-10，三套测试已跑通）

不是纸面推演：`WarehouseBlob` 已真编译、真跑往返，外加两套直接打在 26.3 的
`minecraft-merged.jar` + `datafixerupper-10.0.21` 上的验证。三套共 **90 条断言全绿**。

**测试环境**：JDK 25.0.4.1（`ms-25.0.4.1`），Windows；`WarehouseBlob` 是纯 JVM 类，
不需要启动游戏；`NbtEmbedTest` / `CodecShapeTest` 用 `javac -cp <merged jar + DFU + 依赖>` 直连编译运行
（classpath 拼装见 §7 第 1 步备注）。

| 套件 | 断言 | 覆盖内容 |
| --- | --- | --- |
| `BlobTest`（纯 JVM） | 53 | 往返 1/64/512/975/2048/5000 条、空输入、30 万字节单片段、UTF-8（中文/`×`/emoji/空串）、编码确定性、12 种损坏输入 |
| `NbtEmbedTest`（真 NBT） | 17 | `Codec.BYTE_BUFFER` → `ByteArrayTag` → `NbtIo.writeCompressed` → 读回 → 解容器；并复现单 String 的降级 |
| `CodecShapeTest`（真 CODEC） | 20 | 三字段 CODEC 的**写只写 blob / 读兼容老档 / blob 优先 / 全空 / 坏字段** |

**① 容器体积与 gzip 后的落盘体积**

| 配方条数 | 配方原文（UTF-8） | blob（含容器头） | 落盘（`NbtIo.writeCompressed`） | gzip 比 |
| --- | --- | --- | --- | --- |
| 512 | 31,634 B | 32,159 B | **1,463 B** | 22.0:1 |
| 2048 | 127,914 B | 129,975 B | **5,542 B** | 23.5:1 |
| 5000 | 313,890 B | 318,903 B | **13,135 B** | 24.3:1 |

容器自身的开销 = 129,975 − 127,914 ≈ **2 KB / 2048 条 ≈ 1.0 B/条**（每条一个 1 字节 varint 长度前缀）。
gzip 比 23.5:1 远好于早先整文件测出的 10.8:1 —— 因为配方文本高度重复，而那次测的是混着物品 NBT 的整档。
**结论：2048 条在磁盘上只要 5.4 KB，体积完全不是问题。**

**② 最关键的假设被证实**：16 万字节的 `ByteArrayTag` 能进 `CompoundTag`、能过
`NbtIo.writeCompressed`、能原样读回。5000 条（319 KB）同样通过。
`Codec.BYTE_BUFFER` 在 `NbtOps` 下确实落成 `ByteArrayTag`，长度字段是 int 语义，**不经过 `writeUTF`**。

**③ 顺手查清了「静默丢弃」的精确机理**（比原来的描述更准）：

26.3 的 `NbtIo` 里有个 `NbtIo$StringFallbackDataOutput`，`writeUTF` 的实现是：

```java
try {
    super.writeUTF(s);
} catch (UTFDataFormatException e) {
    Util.logAndPauseIfInIde("Failed to write NBT String", e);
    super.writeUTF("");            // ← 写一个空串进去
}
```

所以失败形态**不是「字段消失」，而是「字段还在、内容被换成空串」**。实测对照：
129,961 UTF-8 字节的配方串写盘后文件只有 **36 B**，回读 `recipes` 键**存在**、内容长度 **0**。
两个后果：

- 判据只能是「读回来还剩几条」，看「有没有这个键」会误判成正常。
- A1 迁移时若只加字段不删旧字段，老档 2048 条读到的是空串 ⇒ 静默变空仓库 ⇒ 必须靠下述 M6 的性质兜住。

**④ 迁移契约（`CodecShapeTest` 实测）**

| 场景 | 实测结果 |
| --- | --- |
| 写一个带 blob 的对象 | 落盘 compound 的键只有 `[blob]` —— 两个老字段**一个字节都不写** |
| 读老存档（`items`+`recipes`，无 `blob`） | 正常读出，走 legacy 分支 |
| 两者并存 | `blob` 优先，老字段忽略 |
| 全空 `{}` | 解出空壳（不报错）；回写时产出 **0 个键** |
| **老字段存在但格式错**（把 `items` 写成 `StringTag`） | **整份 decode 失败**：`Not a list: "这不是列表"` |

最后一条是必须记住的性质：`optionalFieldOf` **只容忍「缺失」，不容忍「存在但格式错」**。
这既说明空壳闸门在迁移事故里真的会拦住（不会静默清空再覆盖），
也说明**物品层「逐条宽容」的解码器一点都不能动** —— 一旦某个条目解析失败就让整份 decode 失败，
一个坏条目就会把整个仓库变成「拒绝服务」。

## 5. 兼容与迁移

| 场景 | 行为 |
| --- | --- |
| 老存档 `{items, learned_recipes}` | `blob` 缺失 ⇒ 走 `new VoidWarehouseData(items, recipes)`，与现在**逐字节等价** |
| 老存档读入后第一次写盘 | 写 `{blob}`，老字段不再产出 ⇒ **自动升级，无迁移命令** |
| 新存档被老版本 mod 读 | 老 codec 只认 `items`/`learned_recipes` ⇒ 读到空仓库 ⇒ 空壳闸门拦下（拒绝服务），**不会覆盖** |
| 新存档损坏（magic/长度越界） | 抛异常 ⇒ 空壳闸门拒绝服务 + `.bak` 可回退；**绝不静默清空** |
| 单条物品片段坏了 | `Broken(byte[])` 原样保留，下次写回 |

**唯一的破坏性一步**是「首次写盘升级」。因此实施时要：

1. 升级前保证 `.bak` 已生成（现有 `backupOnce` 已经做了，确认它在新路径上仍然执行）。
2. 首次写出新格式时**打一条 INFO 日志**（`存储格式已升级到 v2`），方便排障时判断存档属于哪一代。

**降级不保证**。这不比现状更差 —— 现在的存档同样绑 mod 版本。

## 6. 自检断言（验收清单）

全部走"真服务端 + 直接构造"的路线（`VoidWarehouseData.CODEC` 是 public）。

| # | 断言 | 通过判据 | 现状 |
| --- | --- | --- | --- |
| B1 | 往返一致（512 条） | encode → decode → 条目数、每个物品 id、每个数量（含 `10^30`）逐条相等 | 容器层 ✅（`BlobTest`）；`10^30` 属既有 `AMOUNT_CODEC`，不属本次改动 |
| B2 | **2048 条能存**（核心） | 往返后 `learnedRecipeCount() == 2048`；这是现在做不到的 | ✅ 已证（2048 / 5000 条穿过真 `NbtIo` 往返一致） |
| B3 | 5000 条也能存 | 同上（证明只受内存限制） | ✅ 已证（319 KB blob 往返一致） |
| B4 | 坏片段保留 | 手工拼一条非法 frag → decode 不抛、`loadedBrokenCount()==1` → 再 encode 后该字节序列仍在 | 容器层 ✅（只切分、不判断片段合法性）；`Broken` 链待接 |
| B5 | 老存档兼容 | 构造 `{items:[...], learned_recipes:"..."}` → 读出的仓库与直接用 `new VoidWarehouseData(...)` 完全一致 | ✅ CODEC 层已证（`CodecShapeTest` M3）；实体层待接 |
| B6 | 老→新自动升级 | B5 的实例 `encode` 后只有 `blob` 键、没有 `items`/`learned_recipes` | ✅ 已证（落盘 compound 的键只有 `[blob]`） |
| B7 | 空存档 | `{}` → 空仓库 → 往返仍空，且 `isSuspiciouslyEmpty()` 行为不变 | ✅ CODEC 层已证（解出空壳、回写 0 键）；闸门待接 |
| B8 | 容器损坏 | 篡改 magic / payloadLength → 抛 `IllegalStateException`（**不是**返回空仓库） | ✅ 容器层已证（12 种损坏输入全抛 `CorruptException`，无一 OOM） |
| B9 | 数量精度 | `123456789012345678901234567890` 往返不丢 | 容器层 ✅（字节原样，不解释数值）；数值编解码沿用既有 `AMOUNT_CODEC` |
| B10 | 五版本一致 | 同一份 `WarehouseBlob` 在 26.3 / 26.2 / 26.1.2 / 26.1.1 / 1.21.11 产出的 blob **逐字节相同**（拿同一批片段比对 md5） | 待做（源码只放 `common/` 一份，风险低） |

**反证**（证明断言真的咬住代码，不是摆设）：

- 把 `WarehouseBlob.encode` 的长度前缀从 varint 改成 `short` → B2/B3 必须翻红（超 65535）。
- 把 `fromBlob` 的 `Broken` 分支改成"直接丢弃" → B4 必须翻红。
- 把 `BLOB_KEY` 的 getter 改成 `Optional.empty()` → B6 必须翻红。
- 把长度校验改回 `HEADER + payloadLength > blob.length`（负溢出）→ B8 必须翻红（实测表现为 OOM 或报错位置错乱）。
- 去掉条数负数检查、直接 `new ArrayList<>(itemCount)` → B8 必须翻红（损坏 varint 可解出 21 亿条，当场 OOM）。

## 8. 代价与风险（要认下来的）

**代价**

1. **存档不可读**：现在 `void_warehouse.dat` 解 gzip 后是能直接看的 NBT 文本结构，改完是一段二进制。
   排障要靠工具（建议顺手写一个 `VoidWarehouseDump`：读 blob → 打印 `物品 id × 数量` 清单）。
2. **与 NBT 生态脱钩**：`DataFixer` 只能修外层包装，内层语义迁移全靠 `formatVersion` 自己分支。
3. **体积收益有限**：容器开销实测 ≈ **1.0 B/条**，2048 条配方 blob 129,975 B，gzip 后落盘仅 **5,542 B**。
   换成二进制并没有让存档变小多少。**真正的收益是上限，不是体积** —— 别把这条当成优化项去汇报。
4. **A2 能覆盖 90% 的需求，只要 1/3 的工作量**。选 A1 的理由应该是"以后还要往里加字段"，
   而不是"现在要解 65535"。

**风险**

| 风险 | 缓解 |
| --- | --- |
| 容器写坏 = 整仓丢失 | 长度前缀 + 边界检查全部抛异常（不宽容截断）；`.bak` + 空壳闸门兜底 |
| 首次升级写坏 | 升级前强制 `.bak`；升级后打 INFO 日志；自检 B6 覆盖 |
| 五版本不一致 | `WarehouseBlob` 放 `common/` 只写一份；B10 用同一批片段比 md5 |
| 老版本 mod 读新存档 | 空壳闸门拦下（拒绝服务而非清空），行为可接受 |

---

## 9. 一句话结论

A1 能彻底解决 65535，且只改"容器"一层，物品编码与全部现有语义（坏条目保留、空壳闸门、`.bak`）
都不动。代价是存档变二进制、迁移链自管、约 3 天工作量。

**如果目标只是让配方本超过 975 条，A2（分片）是更划算的选择；A1 的价值在"以后不再为存储格式返工"。**
