# 虚空仓库存储改造 A2：配方本逐条拆分（`List<String>` + 宽容 codec）

> 目标只有一件事：**让配方本能超过 975 条**。
> 不做二进制容器、不换物品编码、不动写盘时机 —— 那三条是 A1 的事，A1 的文档是
> `虚空仓库存储-A1二进制容器方案.md`（**已被本文取代**）。
>
> **状态：已实装并验证完毕**（26.3 真服务端 27 条断言 + 209 条系统回归全绿，五版本构建通过）。

---

## 1. 为什么是 A2 不是 A1

975 这个天花板与「性能」「体积」都无关，只和一个字段的编码方式有关：

- 配方本存在 `learned_recipes` 里，历史实现是**全部配方用 `'\n'` 拼成一个 `String`**。
- `StringTag` 走 `DataOutputStream#writeUTF`，上限 **65,535 字节**（数的是 modified UTF-8）。
- 实测边界：975 条 = 65,512 B 通过 / 976 条 = 65,596 B 超限（平均 67.2 B/条）。
- 超限后 `NbtIo$StringFallbackDataOutput.writeUTF` 会 catch 掉 `UTFDataFormatException`，
  打一行日志，然后 **`super.writeUTF("")`** —— 键还在，内容变成空串，回读 0 条。

所以问题只有一句话：**别把整本配方塞进一个 NBT 字符串**。

A1 的答案是「换一个自描述二进制容器」，能顺带解决「以后还要加字段」。但代价是
200 行容器代码 + varint + magic + 版本号 + 边界算术（我在实现 A1 时实测撞出三处
int 溢出漏洞，全在「损坏输入本该抛异常，结果 OOM 或直接放行」这一档）。

A2 的答案是「**一条配方一个元素**」：`ListTag` 的元素计数是 `int`，单个元素只有几十字节，
65535 这个限制<b>根本碰不到</b>。唯一要自己写的，是一个<b>逐元素宽容</b>的
`Codec<List<String>>`（因为 `Codec.STRING.listOf()` 是「全成或全不成」，会把整仓拖成空壳）——
**80 行，零边界算术**。

两者在磁盘上的差别可以忽略（见 §4 ③）：2048 条时 **5,604 B vs 5,542 B，差 62 字节（1.1%）**。

## 2. 格式

```
CompoundTag:
  items                   ListTag   不变
  learned_recipes_lines   ListTag   新增：一条配方一个 StringTag
  learned_recipes         String    旧格式残留，只读不写（读老存档用）
```

一条元素长这样（就是原来的「配方行」，只是不再拼成一个大字符串）：

```
minecraft:iron_ingot*1;minecraft:iron_ore×1
```

**为什么一行一个元素，而不是「N 行一个分片」**：

| 方案 | 坏一格的代价 | 元素数 | 额外开销 |
| --- | --- | --- | --- |
| 一行一个元素 | 只丢这一条配方 | 2048 | 每条 2 字节长度前缀 ≈ 4 KB |
| 128 行一个分片 | 丢掉整个分片（128 条） | 16 | ≈ 32 字节 |

故障隔离严格更好，开销差 4 KB（gzip 之后不到 200 字节）。选一行一个。

**注意 `ListTag` 里每个元素仍然走 `writeUTF`** —— 但那是「单个配方行」，几十字节。
真正的风险变成了「有没有人手工往存档里塞一条 7 万字节的行」，由
`RecipeLinesCodec` 的写盘侧拦住（见 §3 的 `MAX_LINE_BYTES`）。

## 3. 关键代码

### 3.1 `RecipeLinesCodec`（新增，五版本各一份，逐字节相同）

```java
public final class RecipeLinesCodec {

    /** 单个元素允许的最大 UTF-8 字节数，writeUTF 的硬上限是 65535 */
    private static final int MAX_LINE_BYTES = 60_000;

    public static final Codec<List<String>> CODEC = new Codec<>() {

        @Override
        public <T> DataResult<Pair<List<String>, T>> decode(DynamicOps<T> ops, T input) {
            // getList 失败 = 顶层不是列表 -> 整个 decode 失败（有意为之，见类注释）
            return ops.getList(input).map(consumer -> {
                List<String> lines = new ArrayList<>();
                consumer.accept(element ->
                        ops.getStringValue(element).result().ifPresent(lines::add));
                return Pair.of(List.copyOf(lines), input);
            });
        }

        @Override
        public <T> DataResult<T> encode(List<String> input, DynamicOps<T> ops, T prefix) {
            ListBuilder<T> builder = ops.listBuilder();
            for (String line : input) {
                if (line == null) {
                    continue;
                }
                if (line.getBytes(StandardCharsets.UTF_8).length > MAX_LINE_BYTES) {
                    // 写出去也会被静默换成空串，不如不带
                    continue;
                }
                builder.add(ops.createString(line));
            }
            return builder.build(prefix);
        }
    };
}
```

三点设计：

1. **逐元素解析**：`ops.getStringValue(element).result().ifPresent(...)` —— 读不出来的元素
   **跳过它自己**，整体永远成功。这就是绕开 `Codec.STRING.listOf()` 的唯一目的。
2. **顶层类型错时不宽容**：`ops.getList(input)` 失败就直接失败，交给
   `VoidWarehouse.data()` 的空壳闸门拒绝服务。宁可让服主看到明确错误，
   也不能把「整本配方凭空消失」伪装成一次正常读档。
3. **零 MC 类型**：只用 DFU + `java.*`，所以 1.21.11（混淆映射）那份与 26.3 逐字节相同
   （md5 `c49cc642433412601ff75e880b27981f`，五份一致）。

### 3.2 `VoidWarehouseData` 的改动

**① 字段名**：新增 `learned_recipes_lines`，`learned_recipes` 降为「只读不写」。

**② `CODEC` 三字段**（新格式优先、老格式兜底）：

```java
public static final Codec<VoidWarehouseData> CODEC = RecordCodecBuilder.create(instance -> instance.group(
        ITEMS_CODEC.optionalFieldOf(ITEMS_KEY, List.of())
                .forGetter(VoidWarehouseData::decodedEntries),
        // 新格式：一条配方一个元素
        RecipeLinesCodec.CODEC
                .optionalFieldOf(RECIPES_LINES_KEY)
                .forGetter(VoidWarehouseData::recipeTextsLines),
        // 旧格式：只读不写（getter 恒 empty ⇒ OptionalFieldCodec 一个字节都不写这个键）
        Codec.STRING
                .optionalFieldOf(RECIPES_KEY)
                .forGetter(data -> Optional.<String>empty())
).apply(instance, VoidWarehouseData::fromCodec));

private static VoidWarehouseData fromCodec(List<Decoded> items,
                                           Optional<List<String>> recipeLines,
                                           Optional<String> legacyRecipeBlob) {
    if (recipeLines.isPresent()) {
        return new VoidWarehouseData(items, recipeLines.get());
    }
    return new VoidWarehouseData(items, legacyRecipeBlob.orElse(""));
}
```

**③ getter 返回 `Optional`**，空配方本 ⇒ 不写这个键（新档更干净，也省得区分「从没学过」和「学了又清空」）：

```java
private Optional<List<String>> recipeTextsLines() {
    if (this.recipeTexts.isEmpty()) {
        return Optional.empty();
    }
    return Optional.of(List.copyOf(this.recipeTexts));
}
```

**④ 构造器分裂成两个**：`(List<Decoded>, List<String>)` 是当前格式；
`(List<Decoded>, String)` 只留给老存档，内部 `this(loaded, splitLegacyBlob(blob))` 转过去。
`recipeTexts` 仍是 `LinkedHashSet<String>`（文本即标识，去重与存储是同一件事），一行没动。

**⑤ `MAX_RECIPES` 512 → 2048**，且撞上限时补一条 WARN：

```java
if (this.recipeTexts.size() >= VoidWarehouseRecipeBook.MAX_RECIPES) {
    if (!this.capWarned) {
        this.capWarned = true;
        LOGGER.warn("虚空仓库配方本已满（上限 {} 条），新配方不再记录。...",
                VoidWarehouseRecipeBook.MAX_RECIPES, this.recipeTexts.size());
    }
    return false;
}
```

> 原来撞上限是**彻底静默**的（`CraftResultMixin` 丢弃 `learn()` 的返回值），
> 玩家只会觉得「怎么合成过它还是不能从仓库取」。满本是持续状态，所以只报第一次。

## 4. 实测

三套测试，共 **271 条断言**（35 + 27 + 209），全部通过。

| 套件 | 断言 | 跑在哪 | 结果 |
| --- | --- | --- | --- |
| `A2CodecTest` | 35 | 纯 JVM + 真 `NbtIo`（不启动游戏） | 全绿 |
| `A2StorageSelfCheck` | 27 | **真服务端**（`runServer`，跑完 `halt`） | `failures=0` |
| `SystemTest`（既有） | 209 | 真服务端 | `failures=0`（无回归） |

**① 反证：旧格式确实会静默丢内容**

把一条 70,000 字节的字符串用 `NbtIo.write` 写盘，落盘文件只有 **10 字节** ——
内容被 `StringFallbackDataOutput` 换成空串了，键还在。
所以判据只能是「读回来还剩几条」，看「有没有这个键」会误判成正常。

**② 容量：2048 与 5000 都过得去**

| 配方条数 | 配方原文 UTF-8 | NBT 未压缩 | 落盘（gzip） | 压缩比 |
| --- | --- | --- | --- | --- |
| 2048 | 127,914 B | 132,010 B | **5,604 B** | 23.6:1 |
| 5000 | 313,890 B | 323,890 B | **13,225 B** | 24.5:1 |

**③ 与 A1 的对比（同样 2048 条、同样语料）**

| 方案 | NBT 未压缩 | 落盘 | 代码量 | 边界算术 |
| --- | --- | --- | --- | --- |
| A1 二进制容器 | 129,975 B | 5,542 B | ~200 行 + varint/CRC 类 | 有三处 int 溢出坑 |
| **A2 逐条拆分** | 132,010 B | **5,604 B** | **80 行** | **零** |
| 差 | +2,035 B | **+62 B（1.1%）** | −60% | — |

结论很清楚：**只为解 975 的话，A1 多出来的复杂度换不到任何东西。**

**④ 真服务端（`A2StorageSelfCheck`）**

- 学满 2048 条：**439 ms / 489 ms**（两次跑，O(N²) 的 `rebuildRecipes` 累计代价）
- 落盘键：`{learned_recipes_lines, items}` —— 老键一个字节都没写
- 2048 条真写盘 **5,379 B** / 未压缩 74,777 B（13.9:1；测试配方行较短，所以比 ② 低）
- 读回 **2048 条**，首尾抽查都在，物品（圆石 5 个）没被牵连
- 老存档（`learned_recipes` 单串，975 条）读得出来、升级后只写新键、再写再读仍 975 条
- 空配方本 ⇒ 落盘 **0 个键**
- 把列表第 0 个元素换成 `IntTag` ⇒ 解码仍成功，**只少那一条**，其余与物品全在

最后一条是 A2 的核心价值：换成 `Codec.STRING.listOf()` 的话，同一个输入会
`Not a string` 整体失败。

## 5. 兼容与迁移

| 场景 | 行为 |
| --- | --- |
| 老存档 `{items, learned_recipes}` | `learned_recipes_lines` 缺失 ⇒ 走 legacy 分支，按 `'\n'` 拆开，与以前逐行等价 |
| 老存档读入后第一次写盘 | 只写 `learned_recipes_lines` ⇒ **自动升级，无迁移命令、服主无感** |
| 两者并存 | 新格式优先（升级途中崩溃 / 用备份回滚过都会出现这个中间态） |
| 新存档被老版本 mod 读 | 老 codec 只认 `learned_recipes` ⇒ 读到空配方本（物品照旧） ⇒ 空壳闸门拦下，不覆盖 |
| 列表里某元素类型错 | 只丢那一条，其余照常（§4 ④ 最后一条） |
| 整个字段类型错（被改成字符串） | 整份 decode 失败 ⇒ 空壳闸门拒绝服务 + `.bak` 可回退，**绝不静默清空** |

**降级不保证** —— 与 A1 一致，也和现状一致（存档本来就绑 mod 版本）。

> ⚠️ **踩到的坑**：`modern/26.2`、`26.1.2`、`26.1.1`、`versions/1.21.11` 这四份
> `VoidWarehouseData.java` 在**仓库里提交的就是 `\r\r\n`（双 CR）**。任何「读出来
> `replace('\r\n','\n')` 再改再写回」的脚本都会在下一行留下一个孤立的 `\r`，锚点匹配全灭。
> 正确姿势：`raw.replace('\r','')` 归一，写回时按探测到的原 EOL 还原。
> 26.3 那份是干净的 `\r\n`。

> ⚠️ **第二个坑**：新建的 `RecipeLinesCodec.java` 默认是 **LF**，而同目录所有既有
> `.java` 都是 CRLF。`core.autocrlf=true` 会把库里存的 LF 在 checkout 时变 CRLF，
> 所以「工作区 LF」与「别人 clone 出来的 CRLF」**内容相同、字节不同** —— git diff
> 看不出来，但 `-sources.jar` 会不一样。收尾时统一转成 CRLF 再重建，五份 md5 才算真的可复现。

## 8. 代价与风险

**代价**

1. **存档里多一个 `ListTag` 的壳**：一条一个元素比 A1 的稠密 blob 多 2 KB（136 字节/条 → 2 字节/条加上元素头）。
   gzip 后只差 62 字节。**可以忽略。**
2. **`learned_recipes` 这个键在升级后消失**。想回滚到老版本 mod 的话配方本会空。
   但 `learned_recipes_lines` 里条数可能超过 975，老版本本来也装不下。
3. **仍写着 512 时代的那条告警语义**：现在撞 2048 才告警，且只告警一次。

**风险**

| 风险 | 缓解 |
| --- | --- |
| 某元素类型坏 | 宽容 codec 跳过它自己（A5 已证） |
| 顶层字段类型坏 | 整份失败 ⇒ 空壳闸门拒绝服务 + `.bak`（A6/M6 已证） |
| 单行超 6 万字节 | 写盘侧丢弃（正常配方行到不了） |
| `learn()` 的 O(N²) | 2048 条累计 439 ms，一次性代价；真要再放宽得先改增量重建 |

**没做、也不打算做的**：把 `learn()` 的 `rebuildRecipes()` 从「整本重解」改成增量。
理由是 2048 条的上限已经覆盖现实需求（原版约 1500 条），而增量重建要维护
`recipes` / `recipesByOutput` / `recipeGeneration` 三者的一致性，改动面比收益大。
真要支持 5000 条以上，先改这段。

---

## 9. 一句话结论

**A2 = 一条配方一个 NBT 字符串 + 80 行宽容 codec。** 975 的天花板没了，
磁盘上只比 A1 胖 62 字节（1.1%），代码量只有 A1 的四成，没有一处边界算术。
2048 条在真服务端学满、写盘、重启读回全通，209 条既有断言零回归，五版本构建通过。
