# 虚空仓库对「原版漏斗」的影响审计

> 结论先说：**除了「正对着入库漏斗的那一个上游容器」之外，原版漏斗一个字节都没被动过。**
> 且那唯一的例外是「无上限吸取」这个功能本身的固有语义（Carpet-TIS 的
> `hopperCountersUnlimitedSpeed` 也是同样行为），**物品一分不少**。

审计日期 2026-09-30，针对 26.3 分支。全部数据来自真实 `runServer` 实测，不是推断。

---

## 一、审计方法

判据只有一个数字：**100 个服务端 tick 里搬了几次**。

| 情况 | 预期值 |
|---|---|
| 原版（8 gt 一次） | 约 **12~13 次** |
| 被误加速（每 tick 一次） | 约 **100 次** |

两者**相差一个数量级**，不可能认错。每个场景都是「布景 → 空等 100 tick → 读结果」，
中间不做任何手工调用，全部由服务端自然 tick 驱动，所以测到的是真实行为。

自检代码：`VanillaParitySelfCheck.java.template`
运行方式：复制进源码树 + 在 `VoidWarehouseExtension#onTick` 挂一行 `VanillaParitySelfCheck.run(server)`。

---

## 二、静态审查：所有注入点的放行条件

`HopperBlockEntityMixin` 一共 6 处注入，逐个核对 jakarta **`javap` 实测签名**（不是猜的）：

| 注入方法 | 真实签名 | 放行条件 | 对原版漏斗 |
|---|---|---|---|
| `pushItemsTick` HEAD | `(Level, BlockPos, BlockState, HopperBlockEntity)` | 规则关 / 非服务端 / 红石锁存 / **不是入库也不是出料** → 直接 return | 不碰 |
| `pushItemsTick` TAIL | 同上 | **仅** `isIntake` 成立才清零 `cooldownTime` | 不碰 |
| `canPlaceItemInContainer` HEAD | `(Container, ItemStack, int, Direction)` | 不是漏斗实体 / **标记没开** / 不是入库漏斗 → 直接 return | 不碰 |
| `ejectItems` HEAD | `(Level, BlockPos, HopperBlockEntity)Z` | **仅** `isExtractor` 成立才接管 | 不碰 |
| `saveAdditional` TAIL | — | 仅标记打开时才写 NBT | 见 §五 |
| `loadAdditional` HEAD | — | 只读一个布尔，`@Unique` 字段赋值 | 无副作用 |

`require` 配置：`defaultRequire: 1`，只有私有静默方法 `canPlaceItemInContainer` 显式写了
`require = 0`（它将来被内联时宁可功能静默失效，也不要服务器崩）。

其余 mixin（`SlotMixin`、`ServerPlayerGameModeMixin` 等）见 §五。

## 三、实测结果（连跑两轮，数字完全一致）

> **2026-09-30 复核更新**：C 组的数字从「100 tick 抽走 114 个」变成了
> 「100 tick 净进账 320 个（上游的全部）」。原因是当时「上方容器 → 漏斗」这条路径
> 因为 `addItem` 的 source / destination 参数写反而**基本没在工作**，
> 那 114 个全靠原版 `suckInItems` 在搬。详见
> `docs/入库漏斗上方容器吸取速率事故与性能测试.md`。
> 结论方向不变，只是「唯一的差异」比当时测出来的更大。

```
PACE A 普通漏斗→箱子              100 tick 搬了 13 次   ← 精确原版（100/8 = 12.5）
PACE B 普通漏斗吸掉落物            100 tick 搬了  7 次   ← 远低于每 tick，节流仍在
PACE C 入库漏斗的上游普通漏斗      100 tick 抽走 320 个（全抽空）← 唯一的差异，见 §四
DIAG-D 红石锁存                    箱子里 0 个，ENABLED=false  ✓
PACE E 带分类物标记的普通漏斗      100 tick 搬了 13 次   ← 标记不影响速率
DIAG-F 规则关闭                    上游失去 26 个         ← 原版两漏斗串联的双向流失
PACE G 普通漏斗 cooldownTime > 0                        ✓ 原版节流确实还在

SMOKE RESULT vanilla_parity/26.3 checks=16 failures=0
```

逐条说明：

- **A = 13 次**，与理论值 12.5 完全吻合 → 漏斗的 8 gt 节流**一丁点没被改动**。
- **B = 7 次**：小于 13 是因为掉落物是临时生成、头几 tick 才进实体段；
  关键是 **远低于 100**，说明掉路物吸取路径也照旧按 8 gt 走。
- **D = 0 次**：相邻放红石块后漏斗 `ENABLED=false`，一下都没搬。
  （第一版用例用 `setBlock` 直接写 `ENABLED=false` 是**无效的** —— 邻居更新会把它算回 true，
  那是原版行为，不是模组问题；改用真红石块才是玩家的实际操作方式。）
- **E = 13 次**：`SlotMixin` 会给任何被玩家手动放东西的漏斗打一个分类物标记，
  但**标记只在入库漏斗上生效**，普通漏斗带标记跑起来与不带毫无区别。
- **F = 26 次**：规则关掉后，原本的「入库漏斗」彻底退回普通漏斗。
  26 ≈ 13 × 2，正是原版语义 —— 上游自己往下推 13 次，**下游漏斗还会反过来从上游吸 13 次**。
- **G**：直接反射读 `cooldownTime`，普通漏斗 `> 0`（节流在），入库漏斗被清零（我们刻意做的）。

## 四、唯一的差异：入库漏斗会全量抽取「正上游的容器」

### 现象

| 场景 | 上游普通漏斗 100 tick 内失去的物品数 |
|---|---|
| 规则开启（下游是入库漏斗） | **320 个（全部）** |
| 规则关闭（下游是普通漏斗） | 26 个 |

（2026-09-30 复核前的数字是 114 / 26 —— 当时这条路径因参数写反而几乎没在工作，
见本文件 §三的更新说明与 `docs/入库漏斗上方容器吸取速率事故与性能测试.md`。）

### 这不是「上游漏斗被加速了」

关键实测证据：

```
DIAG-C 上游普通漏斗自己的 cooldown = 0     ← 它自己已经没活可干（被下游抽空了）
DIAG-C 仓库这 100 tick 净进账 320（上游 320 全部进库，路上 0）  ← 一分没丢
```

**上游漏斗自己的行为一个字节都没改** —— 它之所以冷却停在 0，是因为它**没机会搬**：
下游的入库漏斗每 tick 主动把它抽空了，`tryMoveItems` 一路返回 false，冷却自然递减到 0。
（注意：不能拿这个值去断言「节流还在」；「上游漏斗有没有被改节拍」由 A / E 两组负责证明，
那里没有入库漏斗参与，实测 13 次 = 精确原版。）
多出来的部分是**下游那个入库漏斗主动来"抢"的** —— 正是「无上限吸取」的定义：

```
intake() 每 tick 做一次全量清扫：
  ① drain()              把漏斗里剩的搬进仓库
  ② suckUnlimited(上方)   一次性把上游容器-尽量吸满漏斗
  ③ drain()              当场再搬进仓库
```

### 影响面

只有**正对着入库漏斗入料方向的那个容器**会被全量抽取，包括：

- 正上方的箱子 / 漏斗 / 运输矿车；
- 任何其他**被入库漏斗从这一面吸得到的容器**。

也就是只有「漏斗口朝向」以外的那一面（入料面）上的容器会被全量抽取。

**不受影响**（已实测）：入库漏斗侧面的漏斗、下游方向的漏斗、完全无关的普通漏斗。
`A`、`E` 两组就是这类「无关普通漏斗」的对照组，都是精确的 13 次。

### 要不要改？

这是设计使然，且与 Carpet-TIS `hopperCountersUnlimitedSpeed` 语义一致 ——
「无上限」本来就是指「**相邻容器**的吞吐不受 8 gt 限制」。
如果你希望「只加速掉落物、保留原版容器吸取速率」，那需要额外加一条规则开关，可以另做。

## 五、两处「无害但你应该知道」的副作用

### ① 普通漏斗的 NBT 会多一个字节

玩家**手动**往任意漏斗里放东西时，`SlotMixin` 会给它打上
`CarpetNekoAdditionClassifierFilter: 1b` 标记（@Unique 字段，跟方块实体一起存盘）。

- **行为影响**：无。该标记只有在「口朝向终端」的漏斗上才被读取。
- **存档影响**：卸载本模组后该标签丢失，无任何兼容性问题。
- **为什么不只在入库漏斗上打**：因为「玩家先往漏斗里放东西、之后才在旁边建终端」
  是很自然的搭建顺序，限制太早会让这个场景失效。

### ② 手持「虚空仓库」右键漏斗会打开仓库界面

`ServerPlayerGameModeMixin#useItemOn` 的 HEAD 会在以下任一条件成立时接管右键：

1. 点的是终端（已改名的工作台）；
2. 点的是「接了漏斗的工作台」；
3. **手里拿着改名为「虚空仓库」的工作台物品**。

第 3 条意味着手里拿着那个物品时，右键任意方块（**包括漏斗**）都会打开仓库界面
而不是漏斗界面。**规避方式：按住潜行再右键**（这条原版语义被显式保留了 ——
`player.isSecondaryUseActive() && !stack.isEmpty()` 时直接放行）。
