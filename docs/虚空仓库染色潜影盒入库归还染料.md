# 虚空仓库：染色潜影盒入库时没归还染料

> 2026-10-02 · 玩家报的第二个问题（同一轮里还删掉了潜影盒模式开关上的一行换算，见文末）

## 现象

往虚空仓库里丢（或漏斗送）一个**装着东西的染色潜影盒**，盒子被拆开后，
仓库里只多了 `2 个潜影壳 + 1 个箱子`，**那个用来给盒子染色的染料消失了**。

无色盒不受影响（它本来就没有染料这一项）。

## 为什么会这样

仓库对潜影盒的定位是「打包单位」：**存进来就拆成原料，取出去再按原料现造一个盒子**
（`VoidWarehouseShulker`）。拆包写在 `VoidWarehouseData#unpackShulkerBox` 里，原来只有两行：

```java
this.put(new ItemStack(Items.SHULKER_SHELL, VoidWarehouseShulker.SHELL_COST));  // 2 个潜影壳
this.put(new ItemStack(Items.CHEST, VoidWarehouseShulker.CHEST_COST));          // 1 个箱子
```

这两行对应的是**无色潜影盒**的原版配方，也正因如此，早期写的时候「能认出染色盒」
（`isShulkerBox` 用 `BlockItem + ShulkerBoxBlock` 反查，天生覆盖 16 色）和
「按配方归还原料」被当成了同一件事 —— 其实不是。

染色盒在原版里有**两步**合成：

```
4 个潜影壳 + ...            → 潜影盒       （实际上：2 潜影壳 + 1 箱子 = 无色潜影盒）
无色潜影盒 + 1 个对应染料    → 染色潜影盒
```

所以一个红盒的正确拆解是 `2 潜影壳 + 1 箱子 + 1 红色染料`。少还那个染料，
等于**玩家每存一次染色盒就凭空亏一个染料** —— 而仓库对外承诺的恰恰是
「拆开 = 逆向合成，严格守恒」。

## 修法

在 `VoidWarehouseShulker` 里加两个方法，把「认颜色」和「颜色→染料」收在同一个类里：

```java
/** 这个盒子的颜色；无色盒返回 null */
public static DyeColor colorOf(ItemStack box)      // 从方块反查：ShulkerBoxBlock#getColor()

/** 拆解这个盒子时应当归还的染料（无色盒返回 EMPTY） */
public static ItemStack dyeOf(ItemStack box)
```

`unpackShulkerBox` 里补上（无色盒拿到的是 `EMPTY`，直接跳过）：

```java
ItemStack dye = VoidWarehouseShulker.dyeOf(box);
if (!dye.isEmpty()) {
    this.put(dye);
}
```

空染色盒走的是另一条路（**整盒入库、不拆**），所以颜色原样保留在仓库里，不用特殊处理。

## 一个必须记下来的版本差异

**26.2 起，16 种染色物品被统一收进了 `ColorCollection`；26.1.x 和 1.21.11 还是 16 个独立字段。**

| 版本 | 染料 | 写法 |
|---|---|---|
| 26.3 / 26.2 | `Items.DYE` 是 `ColorCollection<Item>` | `Items.DYE.pick(color)` |
| 26.1.2 / 26.1.1 / 1.21.11 | 16 个独立 `Item` 字段 | `Items.WHITE_DYE` … `Items.BLACK_DYE`（用 `switch` 列） |

`javap` 实证（26.x 未混淆，直接读 jar）：

```
26.3  Items:  ColorCollection<Item> DYE;  ColorCollection<Item> DYED_SHULKER_BOX;
26.2  Items:  ColorCollection<Item> DYE;  ColorCollection<Item> DYED_SHULKER_BOX;
26.1.1 Items: Item WHITE_DYE; … Item BLACK_DYE;        ← 16 个，没有 ColorCollection
26.1.2 Items: Item WHITE_DYE; … Item BLACK_DYE;        ← 同上
```

同一件事在 `VoidWarehouseNav` 上也露过头：占位符用的红色染色玻璃片，
26.3 是 `Items.STAINED_GLASS_PANE.red()`，26.1.x 是 `Items.RED_STAINED_GLASS_PANE`。
（那份文件里本来就写着这条差异，这次正好印证了它不是孤例。）

> 教训：**「这个 API 在这个版本叫什么」不能用别的版本的名字去猜。**
> 26.1.x 和 26.2 只差一个小版本，`Items` 的形态就变了。

## 自检（真实 26.3 服务端，`checks=75 failures=0`，连跑两次一致）

重点不是「有染料入库了」（那只证明写了一行 `put`），而是**颜色对不对**：

```
16 种颜色逐个校验：red_shulker_box → red_dye、light_gray_shulker_box → light_gray_dye …
16 个染色盒（每个装 10 泥土）→ 泥土 160 + 潜影壳 32 + 箱子 16 + 16 种染料各 1
装满 27 组圆石的红色盒 → 圆石 1,728 + 2 壳 + 1 箱 + 1 红染料，盒子本体 count=0
```

三条反证（没有它们，上面那些断言可能只是空转）：

| 反证 | 期望 |
|---|---|
| 无色盒拆包 | **不许**产生任何染料 |
| 空染色盒（青柠色） | 整盒入库，壳 / 箱 / 染料**一个都不许出现** |
| 手工造一条确实含「1 盒」的文本 | `anyContains` 必须判真（否则「不含 1 盒」是废话） |

`pick(DyeColor)` 如果取错色、或者颜色与物品的顺序错位，第一条就会挂 —— 这是本轮真正的牙。

## 顺带：潜影盒模式开关上的一行换算删掉了

同一轮里按玩家要求删掉 `VoidWarehouseNav.shulkerToggle` 的这行：

```
1 盒 = 27 格 × 堆叠上限（圆石 1,728 个）
```

潜影盒本来就是 27 格，把「圆石 1,728」这种算例摆在开关上，既占一行，
又容易被读成「这个数字是这个模式特有的规矩」。想知道能装多少，看物品格上那行换算就够。

开关的说明从 4 件事缩到 3 件（模式 / 代价 / 被拒条件），开启时 4 行、关闭时 3 行。
