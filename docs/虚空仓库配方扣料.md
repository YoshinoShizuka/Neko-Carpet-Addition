# 虚空仓库配方扣料（`voidWarehouseCraft`）

## 一句话

玩家在合成台里**真的合成过一次**的东西，之后就能直接从虚空仓库按那条配方扣原料取出来。

## 为什么不是「复刻 9 合 1」

9 合 1（`voidWarehouseExchange`）能成立，靠的是一条硬前提：**原版存在 9:1 / 4:1 的换算关系，且能建立价值体系**（`Σ 数量 × 价值` 守恒）。所以它只能覆盖那张静态表里的 47 条边 / 88 个物品，而且为了「成品缺货时把库存换算成成品」，必须带上界、探针、递归和状态副本——那是 1.0.13 卡死事故的来源。

而「活塞」这类东西**没有价值守恒可言**：4 圆石 + 3 木板 + 1 铁锭 + 1 红石，任何「价值」定义都是拍脑袋。全原版一千多条配方也不可能靠人一条条列举。

所以这条规则换了一个完全不同的方向：**不换算，照抄玩家真做过的那一次**。

| | 9 合 1 兑换 | 配方扣料 |
| --- | --- | --- |
| 覆盖范围 | 静态表 47 条边 / 88 物品 | 玩家合成过的任意配方 |
| 依据 | 原版换算关系 + 价值守恒 | 玩家实际摆进合成格的物品 |
| 层数 | 多层（能拆能合、能连续换算） | **一层**（原料必须仓库里现成） |
| 计算 | 上界 + 逐个试探（有探针预算） | 一次算术（合并需求 → 上界 → 摆一遍） |
| 防刷依据 | 价值守恒等式 | 「账目加减」与「产出/余量」严格对账 |

## 数据从哪来

挂 `ResultSlot#onTake` 的 **HEAD**：

```java
@Mixin(ResultSlot.class)
public abstract class CraftResultMixin {
    @Shadow @Final private CraftingContainer craftSlots;

    @Inject(method = "onTake(Lnet/minecraft/world/entity/player/Player;Lnet/minecraft/world/item/ItemStack;)V",
            at = @At("HEAD"))
    ...
}
```

### 为什么必须是 `HEAD`

合成格是在 `onTake` **内部**被消耗的（26.3 字节码里 `craftSlots.removeItem(...)` 出现在方法体中段）。挂 `RETURN` 只能读到一张空网格，记下来的会是一条「产物 ← 什么都不需要」的配方，等于仓库白送东西。

> 这条与本项目的老规矩一致：**断言只能咬真正被执行的代码，位置也一样，早一步晚一步都是错的**。`SlotMixin` 用 `RETURN` 是因为那边要读「写完之后」的状态；这里方向相反。

### 为什么不用 `onTake` 收到的那个 `stack`

直觉写法是拿回调参数里那件产物的 `getCount()` 当「一次产出几个」。核对 26.3 的执行路径之后发现**同一个参数在两条路径上含义完全不同**：

| 路径 | 传进来的东西 |
| --- | --- |
| 单击取出（`doClick` PICKUP） | `slot.getItem()`，正好是一次合成的产物 |
| Shift 快速移动（`CraftingMenu#quickMoveStack`） | 先把产物搬进背包、把槽位里的堆叠**就地减掉**，再把**搬剩的余量**传进来 —— 全搬完时是 `ItemStack.EMPTY`，只搬进去一部分时是零头 |
| 数字键交换（SWAP） | `slot.getItem()` |

也就是说它可能是 4、可能是 2（背包快满）、还可能是空气。而「一次产出几个」是**乘法因子**：记大了，「取 64 个木板」会算成只做 1 次合成 —— 那是凭空造物。

所以产物数量改问权威来源：

```java
server.getRecipeManager().getRecipeFor(RecipeType.CRAFTING, craftSlots.asCraftInput(), level)
```

拿到 `RecipeHolder<CraftingRecipe>` 之后 `assemble(...)` 出这一次的产物。原版自己在每次合成格变化时（`CraftingMenu#slotsChanged`）做的就是这一次查询，所以不多花一分钱。

**多个入口、同一份钩子**：`onTake` 是所有取走方式的共同出口（PICKUP / QUICK_MOVE 每一轮 / SWAP 都经过它），所以不需要去猜「这次到底是谁干的」。

### 一格算一个（最容易写错的一行）

合成格的**每一格只消耗 1 个**物品，与该格的堆叠数量无关：格里放着一组 64 个圆石，合成一次也只吃掉 1 个。

```java
cells.merge(id, 1, Integer::sum);   // 不是 stack.getCount()
```

写错就变成「合成一次活塞扣 64 木板」，而且**只会在玩家格里放着整组时才犯**——自检里专门摆了整组 64 个圆石来钉住这一条。

### 特殊配方不记录

`CustomRecipe`（原版 special recipe：染色、烟火、地图缩放、成书复制、潜影盒染色）一律跳过。它们的产物带数据组件，学下来之后仓库给的是一件**白板**物品——「花 1 皮革胸甲 + 1 红色染料换一件白皮甲」不是功能，是坑。

## 存档格式

配方本存在仓库同一份 `SavedData` 里，字段 `learned_recipes`，**一个字符串**、一条配方一行：

```
minecraft:piston*1;minecraft:cobblestone×4,minecraft:oak_planks×3,minecraft:iron_ingot×1,minecraft:redstone×1
```

### 为什么是一个字符串而不是字符串列表

`Codec.listOf()` 的语义是**全成或全不成**：只要有一条读不懂，整个 `VoidWarehouseData` 就解码失败，上层会把它当成「文件不存在」，**静默造一个空仓库**并覆盖写盘 —— 那是「进一次存档东西全没了」的唯一成因（见 `docs/虚空仓库静默清空事故分析.md`，以及 `ITEMS_CODEC` 那段注释）。

而一个 `Codec.STRING` 字段永远解不失败，坏的只可能是里面某**一行**，由 `VoidWarehouseRecipes.decodeAll` 逐行静默跳过。**用字段失败换行失败** —— 这个交换在仓库这件事上是唯一可接受的方向。

读档时还做一件事：**先解码，再按解码后的规范文本回填**。于是坏行当场丢掉，不会留下「数得出 5 条、实际只有 4 条能用」的幽灵计数。

### 为什么存展开后的文本而不是原版配方 id

- 这条配方是从**玩家实际摆进合成格的物品**记下来的，原版可能根本没有一条 id 与之一一对应（玩家用 2 个橡木 + 2 个云杉木板拼出来的东西）；
- 不依赖 `RecipeManager`：`/reload`、换数据包、换版本都不会让它失效；
- 存档里能直接读出「他当时到底用了什么」。

`Recipe.recipeId` 就是这串编码本身 —— **内容即标识**，于是「同一条配方学两次」在集合里天然只有一条，不需要另维护一份去重键。

## 扣料算法

`VoidWarehouseRecipes` 是纯 Java（零 `net.minecraft` 引用），五个版本共用一份。

### 三步：合并需求 → 取上界 → 摆一遍

1. **合并需求**：把「只有一个候选」的原料项按候选求和。两项都只认 A、各要 1 个，就是「A 要 2 份」；
2. **取上界**：每个候选算 `库存 / 合并后需求`，全部取最小；多候选的原料项取「各候选里最大的」；
3. **从上往下验证**：把这个上界真的摆一遍（`tryAssign`），摆得下就是答案。

### 为什么不能「逐项挑候选、边挑边扣」

最直觉的写法是按原料项顺序挑「剩余最多的候选」、用它压小次数、立刻扣掉。它对「各项原料互不相干」是对的，但**两项都只认同一种物品时会算错**：3 个 A、配方要两项各 1 个 A，正确是能做 1 次，它却让第一项把 3 个 A 全占了，第二项一看没料直接判「做不出来」。

方向虽然安全（少给不少扣），但「明明能做却说不能做」对玩家是实打实的错。这是自检 A7 那一条钉住的行为。

### 为什么不能只算上界不验证

多候选项的上界是「各候选独立算」的：两个都认 `[A, B]` 的项，在一个只有 1 个 A、1 个 B 的仓库里各自算出 1，上界取小还是 1 —— 但真摆的时候两项抢两件东西，一件都摆不下。

**所以必须验证。** 且验证必须有硬预算（`MAX_VERIFY = 64`）——这是本项目付过代价的规矩：任何「从上往下试」都不能无界。正常数据里（配方本记下来的每项都只有一个候选）第一次就成功，预算是 0 消耗。

### 「最多能合成 N 个」与「真能拿到 N 个」同源

`maxCraftable` 与 `plan` 用的是**同一次** `greedy`，而且 `plan` 沿用贪心记下来的候选选择（不重新挑）。两处若各算各的，就会出现「tooltip 说 64、实际给 63」——那是 9 合 1 在 1.0.7 栽过的形态。

自检 B 组用 200 轮随机库存 × 随机配方、2000 个量把这条钉死。

## 与 9 合 1 的接线

配方扣料**不新开一条取货链路**：它只是产出另一份 `VoidWarehouseExchange.Plan`（一串「谁加多少、谁减多少」）。

因为计划的**来源对执行层完全不可见**，所以 `applyExchange` / `Withdrawal` / 回滚（`negate()` + 重规划）/ 漏斗出料 / 打印机补货这五条既有链路**一行都没改**，配方扣料天然接在它们身上。

一处必须注意的分岔：**两套物品 id 口径**。

| | id 形态 | 解析函数 |
| --- | --- | --- |
| 9 合 1 表 | `iron_ingot`（只留 path、只认 `minecraft:`） | `VoidWarehouseExchangeBootstrap.itemOf` |
| 配方本 | `minecraft:iron_ingot`（全命名空间，模组物品也算） | `VoidWarehouseRecipeBook.itemOf` |

把带冒号的 id 喂给前者会拼出 `minecraft:minecraft:iron_ingot` 并抛异常。所以 `VoidWarehouseData.resolveItem` 用「有没有冒号」分流——这不是猜，是两边格式的硬事实（9 合 1 表里从来没有冒号，配方本写出去永远带冒号）。

## 三笔账必须分开记

`amount` 是「一共要给玩家多少」，其中**已经躺在仓库里**的那部分不该再做一遍。否则「仓库里有 5 个活塞、取 10 个」会变成扣 10 份原料却只拿走 5 个新做的。

- 仓库现成的 `fromStock` 个 → 产物那一项**负** `fromStock`；
- 剩下 `need` 个按配方做 `crafts` 次 → 原料负扣；
- 做出来比要的多（木板一次 4 个）→ 余量 `surplus` **入账**回仓库。

三笔合起来净值恰好是「仓库少了原料、多了余量，玩家拿到 amount 个」。

### 产物自己就是原料的配方（地图缩放 / 地图复制 / 潜影盒染色）

这类配方要把 `fromStock` 从配方可用的料里**先扣掉**，否则同一份库存会被数两遍：一份算给玩家、一份算进配方 —— 那就是凭空造物。

扣掉之后这类配方的结果是「做不出来」（保守失败），而不是「做出来了但账对不上」。

## 已知取舍

- **原料被具体化**：用橡木木板合成过的活塞，之后也只认橡木木板（不认云杉）。数据结构（`Part.candidates`）已经支持多候选，只是本版本不往里填——「认所有木板」需要标签支持，那是另一种语义，得单独设计。
- **不处理 `getRemainingItems`**：像蛋糕那样「牛奶桶用掉又还回空桶」的配方按「扣掉 1 个桶」记账，不退回空桶。偏保守（多扣不少扣），不会刷物。
- **背包快满时首学可能记小产出数**：Shift 快速移动只搬进去一部分时，`onTake` 收到的是零头；此时按「一格算一个」的原则记下来的原料是对的，产出数则偏小（多扣不少给）。这是安全方向，且只在**第一次**学这条配方时可能发生（记住之后不再更新）。
- **配方本全服共用**：仓库是共用的，材料也是共用的，把配方按人头分会让「仓库里明明有材料、却因为不是自己合成过而取不出来」变得没道理。
- **配方本上限 512 条**：撞到就停止记录（而不是让存档无限长大）。正常服永远撞不到。

## 自检

`.workbuddy/tools/VoidWarehouseCraftSelfCheck.java.template`，101 项断言、10 组，每组都配反证。真跑 26.3 服务端：

```
SMOKE RESULT vw-craft/26.3 checks=101 failures=0
```

覆盖：纯逻辑（含共享候选反证）、上界与规划口径一致（200 轮 fuzz / 2000 个量）、编解码（含坏数据）、真实配方解析（含整组 64 只算 4 格、木棍产出 4、空网格 / 无配方 / special recipe 反证）、学习幂等（跨进程幂等，配方本存在存档里）、端到端扣料逐项精确、多产出余量入账、回滚逐项还原（含干扰项、部分保留）、规则关闭后恒为 null、存档往返（混坏行只丢那一行）。

装/摘：`python .workbuddy/tools/install_craft_selfcheck.py install|remove [版本]`。
