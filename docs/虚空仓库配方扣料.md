# 虚空仓库配方扣料（`voidWarehouseCraft`）

## 一句话

玩家在合成台里**真的合成过一次**的东西，之后就能直接从虚空仓库按那条配方扣原料取出来。

## 为什么不是「复刻 9 合 1」

9 合 1（`voidWarehouseExchange`）能成立，靠的是一条硬前提：**原版存在 9:1 / 4:1 的换算关系，且能建立价值体系**（`Σ 数量 × 价值` 守恒）。所以它只能覆盖那张静态表里的 47 条边 / 88 个物品，而且为了「成品缺货时把库存换算成成品」，必须带上界、探针、递归和状态副本——那是 1.0.13 卡死事故的来源。

而「活塞」这类东西**没有价值守恒可言**：4 圆石 + 3 木板 + 1 铁锭 + 1 红石，任何「价值」定义都是拍脑袋。全原版一千多条配方也不可能靠人一条条列举。

所以这条规则换了一个完全不同的方向：**不换算，照抄玩家真做过的那一次**。

| | 9 合 1 兑换 | 配方扣料 |
| --- | --- | --- |
| 覆盖范围 | 静态表 47 条边 / 88 物品 | 玩家合成过的任意配方 |
| 依据 | 原版换算关系 + 价值守恒 | 玩家实际摆进合成格的物品 |
| 层数 | 多层（能拆能合、能连续换算） | 最多 4 层（只在**已学配方**之间往下钻） |
| 计算 | 上界 + 逐个试探（有探针预算） | 宽松上界 → 整棵树摆一遍 → 摆不下二分 |
| 防刷依据 | 价值守恒等式 | 「账目加减」与「产出/余量」严格对账 |

## 数据从哪来

挂 `ResultSlot#onTake` 的 **HEAD**：

```java
@Mixin(ResultSlot.class)
public abstract class CraftResultMixin {
    @Shadow @Final private CraftingContainer craftSlots;

    @Inject(method = "onTake(Lnet/minecraft/world/entity/player/Player;Lnet/minecraft/world/item/ItemStack;)V",
            at = @At("HEAD"))
    ...
}
```

### 为什么必须是 `HEAD`

合成格是在 `onTake` **内部**被消耗的（26.3 字节码里 `craftSlots.removeItem(...)` 出现在方法体中段）。挂 `RETURN` 只能读到一张空网格，记下来的会是一条「产物 ← 什么都不需要」的配方，等于仓库白送东西。

> 这条与本项目的老规矩一致：**断言只能咬真正被执行的代码，位置也一样，早一步晚一步都是错的**。`SlotMixin` 用 `RETURN` 是因为那边要读「写完之后」的状态；这里方向相反。

### 为什么不用 `onTake` 收到的那个 `stack`

直觉写法是拿回调参数里那件产物的 `getCount()` 当「一次产出几个」。核对 26.3 的执行路径之后发现**同一个参数在两条路径上含义完全不同**：

| 路径 | 传进来的东西 |
| --- | --- |
| 单击取出（`doClick` PICKUP） | `slot.getItem()`，正好是一次合成的产物 |
| Shift 快速移动（`CraftingMenu#quickMoveStack`） | 先把产物搬进背包、把槽位里的堆叠**就地减掉**，再把**搬剩的余量**传进来 —— 全搬完时是 `ItemStack.EMPTY`，只搬进去一部分时是零头 |
| 数字键交换（SWAP） | `slot.getItem()` |

也就是说它可能是 4、可能是 2（背包快满）、还可能是空气。而「一次产出几个」是**乘法因子**：记大了，「取 64 个木板」会算成只做 1 次合成 —— 那是凭空造物。

所以产物数量改问权威来源：

```java
server.getRecipeManager().getRecipeFor(RecipeType.CRAFTING, craftSlots.asCraftInput(), level)
```

拿到 `RecipeHolder<CraftingRecipe>` 之后 `assemble(...)` 出这一次的产物。原版自己在每次合成格变化时（`CraftingMenu#slotsChanged`）做的就是这一次查询，所以不多花一分钱。

**多个入口、同一份钩子**：`onTake` 是所有取走方式的共同出口（PICKUP / QUICK_MOVE 每一轮 / SWAP 都经过它），所以不需要去猜「这次到底是谁干的」。

### 一格算一个（最容易写错的一行）

合成格的**每一格只消耗 1 个**物品，与该格的堆叠数量无关：格里放着一组 64 个圆石，合成一次也只吃掉 1 个。

```java
cells.merge(id, 1, Integer::sum);   // 不是 stack.getCount()
```

写错就变成「合成一次活塞扣 64 木板」，而且**只会在玩家格里放着整组时才犯**——自检里专门摆了整组 64 个圆石来钉住这一条。

### 特殊配方不记录

`CustomRecipe`（原版 special recipe：染色、烟火、地图缩放、成书复制、潜影盒染色）一律跳过。它们的产物带数据组件，学下来之后仓库给的是一件**白板**物品——「花 1 皮革胸甲 + 1 红色染料换一件白皮甲」不是功能，是坑。

## 存档格式

配方本存在仓库同一份 `SavedData` 里，字段 `learned_recipes_lines`，**一个字符串列表**、一条配方一个元素：

```json
[
  "minecraft:piston*1;minecraft:cobblestone×4,minecraft:oak_planks×3,minecraft:iron_ingot×1,minecraft:redstone×1",
  "minecraft:stick*4;minecraft:oak_planks×1"
]
```

### 为什么是逐条列表，而不是一个大字符串拼起来

NBT 的字符串走 `DataOutputStream#writeUTF`，长度字段是 **u16**，数的是 modified UTF-8 字节 —— **硬上限 65535**。实测平均 67.2 字节/条，所以「全拼成一个字符串」最多只能存 **975 条**（65,512 B 通过，976 条 = 65,596 B 超限）。

真正要命的不是上限本身，是**撞上去之后的失败形态**：26.3 的 `NbtIo$StringFallbackDataOutput#writeUTF` 捕获 `UTFDataFormatException` 之后执行的是 `super.writeUTF("")` —— **键还在、内容变成空串**。不报错、不崩溃、不写任何日志，只在下次读档时表现为「配方本空了」。实测把一个 70,000 字节的字符串写盘，文件只剩 **10 字节**。

这就是当初把上限定在 512 条的真实理由：不是嫌存档大，是怕悄无声息地撞上那堵 975 的墙 —— 而 512 这个数本身没有物理含义，原版就有约 1500 条配方，认真玩一个档完全可能把它填满，填满之后的「不再记录」同样是静默的。

`ListTag` 的元素计数是 **int**，单个元素只有几十字节，**65535 这堵墙再也碰不到**。容量从此只由 `MAX_RECIPES` 决定。

### 为什么自己写 codec，而不是 `Codec.STRING.listOf()`

`Codec.listOf()` 的语义是**全成或全不成**：只要有一条读不懂（实测混进一个 `IntTag` 就报 `Not a string`），整个 `VoidWarehouseData` 就解码失败，上层会把它当成「文件不存在」，**静默造一个空仓库**并覆盖写盘 —— 那是「进一次存档东西全没了」的唯一成因（见 `docs/虚空仓库静默清空事故分析.md`，以及 `ITEMS_CODEC` 那段注释）。

`RecipeLinesCodec` 的解码是**逐元素独立**的：读不出字符串的那个元素丢掉，其余照收，整表永远成功。**用元素失败换条目失败** —— 和原来「用字段失败换行失败」是同一个方向，只是失败粒度从「整份存档」降到「一条配方」。

底层还有一层：元素能读成字符串，不代表里面那行文本是合法配方，`VoidWarehouseRecipes.decodeAll` 继续逐行静默跳过。读档时**先解码，再按解码后的规范文本回填**，所以坏行当场丢掉，不会留下「数得出 5 条、实际只有 4 条能用」的幽灵计数。

顶层类型错（比如被人手工改成字符串）时**不宽容**：让解码失败，交给 `VoidWarehouse.data` 的空壳闸门拒绝服务。宁可让服主看见一个明确的错误，也不能把「整本配方凭空消失」伪装成一次正常读档。

### 旧字段 `learned_recipes` 怎么处理

只读不写：

- **读**：`learned_recipes_lines` 存在就用它（新格式优先）；不存在才读旧字段，按 `\n` 切开、空行丢掉，喂进同一个列表。
- **写**：旧字段那一路的 getter 恒返回 `Optional.empty()`，`optionalFieldOf` 于是**一个字节都不写**。所以老档一旦被这个版本写过，键名就永久换成了 `learned_recipes_lines`。
- **降级不行**：新版本写过的档，旧版本读不到配方（它只认 `learned_recipes`，而那键已经没了）。要回退版本请先备份存档。

完整设计与实测数据见 `docs/虚空仓库存储-A2逐条拆分方案.md`。

### 为什么存展开后的文本而不是原版配方 id

- 这条配方是从**玩家实际摆进合成格的物品**记下来的，原版可能根本没有一条 id 与之一一对应（玩家用 2 个橡木 + 2 个云杉木板拼出来的东西）；
- 不依赖 `RecipeManager`：`/reload`、换数据包、换版本都不会让它失效；
- 存档里能直接读出「他当时到底用了什么」。

`Recipe.recipeId` 就是这串编码本身 —— **内容即标识**，于是「同一条配方学两次」在集合里天然只有一条，不需要另维护一份去重键。

## 扣料算法

`VoidWarehouseRecipes` 是纯 Java（零 `net.minecraft` 引用），五个版本共用一份。

### 一句话：算一个宽松上界 → 把整棵树摆一遍 → 摆不下就二分

- **上界**（`boundCap` + `availOf`）：每种物品按「家里有的 + 全拿去做能做出的」算，单候选项先按物品**合并需求**再相除。这个数**故意估大**（共享原料时会重复计数），它唯一的作用是把搜索区间压窄。
- **摆一遍**（`simulate`）：真的把「做 N 次」这件事整棵树走一遍 —— 每一项扣哪个候选、哪一项不够要往下钻、钻下去做几次、多出来多少。
- **摆错了要能退回去**：一项有多个候选时，试第一个候选失败必须把扣掉的料**原样退回来**再试下一个。1.0.17 之前是「每个分支复制一份账本」（`Model.copy()` + `adopt`），对但贵 —— 满本一次重建要复制 **164,505 次** 40~60 项的小 map，占掉全部耗时的八成。现在改成**记旧值 + 回滚**：每次写账本前把 `(哪本账, 键, 旧值)` 压进撤销日志，失败时倒序贴回。这不是「写逆操作」（那才容易漏），而是机械记录，「所有写都经过日志」这一条由三个 map 字段 `private` 来强制 —— 绕过日志直接写，编译不过。改完账本逐字节不变（7,416 行对拍 SHA-256 相同），速度 5.6×，见 [`配方本满本并发测试报告.md`](配方本满本并发测试报告.md) §12。
- **二分**：上界本身摆得下就直接是答案（只跑一次模拟，实测 79% 的配方走这条）；摆不下就在 `[0, 上界-1]` 上二分最大的可行次数，`⌈log₂(上界+1)⌉` 次探针。

> ⚠️ 1.0.17 之前这一步是「上界减 1 再试，最多退 64 次」。那是错的：上界的**相对**误差只有 6%~33%，但真值本身在万位，绝对虚高于是也在千位（P50 = 3,328 次），64 次永远走不到 —— 满本时 21% 的配方被判成「做不出」而整格从界面消失。事故与量化见 [`配方本满本并发测试报告.md`](配方本满本并发测试报告.md)。

`maxCraftable` 与 `plan` 用的是**同一个 `simulate`**，所以「界面说能合成 N 个」与「真点下去能拿到 N 个」不是两份计算 —— 它们就是同一次模拟。

### 为什么不能「逐项挑候选、边挑边扣」

最直觉的写法是按原料项顺序挑「剩余最多的候选」、用它压小次数、立刻扣掉。它对「各项原料互不相干」是对的，但**两项都只认同一种物品时会算错**：3 个 A、配方要两项各 1 个 A，正确是能做 1 次，它却让第一项把 3 个 A 全占了，第二项一看没料直接判「做不出来」。

方向虽然安全（少给不少扣），但「明明能做却说不能做」对玩家是实打实的错。这是自检 A7 那一条钉住的行为。

### 为什么不能只算上界不验证

多候选项的上界是「各候选独立算」的：两个都认 `[A, B]` 的项，在一个只有 1 个 A、1 个 B 的仓库里各自算出 1，上界取小还是 1 —— 但真摆的时候两项抢两件东西，一件都摆不下。

**所以必须验证。** 且验证必须有硬预算 —— 这是本项目付过代价的规矩：任何「从上往下试」都不能无界。

## 往下钻：原料不够时会顺着别的配方再做一层

1.0.15 只做一层，原料必须仓库里现成。玩家报的原话：

> 合成过一次深色橡木木板和活塞，木板用完之后再取活塞，不会自动扣除深色橡木原木。

这不是 bug，是当时写死的取舍 —— 但对玩家来说它显然就是错的：合成台里他会先做木板再做活塞，仓库凭什么不能？

所以从这一版起，**某一项在库存里凑不够时，会顺着「这件物品的已学配方」继续往下钻**：

```
取 1 个活塞 → 要 3 块木板 → 木板 0 块、原木 1 根
            → 做 1 次「原木 → 4 木板」：扣 1 根原木，用掉 3 块，剩 1 块入账回仓库
```

### 四条硬约束（缺一条就会算出做不出来的账，或者刷物）

| 约束 | 值 | 不做的后果 |
| --- | --- | --- |
| 深度上限 | `MAX_DEPTH = 4` | 「铁锭 ← 铁块 ← …」在模组包里可以很长，不设界就是无限递归 |
| 路径去环 | 展开某项时它的祖先不许再出现在子树里 | 「A 由 A 做出来」自己吃自己（9 合 1 里「撞环返 0」的同源问题） |
| 展开预算 | `MAX_NODES = 512` | 一条配方 9 项 × 每项 3 条配方 × 4 层 = 乘积爆炸 |
| 先吃库存再合成 | 有 2 块木板、要 3 块 ⇒ 扣 2 块 + 做 1 次 | 「一缺货就整项去做」会白扣一次原木，玩家看到的是「明明有木板还扣我原木」 |

预算用完 / 撞环 / 超过深度，一律**保守失败**（这项没料），绝不返回一个没验证过的账。自检 K6/K7 量的是深度边界，K8 是撞环。

### 闭包必须取到「深一层」

这就是 1.0.15 那个 bug 的直接成因：快照里只有「木板」，没有「原木」，模拟器看到「木板 0、原木 0」，自然判没料。

`stockClosure` 会沿着配方树把整条闭包都取出来（同样受深度与 200 条目的上限约束），`stockFor` 只是它的一层薄包装。自检 K5 直接盯着「闭包里必须有原木」。

### 往下钻只在「已学配方」之间发生

`byOutput` 是唯一的入口 —— 没有学过的配方不会凭空出现。所以「仓库能替玩家做什么」完全由「他在合成台上真做过什么」决定，这条边界就是防止仓库变成万能合成台的关键。

## 与 9 合 1 的接线

配方扣料**不新开一条取货链路**：它只是产出另一份 `VoidWarehouseExchange.Plan`（一串「谁加多少、谁减多少」）。

因为计划的**来源对执行层完全不可见**，所以 `applyExchange` / `Withdrawal` / 回滚（`negate()` + 重规划）/ 漏斗出料 / 打印机补货这五条既有链路**一行都没改**，配方扣料天然接在它们身上。

一处必须注意的分岔：**两套物品 id 口径**。

| | id 形态 | 解析函数 |
| --- | --- | --- |
| 9 合 1 表 | `iron_ingot`（只留 path、只认 `minecraft:`） | `VoidWarehouseExchangeBootstrap.itemOf` |
| 配方本 | `minecraft:iron_ingot`（全命名空间，模组物品也算） | `VoidWarehouseRecipeBook.itemOf` |

把带冒号的 id 喂给前者会拼出 `minecraft:minecraft:iron_ingot` 并抛异常。所以 `VoidWarehouseData.resolveItem` 用「有没有冒号」分流——这不是猜，是两边格式的硬事实（9 合 1 表里从来没有冒号，配方本写出去永远带冒号）。

## 三笔账必须分开记

`amount` 是「一共要给玩家多少」，其中**已经躺在仓库里**的那部分不该再做一遍。否则「仓库里有 5 个活塞、取 10 个」会变成扣 10 份原料却只拿走 5 个新做的。

- 仓库现成的 `fromStock` 个 → 产物那一项**负** `fromStock`；
- 剩下 `need` 个按配方做 `crafts` 次 → 原料负扣；
- 做出来比要的多（木板一次 4 个）→ 余量 `surplus` **入账**回仓库。

三笔合起来净值恰好是「仓库少了原料、多了余量，玩家拿到 amount 个」。

### 产物自己就是原料的配方（地图缩放 / 地图复制 / 潜影盒染色）

这类配方要把 `fromStock` 从配方可用的料里**先扣掉**，否则同一份库存会被数两遍：一份算给玩家、一份算进配方 —— 那就是凭空造物。

扣掉之后这类配方的结果是「做不出来」（保守失败），而不是「做出来了但账对不上」。

## 木板可互换（`#minecraft:planks`）怎么处理

原版活塞配方第一格写的是**标签** `#minecraft:planks`，十二种木板都算数。本模组的处理是**不认标签，认具体物品**。

### 学习：按格里摆的东西记，一条木板一条配方

`VoidWarehouseRecipeBook#fromGrid` 遍历合成格，取的是 `stack.getItem()` 的**完整 id**（带命名空间），
每项原料构造 `new Part(List.of(id), count)` —— **单候选**。所以「橡木活塞」与「白桦活塞」在配方本里是
**两条独立记录**，产物相同、原料不同：

```
minecraft:piston*1;minecraft:oak_planks×3,minecraft:cobblestone×4,minecraft:iron_ingot×1,minecraft:redstone×1
minecraft:piston*1;minecraft:birch_planks×3,minecraft:cobblestone×4,minecraft:iron_ingot×1,minecraft:redstone×1
```

`recipeId` 由内容生成（`format(output, outputCount, parts)`），所以两条的 id 天然不同、各自占一行，
「同一条学两次」才会折叠。**物品不按标签归组**：`Part.candidates` 这个字段本来就是为多候选留的
（注释里写的正是「12 种木板都算数」），但本版本只往里填一个元素。

### 选哪一条：在「配方之间」挑，不是在「木板之间」挑

`VoidWarehouseData#planCraft` 拿到的候选是 `recipesByOutput.get("minecraft:piston")` —— 一个**列表**。
挑哪一条分两种形态（下一节展开）：**「尽量给」挑做得最多的那条，精确请求按学会顺序挑第一条能做的**。
共同点是：一旦选中某一条，就只按它的**单一候选**扣料，**不会在几种木板之间比较或混搭**。

- 顺序的来源是配方本里 `recipeTexts` 的写入顺序 = **玩家学会的先后**（存档按行顺序存），
  不是背包顺序、不是物品栏位次、也不是库存多少；
- 先学的那条做不出来（木板不足 3 块）→ 自动落到下一条，扣的是那条指定的木材；
- 只学过橡木版、仓库里只有白桦木板 → **做不出来**（`plan == null`，整次拒绝，仓库一个字节不动）。
  这是「原料被具体化」的正经代价，不是 bug；
- **不混搭**：橡木 1 块 + 白桦 2 块凑够 3 块也不行，一次合成只用一条配方。

### 扣料落到哪一格

计划里的每一笔是 `itemId → ±数量`，执行时 `applyExchange` 用 `find(new ItemStack(item))` 定位 ——
**纯净物品那一格**（同 Item + 同数据组件）。所以附魔 / 改名 / 带药水数据的橡木木板不算数，
扣不到它们头上。仓库内部按创造栏顺序排的 `entries` 只影响界面分页，与扣料选择无关。

### 「尽量给」挑哪一条：必须与界面同一个口径（1.0.15 修）

界面上的「可合成 N 个」由 `collectCraftOffers` 取**同一产物所有配方里 `maxCraftable` 最大的那条**
（上表最后一行：64）。而「取一组 / 取一盒」原先按**学会顺序**取第一条，两条口径在
「先学会的那条恰好料更少」时会分叉：

> oak=192（64 个活塞）、birch=3（1 个活塞），学序 birch→oak ⇒ tooltip 写「可合成 64」，
> 右键实际只给 **1** 个。

这违反「界面上的数字不能大于真值」这条硬规矩（1.0.7 栽过一次的形态）。现在两条路共用同一条判据：

| 请求形态 | 挑哪一条配方 | 理由 |
| --- | --- | --- |
| 「尽量给」（右键一组 / 取一盒，`allowPartial = true`） | 先对每条候选算 `maxCraftable`，**取最大的那条**再 `plan` | 与界面口径逐字相同，界面写多少就能给多少 |
| 精确请求（左键取 1 / 打印机按需取） | 按学会顺序逐条试，**第一条能一次性满足的** | 没有「最多」可言；顺序稳定，账才稳定 |

持平（两条做得一样多）时**取先学会的那条**，两侧的 tie-break 一致。实测（`.workbuddy/tools/CraftCheck.java`）：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 学序 oak→birch，两种木板各 192，取 1 活塞 | 扣 `oak_planks×3` | 同 |
| 学序 birch→oak，同库存，取 1 活塞 | 扣 `birch_planks×3` | 同 |
| 只学 oak，仓库只有 birch 木板 | `null`（做不出来） | 同 |
| 学序 oak→birch，oak 只剩 1 块 | 落到 birch | 同 |
| oak=192、birch=3，学序 **birch→oak**，「取一组」 | 界面 64 / 实际 **1** ❌ | 界面 64 / 实际 **64** ✅ |

自检里钉了 9 条（L 组），且**故意把料少的那条先学** —— 用旧实现跑同一套自检时 L3/L4/L5 三连失败，
修复后 138 项全绿，说明这组断言不是空转。

复跑纯逻辑那一半：`javac -d out common/src/main/java/neko/voidwarehouse/VoidWarehouseRecipes.java .workbuddy/tools/CraftCheck.java && java -cp out CraftCheck`
（输出另存 `.workbuddy/tools/CraftCheck.out.txt`）

## 学习时的提示：记住了 / 快满了 / 已满

配方本以前是**完全静默**的：学会了没有、撞没撞上限，玩家只能打开界面数格子猜。撞上限尤其糟 ——
合成照做，但那条配方没记，等哪天真要用了才发现界面里少了这一格，而那时已经想不起来是哪一次漏的。

提示走聊天栏，`[虚空仓库] ` 亮金前缀沿用 `VoidWarehouseText.info`，正文浅灰、关键数字亮绿。真实文案：

| 场合 | 发出去的内容 | 频率 |
| --- | --- | --- |
| 学会一条新配方 | `[虚空仓库] 已记住配方：2 桦木木板 → 4 木棍` | 每次学成 |
| 同产物本来还有别的走法 | `└ 还能这样合：2 橡木木板 → 4 木棍；…（另有 3 条）` | 随上一条，最多列 5 条 |
| 用到上限的 90%（2048 → 1844 条） | `[虚空仓库] 配方本快满了：1,844 / 2,048 条已用。`<br>`└ 满了之后，新配方不会再被记住。` | 每个玩家一次 |
| 已满，这条没记上 | `[虚空仓库] 配方本已满（2,048 / 2,048 条），这条配方没记住。`<br>`└ 已记的配方仍能正常扣料；要记新的得先腾出空位。` | 边沿必报一次，之后每 30 秒最多一次 |
| 重复合成同一件东西 | **不发** | — |
| `voidWarehouseCraft` 没开 | **不发** | — |

`└` 那几行刻意**不带**前缀：它是上一条的补充而不是独立消息，缩进一眼就能看出从属关系。
英文客户端由 `VoidWarehouseText.isEnglish(player)` 走另一套文案，`└` 与 `→` 不译。

### 「同产物已有配方」必须在 `learn` 之前取

「2 橡木木板 → 木棍」与「2 桦木木板 → 木棍」在仓库里是**两条独立配方** —— 从合成格记录的是
玩家当时实际放的那一种，不做 tag 归一（见上文「木板可互换怎么处理」）。所以新学桦木那条时，
「已有」里应该出现橡木那条。

顺序反了不会报错，只是提示里多一句话：`learn` 之后新配方已经进了本子，再按产物去查就会把它
**自己**列进「已有」，玩家看到的是「还能这样合：… 2 桦木木板 → 4 木棍」—— 就是刚学的那条。

因为「错也不崩」，它没法靠人眼守。做法是把这两行固化进数据层：

```java
public LearnOutcome learnCapturingOthers(Recipe recipe) {
    List<Recipe> othersBefore = this.recipesFor(recipe.output());  // ← 先取
    LearnResult result = this.learnWithResult(recipe);             // ← 再学
    return new LearnOutcome(result, othersBefore);
}
```

返回值 `LearnOutcome` 是个 record，`othersBefore` 在构造器里 `List.copyOf` 存快照。自检直接断言
「交出来的快照里没有刚学的那条」，不需要真玩家、也不需要拦聊天消息。

### 为什么最多列 5 条，而且要先排序

木棍这类配方两侧各能堆到十几条（每种木板一条）。全列出来会把聊天栏刷满，而玩家真正需要知道的
只有「这个产物还有别的走法」这件事本身，不是每一条走法的全文。

排序是必须的：`recipesFor` 从 `recipesByOutput` 的列表拷出来，那个列表的顺序取决于**学习顺序**，
也就是取决于玩家什么时候合成过什么。不排序的话，同一件事在两次提示里会列出不同的前 5 条，
玩家会以为配方本自己变了。所以按 `recipeId` 排完再截断，其余折成「另有 N 条」。

### 满了之后为什么要节流

满本之后**每一次**合成都会走到「没记上」这个分支。只报一次不行（换个玩家、或者过一阵子再看，
就再也不知道为什么没记上）；每次都报更不行（每合一次刷两行，比静默还烦）。

所以分两层：**边沿**必报一次（从「没满」跨到「满」的那一刻），之后按 **30 秒**（600 tick）节流。
节流状态按玩家记，用 `LinkedHashMap` 的 LRU 封顶 512 人 —— 不是 `WeakHashMap`：键是 `UUID`
这种不可变值，弱引用会把状态随手丢掉，节流就形同不存在；封顶淘汰的代价只是可能多提示一次。

边沿标记还要**复位**：配方本被清空、或用量掉回阈值以下之后，下一次再撞上同一个坎应该重新提示一次。
不复位的话那个 `fullNotified` 会一辈子卡住。

### 为什么提示不在数据层发

数据层（`VoidWarehouseData`）的定位是纯状态。它一旦自己 `sendSystemMessage`，就绑死了
「必须有真玩家」这个前提 —— 自检没法跑、打印机那种无人路径也没法复用。

所以分成两半：`learnWithResult` 只回答「记住了没有、为什么没记住」（`LEARNED` / `DUPLICATE` /
`FULL` / `DISABLED`），`VoidWarehouseRecipeNotice#onCrafted` **返回要发的那几行**，
由 `CraftResultMixin` 逐行 `sendSystemMessage`。跟 `PrinterRestockNetwork` 那边定的规矩是同一条。

`onCrafted` 的 `used` / `max` / `nowTick` 全是入参而不是从 `data` 里读：真把配方本填到 2048 条
既慢（每条都要全量重建）又要造几十秒的存档，拆成入参之后阈值与节流判断就是一个纯函数，
造数字零成本。产品侧照旧从 `recipeBookUsed()` 与 `MAX_RECIPES` 取，口径没变。

### 物品名必须是组件，不能 `getString()`

中文客户端看到英文名的老坑（`PrinterRestockNetwork#notifyTaken` 踩过）。`ItemStack#getHoverName()`
给的是可翻译组件，由客户端按自己的语言渲染；在服务端 `getString()` 会拿**服务端**语言表现场解析，
单人存档里恰好正常（同一个 JVM），专用服务器上永远是英文。

解析不出物品（这个版本没这件东西，比如语料按 26.3 导、跑在 26.1.2 上）时**退回裸 id**：
宁可显示得难看，也不能让整条提示消失。

### 三态是怎么测的

P 组 41 条断言（见下节），三条变异验证它有没有牙：

| 变异 | 改了什么 | 咬住了谁 |
| --- | --- | --- |
| A | `learnCapturingOthers` 的两行顺序对调 | P15b（15→16 条）、P15c → 2 failures |
| B | `LIST_LIMIT` 5 → 100 | P6（箭头数）、P6b → 2 failures |
| C | `FULL_REPEAT_TICKS` 600 → 0 | P11（0 行实测 2）、P11b（2 行实测 0）→ 2 failures |

⚠️ 变异 A 第一次跑出 `failures=0` 是**假绿**：`mutate_p.py` 拿 LF 锚点去匹配 CRLF 的
`VoidWarehouseData.java`，`assert old in s` 抛异常被 shell 循环吞掉，文件根本没改。
做变异测试时**先 `grep` 确认变异真的写进去了**，再看断言读数。

## 已知取舍

- **最多钻 4 层**：更长的链（模组包里的多级中间产物）会停在「这一项找不到料」，结果是保守失败（取不到），不会算错账。层数、节点数、闭包条目数都是硬上限。
- **原料被具体化**：用橡木木板合成过的活塞，之后也只认橡木木板（不认云杉）。数据结构（`Part.candidates`）已经支持多候选，只是本版本不往里填——「认所有木板」需要标签支持，那是另一种语义，得单独设计。详见上一节「木板可互换怎么处理」。
- **不处理 `getRemainingItems`**：像蛋糕那样「牛奶桶用掉又还回空桶」的配方按「扣掉 1 个桶」记账，不退回空桶。偏保守（多扣不少扣），不会刷物。
- **背包快满时首学可能记小产出数**：Shift 快速移动只搬进去一部分时，`onTake` 收到的是零头；此时按「一格算一个」的原则记下来的原料是对的，产出数则偏小（多扣不少给）。这是安全方向，且只在**第一次**学这条配方时可能发生（记住之后不再更新）。
- **配方本全服共用**：仓库是共用的，材料也是共用的，把配方按人头分会让「仓库里明明有材料、却因为不是自己合成过而取不出来」变得没道理。
- **配方本上限 2048 条**：撞到就停止记录（而不是让存档无限长大），并在服务端日志里报一次 `WARN`。原版约 1500 条配方，2048 留了余量。条数本身的代价在 `rebuildRecipes()` —— 每学一条都要全量重建，是 O(N²)，实测 512 条 56.8 ms、2048 条 439~489 ms，且只发生在「学会一条新配方」那一刻。

## 自检


覆盖：纯逻辑（含共享候选反证）、上界与规划口径一致（200 轮 fuzz / 2000 个量，另有一组**带子配方的递归 fuzz**）、编解码（含坏数据）、真实配方解析（含整组 64 只算 4 格、木棍产出 4、空网格 / 无配方 / special recipe 反证）、学习幂等（跨进程幂等，配方本存在存档里）、端到端扣料逐项精确、多产出余量入账、回滚逐项还原（含干扰项、部分保留）、规则关闭后恒为 null、存档往返（混坏行只丢那一行）、**往下钻**（木板没货扣原木 / 不带子配方必须失败的反证 / 先吃库存再补做 / 闭包含深一层 / 深度上限 / 撞环不崩 / 真服务端整链路）、**可互换原料**（同一产物两条配方 / 界面数与实得数一致 / 料少的那条先学也必须给满 / 只剩一种木材时只给 1 / 精确请求落到下一条 / 不跨木材通用）、**配方本提示**（先取后学的快照不含自己 / 截断到 5 条 + 「另有 N 条」 / 1844 与 1843 的阈值边界 / 满本边沿 + 30 秒节流 / 掉回阈值后复位 / 双语 / 渲染形状）。
