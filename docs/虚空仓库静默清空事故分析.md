# 虚空仓库「静默清空」事故：根因与修复

## 一、事故现象

玩家进入存档后，虚空仓库里**全部物品消失**。实测数据：

| | 备份（19:40） | 事故后（21:39） |
|---|---|---|
| 条目数 | 392 | 6 |
| 物品总数 | 6,434,289 | 245 |
| 文件大小 | 4,579 B | 179 B |

剩下那 6 条是**打印机建材的零头**（`moss_block=183`、`wheat_seeds=11`、`iron_block=4` …），
而备份里同名物品的量级是**万~几十万**。这证明**不是「读出 392 条中的 6 条」，
而是在一个全新的空仓库里被灌了 6 笔零头**。

## 二、根因（javap 逐行证实）

### 2.1 `SavedDataStorage.computeIfAbsent` 会静默重建

`net.minecraft.world.level.storage.SavedDataStorage`：

```java
public <T> T computeIfAbsent(SavedDataType<T> type) {
    T existing = get(type);
    if (existing != null) return existing;          // ← 只有这条是「读到了」
    T fresh = type.constructor().get();             // ← 静默造一个全新空实例
    set(type, fresh);                               // ← 无条件 setDirty()
    return fresh;
}

public <T> SavedData get(SavedDataType<T> type) {
    Optional<SavedData> cached = cache.get(type);
    if (cached == null) {
        cached = Optional.ofNullable(readSavedData(type));   // ← 读不出来 → empty
        cache.put(type, cached);                             // ← empty 被永久缓存
    }
    return cached.orElse(null);
}

private <T> T readSavedData(SavedDataType<T> type) {
    try {
        Path file = getDataFile(type.id());
        if (Files.exists(file)) {
            CompoundTag tag = readTagFromDisk(file, type.dataFixType(), dataVersion);
            RegistryOps<NbtOps> ops = registries.createSerializationContext(NbtOps.INSTANCE);
            return type.codec().parse(ops, tag.get("data"))
                       .resultOrPartial(err -> LOGGER.error(...))   // ← 只打日志，不抛
                       .orElse(null);                                 // ← 失败即 null
        }
        return null;      // ← 文件不存在：**一行日志都不打**
    } catch (Exception e) {
        LOGGER.error("Error loading saved data: {}", type, e);
        return null;
    }
}
```

三条致命的叠加效应：

1. **`computeIfAbsent` 无法区分「文件不存在」与「解码失败」** —— 两者都返回 null，
   都走「造新实例 + 标脏」。
2. **`cache.put(type, Optional.empty())` 是永久性的** —— 第一次读失败之后，
   整个进程生命周期内每次 `get()` 都直接返回 null，不会再尝试读盘。
3. **`set()` 无条件 `setDirty()`** —— 空实例被标脏，退出保存时**正常写盘覆盖**完好存档。

### 2.2 `Codec.list` 是「全成或全不成」

`com.mojang.serialization.codecs.ListCodec`：

```java
public void accept(T value) {
    DataResult<Pair<E, T>> elementResult = elementCodec.decode(ops, value);
    elementResult.error().ifPresent(error -> failed.add(value));
    elementResult.resultOrPartial().ifPresent(pair -> elements.add(pair.getFirst()));
    result = result.apply2stable((r, e) -> r, elementResult);   // ← 错误被累加
}
public DataResult<Pair<List<E>, T>> build() {
    ...
    return result.map(ignored -> pair).setPartial(pair);        // ← Error.map 仍是 Error
}
```

**任意一条坏数据 → 整个 `DataResult` 是 error 状态 → `readSavedData` 返回 null
→ `computeIfAbsent` 静默重建 → 退出时覆盖写盘。**

那条「坏数据」可能只是**某个模组被卸载后残留的一件物品**。

### 2.3 关键佐证：日志里连一条解析错误都没有

`readSavedData` 有**且只有一个**返回 null 却**不打任何日志**的分支：
`Files.exists(path) == false`。

本次事故的日志里没有任何 `Failed to parse saved data for ...`（这是
`resultOrPartial` 的回调打的那句），说明 **codec 解析本身没报错**，
`readSavedData` 是在更早的地方就返回了 null。

> 事故当时能做的判断到此为止；之后的防线设计**不再依赖对触发条件的精确复现**，
> 而是「不管因为什么读不到，都绝不允许空壳写盘」——
> 因为触发路径可能有多种（路径不一致、加载时序、并发读……），
> 逐一堵死既不可能也不必要，**只要保证「空壳永远不落盘」就守住了数据**。

## 三、修复（三层防线）

### 防线 1：单条坏数据不牵连整表

`VoidWarehouseData` 里把 `RawEntry.CODEC.listOf()` 换成自实现的 `ITEMS_CODEC`：
逐条独立解码，成功的进仓库，失败的**连同原文**进 `brokenEntries`。
**无论多少条失败，这个方法永远返回 success。**

日志（实测输出）：

```
虚空仓库第 1 条记录解码失败，已跳过（其余 1 条不受影响）：
  DataResult.Error['Not a map: "这不是一个物品"': RawEntry[item=Optional.empty, ...]]
虚空仓库共有 1 条记录解码失败（总 3 条），已保留可读部分继续运行。
```

坏条在写盘时会**原样写回** —— 读不懂 ≠ 可以丢。那个模组装回来它们还能用。

### 防线 2：空壳闸门

`VoidWarehouse.data()` 拿到实例后立刻校验两件事：

```java
int onDisk = countItemsOnDisk(server, overworld);   // 独立读盘，数 items 的真实条数
if (data.isSuspiciouslyEmpty()                       // ① 读到了记录却一条都没还原成格子
        || (onDisk > 0 && data.loadedCount() == 0 && data.isEmpty())) {   // ② 磁盘有货、实例是全新空对象
    throw new IllegalStateException(...);            // 拒绝服务，绝不返回空壳
}
```

- 判据 ① 处理「解码整片失败」；
- 判据 ② 处理 `computeIfAbsent` 走了「新建」分支（`loadedCount` 还是 0）；
- `countItemsOnDisk` 是**独立于 SavedData 加载流程的第二意见**，直接用
  `NbtIo.readCompressed` 读文件数条数，不受 `cache` 里那个 `Optional.empty()` 影响。

**真·空仓库不会误拦**：玩家自己清空的仓库，文件里 `items` 是空列表 → `onDisk == 0`；
正常加载过的空仓库 → `isSuspiciouslyEmpty()` 为 false。

### 防线 3：写盘前快照

`backupOnce()` 在**本进程第一次**触碰仓库时，把磁盘上的文件复制成 `.bak`。
一局一次，语义正好是「进入存档时的上一版」，出问题能直接回滚。

纯 IO、失败只记日志 —— **绝不能因为备份失败就让仓库用不了**。

## 四、路径必须与游戏内部同构

`backupOnce` / `countItemsOnDisk` 都需要知道文件在哪。**不要自己拼字符串**，用游戏自己的方法：

```java
Path root = server.getWorldPath(LevelResource.ROOT);
Path dimension = DimensionType.getStorageFolder(level.dimension(), root);
Path file = dimension.resolve("data").resolve("carpet_neko_addition/void_warehouse.dat");
```

`ServerChunkCache` 建 `SavedDataStorage` 时用的就是
`LevelStorageAccess.getDimensionPath(dimension).resolve("data")`，
而 `getDimensionPath` 内部正是 `DimensionType.getStorageFolder(key, levelDirectory.path())`。
复用同一个方法，路径永远不会跑偏。

> ⚠️ `ServerLevel` **没有** `getDataStoragePath()` 这类方法，不要凭印象写。
> 本次就是这么发现并改掉的。

## 五、自检（`ShellGuardSelfCheck`）

`.workbuddy/tools/ShellGuardSelfCheck.java.template` 是这套防线的回归测试，
挂到 `VoidWarehouseExtension.onTick` 后在真实 `runServer` 里跑，**16 项全通过**：

| 组 | 断言 |
|---|---|
| 单条坏不牵连整表 | S1 整体解码成功；S3/S4 两条好记录原样保留；S5 坏条记为 broken；S6 载入计数正确 |
| 坏条不丢 | S7 重新编码成功；S8 写回仍是 3 条；S9 坏条原文一字不差 |
| 空壳闸门 | S10 正常仓库不误判；S11 空对象自身看不出问题；S12a/b/c 造现场后判据成立 |
| 不误拦 | S13 真·空仓库放行；S14 缺 `items` 字段也能解析（不整表失败） |

**S14 是测出来的真问题**：`ITEMS_CODEC` 最初写成 `fieldOf`（必需字段），
导致缺 `items` 的老文件整体解析失败 —— 正是要防的场景。改成
`optionalFieldOf(ITEMS_KEY, List.of())` 后通过。

## 六、多版本同步的坑

`sync_restock.py` 做整包复制时，**1.21.11 有两个文件不能盲拷**：

1. `VoidWarehouseData.java` —— 与 26.3 只差两处（少一个 `Identifier` import、
   `SavedDataType` 的 id 是 `String` 而非 `Identifier`），但盲拷会编译失败。
   现改为「整文件复制 + 用脚本改这两处」。
2. `PrinterRestockNetwork.java` —— Fabric API 注册入口在 1.21.x 叫
   `playC2S()` / `playS2C()`，26.x（fabric-api 6.3.x）改名为
   `serverboundPlay()` / `clientboundPlay()`。已在 `SKIP_PER_TARGET` 里排除。

> 教训：注释里写的「1.21.11 的数据层是 SavedData + CompoundTag」是**过时的**，
> 实际它也已经用 `SavedDataType + Codec`。改代码前先 `diff` 一遍，别信注释。
