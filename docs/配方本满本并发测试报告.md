## 1. 结论

**一句话**：A2 的**存储改造本身没有问题**（回归 209 条 × 5 版本全绿、可靠性 10 条全绿、界面 6 条全绿），但满本把一条**早就存在、只是从未被触发过**的搜索缺陷照了出来 —— `VoidWarehouseRecipes.maxCraftable` 的「估上界 + 逐个退让」在满本时会**退不到真值**，于是：

- **21% 的配方被判「做不出」**（26.3：1236 条里 260 条），界面上那些物品**整格消失**；
- 而且这批误判**吃掉了 93% 的重建时间** —— 性能问题和正确性问题是**同一个根因**。

**为什么只用一份语料**：语料若各版本各导一份，就同时变了「版本」和「配方集」两个变量，跨版本就没法比。用 26.3 的 1236 条喂五版本，输出的是「同一负载在五个版本上的行为」，这正是对比需要的。代价是 26.2 及更早版本里有 17–43 条配方的原料在该版本中不存在 —— 那些会合法地返回 0，报告里单列（见 §4）。

### 2.2 判定标准

沿用方案 §5，一个 tick 的预算是 **50 ms**：

| 指标 | 优 | 可接受 | 不通过 |
| --- | --- | --- | --- |
| 满本 `exchangeOffers` 单次重建 | < 10 ms | 10 – 50 ms | **> 50 ms** |
| `withdraw` P99 | < 5 ms | 5 – 50 ms | **> 50 ms** |
| 菜单构造 P95 | < 5 ms | 5 – 50 ms | **> 50 ms** |
| 20 人 × 60 次取货总计 | < 200 ms | 200 – 1000 ms | **> 2000 ms** |
| 断言通过率 | — | — | **任何一条 FAIL 都算不通过** |

定时在 50 ms 而不是「感觉快就行」，是因为这条路径**在 tick 里同步执行**：超过 50 ms 不是「慢一点」，而是「这一 tick 的其余工作全部推迟」。

### 2.3 与方案的偏差

方案原定 A–D 四组（只量快慢）。A–D 跑完先看到 `A2` 失败与一条更严重的 `E1`，于是**追加了两组**：

- **E 组**：按规模扫「`maxCraftable` 判 0、但 `plan(1)` 做得出」的条数 —— 量出**丢多少**；
- **F 组**：复刻上界算法 + `plan` 二分求真值 —— 量出**错在哪个量级**，用来决定「调大 64」还是「换算法」。

F 组的复刻是**可证伪**的：`boundCap`/`availOf` 都是 `private`，只能按同一段算法拼回来，正确性由一条自洽断言兜底 —— 凡返回 `R > 0` 的配方，必然满足 `cap − R_crafts < 64`（它就是「从 `cap` 往下退 p 次才成」，p 不可能 ≥ 64）。**五版本覆盖率全部 100.0%（976/976、950/950、924/924×3）**，所以 §6.2 的上界数字可以直接当实测用。

## 5. 瓶颈分析

### 5.1 根因：一条「估上界 + 逐个退让」的线性阶梯

`VoidWarehouseRecipes.maxCraftable`（`common/src/main/java/neko/voidwarehouse/VoidWarehouseRecipes.java:220`）：

```java
BigInteger cap = boundCap(recipe.parts(),
        id -> availOf(id, stock, byOutput, cache, new LinkedHashSet<>(), 0, budget));
BigInteger out = BigInteger.valueOf(recipe.outputCount());
for (int probe = 0; probe < MAX_VERIFY && cap.signum() > 0; probe++, cap = cap.subtract(ONE)) {
    Model model = new Model(stock);
    if (simulate(recipe, cap, model, byOutput, 0, new LinkedHashSet<>(), new int[]{MAX_NODES})) {
        return cap.multiply(out);
    }
}
return ZERO;
```

先用 `boundCap`/`availOf` 估一个**宽松上界**（明知会重复计数），再从 `cap` 开始**每次减 1** 重跑一遍 `simulate`，最多 `MAX_VERIFY = 64` 次。

这段代码的注释里写着它自己的前提假设：

> 那个事故的根因是「上界虚高 × 逐个试探几百次」，而这里的试探上限是 `MAX_VERIFY = 64` **且正常数据里第一次就成**。

**满本把这个前提打破了。**

### 5.2 上界的虚高幅度：不大，但绝对量致命

F 组复刻上界、用 `plan` 二分求 `true`（单位都是**合成次数**）。下表是遍历顺序里最先命中的 4 条，**不是最坏的 4 条**（全量分布的 P50 见 §5.3）：

| 配方 | 上界 `cap` | 真值 `true` | 相对虚高 | **绝对差（需要退让几次）** |
| --- | --- | --- | --- | --- |
| `activator_rail`（9 项） | 18,313 | 16,667 | 9.9% | **1,646** |
| `blue_banner`（7 项） | 6,677 | 5,013 | 33.2% | **1,664** |
| `barrel`（8 项） | 8,309 | 7,838 | 6.0% | **471** |
| `anvil`（7 项） | 3,709 | 3,230 | 14.8% | **479** |

**关键点：相对误差只有 6%–33%，但步长是 1，而数值在万位。**

```
相对虚高 6% × 真值 7,838  = 471 次的绝对差   ← 需要退让 471 次
MAX_VERIFY                = 64              ← 只退 64 次
```

相对误差小 ⇒ 上界「估得挺准」⇒ 但**绝对差**是几百到几万 ⇒ 线性步长必然走不到。所以 `MAX_VERIFY = 64` 不是「偶尔不够」，而是**在这批配方上永远不够**。

### 5.3 丢多少、要退让多少次

**按规模扫（E 组）**：配方本越大，丢得越多，而且**不是满本才开始**：

| 配方条数 | 26.3 判 0 | 26.3 误判 | 占比 | 其余四版本误判 | 占比 |
| --- | --- | --- | --- | --- | --- |
| 100 | 0 | 0 | 0.0% | 0 | 0.0% |
| 300 | 5 | 5 | 1.7% | 5 | 1.7% |
| 600 | 57 | 57 | 9.5% | 53 | 8.8% |
| 900 | 92 | 92 | 10.2% | 84 | 9.3% |
| 1236 | 260 | 260 | 21.0% | 269 | 21.8% |

26.3 的「判 0」与「误判」两列**逐档完全相等** ⇒ 每一条都是假阴性，没有一条是真的做不出。

300 条档命中的是 `bone_meal` / `coal` / `coal_block` / `copper_chain` —— **全是单层或双层的简单配方**。这条值得注意：门槛不是「配方复杂」，而是「**上界比真值大出的绝对次数够大**」。简单配方在原料堆成万时，真值本身就是几千，1 个百分点的虚高就够 64 次了。

**按配方求真值（F 组）**，算出「要退让几次才能摸到真值」：

| 版本 | 样本 | P50 | P95 | max | **> 64 的占比** |
| --- | --- | --- | --- | --- | --- |
| 26.3 | 260 | 3,328 | 19,955 | 114,081 | **260/260 = 100%** |
| 26.2 / 26.1.2 / 26.1.1 / 1.21.11 | 269 | 4,864 | 15,072 | 114,081 | **269/269 = 100%** |

**100% 的误判配方都需要超过 64 次退让。** 差得不是一点点：P50 要 **52 倍**于 64，最坏要 **1,783 倍**。所以 `MAX_VERIFY = 64` 在这批数据上不是「差一点」，是**差一到三个数量级**。

### 5.4 时间归因：21% 的配方吃掉 93% 的时间

| 版本 | 判 0 配方 | 占总条数 | 这批耗时 | 占重建耗时 | 其余配方耗时 |
| --- | --- | --- | --- | --- | --- |
| 26.3 | 260 | 21.0% | **513.5 ms** | **93.4%** | 36.3 ms（976 条） |
| 26.2 | 286 | 23.1% | 581.8 ms | 92.2% | 49.1 ms（950 条） |
| 26.1.2 | 312 | 25.2% | 573.6 ms | 92.5% | 46.6 ms（924 条） |
| 26.1.1 | 312 | 25.2% | 580.0 ms | 92.5% | 47.1 ms（924 条） |
| 1.21.11 | 312 | 25.2% | 570.1 ms | 92.5% | 46.4 ms（924 条） |

推算单次 `simulate` 的成本，两条独立路径互相印证：

```
失败配方：1,975 µs ÷ 64 次 = 30.9 µs/次     ← 精确：次数已知
成功配方：   37 µs（1 次模拟 + 少量开销）    ← 同一量级
```

**两条一交叉，机制就没有别的解释了**：成功的配方第一次就成（1 次 simulate），失败的配方硬跑满 64 次。**失败的每条贵 53 倍**（1,975 µs vs 37 µs）。

> 下面几节统一用 **≈ 35 µs/次 simulate** 这个单价做估算。它在三次独立运行里分别算得 30.9 / 37.9 / 41.6，取整后误差 ≈ ±20% —— 只影响「大概多少」的量级判断，不影响「64 够不够」的结论（那部分是精确的整数比较）。

**所以 P0 和 P1 是同一个根因**：那 21% 的配方既被判错、又是耗时的全部来源。这也意味着「先优化性能、正确性以后再说」不成立 —— 性能本来就花在无效劳动上。

### 5.5 三个反直觉现象，一个解释

| 现象 | 观测 | 解释 |
| --- | --- | --- |
| **原料量无关** | 100 → 100,000 个/种，耗时不变（232 / 319 / 322 / 318 ms） | 成本 = `探针次数 × simulate 成本`，而 `simulate` 被 `MAX_NODES=512` / `MAX_DEPTH=4` 截断，与数量无关；数量本身只是 `BigInteger` |
| **超线性增长** | 配方 12.4 倍 → 耗时 90 倍 | 配方数 ×2.06（600→1236）时，失败率 9.5% → 21.0%（×2.2），两者相乘 ×4.5；实测 ×11.0（29.55→323.80 ms），多出来的部分是「单次 simulate 本身也变贵了」—— `byOutput` 里每个产物可选的替代配方变多，同样 512 个节点的预算探索得更慢 |
| **P50 只有 11 µs** | 但 P99 是它的约 600 倍 | 分布是**双峰**的：78.96% 的配方 1 次模拟就成（≈37 µs）；21.04% 的配方跑满 64 次（≈2.0 ms）。中间几乎没有样本 |

### 5.6 为什么「把 64 调大」不成立

| 方案 | 探针次数 | 单条成本 | 260 条合计 | 结论 |
| --- | --- | --- | --- | --- |
| 现状 `MAX_VERIFY=64` | 64 | 2.2 ms | 0.51 s | 全错 |
| 调到 P50（3,328） | 3,328 | 116 ms | 30.3 s | 仍有一半错，且慢 52 倍 |
| 调到 max（114,081） | 114,081 | 4.0 s | **1,039 s** | 荒谬 |
| **二分（`simulate` 对次数单调）** | **⌈log₂(cap+1)⌉ = 15** | **0.53 ms** | **0.14 s** | **既对又快** |

`simulate(recipe, crafts)` 对 `crafts` 单调（做得越多越难），而现在的代码**已经在依赖这条单调性**（从 `cap` 往下找第一个可行的，就认为它是最大值）。所以换成二分**不引入任何新假设**，只是把「线性扫描」换成「对数查找」。

### 5.7 修完 P0 之后，P1 仍然不达标

按 §5.4 的单价估算（260 条从 64 次降到 15 次）：

```
修复后合计 ≈ 36.3 ms + 513.5 ms × (15/64) ≈ 157 ms    （全部 1236 条，为原来的 29%）
按同一比例折算到满本重建：323.80 ms × 29% ≈ 93 ms
那 260 条一旦判对，还要为它们各跑一次 plan(best, maxOut)：+260 × 35 µs ≈ +9 ms
────────────────────────────────────────────────
满本重建预计落在 65 – 140 ms（多轮波动），中位约 100 ms
```

**仍是 50 ms 预算的 1.3 – 2.8 倍。** 所以「把 P0 修好，性能就顺带好了」是**错的**：二分把 4.5–9.6 倍压到 1.3–2.8 倍，tick 预算还需要另一条独立优化（见 §6 建议 R2）。

## 9. 方法学限制

1. **假玩家没有客户端**：量的是服务端 CPU。客户端渲染、网络包大小不在范围内。
2. **单机、无网络延迟**：真实多人服里 `withdraw` 前面还有一次 C2S 往返，与本改动无关，未计入。
3. **语料来自 26.3**：其余四版本有 17–43 条配方的原料在该版本不存在（合法返回 0）。比的是「同一负载在五个版本上的行为」。
4. **A 组是递增跑的**：后面的档位享受 JIT 预热，绝对值对小规模**偏乐观**。增长形态（超线性）不受影响。
5. **固定 `markChanged()` 模拟每 tick 都有库存变动**：这是最坏情况。真实场景是「变动率 × 重建成本」，不是每 tick 都付。
6. **步长 1 的退让是逐次重跑 `simulate`**，没有增量复用 —— 所以「探针次数 = 时间倍数」这个换算成立。若将来改成增量，§5.6 的估算要重算。
7. **F 组的真值用 `plan()` 二分求**，依赖「能做 k 个」对 k 单调。若某条配方的贪心分支造成跳变，二分只会**低估**真值 ⇒ `need` 偏大 ⇒ 结论方向偏保守。**修复后已实测到这种非单调确实存在**（26.2 起的 `green_cushion`，见 §10.5），影响是「真值偏低」，没有反向风险。
8. **版本间性能不可比**：同版本重复运行差异就有 ±40%，大于版本间差异。要排名次需要固定负载多轮取样。

## 10. 修复与复测（R1 已落地）

> 本章是本报告里唯一描述**现状**的部分。§1–§9 是修复前的快照。

### 10.1 改了什么

只有一处算法改动，落在 `common/src/main/java/neko/voidwarehouse/VoidWarehouseRecipes.java`。**`common/` 是五版本的共享纯逻辑层** —— 五个子工程都 `implementation project(':common')`，并把它的 class 合进各自的 jar。所以改一处**五版本同时生效**，不需要逐版本同步。此外修正了五份 `VoidWarehouseData` 的注释（「试探上限是 64 且正常数据里第一次就成」—— 那句话已被本轮测试直接证伪）。

`maxCraftable` 的「算宽松上界 → 从 `cap` 起每次减 1 重摆，最多 64 次 → 都不成就返回 0」换成：

1. 算宽松上界 `cap`（`boundCap` / `availOf`，一个字没动）；
2. **快路径**：`feasible(cap)` 成立就直接返回 —— 它既是上界又可行，那它就是答案。实测 **79%** 的配方走这条，与修复前一样只跑 **1 次** `simulate`；
3. **慢路径**：在 `[0, cap-1]` 上二分。`feasible(crafts)` = 拿**崭新的 `Model`** 与**崭新的 `MAX_NODES` 预算**跑一次 `simulate`；
4. `feasible(crafts ≤ 0)` 返回 `false`，让 `best` 稳稳停在 `ZERO`，顺便省掉一次没意义的整树模拟。

`MAX_VERIFY` 常量删除。

**两个设计要点，缺一不可**：

- **探针之间必须彻底隔离**。每次探针新建 `Model` 与新建 `int[]{MAX_NODES}` 预算 —— 若共用预算，前一次挖深会让后一次因预算耗尽而假失败，二分的单调性前提当场作废，而症状是「偶发少报」，极难查。
- **快路径必须留着**。删掉它、让所有配方都走二分，等于把 79% 的配方从 1 次探针抬到 `⌈log₂⌉` 次，白贵一个数量级。

**为什么二分不引入新假设**：旧代码「从 `cap` 往下找第一个摆得下的，就当成最大值」本身就依赖「可行集是区间（做得越多越难）」。二分只是把线性扫描换成对数查找。万一某处真的非单调，二分只会**低估**，绝不**高估** —— 而高估是「显示能取、点下去失败」，那是方向错得最贵的一种。

### 10.3 「该出现却没出现」的答案

用户关心的是这一句：**把配方本攒到 300~600 条，有没有物品该出现却没出现。**

- **修复后（E 组，按规模扫）**：100 / 300 / 600 / 900 / 1236 五档 `lost` **全为 0**。
- **修复后（G 组，从货架侧反查）**：五档 `absent=0 missing=0`。G 组的判据**不经过 `maxCraftable`** —— 它枚举「有配方、仓库里没货、却不在货架上」的产物，再用 `plan(1)` 直接问一句「现在点一下能不能做出来」。答能就是界面把它藏了。零条。

**一个可自查的等式**：26.3 满本共有 **1042** 种产物，其中 **296** 种同时也是原料（有货，按规则不出虚拟格），`1042 − 296 = 746` —— 正好等于修复后的虚拟格数。修复前是 651，差的那 **95** 格就是被二分救回来的。**货架与配方本一条不多、一条不少地对上了。**

> 反过来说：**任何「中位数很好看、P99 很糟」的性能画像，都值得怀疑它的尾部是不是在悄悄失败。** 这次就是 6,627 µs 的 P99 背后藏着 260 条永远返回 0 的配方。

### 10.5 两条判据的自我修正（测具的坑，记下来）

这两次都是**测具先错、差点冤枉被测代码**，值得单列：

1. **真值二分的 `hi` 不能截断**。F 组原本用 `min(cap × outputCount, 100_000)` 当上界，真值超过 10 万时被压成 10 万本身，于是冒出一堆「新实现报得比真值大」的假报警（`bone_meal` / `copper_bars` 等 21 例）。改成 `hi = cap`（**次数**口径）即可 —— `boundCap` 按定义就是上界，二分区间天然盖住真值，永远不需要截断。
2. **`got > truth` 不等于「判多」**。`maxCraftable` 只返回**自己用 `simulate` 验证过的数**（快路径验证 `cap`，二分只把 `feasible` 的 `mid` 记成 `best`），所以「报一个取不出来的数」在结构上就不可能发生。`got > truth` 只说明**可行集不是区间**、`truth` 的二分漏掉了更大的可行点 —— 26.2 / 26.1.2 / 26.1.1 / 1.21.11 上各 1 例（`green_cushion`：`got=13392` 可行，`truth=10046` 却漏了）。修正后的三条判据是：
   - **F1 可达性**：`got > 0` 时 `plan(recipe, got)` 必须成功（不变式，防将来有人加一条「猜」的快路径）；
   - **F2 判少**：`got < truth` 必须为 0 —— `truth` 永远是可行点，比它小就是真漏报；
   - **非单调**：`got > truth` 的条数只作观测，不判失败。

`green_cushion` 那 1 例还顺带证明了 §9 第 7 条的担心是**真实的**：可行集确实不是严格区间。但它落在「二分低估」的方向上（保守），且 `maxCraftable` 这次报的是**更大**的那个数，所以对玩家无害。要在非单调情形下求严格最大值，只能退回线性扫描 —— 而在 18,000 次的区间上线性扫描是本报告 §5.6 已经否掉的方案。

### 10.6 仍未解决：P1-1

**123 – 162 ms 依然是 50 ms tick 预算的 2.5 – 3.2 倍。** 修复前是 4.5 – 9.6 倍。

这条**不会**因为修好 P0-1 而消失：问题不在「单条算得慢」，而在「每次库存变化都把 1236 条**全部**重算一遍」。要做的是 §6 的 R2 —— 让 `collectCraftOffers` 只算当前页需要的产物，或让 `markChanged` 只脏化受影响的产物集合。它要碰 U2「展示顺序稳定」和分页总数统计（不全算怎么知道总页数），风险中等，本轮没做。


`chiseled_copper` 只有 **2** 个原料，却花 5.2 ms，说明贵的不是「原料多」，而是**上界 `cap` 大** —— 铜类原料在合成里的可用量是万级，二分要 `⌈log₂(cap+1)⌉ ≈ 14+` 次探针，每次探针都重跑一遍带兄弟配方分支的递归 `simulate`。B 组的数据正好从另一个角度印证：同一份 1236 条配方，只把每种原料的量从 100 抬到 100,000，重建耗时从 **75.91 → 99.02 → 122.12 → 128.37 ms** 单调上升 —— 库存越大 `cap` 越大、探针越多。**耗时 ≈ 探针数 × 单次递归成本，两个乘数都还在**，这是 R2 的靶子：探针数要降（按页 / 按脏化集合），单次递归成本也要降（同一份库存下兄弟配方共享已算结果）。

顺带把其余几组的本轮读数记齐（26.3，供下次对比）：A 组 100/300/600/900/1236 = 6.07 / 7.48 / 28.08 / 40.80 / 123.88 ms；`withdraw` p50 12.4 µs / p99 886 µs / 60 次全成功；菜单 90 格、p95 0.042 ms；20 人 60 次取货 7.23 ms、avg 120.6 µs；满本堆占用 262.6 MB（2048 条）。

### 11.5 跨版本 `offers` 不一样，不是回归

26.3 的满本虚拟格是 **746**，其余四版是 671 / 652 / 652 / 652。这个差**两轮完全一样**，成因是跨版本复用同一份语料（在 26.3 导出）：

- 语料共 **1042** 种产物，其中 **296** 种同时也是原料（有货，按规则不出虚拟格）——`1042 − 296 = 746`，26.3 严丝合缝。
- 其余版本少 75 / 94 格，来自两件事叠加：`VoidWarehouseRecipeBook.itemOf(id)` 对**本版本不存在的物品**返回 `null`（这些条目在各界被整条跳过），以及判 0 的 17 / 43 条。
- 这两个数**不能直接相减对齐**：`zero` 按**配方**计、`offers` 按**产物**计，同一产物可能有多条候选配方。所以别拿 746 − 671 去反推「少了 75 个物品」。

要紧的是：`E1` 与 `G1` 在四个非 26.3 版本上同样全 0 —— 判 0 的每一条都真做不出，货架上一条没藏。**语料比版本新这件事只缩小了覆盖面，没有制造假绿。**

### 11.6 本轮顺手修掉的两处工具缺陷

两处都在 `.workbuddy/tools/`，不进 jar、不影响产物，但会让「完整测试」跑不起来或跑出不可信的日志：

1. **`install_craft_selfcheck.py` 不接受裸版本号。** `DEFAULT_TARGETS` 存的是 `modern/26.3` 这种带前缀的路径，而拼接处直接 `os.path.join(ROOT, target, ...)`，命令行传 `26.1.1` 就拼成 `ROOT/26.1.1/src/...` → `FileNotFoundError`。配方专项因此一直只能「四版本全装」。加了 `resolve_target()`：带分隔符原样用，裸版本号补 `modern/` 前缀。
2. **`SystemTest` 的 `RESULT` 行版本标签是模板里写死的 `v26.3`。** 五个版本共用一份模板，于是五份日志全都自称 `v26.3` —— 事后按版本号 grep 一无所获，日志失去自证能力。改成安装时按目标版本注入（`"SYSTEM TEST RESULT v%s checks="`），本轮五份日志已分别打出 `v26.3 / v26.2 / v26.1.2 / v26.1.1 / v1.21.11`。

两处改完各跑了一次「装 → 摘」往返。`install_systest.py` 写 `Extension` 时是「探测原文件换行 → 原样写回」，抽检 26.1.1 摘完后 `git ls-files --eol` 仍是 `i/lf w/crlf`、`git status` 无差异；`install_craft_selfcheck.py` 的 111 行仍为纯 LF（`i/lf w/lf`），与改动前一致。

## 12. R2：把「复制小 map」换成「记旧值回滚」（P1-1 闭合）

> 一句话：**满本重建 123.88 → 22.17 ms，五版本 A2 判据首次全绿**。
> 但真正值得记的不是这个数字，而是**§6 里我原本给 R2 开的方子是错的** —— 见 §12.6。

### 12.1 先归因，再动手

§6 的 R2 建议写的是「按页算」或「只脏化受影响的产物集」。动手前先做了一件事：**把 123 ms 拆开看**。做法是把 `common/` 的 `VoidWarehouseRecipes.java` 原样复制到离线台、只插入 6 处计数器（脚本断言每个锚点唯一，锚点漂移就拒绝生成），然后复刻 `collectCraftOffers` 的口径跑一遍全文语料。

复刻是否可信，用一个数校验：脚本算出「需要计算的产物」**746** 个 —— 与真服务端 A 组打出的 `offers=746` 完全一致，说明语料、库存口径、跳过规则（有货的产物不出虚拟格）都复刻对了。

归因结果（26.3，1236 条配方 / 每种原料 10000）：

| 阶段 | 耗时 | 占比 |
| --- | --- | --- |
| `stockClosure`（每配方一次闭包） | 3.25 ms | 2.7% |
| `maxCraftable`（上界 + 探针） | **97.71 ms** | **82.7%** |
| `plan`（给选中的配方算账单） | 10.43 ms | 8.8% |
| 其余（排序 / 建 offer / ItemStack） | 6.8 ms | 5.7% |

再往下切一层：

- 探针合计 **5,393** 次；`simulate` 走过 **51,645** 个节点；往下钻 **41,156** 次。
- **`Model.copy()` 被调用 164,505 次** —— 平均每次探针 30 次，每次复制要重建一个 40~60 项的 `HashMap` 外加两个 `LinkedHashMap`。
- 542 条配方走快路径（1 次探针）合计 **5.7 ms**；324 条走二分（16~17 次探针）合计 **92.0 ms** —— **37% 的配方吃掉 78% 的时间**。

**结论：钱不在「算了几条配方」，在「每次探针复制了几十份账本」。** §6 的两条 R2 路线（按页算 / 脏化集合）优化的都是「算几条」，而真正的乘数是「每条算多贵」—— 方向错了。

### 12.2 改了什么

只动 `common/src/main/java/neko/voidwarehouse/VoidWarehouseRecipes.java` 一个文件（共享层，五版本同时生效）。三处，主次分明：

**① 主干：`Model` 从「每个分支复制一份」改成「记旧值 + 回滚」。**

原写法是 copy-on-branch：
```java
Model trial = model.copy();          // 复制 pool + consumed + surplus
if (supply(candidate, amount, trial, ...)) { model.adopt(trial); ... }
```
新写法是日志化撤销：
```java
int mark = model.mark();
if (supply(candidate, amount, model, ...)) { ... }   // 成功就不回滚
model.rollback(mark);                                // 失败按日志倒序贴回旧值
```

旧注释里明确否决过「改用逆操作」，理由是「逆操作的写法容易漏，漏一处就是账目对不上」。这个担心是对的，但**「记旧值」不是「写逆操作」**：它不推导任何反向运算，只是把 `(哪本账, 键, 旧值)` 压栈，回滚时贴回去。而「所有写都必须经过日志」这一条不是靠自觉，是靠三个 map 字段全部 `private`、只暴露 `setPool` / `addConsumed` / `addSurplus` 来**强制** —— 想绕过日志直接写 map，当场编译不过。

代价是撤销日志本身要分配。这里用三个平行数组（`int[] / String[] / BigInteger[]`）+ 倍增扩容，不用对象，避免每次写都装箱。回滚后还要把 `undoKey` / `undoOld` 的尾部槽位置空，否则数组会一直拽着字符串不放。

**② 附带：`pool` 改成对库存的惰性覆盖层。**

原来 `Model(stock)` 一上来就 `new HashMap<>(stock)`，每次探针都要复制一遍 40~60 项的库存。改成「自己的覆盖值优先，没有就回落到库存快照」——探针只需要付一次构造成本，而不是每次一次。`available(item)` 因此只做一次哈希查找（覆盖值不会是 `null`，所以 `get != null` 就等价于 `containsKey`，省掉第二次查找）。

**③ 附带：探针关掉扣料账本。**

`maxCraftable` 的探针只问「摆不摆得下」，`consumed` / `surplus` 既不参与判断也不被读取。加一个 `trackBooks` 开关，探针传 `false`，`plan` 传 `true`。实测把写操作从 198,024 次降到 90,658 次。

**④ 附带：小整数走 `long`。** `ceil(rest / out)` 与 `crafts × count` 是模拟器最热的两行，量级远在 `long` 内（阈值取 40 位，`2^40 ≈ 1.1×10¹²`，再乘 64 也不溢出），超出就退回 `BigInteger` 原路。顺带把 1~64 的 `BigInteger` 做成常量表 —— `BigInteger.valueOf` 只缓存 -16~16，其余每次都新建。

> **诚实记一笔**：③ 和 ④ 在离线台上**测不出差别**（38.77 / 41.54 / 41.35 / 43.49 ms，与只做 ①② 时的 37.69 ~ 41.51 ms 同区间，噪声比效应大）。保留它们不是因为测得有效，而是因为它们**行为可证明等价**（见 §12.3 的对拍）且降低了实际工作量；如果将来有人要精简代码，这两处是最先可以删的，删了不影响正确性。

### 12.3 正确性：7,416 行输出对拍同一个 SHA-256

性能改动最怕「快了，但答案变了」。所以**每次改动都跑一次对拍**：

- 把 `HEAD` 版本的 `VoidWarehouseRecipes.java` 与工作区版本分别编译到两个目录，喂同一份语料、同一套库存口径；
- 每条配方输出 `maxCraftable` 的结果，外加 5 个目标量（1 / 1 份 / 7 份 / 64 份 / 9999 份）的 `plan`，**把 `consumed` 与 `surplus` 的完整内容按 key 排序打出来** —— 这是扣料账本的指纹，回滚只要错一格就会差出来；
- 全部输出算 SHA-256。

三次改动（trail / trackBooks / long 快路径）各跑一次，三次结果都是：


7416 = 1236 条 × 6 项。**这比对拍是这类重构唯一可信的验收方式** —— 只跑压测通过不代表账本没漂，因为压测只验「能不能做出来多少」，不验「扣了哪些、还回哪些」。

### 12.6 为什么没走「减少探针」这条路（原定 R2 是错的）

归因之后先想到的是「324 条配方各跑 16~17 次探针，能不能少跑几次」。于是量了「真值 ÷ 上界」：

```
多探针配方 真值/上界 分布：<1/16 0 ｜ 1/16~1/4 0 ｜ 1/4~1/2 0 ｜ >1/2 324
```

**324 条全部落在上界的一半以上**（`purple_wool_stairs` 上界 40,000 / 真值 35,000；`magenta_cushion` 36,665 / 35,000；`acacia_chest_boat` 16,250 / 16,248）。也就是说上界估得**很紧**，不是「虚高得离谱」，那就没有「先跳几次再二分」的空间 —— 在 `[0, 65000]` 里用 yes/no 问答定位一个整数，16 次本来就接近信息论下限。**探针数压不动，只能压单次成本。**

这条否掉了 §6 里两条候选路线的另一半（「按页算」只减少调用次数，不减少每次的复制量，最多省掉 3.25 ms 的闭包 + 部分 `plan`，收益 < 15%，却要动 U2 顺序与分页总数 —— 代价远大于收益）。所以 R2 最终做的既不是「按页算」也不是「脏化集合」，而是把**每次探针的固定开销**打掉。

> ⚠️ **这段里的「收益 < 15%」只对『按页算』成立，对『脏化集合』是错的。** 当时把两条路线混在一起估，结论下早了：真正按受影响产物增量重算，能省掉 **93% 的产物重算**（一次改动只碰 13/746 个），R3 实测 **14.7×**。教训不是「先归因再优化」错了（那条仍然成立，也正是它把 R2/R3 都指对了），而是**估算必须在真实调用序列上量**，不能在脑子里把两条不同代价的路线归成一类。详见 §13.6。

## 13. R3：按受影响产物增量重算（P2-1 的代价侧闭合）

### 13.1 原定的 R3 是错的，先看测量

§6 的 R3 写的是「`maxCraftable` / `stockFor` 结果按 `(recipeId, stockVersion)` 缓存到 tick 级，供 `collectCraftOffers` 与 `resolveCraft` 共用」。按 R2 的规矩，先量再改。测量台 `C:/tmp/harness2/Dirty.java`（不进仓库，只复刻 `collectCraftOffers` 的口径）跑出两组数：

**① tick 级缓存的命中率是 0.0%**

```
---- tick 级缓存命中率（60 次取货、每次推进版本）----
  maxCraftable 调用 65 次，同版本重复 0 次 ⇒ 命中率 0.0%
  对照（同版本内全量问 3 遍）：2598 次调用、重复 1732 次 ⇒ 命中率 66.7%
```

原因很硬：**一次取货必然改库存**，`markChanged()` 随之推进版本，于是「同一个版本里再问同一条配方」在真实操作序列里根本不会发生。对照那行说明缓存机制本身是好的（同版本内问三遍能中 66.7%），只是**真实序列里不存在这种输入**。这条路线直接作废。

**② 但「一次改动会影响多少产物」很小**

```
产物 746 个（参与 offers 的）｜ 反向索引覆盖物品 443 种
---- 一次改动影响的产物数（按物品计）----
 0 个 0 ｜ 1~5 个 280 ｜ 6~20 个 104 ｜ 21~60 个 31 ｜ 61~150 个 26 ｜ >150 个 2
平均 13.0 个产物/物品（占 746 个产物的 1.7%）｜ 最坏 minecraft:oak_log = 184 个（24.7%）
```

所以真正在重复的不是「同一条配方被问两次」，而是「**整张表被重算一次，而其中 733 个产物一个字都不会变**」。R3 改成这个形态。

### 13.2 改法：三个原语记脏 + 依赖集 + 增量重算

**脏集合从哪来。** `VoidWarehouseData` 里能改库存的只有三个原语 —— `consume`（整个仓库唯一一处「减少数量」）、`produce`（9 合 1 找零）、`put`（`insert` / `restore` 走）。三处各加一行 `changedItems.add(item)`；`entries` 的其它写入路径只剩构造期的 `absorb`，那时缓存还没建过，天然整批。**这个集合是完备的**，而且「少记一处」的后果只是「那件物品相关的产物一直显示旧数字」，不会有更坏的形态。

**凭什么说「只有 13 个会变」。** 一个产物的结果只依赖它候选配方**整条闭包**里那些物品的数量（`stockClosure` 的键集），外加它自己的数量（决定它出不出现在界面上）。这张依赖集在配方本换版时算一次（`buildCraftDeps`），之后每次改动只重算「依赖集里含脏物品」的产物。

**为什么不建反查索引（物品 → 产物）。** 一次改动只有一两个物品、产物有几百个，直接拿脏物品去问每个产物的依赖集是 `746 × 2` 次哈希查找（实测约 30 µs），比维护一张反查表省事得多，也不会出现「表没同步」这类事故。脏物品超过 96 个时直接整批重算（`96 × 746` 已接近整批的量级）。

**为什么不需要动分页与展示序。** §6 当初否掉「脏化集合」的理由是「要先想清怎么在不全算的前提下知道总页数」。这个顾虑**在这一版形态下不存在**：表还是那张完整的表（746 个产物，该是 `null` 的仍是 `null`），只是**没重算那些结果不会变的项**。分页总数、`unifiedOrder` 的归并、`-(下标+1)` 编码全部照旧。

顺序稳定靠的是 `craftOffers` 用 `LinkedHashMap`：整批重算时按 `recipesByOutput` 的遍历序填充，增量更新走 `put`，**对已有键不改顺序**。于是「同一份库存、同一份配方本」无论走过多少次增量，遍历顺序都和整批一致 —— 不靠排序兜底（`rankOf` 只保证秩唯一，同秩时的先后由遍历序决定）。

**顺手多出一条快捷路径。** `Container#setChanged()` 会调 `markChanged()`，而它「什么都没改」。既然脏集合为空就等价于「一格都没变」，这种情况直接沿用上一份表，一次乘法都不做。判据必须带上 `craftCacheBusted`：`clearContent()` 会把库存整体清空却**不逐件记账**，少了这一项就会把上一份「还带着已经不存在的物品」的表当新表返回。

### 13.3 正确性：增量与整批逐字节对拍

新增 `VoidWarehouseCraftSelfCheck` 的 **M 组（11 条）**。做法是给每一次改动都配一份**整批重算**的对照：把同一份库存原地 `clearContent()` 再灌回（这会强制每个产物都重算一遍），配方本一个字不动 —— 于是两边是「同一份输入、两种算法」，把可兑表按字面量摊平（`itemId|obtainable|bulk|boxed|craft|账目`）逐字节比对，**顺序照原样不排序**（顺序本身就是要证的东西）。

覆盖的改动类型：某格少 1 / 产物自己进仓库 / 产物再取空 / 动最上游一层（三层下钻全变）/ 一种原料抽干 / 学一条新配方（依赖集重建）/ 同一 tick 连改三处 / 只 `clearContent()` 不灌料 / 清空后重灌 / 逐格抽干。

**两次变异测试证明这组有牙**（改坏产品代码，看自检是否当场红）：

| 注入的变异 | 结果 |
| --- | --- |
| `buildCraftDeps` 里去掉「产物自己」（`items.add(group.getKey())`） | **M3/M4 红**：增量里活塞明明有货，却还挂在「可合成」表上 |
| 快捷路径去掉 `!craftCacheBusted` 判据 | **M9 红**：清空仓库后第一读把旧表原样返回 |

> 第一个变异是**理论上的必踩点** —— 产物自己几乎不在自己的闭包里（活塞用的是木板，不是活塞），「有货就不出虚拟格」这条闸门完全靠显式把产物自己塞进依赖集。第二个变异是**写完自检才想到的洞**：M 组每次都 `clearContent()` 后立刻灌料，脏集合马上又非空，正好把它盖住；M9 是专门为它补的一档。

### 13.6 为什么 §12.6 里「收益 < 15%」是错的

R2 那轮把「按页算」和「脏化集合」归成一类，估出「最多省 15%」。这个估计对「按页算」成立（它只减少调用次数，不减少每次探针的复制量），对「脏化集合」完全不成立 —— 后者省掉的是**被跳过那些产物的全部探针**，实测 93%（733/746）。

当时的推理漏洞很具体：**用一个静态比例（闭包占 2.7% + 部分 `plan`）去代表一条动态路线的收益**。正确做法就是本轮 `Dirty.java` 干的事 —— 在真实语料上把「一次改动影响多少产物」直接数出来。教训写进 `REFERENCE-lessons.md`：**估算必须在真实调用序列上量；把两条代价结构不同的路线归成一类，比不做估算更危险，因为它会让人理直气壮地跳过唯一有效的那条。**

「先归因再优化」这条本身仍然成立，而且正是它把 R2 和 R3 都指对了：R2 归因到「每次探针的固定开销」，R3 归因到「每次都重算整张表」。

### 13.7 P2-1 现在的状态

P2-1（`resolveCraft(allowPartial)` 对同一产物的每条候选配方都跑一次 `maxCraftable`）的**结构性重复仍在** —— 本轮**没有**改 `planCraft` / `planCraftWith` 的任何一行，因为取货路径必须重新规划（旧名单可以点击，但账必须在点下去那一刻重算，这是「不会凭空造物」的依据）。

实测它的绝对代价已经不值得动：

### 13.8 遗留

- **配方本换版后的第一次重建仍是整批**（`max_ms` 23–73 ms，见 §13.4 末段）。学一条新配方就会付一次：`craftDeps` 整张重建 + 746 个产物全部重算。暖机下比稳态多 3~8 ms，仍在 50 ms 预算内，但余量比稳态小一个数量级。要压它得把 `buildCraftDeps` 也做成增量（按物品记忆化的可达集，把 746 次闭包遍历压成 443 次 DFS + 1236 次集合合并）—— 收益只在「刚学完配方的那一 tick」，暂不做。
- **`craftDeps` 的内存**：746 个产物 × 平均 40 来个闭包键 ≈ 3 万个字符串引用。相对整个存档可忽略，但它是**每个 `VoidWarehouseData` 实例一份**（存档唯一，所以只有一个实例）。
- ✅ **`CRAFT_DIRTY_LIMIT = 96` 那条分支没有被单测直接覆盖** → **已关闭（§14.4 / §14.6）**。当时的判断是「真要直接测，得在一次 tick 里改动 97 种不同物品 —— 现有工具造不出来，收益不抵成本」，这个判断错在**方法**上而不是成本上：这条分支**没有可观测的行为差异**，用「造数据 + 比结果」这条路根本测不出来。改用「往私有缓存泼错值、看它有没有被纠正」之后，造 97 种填充物只是三十行代码（按 `craftDeps` 的并集当排除集，从注册表顺序取前 97 个可入库物品）。

## 14. 收尾：一段三轮没生效的去重，与 `CRAFT_DIRTY_LIMIT` 的两侧边界

§13.8 留了两条尾巴，这一节把它们收掉：

1. 「`collectCraftOffers` 里 `taken.contains(itemId)` 的去重从未生效」—— 上一轮定性清楚了但没动代码，
   因为修它会改变「两个规则都开」时的 `offers` 计数，要等人拍板。本轮修了。
2. 「`CRAFT_DIRTY_LIMIT = 96` 那条分支没有直接单测」—— 本轮补了 12 条断言（N 组），
   并且设计了一个能**真正观察到分支跑没跑**的判据。

### 14.1 症状：同一件东西占两格，一格「可兑」一格「可合成」

复现路径很短：9 合 1 表里本来就有 `iron_ingot → iron_block`（9:1，`VoidWarehouseExchange` 第 195 行），
玩家再学一条「9 个铁锭 → 1 个铁块」的配方，然后仓库里有 18 个铁锭、0 个铁块。
此时两条路**都**认为可以给出 `iron_block`：

| 来源 | `ExchangeOffer.itemId()` | `craft` | 谁该留 |
| --- | --- | --- | --- |
| 9 合 1 | `iron_block`（**只留 path**） | `false` | ✅ 优先 |
| 配方扣料 | `minecraft:iron_block`（**全命名空间**） | `true` | ❌ 应被滤掉 |

去重代码是 `taken.contains(offer.itemId())`，而 `taken` 里装的是第一行的 path 口径。
`Set<String>.contains` 拿 `"iron_block"` 比 `"minecraft:iron_block"` —— **恒为 `false`**，
整段去重从 R3 落地那天起就没生效过。

没被玩家报障，是巧合叠巧合：语料 1042 个产物里有 65 个落在 9 合 1 表内，但
`voidWarehouseExchange` **默认是 `false`**，而 A2 / 大部分 `SystemTest` 组只开配方扣料，
`collectNineInOneOffers` 一条都不产、`taken` 本来就是空的 —— 连「恒 `false`」都测不出来。

### 14.2 两处注释与事实相反

改代码之前先把「为什么没人发现」查清楚了，结论是文档在骗人：

- `VoidWarehouseRecipes.Recipe#output` 写着「`minecraft:` 前缀已去掉，与 9 合 1 表的口径一致」——
  事实是它来自 `VoidWarehouseRecipeBook.idOf`（即 `Identifier#toString`），**带全名**。
- `ExchangeOffer#itemId` 写着「两者只在各自内部使用，不互相查表，所以不必统一」——
  事实是 `exchangeOffers()` 天天拿它们互相比。**两处注释合起来把唯一的 bug 说成了设计。**

已经订正（`common/` 一份 + 五个 `VoidWarehouseData` 副本）。

### 14.3 改法：只在一处归一，且不给 `withDefaultNamespace` 喂全名

```java
java.util.Set<String> taken = new java.util.HashSet<>(built.size() * 2);
for (ExchangeOffer offer : built) {
    String raw  = offer.itemId();
    String full = raw.indexOf(':') >= 0 ? raw : "minecraft:" + raw;
    String canonical = VoidWarehouseRecipeBook.idOf(VoidWarehouseRecipeBook.itemOf(full));
    taken.add(canonical != null ? canonical : raw);
}
```

- **归一只留这一处**：`exchangeOffers()` 是唯一同时看得见两种口径的地方，翻译放这里，
  `collectCraftOffers` 只管按全名比。
- 🔴 **不能用 `VoidWarehouseExchangeBootstrap.itemOf` 吃全名**：它内部是
  `Identifier#withDefaultNamespace`，会把 `minecraft:iron_ingot` 拼成 `minecraft:minecraft:iron_ingot`
  并**当场抛 `IdentifierException`**。第一版就是这么写的，把整组自检炸成日志里一句「自检抛异常」，
  连哪条断言都没跑到。换 `RecipeBook.itemOf`（`tryParse`）才对，两种口径都认。
- **翻译不出来的原样留着**（`canonical == null` 时 `add(raw)`）：这个版本没有这件物品时宁可不去重，
  也不要把 id 丢掉。
- 语义**只会少不会多**：`taken` 里多一个 id，最坏是滤掉一格；不会凭空造出一格。

### 14.4 `CRAFT_DIRTY_LIMIT` 怎么测：错值泼水法

那条分支（`changedItems.size() > 96` → 整批重算）**没有任何可观测的行为差异** ——
整批和增量给出的结果本来就该一分不差。所以「跑完对比结果」测不出分支跑没跑，
断言会变成一句永远绿的废话。

判据改成**往私有缓存里泼一条错值，看它有没有被纠正**（反射拿 `craftOffers`、`craftDeps`、`CRAFT_DIRTY_LIMIT`）：

| 读数 | 脏物品数 | 走哪条 | 错值（`piston` 那一格被置 `null`）的结局 |
| --- | --- | --- | --- |
| N4 | 恰好 96（= 阈值） | 增量 | **原样留着** —— 96 个填充物全在依赖集之外，一格都不重算 |
| N5 | 97（阈值 + 1） | 整批 | **被纠正** —— 每格都重算 |

于是「96 → 错值还在、97 → 错值没了」这一对读数就把阈值钉死在原地，
同时证明那段循环体真的在跑，而不是永远进不去的死代码。

四条配套的防线，缺一条这组就会变成假绿或假红：

- **填充物必须真的在依赖集之外**：靠反射读 `craftDeps`，把它所有 `value` 并起来当排除集，
  而不是硬编码一串物品名（配方本会随组内 `learn` 变）。
- **阈值反射读，不在测试里抄一份**：抄一份就有两个真相，产品那边调了常量而测试还按 96 造数据，
  测的就变成一条不存在的线。
- **N5c 断言缓存是同一个 map 对象**：只有「配方本换版」那条分支会 `new` 一个新 map。
  真被换掉的话，泼进去的错值会随口消失，N4/N5 会看着像通过、其实什么都没测到。
- **潜影盒不进填充物**：`insert` 会把非空盒拆成壳 + 箱 + 染料，一次 `insert` 多记好几样物品，
  脏集合的 `size` 跟预期对不上，96/97 就假了。

补完 N1c / N6 之后又做了**三次变异**（都只改 26.3、跑完 `git checkout` 还原），确认新断言不是摆设：

| 变异 | 改了什么 | 咬住的断言 | `checks / failures` |
| --- | --- | --- | --- |
| **A** | `taken.add(...)` 注释掉 —— 还原成 1.0.17 修掉的那个形状 | N1（实测 2 格）、N2（重复 `iron_block / minecraft:iron_block`）、**N1c 格数**（实测 2 格） | 166 / **3** |
| **B** | 把 9 合 1 那半的 `iron_block` 从 `built` 里丢掉 —— 留下的那格变成配方 | N1b、**N1c 数量（实测 4，期望 2）** | 166 / **2** |

B 是这轮真正想验的那一条：只用 9:1 配方时，两条路算出来的数**都是 2**，

C 则说明 N6 判的是「**写多少、给多少**」这条红线，不是「给得够不够多」——
判据用等号而不是「大于等于」，因为多给同样是在动玩家没要的东西。

### 14.6 N 组 17 条断言

| 编号 | 断言 | 反证 / 前置 |
| --- | --- | --- |
| N0 | `craftOffers` 里 `iron_block` 那一格算得出来 | 学不进去 = N1 空转 |
| N1 | 该物品**只占一格** | 变异后实测 2 格 |
| N1b | 留下的那格是 9 合 1 | 防「滤错方向」 |
| N2 | 整张表**没有两格指向同一件物品**（按 `Item` 对象比） | 不依赖具体样本 |
| **N1c 前置** | 再学一条 **4:1** 的 `iron_block` 后，配方那半**单独**算出 **4** | 两格数字必须真的不同，否则下面是空断言 |
| **N1c ×2** | 仍然只占一格；那一格写的是 **2**（9 合 1 口径）而不是 4 | 变异 A 咬格数、变异 B 咬数字 |
| **N6** | 界面写能拿 `n` 个 → 按量要 `n` 个**正好**拿到 `n` 个 | 变异 C 当场红 |
| **N6b** | 按量要得比界面多时整段让位给配方（界面 2 / 按量 4） | 已知边角，**钉住行为而非正确性** |
| N3 ×4 | 前置：`piston` 在缓存里 / 凑到 97 种填充物 / 反射读得到 / 重新取到缓存对象 | 任一条不成立就中止 |
| N4 ×2 | 96 种 → 错值还在 | 证明走的是增量 |
| N5 ×3 | 97 种 → 错值被纠正、`piston` 回到表里、map 是同一个对象 | 证明走的是整批 |

**N1c 为什么必须换比例**：N1 学的那条配方是 9:1，**与 9 合 1 比例完全相同**，
于是两格算出来都是 2 —— 就算去重失效、玩家真看见两格，两个数字也一样，看不出更难看的那种表现。
再学一条 4:1 把两边逼开（配方 4 / 9 合 1 2），「只剩一格」和「那一格写 2」才同时有意义。
后者尤其要紧：`VoidWarehouseMenu#withdrawFrom` 只取 `target.template()`，
**完全不看 `offer().craft()`**，取货永远按 `planExchange`「9 合 1 优先」那条走；
tooltip 写成 4 而实际扣 9 合 1 的料，就是「写的数不是给的数」。

**N6 为什么写成等号**：界面走 `planExchangeMax`（允许部分），按量取货走 `planExchange`（精确），
这两条不是同一条路。唯一必须守住的共同真相是「界面写能拿几个，按量要几个就真能拿到几个」。
写成「大于等于」会放过「多给」，而多给同样是在动玩家没要的东西。

**N6b 是留着的一条已知边角**：同一份 18 锭库存下，界面 `planExchangeMax(铁块, 64)` 给 **2**
（9 合 1 允许部分），按量 `planExchange(铁块, 4)` 因为 9 合 1 兑不出 4 个整量而**整段让位给配方**，
给的是 **4**。方向是「多给」，不会造成点了拿不到，但确实违反「tooltip 写的数就是实际给的数」。
要修得动 `planExchange` 的分派顺序（先算 9 合 1 的上限再统一裁），属于语义变更，
本轮只把它变成一条可观测的读数 —— 将来谁把这条改绿了，等于承认改了分派顺序。

**缓存引用必须重新取**：N1c 的 `learn` 会让 `recipeGeneration++`，
下一次读走「配方本换版」那条分支、重新 `new` 一个 `craftOffers` map。
N3 还抱着 N0 抓到的那份 `initialCache` 的话，泼进去的错值落在一个已经被丢掉的对象上，
读数变成「错值本来就不在」，看着像通过、其实什么都没测到。所以 N3 开头**重新反射取一次**，
并补了一条「反射取得到」的前置（N3 由 ×3 变 ×4）。N5c 再守住「之后一直没被换掉」。

还有两条**踩坑记录**，注释都写进模板了：

- **`voidWarehouseExchange` 默认 `false`**：不显式打开的话 9 合 1 那半根本不存在，
  N1 会「只剩一格」地假绿。开完在组尾还原。
- **`learn` 的返回值不能当前置**：配方本落在存档 `.dat` 里、**跨进程持久化**，
  同一台机器跑第二遍 `learn` 必然返回 `false`（已存在）。改成看「缓存里那一格算出来没有」，
  两种情形都成立。

### 14.8 哪些数会变、哪些不会

**不会变**：只开配方扣料时（`voidWarehouseCraft` 开、`voidWarehouseExchange` 关）整条路径完全不受影响 ——

| 版本 | 改动前 | 改动后 |
| --- | --- | --- |
| 26.3 | 738 | **738** |

| 26.1.2 / 26.1.1 / 1.21.11 | 644 | **644** |

第一反应是「改坏了」，但 `sink` 是**非负数之和**，去重只会让 `offers` 变少、**不可能让它变大** ⇒
这条改动在结构上不可能是原因。真相是新增的 N 组往测试存档里多学了 3 条配方（`learn` 落盘），
`offers` 基数变了。两次相同运行给出逐字相同的 `sink`，也确认了它是确定量而非噪声。

本轮读数 9,901,959 / 8,893,383 / 10,798,292 / 10,019,028 / 18,984,148 互不相同。
**能跨版本比的只有断言**，1,884 条全绿才是本轮的真指纹。

## 15. R4：预编译配方树 + 共享库存快照 + 可复位模拟草稿纸

R3 把**稳态增量**压到 0.93 ms，但 §13.8 第一条留着：**配方本换版后的第一次重建仍是整批**
（`max_ms` 23–73 ms）。这一轮专门收它。

### 15.1 症状：整批那条路还值 45 ms

真服务端探针 `R4BatchProbe`（学一条语料外配方把配方本顶到换版，再读 `exchangeOffers()`），
同一台机器、同一份 `run/` 存档、同一个探针，先后跑新旧代码各三轮：

| 轮次 | 改前 `batch_ms` | 改后 `batch_ms` | 改前 `incremental_ms` | 改后 `incremental_ms` |
| --- | --- | --- | --- | --- |
| 0 | 40.86 | 20.22 | 1.299 | 1.392 |
| 1 | 50.98 | 21.74 | 1.709 | 1.047 |
| 2 | 45.42 | 14.27 | 1.412 | 1.099 |
| **中位** | **45.42** | **20.22** | **1.41** | **1.10** |

`offers=747`、`sink=5976` 两版**完全相同**（747 而不是 746，是因为探针多学了一条配方）。
增量那条路本轮没有专门改，1.41 → 1.10 是「同一个 `Scratch` 顺手省掉了几次数组分配」的副产品。

45 ms 不是只在开服时付一次：**学一条配方就付一次**。玩家在界面里连合 8 次，就付 8 次。

### 15.2 归因：整批的大头不是「依赖集重建」

§13.8 当时的假设是「要压它得把 `buildCraftDeps` 做成增量（按物品记忆化可达集）」。
`Attrib2.java`（与 R2 那台 `Attrib` 同口径：746 产物 / 10,000 原料 / 预热两轮）把它否了：

| 阶段 | 改前 | 改后 |
| --- | --- | --- |
| 整批 `offers` 总计 | 39.53 ms | 15.57 / 18.20 ms |
| 其中 `maxCraftable` | 22.79 ms | 10.54 / 12.69 ms |

真正的重复是**每次探针都重新展开一棵树**：满本 866 条走闭包路径的配方，每条都要

1. `Map<String, List<Recipe>>` 现查一遍；
2. 每个原料槽位现查 `List<ItemStack>`、现算候选 id 字符串；
3. 各自铺一个 40 项 `map` 装库存 —— 而这一 tick 里库存**一个字节都没变**。

`amount` 回调（服务端要走 `Identifier` 解析 + 注册表查表）合计 **7,478 次**，全批实际只需要问
**1,223 个槽位**。这就是 §15.7 那个 6.1 倍。

### 15.3 与 AE2 的对应关系

用户提的路线（先算好配方树、先序遍历、叶子处问够不够）正是现有语义，所以**不是重写算法，
是换数据结构**。三处一一对应 AE2 的 `CraftingTreeNode` / `CraftingSimulationState`：

| AE2 | 这里 | 作用 |
| --- | --- | --- |
| `CraftingTreeNode`（预建树，每个节点记 pattern 与输入槽） | `Tree` + `Node` + `RecipeNode` + `PartNode` | 配方本换版时编译一次，之后全走 `int[]` 下标 |
| `CraftingSimulationState`（一次模拟的可变状态） | `Scratch` | 可复位草稿纸，世代戳 + 撤销日志 |
| `IStorageMonitor` 提供的库存视图 | `Tree#stockArray(...)` | 一次打成 `BigInteger[]`，全批共享 |

### 15.4 实现

`common/src/main/java/neko/voidwarehouse/VoidWarehouseRecipes.java`（870 → 1,423 行）：

```java
public static final class Tree {
    private final String[] ids;                         // 槽位 → 物品 id
    private final Node[] nodes;                         // 槽位 → 节点
    private final Map<String, Integer> slots;           // 物品 id → 槽位
    public static Tree compile(Map<String, List<Recipe>> byOutput);
    public BigInteger[] stockArray(Function<String, BigInteger> amount);       // 全树 1,223 个槽位
    public BigInteger[] stockArray(int rootSlot, Function<String, BigInteger> amount); // 只取闭包
}
public static final class RecipeNode {
    public final Recipe recipe;
    public final int outputSlot, outputCount;
    final PartNode[] parts;        // 普通槽位
    final int[] forcedSlots;       // 只有一个候选的槽位（预解析，省一层数组）
    final int[] forcedCounts;
    final PartNode[] multiParts;   // 多候选槽位
}
static final class PartNode { final int count; final int[] candidates; }
```

`Scratch` 有六条平行数组（`pool` / `stamp` / `onPath` / `cache` / `cacheStamp` / `boundPath`），
两个世代号 `modelEpoch` / `cacheEpoch`：

```java
BigInteger overridden = scratch.stamp[slot] == scratch.modelEpoch ? scratch.pool[slot] : null;
```

**复位 = `epoch++`**，不需要清数组（溢出到 `Integer.MIN_VALUE` 时才 `fill(stamp, 0)` 重来）。
这等价于 R2 那个「记旧值 + 回滚」的撤销日志，但日志本身也免了。

接线（五份 `VoidWarehouseData` 逐字节一致，靠 `C:\tmp\r4\r4_sync_4.py` 同步）：

- 字段 `craftTree` / `craftScratch`，在构造函数与 `rebuildRecipes()` 里与 `recipesByOutput` 同步重建；
- `computeCraftOffer(itemId, snapshot)` 整批时共享一次 `stockArray(...)`，增量时传 `null` 只取闭包；
- `craftStock(recipe)` 从 `Map` 改成 `BigInteger[]`（闭包版）；
- `usable(tree, scratch)` 做长度校验 —— 长度不符就新建，防跨版本档读到越界下标。

### 15.7 闭包到底多大（这条决定了「只取闭包」是否安全）

`Probe2.java` 在真实语料上**逐条配方**数了闭包规模（满本 866 条配方，分布在 746 个产物下）：

| 闭包槽位数 | 0 | 8 | 16 | 24 | 32 | 40 |
| --- | --- | --- | --- | --- | --- | --- |
| 配方条数 | 596 | 88 | 71 | 89 | 21 | 1 |

**最大 40**（`magenta_harness`），而 `MAX_CLOSURE = 256`、`MAX_DEPTH = 4`。离上限还有六倍余量，
所以「单次取货只取闭包」不会因为截断而改变语义 —— 这一点 `stockArray(rootSlot, ...)` 里
按旧 `stockClosure` 逐条对齐过（同样的深度上限、同样的路径去环、同样的截断顺序）。

`0` 那 596 条是「原料全是基础物品、没有子配方」的配方：闭包就是它自己。

### 15.8 遗留

- **`Scratch` 只给主线程用**。跨线程共享会读到别人的世代号 —— 现在靠「仓库数据是 server 单例、
  所有调用都在主线程」保证。真要并行化得一人一张草稿纸（`ThreadLocal` 或池），本轮没做。
- **`Tree` 的内存**：1,223 个槽位 × 一个 `Node`，每个 `Node` 指向它作为产物的那几条 `RecipeNode`。
  `RecipeNode` 的候选是 `int[]`，比原来的字符串 map 小得多，净变化接近零。
- **增量那条路还能再省 0.2 ms**：单次取货现在每次都要 `stockArray(rootSlot, ...)` 走一遍闭包 DFS
  （闭包实测最大 40 个槽位、多数在 0 – 24）。若把闭包下标**缓存在 `Tree` 里**（每个产物一份 `int[]`，
  配方本换版时重算），取货就退化成「按数组下标读」。收益 0.1 – 0.2 ms / 次点击，暂不做。
- 上一轮 §14.9 的三条遗留状态不变；§13.8 第 1 条（整批 23–73 ms）**本轮关闭**。
