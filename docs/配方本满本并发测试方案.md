# 配方本满本 + 多玩家并发：测试方案

> **测试对象**：2026-11-10 的 A2 提交 —— 配方本上限 512 → 2048 条、存档由「一个字符串拼全部」改为「一条配方一个元素」。
> **一句话目标**：把 26.3 的全部合成配方塞满配方本、给足原料、让 20 个玩家同时用，看会不会出性能问题，并把瓶颈指到具体那一行。
> **Five-version scope.** 26.3 / 26.2 / 26.1.2 / 26.1.1 / 1.21.11 各跑一遍，用**同一份**负载，版本之间只留「版本」这一个变量。

---

## 1. 要回答的三个问题

| # | 问题 | 为什么值得单独问 |
| --- | --- | --- |
| Q1 | 配方本从 512 放到 1236 条（26.3 全部合成配方），**取货路径**会不会变慢？ | `withdraw` 走 `planCraft` → `maxCraftable`，后者在 `recipesByOutput` 上做深度 ≤ 4 的搜索。配方本变大 = 每个节点的候选变多 |
| Q2 | 同一条件下，**界面路径**（`exchangeOffers` 重建）会不会拖垮 tick？ | 这条路径对**每个虚拟格候选**都跑一次 `stockFor` + `maxCraftable` + `plan`，是 O(产物数 × 搜索)。它按 tick 缓存，但只要库存一动，下一个 tick 必然全量重算 |
| Q3 | 20 个玩家并发时，上面两条会不会互相放大？ | 缓存是「按 tick 合并」的，20 人同 tick 只算一次；但**跨 tick 的持续取货**会让每个 tick 都有一次全量重建 |

之所以不把「配方本变大」只当成「存档变大」，是因为它真正放大的是**搜索空间**，不是内存占用 —— 这一点在 A2 落地前没有被单独测过。

---

## 2. 本次改动的风险面

改了两个文件，风险面却分三层：

| 层 | 改动 | 风险 | 对应的测试 |
| --- | --- | --- | --- |
| 存储 | `learned_recipes`（单字符串）→ `learned_recipes_lines`（列表） | 老档读不出 / 写丢 / 降级丢配方 | 可靠性 R1、R2 |
| 容量 | `MAX_RECIPES` 512 → 2048 | 配方本真的能长到 1000+ 条，**搜索规模随之变大** | 性能 A 组、B 组 |
| 代码 | 新增 `RecipeLinesCodec`（自己写的宽容 codec） | 坏元素容忍、顶层类型错时的失败路径 | 可靠性 R2 + 既有 `A2StorageSelfCheck` |

第一层和第三层在 A2 落地时已经用 271 条断言锁死了（`A2CodecTest` 35 + `A2StorageSelfCheck` 27 + 既有 `SystemTest` 209）。**本方案补的是第二层** —— 容量放大之后的运行时行为。

## 3. 测试环境与负载

### 3.1 环境

| 项 | 值 |
| --- | --- |
| JDK | Microsoft OpenJDK 25.0.4.1 |
| 构建 | Gradle 9.7.0，`TARGET_MC_VERSIONS=<ver>` 逐版本跑 |
| 运行 | `runServer`（**真服务端**，不是单机客户端） |
| 判据来源 | 日志里的 `A2S RESULT checks=N failures=M`。**不看退出码** —— `runServer` 崩服也返回 `EXIT=0` |

### 3.2 语料：26.3 的全部合成配方

由 `RecipeCorpusExport`（一次性工具，只跑 26.3）从 `RecipeManager` 枚举后导出到 `C:/tmp/nca_recipes_263.txt`：

| 项 | 值 | 说明 |
| --- | --- | --- |
| RecipeManager 总条目 | 2942 | 含熔炉、锻造、切石机等 |
| 非 crafting | 1674 | 被 `instanceof CraftingRecipe` 挡掉 |
| `CustomRecipe` | 24 | 染色、烟火、地图缩放、成书复制 —— 产物带数据组件，模组按设计不记 |
| 其它 display 类型 | 0 | 26.3 的 crafting 都能解析 |
| 产物读不出 | 8 | 少数配方的 display 不是 `ItemStackSlotDisplay` |
| **最终写入** | **1236 条** | 1042 种产物 / 477 种原料 / 平均 4.37 项 |
| 原料项数分布 | 1:86 / 2:337 / 3:161 / 4:122 / 5:53 / 6:255 / 7:49 / 8:26 / 9:147 | 与真实原版一致 |
| 文件大小 | 171,898 字节 | 压缩后落盘约 19.7 KB |

**为什么要把语料固化成文件**：五个版本的配方 API 差异很大（26.x 是 `PlacementInfo` + `RecipeDisplay`，1.21.x 是传统的 `getIngredients()`）。逐版本解析等于给自己造五份失配风险。所以**只在 26.3 上真解析一次**，其余版本读同一份文本 —— 语料的可信度由 26.3 保证，**可比性由「同一份文件」保证**。

口径与真实玩家存档同构：产物 id 走 `VoidWarehouseRecipeBook.idOf`（保留完整命名空间），一条配方一个 `Recipe`，文本走 `encode`，**原料只取第一个候选**（真实玩家记下来的是他实际摆进格子的那一种，`#minecraft:planks` 只会是「橡木木板」）。

### 3.3 玩家：20 个真实 `ServerPlayer`

26.3 的 fabric-api 已经没有 `FakePlayer`。这里走原版自己的构造链：

```
new ServerPlayer(server, level, profile, clientInformation)
  + Connection(PacketFlow.SERVERBOUND)
  + ServerGamePacketListenerImpl(server, conn, player, CommonListenerCookie.createInitial(...))
```

有了连接，「同步给客户端 / 发消息」的代码路径才会真的执行。语言显式写 `zh_cn`（不能用 `ClientInformation.createDefault()`，它是 `en_us`，会让 `VoidWarehouseText.isEnglish` 把中文玩家判成英文）。

### 3.4 为什么这个负载是「最重」的

`collectCraftOffers` 的入选条件是**仓库里一件都没有、但做得出来**。所以：

- **原料全满 + 产物全空** ⇒ 全部 1042 种产物都成为虚拟格候选 —— 这是这张表能到达的最大规模；
- 真实存档里玩家只学过一部分、仓库里也存着一部分货，虚拟格远少于这个数。

⚠️ 但「产物全空」做不到 100%：477 种原料里有 **约 300 种同时是别的配方的产物**（木板、台阶、锭……）。它们一旦有货就不出虚拟格，所以实测虚拟格是 **651**（≈1042 − 双重身份 − 依赖炉子/锻造的）。这本身是正确行为，不是缺陷；测试里把它记成**说明项**而不是断言。

## 4. 四类测试的设计

### 4.1 性能

分四组，全部在**同一个真服务端进程**里跑，以减少 JVM 冷启差异。

| 组 | 变量 | 固定项 | 指标 | 目的 |
| --- | --- | --- | --- | --- |
| **A 规模曲线** | 配方 100 / 300 / 600 / 900 / 1236 条 | 原料 10,000/种 | `exchangeOffers()` 单次重建（3 次取中位） | 找增长形态与拐点 |
| **B 原料量曲线** | 原料 100 / 1,000 / 10,000 / 100,000 | 配方取 A 组满档 | 同上 | 判断「贵的到底是配方多还是原料多」 |
| **C 交互路径** | — | 满档 | `withdraw` P50/P95/P99、菜单构造、20 人并发 60 次取货 | 玩家真正感知的那条路 |
| **D 热点定位** | 逐条配方 | 满档 | 单条 `maxCraftable` 的耗时分布 + Top-5 最贵配方 | 把「340 ms」拆到具体是哪几条 |
| **E 正确性扫描** | 配方 100 / 300 / 600 / 900 / 1236 条 | 原料 10,000/种 | 「`maxCraftable` 判 0、但 `plan(1)` 做得出」的条数 | 量出**界面丢配方**的规模梯度；修复后应全档为 0，是回归闸门 |
| **F 双向精确性** | 满档 | — | 逐条把 `maxCraftable` 与 `plan` 二分求出的真值对比，分别计 `over` / `under` / `exact` | 判多（点下去会失败）与判少（界面少报）都必须是 0 |
| **G 界面货架对账** | 100 / 300 / 600 / 900 / 1236 条 | 原料 10,000/种 | 对每个「有配方、仓库没货、却不在货架上」的产物用 `plan(1)` 直接问一句做不做得出 | 判据**不经过** `maxCraftable`，与 F 组互为独立证据 |

**A/B 两组的保护**：单次超过 3000 ms 就记为该档不可用并停止加大规模。理由是最初的「一次拉满」实验（1236 条 + 每种 10 万）第二次重建把服务器卡到 **60 秒**，被 vanilla watchdog 强制关机。梯度实验能在不炸服的前提下拿到曲线。

**B 组存在的意义**：如果耗时随原料量增长，说明瓶颈在「能做的太多」；如果随配方条数增长，说明瓶颈在「候选太多」。这两种结论对应完全不同的优化方向，事前不能靠猜。

**E/F/G 三组是跑完 A~D 之后补的**。原方案只打算量「快不快」，A~D 跑完却先看到一条断言失败（满本 361 ms）和一条更严重的正确性问题（界面不出格子）。于是补 E 组把「错多少」量出来、F 组把「错在哪个量级」量出来 —— **性能报告里不能只有耗时，得说清耗时花在哪次无用劳动上**。G 组则是修复后补的：F 组是逐条算法对账，G 组从**货架侧**反查同一个问题，两条路径互为独立证据。

**F/G 两组为什么不共用判据**：F 组用 `plan` 二分求真值，本质上还是在问「同一套模拟器的另一个用法」；G 组问的是「货架上到底有没有这一格」，以及「若没有，`plan(1)` 能不能做出来」——它只看玩家看得见的结果，与 `maxCraftable` 的返回值无关。修复前 F2 与 G1 会同时红（各 260 条），修复后必须同时绿。

**F 组为什么要复刻上界**：`boundCap` / `availOf` 都是 `private`，压测只能用公共 API 把同一段算法拼回来。复刻的正确性靠一条自洽断言兜底 —— 凡 `maxCraftable` 返回 `R > 0` 的配方，必然满足 `cap − R_crafts < MAX_VERIFY`（它就是「从 `cap` 往下退 p 次才成」，p 不可能 ≥ 64）。这条断言覆盖率 100% 才认数据，否则作废重抄。**任何一处走样（`cache` 共享范围、`path` 是否每次新建、`budget` 消耗顺序）都会当场把它打下来。**

### 4.2 界面

| # | 断言 | 判据 |
| --- | --- | --- |
| U1 | 虚拟格全部标了「可合成」 | `offer.craft()` 全为 true |
| U1 | 每格都有可展示样品与可数上限 | `template` 非空 且 `obtainable > 0` |
| U2 | 同库存下两次重建的展示顺序一致 | 逐项 `itemId` 相等（界面不能每次开都跳） |
| U3 | 同 tick 第二次读返回**同一份引用** | 引用相等 —— 这是「按 tick 合并」的唯一直接判据 |
| U4 | 双语分流正确 | `zh_cn` 判中文、`en_us` 判英文 |

U2 有个坑：两次重建之间**绝不能让库存变**。最初版本拿「并发取货之前」的 offers 和「之后」的重建结果比，虚拟格集合本来就不同 —— 那是测试设计错，不是产品缺陷，已在方案里固化。

### 4.3 回归

跑既有的 `SystemTest`（**209 条断言**，覆盖虚空仓库/兑换/配方扣料/补货/直放/双语/多人压力），五版本各一次。判据：`failures=0`。

这一组的价值是「证明 A2 没碰坏别的东西」，与性能无关，所以单独跑、单独出结论。

### 4.4 可靠性

| # | 断言 | 判据 | 对应的真实事故形态 |
| --- | --- | --- | --- |
| R1 | 满本可编码、写新键不写老键、元素数一致 | `learned_recipes_lines` 存在且 size == 条数 | 老键残留会让文件白白变大 |
| R1 | 写盘 → 读回条数一致、仍能反查 | 全等 | **975 天花板事故**：键还在、内容变空串 |
| R2 | 补到 `MAX_RECIPES` 后第 N+1 条全被拒、条数不撑破 | 100/100 被拒 | 上限失效会让存档无限长 |
| R3 | 取货后总库存严格减少、净减少 ≥ 取出的件数 | 单调性 | **凭空造物**是本项目最不可接受的一类 bug |

R1 的判据必须用「读回来还剩几条」，**不能用 `contains(key)`** —— 旧格式撞 65535 时的失败形态是「键还在、内容长度为 0」，查键会误判成正常。

## 5. 判定标准

### 5.1 通过线

一个服务端 tick 的预算是 **50 ms**（20 tps）。所以：

| 指标 | 优 | 可接受 | **不通过** |
| --- | --- | --- | --- |
| `exchangeOffers` 单次重建（满本） | < 10 ms | 10 – 50 ms | **> 50 ms**（一个 tick 装不下，必然掉 tick） |
| `withdraw` 单次 P99 | < 5 ms | 5 – 50 ms | **> 50 ms**（点击后有明显延迟） |
| 菜单构造 P95 | < 5 ms | 5 – 50 ms | **> 50 ms**（开界面卡住） |
| 20 人并发 60 次取货总计 | < 200 ms | 200 – 1000 ms | **> 2000 ms** |
| 断言通过率 | — | — | **任何一条 FAIL 都算不通过** |

阈值定在 50 ms 而不是「感觉快就行」，是因为这条路径**在 tick 里同步执行**：超过 50 ms 就不是「慢一点」，而是「这一 tick 的其余工作全部推迟」。

### 5.2 定级口径

出现 FAIL 时按影响面定级：

| 级别 | 定义 | 处置 |
| --- | --- | --- |
| **P0** | 能让服务器卡死 / watchdog 关机 / 存档丢数据 | 阻塞发布 |
| **P1** | 单个 tick 超预算，持续有库存变动时稳定掉 tick | 发布前修，或明确写进已知限制 |
| **P2** | 有可感知延迟但不掉 tick | 记录，排进下一轮 |
| **P3** | 只在极端负载下出现，且可绕开 | 记录 |

## 6. 复现方式

```bash
# 1) 导出语料（只 26.3，一次性）
python .workbuddy/tools/install_stress_tool.py install RecipeCorpusExport 26.3
TARGET_MC_VERSIONS=26.3 ./gradlew :modern:26.3:runServer --no-daemon
#    产出 C:/tmp/nca_recipes_263.txt，日志里找 CORPUS RESULT written=1236
python .workbuddy/tools/install_stress_tool.py remove RecipeCorpusExport 26.3

# 2) 五版本压测
for ver in 26.3 26.2 26.1.2 26.1.1 1.21.11; do
  python .workbuddy/tools/install_stress_tool.py install A2StressTest $ver
  pre=modern; [ "$ver" = "1.21.11" ] && pre=versions
  TARGET_MC_VERSIONS=$ver ./gradlew :$pre:$ver:runServer --no-daemon > a2s_$ver.log 2>&1
  grep "A2S RESULT" a2s_$ver.log
done

# 3) 回归
python .workbuddy/tools/install_systest.py install <ver>
TARGET_MC_VERSIONS=<ver> ./gradlew :<pre>:<ver>:runServer --no-daemon
```

工具清单：

| 文件 | 作用 |
| --- | --- |
| `.workbuddy/tools/RecipeCorpusExport.java.template` | 26.3 配方语料导出（一次性） |
| `.workbuddy/tools/A2StressTest.java.template` | 压测主体，**五版本共用同一份源码** |
| `.workbuddy/tools/install_stress_tool.py` | 装/摘钩子（`install|remove <Class|all> [ver]`） |

钩子挂在 `VoidWarehouseExtension#onTick` 的 `noteServerTick` 之后 —— 必须在那之前，否则 tick 计数不走，工具永远不触发。

## 7. 已知的方法学限制

1. **假玩家没有客户端**。所以「客户端渲染 / 网络包大小」这一类成本不在本方案的度量范围内。本方案量的是**服务端 CPU**。
2. **单机、无网络延迟**。真实多人服里 `withdraw` 前面还有一次 C2S 包往返，那部分与本改动无关，未计入。
3. **语料来自 26.3**。其余四版本的配方数可能与 26.3 略有差异（版本间增删了几个物品），用同一份语料保证的是**可比性**，不是「该版本自己的全部配方」。要测该版本自己的全集，需按版本各导出一次。
4. **JIT 与冷启**。A 组按 100 → 1236 递增，后面的档位享受了预热，可能**低估**小规模的真实成本。所以 A 组的绝对值偏乐观，但**增长形态**（超线性）不受影响。
5. **`MARK` 用 `markChanged()` 强制失效缓存**，模拟的是「每一个 tick 库存都有变动」的最坏情况。真实场景里变动是间歇的，所以稳态成本会是「变动率 × 340 ms」而不是「每 tick 340 ms」。
6. **内存数字含 2048 条满本 + 全部原料**，不是纯配方本的开销。
